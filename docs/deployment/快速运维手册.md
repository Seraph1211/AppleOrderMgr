## 官网刷新退役

官网爬虫、浏览器批量刷新、代理切换和系统爬虫日志已退役。旧接口返回 HTTP 410；历史数据只允许通过 `archive` schema 受控查询和恢复。

## 日常只读检查

```bash
cd /var/www/apple-order-mgr/current
docker compose --env-file release.env -f docker-compose.prod.yml ps
docker compose --env-file release.env -f docker-compose.prod.yml logs --tail=100 api
docker compose --env-file release.env -f docker-compose.prod.yml logs --tail=100 email-worker
docker compose --env-file release.env -f docker-compose.prod.yml -f images.override.yml --profile wecom logs --tail=100 wecom-worker
curl -i http://127.0.0.1:3001/api/health/live
curl -i http://127.0.0.1:3001/api/health/ready
curl -I https://apple.godp.me/
```

`live` 只说明 API 进程存活，`ready` 只额外验证数据库连通。两者都不能证明邮件处理或企微推送正常。

## 服务操作

更新 Compose 服务时使用：

```bash
docker compose --env-file release.env -f docker-compose.prod.yml -f images.override.yml --profile order-mail --profile wecom up -d api email-worker order-mail-worker wecom-worker
```

不要运行不带项目范围的 Docker 清理、停止或重启命令。PostgreSQL 和 Nginx 是宿主机共享服务，不能随应用 Compose 操作。

## 常见症状

| 症状          | 优先检查                                                                                                                           |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 前端打不开    | `current` 链接、静态文件、Nginx 站点配置和证书                                                                                     |
| API 502       | `api` 容器、`127.0.0.1:3001`、Nginx upstream                                                                                       |
| readiness 503 | PostgreSQL 连接、环境变量、Migration 状态                                                                                          |
| 邮件未入库    | `email-worker` 日志、IMAP 网络、授权码、精确地址／域名白名单、`SUBJECT_NOT_ALLOWED`／`SENDER_NOT_ALLOWED`、主题/正文格式、未读状态 |
| 邮件状态未更新 | `order-mail-worker` 日志、生命周期开关、订单号精确匹配和待复核原因                                                                 |
| 登录失败      | 用户状态、JWT 配置、当前设备会话是否失效                                                                                               |

## 日志与磁盘

应用日志写入 Docker stdout/stderr，并由 `json-file` 限制为每个容器最多 5 个 10 MB 文件。查看磁盘前先限定项目：

```bash
docker compose --env-file release.env -f docker-compose.prod.yml ps -q
docker system df
find /var/www/apple-order-mgr/releases -maxdepth 2 -type f -printf '%s %p\n' | sort -n | tail
```

发布目录和数据库备份的删除必须先列出版本、确认当前 `current` 指向和回滚保留策略，再单独执行。

## Nginx 与数据库

站点配置变更后：

```bash
nginx -t
systemctl reload nginx
```

数据库备份、恢复和迁移遵循[数据库初始化与迁移指南](../database/数据库初始化与迁移指南.md)。不要通过删除表、Migration 记录或数据库目录来处理迁移故障。

## 订单列表邮件通道

此通道与自动建单邮件、监控通知独立。先应用正式 Migration 20260920000003-add-order-mail.js，再为API和独立Worker配置相同 ORDER_MAIL_*；模板见仓库 .env.example。ORDER_MAIL_ENABLED 默认false，启用需明确配置账号及凭据。IMAP固定TLS 993、SMTP固定TLS 465，校验证书，不支持降级明文。生产环境文件是受保护配置，禁止将真实密码提交仓库；若用 ORDER_MAIL_PASSWORD_FILE，应给API和Worker分别挂载同一只读凭据文件，示例路径为 /run/secrets/order-mail-password。生产Compose未默认挂载此文件，须在部署override中声明volume；也可由受保护环境文件注入 ORDER_MAIL_PASSWORD。

启动本地专用通道命令：docker compose -f docker-compose.dev.yml --profile order-mail up -d order-mail-worker。生产按正式发布步骤发布迁移/API/前端后，使用 docker-compose.prod.yml 的 order-mail profile显式启动独立Worker；普通email-worker不会连接新总收件箱。原邮箱凭据、监控SMTP、全局订单来源开关不变。回滚前先停止order-mail-worker并关闭开关，禁止直接回滚含真实发送历史的数据库表。

首次同步默认最近30天，按服务端邮件日期搜索并持久化起点；之后修改回查天数不自动重置已存在游标。只读打开邮箱，不修改已读标记。每封上限10MB；默认接受apple.com、apple.com.cn及子域，真实来源须用邮件头核实后按ORDER_MAIL_SENDER_DOMAINS精确配置，不凭显示名称放行。暂不解析PDF等附件中的订单号，多订单号或无完整W订单号不自动关联。

管理员在用户权限管理授予“订单邮件 / 查看完整订单邮件、附件并转发”，依赖订单读取且继续受订单TAG范围限制。普通用户默认无此权限。

转发邮件同时提供 HTML 正文与纯文本备用，继续附加原附件及原始 EML；系统预览保持纯文本。外部图片是否加载取决于收件客户端。正文格式与真实 QQ 验收见[排版修复记录](../archive/2026-09/2026-09-20-邮件转发正文排版修复.md)。

queued=待发；sending=发送中；retry_wait=明确临时失败待重试；accepted=SMTP接受，非最终送达；unknown=网络或进程中断，需核对目标收件箱及邮件服务器日志，禁止盲目重新发送；failed=失败；cancelled=授权撤销或内容过期。发送前临时数据库失败使用PREPARE_TEMPORARY重试。原始内容180天清理；查看正文、下载附件和转发均有操作审计，发送队列保留加密目标和备注。

2026-09-20 已发布生产并启用真实邮箱。当前版本使用 shared/order-mail.env 独立环境文件，由 images.override.yml 仅为 API 和 order-mail-worker 注入。生产操作必须使用 `docker compose --env-file release.env -f docker-compose.prod.yml -f images.override.yml --profile order-mail ...`，保留其他服务各自的镜像。真实订单查看、PDF 下载及无敏感内容测试邮件到达 QQ 已验证，范围与回滚见[上线验收记录](../archive/2026-09/2026-09-20-订单邮件上线与真实收发验收.md)。

## 企微订单通知运维

功能入口与状态解释见[企微订单通知](../design/企微订单通知.md)。上线顺序为：备份 → 正式 Migration `20260920000004-add-wecom-notifications.js` → 包含新依赖的 API／收单 Worker 制品 → 显式启动 `wecom` profile → 后台保存测试群配置（自动通知关闭）→ 获授权后发送固定测试消息 → 核对群内实际收到 → 正式启用。

新增企微 Worker 不随默认 profile 启动；生产镜像同时供 API／收单 Worker／企微 Worker 使用。配置表默认关闭，Webhook 用现有字段密钥加密，不写 `.env.example` 或发布说明。需要恢复发送时先看页面暂停原因、积压、心跳；不要直接把 unknown 记录改回 pending，避免重复发消息。停用不会撤回已发出的网络请求。

回滚优先停用通知并停止企微 Worker、回退应用制品，保留通知表和历史供核对。Migration down 会删除配置与历史，只能在备份及明确数据库回滚授权后执行。切勿影响同机其他系统。

## AOS账号设置索引回填与恢复

上线顺序为正式Migration、API独立增量捕获、Worker有界回填、比例技术验收；API资源标签和Duo独有文件必须保留。新增signal事件id映射兼容旧API信号inbox；不全量覆盖API旧AOS服务。回填不发历史通知，不重置原全局汇总窗口。

后台每秒最多一页，在库存全局锁外复制并解压：最多1000回执／100行表片段，仅1个最多4MiB候选块，逐块释放；SQL1500ms预算、页准备2秒预算，失败30秒后重试。账号宇宙从全部保留期账号目录元数据逐日建立，每tick只处理1个实际business_date；registryVersion／registryAfterDate／registryPages可续跑，旧r3部分状态自动重走元数据但不删除registry；每SQL最多1500ms且日片整体2秒。回执metadata先按file_key／byte_offset有序LIMIT1000并物化，再按三日／实例筛块；即使整页被过滤仍推进offset，不读或解压无关原文，只有实际耗尽回执才结束文件。设置用最近3日签名候选，游标为原fileId／byteOffset，压实换块不改变位置。body记录pages／blocks／rawBytes／scannedReceipts／lastPageMs及reason；失败仅记录白名单SQLSTATE，不含原文／SQL／凭据。

仅对明确实例手动有界加速或重走索引。本次生产最小增量保全旧package.json，在库存Worker容器内直接用node；完整安装当前源码时也可用npm run logs:accounts:backfill --代替node及脚本路径：

```bash
node /app/scripts/backfillAosAccountIndex.js --device <device-uuid> --instance <local-uuid> --pages 100
node /app/scripts/backfillAosAccountIndex.js --device <device-uuid> --instance <local-uuid> --reset --pages 100
```

`--reset`不删除账号／设置／历史通知，不补发信号，重新取当前最近3自然日重建游标，绝不退回全历史；每次最多1000次有界推进，与后台advisory锁互斥；busy间隔250ms且连续8次即退出，不能无界并行压垮数据库。停用实例恢复且采集ready后自动重走；error保留retryAfter，history gap必须重走最近3日而非直接标ready。`WAITING_REALTIME_CAPTURE`等待新API真实日志接收（含全重复批次）或采集状态报告事务建立服务器水位；直接ingest或历史回填不能建立水位，也不能手工设ready。若回填seed早于该水位，会在tick开始立即重扫，防API上线前已扫文件的尾部漏索引。累计expired仅诊断，不因范围外旧日志过期永久禁用；回填3天范围内实际丢日期才保留HISTORY_GAP诊断。

采集snapshot整体ready／pending／字节水位目前不能按日期拆分；若整体未完成，即使缺口可能在范围外，也保守标CURRENT_LOG_COVERAGE（读取时LOG_COVERAGE_INCOMPLETE），不得靠累计旧expired推测当前范围失败或跳过覆盖门槛。

比例未知时先查AosAccountIndexState的status／reason、采集ready／pending／scannedBytes，再查投递aosAccountRatio的scope/source reason；原编号有缺启动或规格／城市冲突不能用部分账号数冒充分母。无可证明历史的scope保持N/—，不借未来设置修补过去。

当前默认仅验证北京时间最近3自然日（含今天），seed固定firstDate／lastDate；所有原文查询在SQL层按business_date过滤，CLI与reset均不得扩大为全部历史。registry允许读取已有账号目录metadata以保留已识别编号宇宙，不解压范围外原文；账号最近启动早于范围且无既有可信索引时D未知。后台不是即时全实例完成，先以指定实例有限页数推进并记录实际吞吐，不能按原90天估算或承诺所有scope精确。

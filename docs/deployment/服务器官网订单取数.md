## 管理台 HTTP 队列部署

管理台新版执行入口为 `npm run official:queue:http`（宿主 Python，独立容器运行 HTTP），对应 `scripts/officialOrder/apple-official-order-queue.service`。部署使用独立 `OFFICIAL_ORDER_ROOT`，不复用已冻结补录目录；旧浏览器队列必须先停止，保留原待处理任务与历史记录，不能同时运行新旧领取器。

所需目录为 `release`（当前源码，目录 0755／源码文件 0644，不含私密配置）、`deps`（Node 依赖）、`private`（0700）及 `evidence`。预建根目录下的 `node_modules` 挂载点；tar 仅含文件时，0700 umask 会使自动创建的源码父目录不可被容器读取，发布时须核对目录遍历权限。私密配置文件 0600，容器所需文件归 UID 1000：`db.json` 连接原共享研究库；`evidence.key` 是独立 32 字节证据密钥；`httpConfig.json` 提供经过核验的累计 `maxTotalRequests`，不能复制历史额度或重置 budget；`iproyal-api.json` 包含现有 `apiToken` 与 `subuserHash`，或者现有 `username`、基础 `password`。不得将实际配置提交 Git。API 仅请求官方 [generate-proxy-list](https://docs.iproyal.com/proxies/residential/api/access)，生成中国区、24 小时 sticky 配置并加 `_killswitch-1`，不购买或充值。

`OFFICIAL_API_CONTAINER` 默认 `apple-order-mgr-prod-api-1`；`OFFICIAL_HTTP_RUNTIME` 指向固定 Python venv。研究网络、Node 镜像、全局 Gate、前后 Nginx 出口探测复用下述运行环境。每次 attempt 保存独立输入及审计；`egress.json` 持久保留失败／未知占用出口；`finish-任务ID.json` 的 STARTED 是未知提交保护，须先核对业务库后人工对账，不能删除后重跑。`STOP` 或 `http-cleanup-blocked.json` 存在时停止领取和成功回写，保留在途结果。

发布顺序：核对当前生产制品并制作增量候选，备份与验证回退，停止旧队列，发布 API 与前端、安装独立 HTTP 运行目录，配置 API 提取及共享 Gate，检查无未决意图，再启用 systemd。以一笔人工选择的真实订单完成采集、成功事务及回读，再观察小批次；服务在线或代理生成成功不能代替官网验收。当前发布状态见开发进度。

2026-10-09 管理台队列十路并发已发布 `20261009-official-concurrency`，配置及只读核验通过，见[发布记录](../archive/2026-10/2026-10-09-官网手动刷新十路并发生产发布.md)。发布时须同步更新 API 内的 `officialOrderRefreshService.js` 和宿主 `runOfficialOrderHttpQueue.py`，两端上限均为 10；全局 Gate 仍约 5 RPS。先停止领取并等待在途任务及提交意图结清，再切换两个组件，核对资源后恢复。回退也须同步恢复两端版本。独立补录 CLI 的五单分波策略不受此改动影响；真实十路吞吐与稳定性另行验收。

## 有界采集与正式写入

只有仍有效的计划、明确未完成目标、可靠代理游标以及启动前检查全部满足时，才使用以下模板。参数由本次核验产生；命令中的必填变量会在缺失时直接拒绝。当前已处理的 489 单无需因整理文档重新跑一遍。

```bash
python3 -B "$OFFICIAL_ROOT/release/scripts/officialOrder/runHttpBatch.py" \
  --root "$OFFICIAL_ROOT" \
  --concurrency 5 \
  --ids "${ORDER_IDS:?填写已核验且在计划内的逗号分隔ID}" \
  --limit "${BATCH_LIMIT:?填写本轮有界处理数量}" \
  --proxy-index "${NEXT_PROXY_INDEX:?填写已核验代理游标}"
```

**上面没有 `--apply`，仍会真实访问 Apple、消耗代理流量和尝试预算，只是不写业务字段。** 正式回写在相同参数模板末尾显式加 `--apply`。HTTP 两种模式各有日志，不能假定演练后再次启动正式批次会复用刚才的采样；避免为了预览反复采集。

已存在且仍在有效期内的单样本，可用以下入口做写入前只读核验，不重新请求 Apple；它会保存本地 payload／preview 审计：

```bash
python3 -B "$OFFICIAL_ROOT/release/scripts/officialOrder/applyHttpSample.py" \
  --root "$OFFICIAL_ROOT" \
  --audit "${HTTP_AUDIT_NAME:?填写原http-sample审计文件名}"
```

该入口仍检查全局未知意图、原计划、来源链和当前业务行；原样本过期或已有意图时不能删文件重试。正式采集优先通过批次入口编排，不直接调用底层 sampler 绕过历史隔离／暂缓语义。

按[技术说明中的双重预算](../design/官网订单HTTP采集技术说明.md#4-并发限流与失败预算)运行：5 单并发、约 5 RPS、每单滚动 24 小时最多 10 次、单轮最多 3 个实际 run；账号／登录暂停 15 分钟，代理暂停和拒用独立。当前分波收集，整波停止采集后串行核验回写；失败终态及 `BATCH_PASS_FINISHED` 不表示两个字段都完整。

## 独立回读与报告

本批必须使用 v7；它能同时验证原 HTTP 链、历史 605 日期、两批付款变更及用户确认的四单日期。旧 v3～v6 不认识全部附加链，不能用其误报结果覆盖最新验收。

```bash
python3 -B "$OFFICIAL_ROOT/candidates/confirmed-dates-v2/official-original-scope-progress-v7.py" \
  --root "$OFFICIAL_ROOT"
```

回读器先取得保护锁，再校验原计划／证据、查询当前业务行与设备，并将报告保存到受限 `evidence` 目录。它不访问 Apple、不改业务数据，但会写新的本地报告。退出码 0 表示本次检查无异常 ID，1 表示报告完成但存在异常 ID，2 表示回读未能完成；不能仅凭非零退出码推断前次事务已回滚。

每次报告至少记录：原范围总数、状态处理数、日期有值数、本次可验证新增日期数、两字段通过数、缺日期 ID、冲突及缺行。`maximumObservedSampleOverlap` 是样本时段重叠证据，不是请求 RPS。普通字段查询可确认当前值，不能替代完整原证据链回读。

**源码同步现状：** v7、基础脚本及其依赖现已按生产 manifest 同步至[冻结回读目录](../../scripts/officialOrder/readback/20261008/README.md)，源码同步改动尚未提交 Git。仍无通用 `official:readback` npm 命令，原服务器运行入口保持。迁移时须保全全部 10 文件候选、manifest、私密证据和运行依赖，不要只拷贝一个 `.py`；源码可见不代表配置已通用化或已接入系统队列。

## 故障定位与恢复

先识别停在哪一层，再选择相应核验入口。所有恢复保留旧日志、失败正文、attempt、预算、暂停和拒用出口。具体窄形状以当前核验器代码为准，历史命令不能套用到另一个失败。

| 现象 | 先核对 | 处理边界 |
| --- | --- | --- |
| `ACCOUNT_COOLDOWN`／`ORDER_ATTEMPT_LIMIT` | 当前账号、暂停截止、24 小时窗口、预检审计 | 保留暂缓；旧策略的一次重开只适用于已冻结来源，不反复授权重置 |
| `AUTHENTICATION_REQUIRED`／`NO_GUEST_ACTION`／`NO_VALID_ORDER_DATA` | 是否跳到登录、页面 action 和完整模型 | 当前 HTTP 不转为自动密码登录；新增流程需单独实现和验收 |
| `HTTP_541`／明确只读网络失败 | run 终态、完整审计、清理、前后出口及剩余额度 | 严格已知形状可同轮换出口，最多 3 run；未验证详情不回写 |
| `probe-before` 失败且无 run | 原批次／样本 ID、私密审计、零研究运行及无写入制品 | 显式 `--reconcile-probe-failure` 追加对账；不是完成订单 |
| `EGRESS_CHANGED_OR_UNVERIFIED` | 前后出口、拒用记录、run、加密正文和容器清理 | 不回写；已知只读形状走核验／隔离，其余保持未决 |
| `BATCH_RECONCILIATION_REQUIRED`／清理失败 | 两种模式日志、活跃进程、容器、意图和 STOP | 先证明无在途／未知写入；不删除最后一条日志或阻断文件续跑 |
| `HTTP_APPLY_ORDER_CHANGED` | 是否已写意图、原完整快照、实际变化字段与业务事件 | 保留其他合法业务更新，建立明确附加链；不忽略整行摘要 |
| SSH 中断／超时／缺少 COMMIT 返回 | 原 intent、原进程、数据库行和前后快照 | 提交未知时禁止再次 `--apply`；先确定第一次结果 |
| 日期未填但状态成功 | `dateAction`、每项状态、日期原文 | 缺日期与采集失败分开；不拿退货取件日或邮件时间补值 |
| `EACCES` | release 清单与容器 UID 1000 的属主／权限 | 修正有依据的文件归属并复验摘要，不扩大敏感目录读取权限 |

探测失败对账支持的参数为 `--reconcile-probe-failure --journal apply|dry-run --order-id ID --batch-attempt-id ID --sample-attempt-id ID`，与正常批次一样传 `--root`；实际运行前核验原零 run 证据。已启动采集的隔离入口是 `--quarantine-failed-read --proof PATH --proof-sha256 SHA` 加对应身份参数，不能用旧证明处理新 attempt。参数说明以 `--help` 和 `httpFailureQuarantine.py` 为准。

不支持通用“失败后全部重跑”。`--freeze-deferred`／`--reopen-deferred` 是本批旧策略到新策略的一次受控授权，需原 manifest、来源截止及摘要；不是每过 15 分钟自动续跑。被隔离目标的重新采集使用已经明确审查的独立恢复操作，普通入口不会自动解除。

### 停止与未知结果对账

`private/STOP` 是合作式停止信号。需要停止时先持久保存带原因和身份的标记，保留已有标记，不通过强杀正在提交的事务假定回滚。检查批次、采样、写入进程及容器终态，并保留全部结果；已进入事务的调用须等到明确提交或回滚证据。

去除 STOP 前须证明未决意图已核实、无残留采集／写入进程、原计划和审计一致，并完成独立回读。专用操作创建的 STOP 只能按原身份／nonce 精确解除，不能把另一操作的 STOP 删除。没有证据时保持停止。

## 发布、迁移与回退

独立工具发布按以下顺序交付，API／前端与旧队列保持各自发布边界：

1. 在隔离工作树完成对应回归，冻结制品文件清单、依赖锁和 SHA-256；保存来源版本及未提交差异的完整源码快照。
2. 停止新批次并取得批次／采样／回写三锁；核对无在途和未知提交。保存当前 release 指针、研究库保护记录及私密证据的受控备份。
3. 新版本放独立目录，逐文件核验 manifest、Python 3.6 语法和 Node 语法，检查 UID／权限及运行依赖。禁止原地覆盖活跃 release。
4. 仅在全部门禁通过后切换指针；使用固定少量目标验证真实出口、请求限流、资源、字段边界和独立回读，再扩大到批准规模。
5. 有回归时停止新任务并保留现场；回退只切回经核验且能理解现有日志／变更链的兼容版本。不能为兼容旧回读器删除新证据，不能自动撤销已验证业务数据。

业务数据纠错必须针对原事务和当前并发变化做新的审计操作；恢复旧数据库整库备份会覆盖其他任务的合法变更，不属于工具回退步骤。证据保全应包括原计划、全部日志、GCM 密文与密钥、研究库 run／attempt／预算／暂停、代理池历史与拒用集合、payload／preview／result／basis、candidate 清单及独立报告。

## 与旧管理台队列的关系

管理台现使用 `/var/www/apple-order-mgr/shared/official-http-refresh`，同名 `apple-official-order-queue.service` 已改为 HTTP 入口。原 `/var/www/apple-order-mgr/shared/official-orders` 及浏览器 unit 备份保留，不能并行启用旧领取器。API 和管理员权限延续，HTTP 新任务仅刷新所选订单，不按账号展开；浏览器登录与会话复用退出手动主链。生产回读确认原 1156 项排队任务仍在暂停批次中，当前无未暂停积压或在途任务，见[发布记录](../archive/2026-10/2026-10-08-官网HTTP手动刷新接入与生产发布.md)。

浏览器收据、序列号绑定及历史 605／四单日期工具都不是普通 HTTP 续跑入口。四单意图已 `APPLIED`，再次运行专用 `applyConfirmedDates.py --apply` 会被保护拒绝；日期例外不能扩展至其他订单。管理台 HTTP 接入已完成；后续 SN 及历史暂停任务恢复须按各自需求与验收推进。

## 库存退货检查运行边界（2026-10-10，已发布）

库存核对由 API 内部定时器执行，仅查询本系统数据库的“官网订单状态”，不依赖 HTTP 队列执行器。每分钟分批检查到期订单，每单持久间隔 30 分钟；库存模块关闭时停止核对。页面“系统状态核对”展示来源时间、核对时间及状态缺失提示。

纠错发布先停止官网领取器并等待在途结果落库，通过原批次取消服务取消历史 stock_returns 批次的排队任务，保留已完成与失败记录。新版本移除自动入队入口后恢复领取器，仅继续原有人工任务。无明确 SN 对应时人工确认，禁止按整单或数量猜测。

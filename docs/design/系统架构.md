## 当前系统

React 管理台通过 Express API 管理用户、Apple ID、取机人、订单、渠道、Excel 导入导出、仪表板与系统日志。持久化使用 PostgreSQL 和 Sequelize；邮件、爬虫以独立 Worker 运行。

```text
浏览器 → Vite 开发代理 / 生产 Nginx → Express API → PostgreSQL
IMAP 邮箱 → 邮件 Worker → 接收/重试状态机 → 严格解析 → 订单、邮件终态与首次刷新任务事务写入
爬虫 Worker → 筛选待刷新订单 → 代理访问 Apple → 短事务更新订单与日志
订单入库 → 同事务幂等登记付款任务 → API 内 10 秒补偿调度器 → PostgreSQL 调度锁 → 自动／手动分配
```

邮件入库与官网补全由不同进程承担；不能把历史“邮件到达立即同步触发爬虫”的图示当成独立 Worker 的可靠任务投递保证。

## 业务数据边界

- 商品数量以邮件为准；取消订单时官网数量为 0 不覆盖邮件数量。
- 订单状态、官网支付/取货状态、商品图片、官网金额和官网订单创建时间来自官网；付款窗口固定使用包含时分的官网创建时间加 30 分钟，只有日期时保持未知，金额缺失不能用固定单价伪造。
- Apple ID 与邮件中取机人信息来自邮件；基础资料匹配用于填充订单快照。
- 渠道按订单、取机人的 tag 聚合，不存在独立渠道主表。
- 外部付款人、取机人、Apple ID、系统员工是不同主体。可登录用户均为内部员工，外部付款人不登录系统，由员工在本人任务中手工登记姓名；垫付、归还、退款责任等内部结算仍在[规划阶段](../planning/付款人与内部结算方案.md)。

## 运行拓扑与限制

本地使用[开发 Compose](../../docker-compose.dev.yml)，默认编排 PostgreSQL、迁移任务、API 和 Vite 前端。邮件、爬虫 Worker 通过 profile 显式启用；依赖封装在开发镜像中，数据库、日志、上传、覆盖率和前端构建产物使用 Docker volume。

生产使用[生产 Compose](../../docker-compose.prod.yml)运行 api、email-worker、crawler-worker，迁移由一次性容器执行。宿主机 PostgreSQL 15 作为独立数据库，宿主机共享 Nginx 服务静态前端并把 `/api/` 转发到仅监听回环地址的 3001 端口。镜像和前端在本地 `main` 构建为版本化制品，服务器不执行 npm 构建。详细边界与回滚见[生产环境部署指南](../deployment/生产环境部署指南.md)。

订单刷新任务租约及跨进程暂停、代理 Provider 切换请求、邮件启动/定时回溯、持久化重试和中断恢复通过 PostgreSQL 协调。API 只提交代理切换请求；独立爬虫 Worker 在批次边界初始化、验证并确认实际 Provider，不能把 API 进程内状态冒充 Worker 状态。浏览器、真实邮箱、官网和生产验收状态以[开发进度](../development/开发进度.md)为准，不能由本地测试推断。

普通账号的业务权限来自 `user_permissions`，旧 `operator/readOnly` 仅保留兼容标签；管理员固定拥有代码目录中的全部权限。付款调度器运行在 API 进程，默认业务开关关闭，多副本依靠 PostgreSQL advisory lock 协调；邮件和爬虫仍为独立 Worker。订单链接不会进入普通订单 DTO，只能由具备专用权限的当前任务负责人通过无缓存入口复制；该入口不按付款截止或业务状态额外限制。

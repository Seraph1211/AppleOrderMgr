## 事务和防重复算法

统一常量 `STOCK_LOCK_NAMESPACE=641004`、`STOCK_LOCK_KEY=1`；使用参数绑定执行 `pg_advisory_xact_lock(namespace,key)`。先取得模块锁，再取得订单／销售／实物所需行锁。修改旧取货绑定的路径也先取模块锁，避免它与新来源绑定以相反顺序锁住订单和实物。

每个账务命令按以下顺序执行：

1. 在事务外校验格式和功能权限；外部 OCR、OSS HEAD、文件解析均在业务事务之外完成。
2. 开启事务，取得模块锁，检查当前有效权限。首期事务等待上限5秒、语句上限10秒；超时返回可重试错误，客户端用原 requestKey 重试。
3. 查找 `(actorKey,requestKey)`，比较规范化内容摘要。同键不同内容409；已有成功操作重新鉴权并返回结果引用，不再次写账。
4. 对新的业务命令检查模块已启用，重读目标、expectedVersion 和所有依赖，检查数量、位置、金额、权限、关联状态，不相信前端缓存或导入预览。先插入operation行，resultRefs临时为空，供事件外键引用；该行在提交前对其他事务不可见。
5. 执行业务更新，递增版本，追加事件，最后补全operation.resultRefs。任何一项失败整体回滚，幂等成功记录也不落库。
6. 提交后按当前权限构造 DTO。网络响应丢失仍可查询或以原键重试；前端只在成功响应或查询证实后标记完成。

纯查询不取写锁，多表汇总需要同一数据库快照或单条聚合查询；不以每行独立请求拼出可能互相矛盾的总数。实现期若一次500行导入无法在预算内完成，先以度量优化批量SQL，不擅自放弃事务或拆出静默部分成功。

旧取货接口不增加必填requestKey，继续使用“订单与SN相同返回已有绑定、解除按旧UUID”的幂等规则；内部事务生成独立operationId审计。stock开关仅限制新业务写入，不禁止旧绑定桥接或已经成功命令的授权重放；禁用后已授权历史仍可查询对账。

## 关键业务算法

### 登记实物与来源绑定

收货先规范化 SN 并查 StockUnit。未存在则创建，存在 registered 则完善并入账；已在库、在途或已售拒绝再次收货。整个批次要么全部成功，要么全部不写。新入账的商品和真实位置必填，拿货日或价格不确定时成本 pending；这不阻止真实机器参与销售，利润提示待核实。

绑定只写 PickupDevice 活动关系，并同时追加旧PickupRecordEvent和新StockEvent。原扫码仅创建 registered 身份，不登记现货；明确“确认入库”才改变stockUnits位置和状态。相同订单已有绑定但stockUnitId为空时，幂等返回前先补齐身份桥接，不改原绑定UUID和时间。原解绑删除活动绑定，不删除主档，也不清空成本、位置、销售或照片。

来源补关联先按完整订单校验TAG，检查当前bindingId与单台version。已经绑定另一订单时，必须明确发起更正并具备旧、新订单访问权限；冲突不自动覆盖。不改变订单商品数量、付款、邮件或人工取货状态。

### 接单和挑货

按规格批量计算 Q、R、A。reserve在模块锁下保证所有行 A>=新增需求，再将整单转reserved。调整已接单数量按新旧差额校验，不能少于已挑数量；取消释放整单占用及picked实机，不删订单历史。

picks接收完整目标集合，验证每台所在warehouse、product与需求一致，且不存在其他有效picked/shipped关系。暂存允许未挑齐；只有ship要求逐行挑齐。处理差异时将移除项标released，新项picked，保留本单已选项；头version递增。手机重复扫描同一SN只提示已在清单内，不增加数量。

ship在一个事务中检查版本、reserved状态、逐行数量、全部SN现状、逐台正售价和实际交货人，然后标记sale/shipped、saleUnits/shipped、stockUnits/sold并清空当前位置。每台记录实际出库位置和成本快照；数量R随着头状态改变而减少，不再另减一次预留。未确认成本留null并提示部分毛利不可算。

本次可选同时登记客户全额付款，但调用方须有相应财务权限。无财务权限仍可完成出货，交由有权限人员补录付款，不能用“已出货”自动证明货款已收。

### 转仓和代卖

发送转运前验证SN、位置、未被pick锁定；重庆移出后仍需 Q−R>=0。单位改in_transit、location清空；目的仓实际接收时改in_stock及目标位置，不能运输中双计。允许分次确认转运实收，头状态按子项归集。

全国取出的registered机器可完善商品后直接dispatch给明威，起点用originLabel描述，不经过重庆现货。consignmentSale只能选择该代卖位置的在库实机，直接生成已售单，不走重庆数量占用；一次反馈可含不同型号，按规格自动归组。仍只记录真正售出的SN，未售不产生收入。

### 费用与钱款

费用只在已售实机上分配，共用整单或显式所选SN子集，专属费用是子集只有1台的情况。所有分摊使用BigInt分，按SN升序分配余分；修改费用生成新分摊版本，不删旧版本。

客户付款首期按销售全额登记，receivedAt可在交货前后。agent只形成代收余额；company在同一事务形成唯一directCustomer到账并分配全额，不再记录代理转回。代理到账可关联多笔销售和多台，按具体实机金额分配，尾款继续保留待转回；同一账款不能被两笔并发到账超额核销。

每个转款人汇总：有效客户代收全额之和减去该代收人对应实机的有效公司到账分配。实际到账总额另按receipt统计，其未分配部分不能自动抵扣任意客户销售。费用不冲减代理应转回金额。

### 更正与历史导入

所有已生效事实更正用限定kind的correction命令，不做通用PATCH任意字段。预览不修改业务，返回10分钟有效的 `previewToken` 和差异摘要：使用现有fieldEncryption的认证加密封装`purpose/userId/requestHash/targetVersions/expiresAt`。提交须同时提供token和同一changes，解密校验用途、用户、期限及所有当前版本，再在模块锁下执行；不可把客户端传入的previewHash当可信授权。

未出货单取消不属于纠错。已售错绑SN要同时说明错误机器和真实机器的去向，两个身份及已有关联须无冲突；不能借此实现真实退货。作废误录销售、修改收款等必须连同受影响资金关联一起预览和原子修正；无法保持实物和资金一致就拒绝，不留下负数或半完成状态。

导入分四类：期初实物、历史销售、客户付款、公司到账。预览一次读取所有相关SN、外部记录键、商品与人员，验证并归组；按行提示错误，但确认提交整批原子执行。资金稳定externalRecordKey必填，不能用金额日期猜测重复；历史销售一个SN只允许一条有效已售关系。

期初以cutoverAt对应的未售现货为起点。历史销售发生时间必须早于cutoverAt，只允许创建新的历史sold主档或把registered身份补成历史sold；若已存在inStock/inTransit/newSale则拒绝冲突，不能再次扣当前现货。历史来源订单、实际仓库不明允许明确待补，不能虚构某重庆仓。后补资金照实关联已导入销售，历史有多少未转回就继续保留多少。

基础资料配置由库存页“设置”入口进入，管理员或对应授权者维护规格、位置、人员和价格；不新增复杂CRM。系统启用配置与业务资料分开，启用前明确cutoverAt。无权限入口不显示，API仍独立保护。

业务表格沿用浅色蓝色规范、标准按钮／输入／badge、Lucide图标、分页和现有搜索习惯；非仪表盘不做业务卡片网格。页内状态覆盖loading/empty/error/permission/conflict/saving；失败保留用户输入，版本冲突提示刷新对照，不直接覆盖。

手机宽度375px与短视口可完成核心查询、收货、挑货、出货和到账登记；主要触控区>=44px，输入字号>=16px，表单内容可滚动，软键盘不遮挡提交，页面不整体横向溢出。宽字段进入详情但不能借隐藏代替权限。桌面1366/1440/1920px检查表格可读性。统计、字段和金额校验两端一致。

把扫码能力抽为可复用组件或hook，识别后回调由当前业务决定。旧pickup流程继续绑定订单，新receive进入待确认清单，pick只匹配当前需求，不自动入库或出货。图片OCR候选必须人工核对；关闭、切页、隐藏页面及时释放相机，取消及失败不显示为成功。电脑允许手工或扫描枪键入SN。

## 附件和安全实现

- 新上传路径固定为 `pickup-evidence/stock/{kind}/{attachmentId}.{ext}`，复用既有受控前缀和私有Bucket，服务器生成，不接受任意路径。扩展ossService受控签名方法，保持原接口不变；上线核对现有RAM实际授权确实覆盖该路径，不能仅凭文档推断。
- prepare先校验所有目标权限并登记预备元数据；HEAD大小和Content-Type在锁外检查，confirm在事务内复验状态及目标权限。JPG/PNG/WebP/PDF<=10MiB，OCR仍仅前三种。
- 原取货照片可关联显示，但读取继续执行原pickups/TAG权限；不得因关联到stock实物就绕过旧凭证权限。新增一张照片关联多台时，所有涉及目标都可读才签名；混有资金凭证还需财务权限。
- 日志只记录actorId、实体ID、动作、结果和错误码，凭证URL、照片、联系方式、导入原文、完整财务快照不写日志；审计敏感内容通过fieldEncryption加密保存。
- sourceOrder、历史事件、筛选统计、OCR结果、Excel、附件及幂等重放全部使用权限投影；未知字段直接拒绝，不允许把cost或amount藏在notes外层绕过权限。

## 迁移和切换步骤

1. 开发者从已核实的完整基线创建隔离分支／工作树，保留主工作区其他未提交内容；当前主目录存在大量其他任务修改，不能整体提交它们。
2. 编写新Migration的up/down，先建商品、资料、settings、units，兼容回填旧绑定，再建销售、流转、资金、附件与导入表；新模块disabled。Migration只做结构与身份桥接，不做真实盘点或销售推断。
3. 在专用空测试库演练全部up/down/up及旧绑定回填，验证旧数据摘要和旧API契约；有新业务时down必须拒绝删除。schema变更与业务历史导入分开执行。
4. 先发布兼容API：无新模块使用时也能维护old binding与StockUnit身份；旧前端仍可扫码。新前端发布后再由管理员显式配置和启用stock。生产迁移、发布和真实导入另按当前会话授权执行。
5. 回滚优先关闭stock新写入并恢复兼容应用制品，保留新增表及事件；不以down清除已录实物或款项。若回退到不认识stock的旧代码，旧取货仍能写nullable bridge；恢复前运行 `npm run stock:repair-bridges` 只读核对，再由明确管理员执行 `--apply --actor-id=<ID>` 幂等补齐。

## 开发完成与交付格式

开发者交付时提交：变更文件和提交范围、实际Migration文件名、API与页面完成情况、专项验收逐项结果、失败或跳过原因、PC/H5证据、原取货兼容结果、数据库回滚边界和剩余真实业务验收项。禁止把文档检查或合成测试写成真实扫码／到账／生产验收。

按仓库现有入口执行相关检查：

```bash
docker compose -f docker-compose.dev.yml exec api npm run lint
docker compose -f docker-compose.dev.yml exec api npm test -- --runInBand
docker compose -f docker-compose.dev.yml exec api npm run docs:check
docker compose -f docker-compose.dev.yml exec frontend npm run lint
docker compose -f docker-compose.dev.yml exec frontend npx vite build
```

开发容器未运行时，可用`docker compose ... run --rm --no-deps api`执行纯文档或静态检查；不得为检查意外启动邮件、爬虫、其他Worker或业务库迁移。数据库测试按专项清单的独立库门控，真实样本在明确授权下执行。

本方案已给出编码所需默认决策，不保留需要今晚继续回答的业务问题。若实现中遇到与真实现状冲突的证据，应记录具体冲突，不擅自改变已确认的成本、库存或结算含义。

# 生产环境部署指南

> 状态：当前有效
>
> 最近核对：2026-10-30
>
> 适用环境：`PP_CloudServer`；宿主机 Nginx、宿主机 PostgreSQL 15、本地构建发布制品

## 部署结论

生产环境保留宿主机 PostgreSQL 和共享 Nginx。Apple 订单管理系统通过 Docker Compose 管理 `api`、`email-worker`、`order-mail-worker`、`wecom-worker` 和显式启用的 `inventory-worker`，数据库迁移由一次性 `migrate` 与 `security-migrate` 容器执行。官网爬虫 Worker 已退役。

发布制品必须在本地 `main` 分支构建为 `linux/amd64`。服务器只加载镜像、校验制品、执行迁移和切换版本，不在服务器执行 `npm install`、前端构建或源码编译。

```text
Internet
   │
宿主机 Nginx（同时承载其他网站）
   ├─ /      → /var/www/apple-order-mgr/current/frontend
   └─ /api/  → 127.0.0.1:3001
                         │
                  Compose: api
                  Compose: email-worker
                  Compose: order-mail-worker
                  Compose: wecom-worker
                         │ host.docker.internal:5432
                  宿主机 PostgreSQL 15
```

## 边界与理由

| 部件            | 管理方式             | 约束                                                                         |
| --------------- | -------------------- | ---------------------------------------------------------------------------- |
| PostgreSQL      | 宿主机独立服务       | 不纳入本项目 Compose，不随应用发布重启；按发布分级决定新鲜备份或复用恢复证明 |
| Nginx           | 宿主机共享服务       | 只改本站点配置；先执行 `nginx -t`，通过后 reload；不影响其他站点             |
| API             | Compose              | 仅绑定 `127.0.0.1:3001`，由 Nginx 访问                                       |
| 邮件 Worker     | Compose              | 与 API 分离；发件人白名单可选，日志单独查看                                  |
| 订单邮件 Worker | Compose              | 只读同步官方订单邮件并归并生命周期                                           |
| 企微 Worker     | Compose              | 按持久化投递队列幂等推送新订单                                               |
| 前端            | Nginx 静态文件       | 位于版本化发布目录，通过 `current` 软链接切换                                |
| 历史上传        | Nginx 兼容路径       | 暂保留旧 `/uploads/` 别名；鉴权下载接口完成后移除                            |
| 日志            | Docker stdout/stderr | `json-file` 自动轮转；不再依赖容器内永久日志文件                             |

宿主机 PostgreSQL 的选择符合当前单服务器规模，也避免数据库随应用 Compose 被误删或重建。它仍需要独立备份、权限和监控；如果未来迁移到托管数据库，只需替换连接配置和网络策略，不应把数据库临时塞回应用 Compose。

## 环境配置

生产环境变量保存在 `/var/www/apple-order-mgr/shared/app.env`，权限必须为 `600`。不得把它放入发布制品或 Git。

必要配置包括：

- 数据库：`DB_HOST=host.docker.internal`、`DB_PORT=5432`、`DB_NAME`、`DB_USER`、`DB_PASSWORD`、`DB_SSL=false`
- 加密：`FIELD_ENCRYPTION_KEY`、`FIELD_ENCRYPTION_KEY_VERSION`
- 认证：`JWT_SECRET`、`JWT_EXPIRES_IN`
- 前端：`FRONTEND_URL=https://apple.godp.me`
- 邮件：`IMAP_HOST`、`IMAP_PORT`、`IMAP_USER`、`IMAP_PASSWORD`、`IMAP_MARK_SEEN`；`IMAP_ALLOWED_SENDERS` 配置精确地址，`IMAP_ALLOWED_SENDER_DOMAINS` 配置精确域名，两者均为空时接受任意标准化 From
- 运行：`NODE_ENV=production`、`RUN_WORKERS_IN_API=false`、`LOG_TO_FILES=false`

数据库连接池由 Compose 按进程覆盖：API 最大 8，两个 Worker 各最大 3，迁移进程最大 2。正常运行时理论上最多使用 14 个应用连接。

生产 Compose 固定使用 `172.28.240.0/24`，PostgreSQL 的 `pg_hba.conf` 只允许该网段以 `apple_user` 访问 `apple_order_mgr`。调整网段前必须先核对服务器其他 Docker 网络，并同步修改数据库访问规则；不要给全部容器网段或公网开放数据库。

## 本地构建发布制品

先在仓库根目录核对分支和质量门禁：

```bash
git branch --show-current
git status --short
npm run lint
npm test -- --runInBand
npm run docs:check
npm --prefix frontend run lint
npm --prefix frontend run build
```

构建：

```bash
./scripts/buildProductionRelease.sh
```

脚本会：

1. 拒绝非 `main` 分支；
2. 计算当前工作树的 Git tree hash，未提交变更也纳入版本标识；
3. 构建 `linux/amd64` 的运行镜像、迁移镜像和前端；
4. 生成 `images.tar.gz`、前端静态文件、Compose、Nginx 示例、源码快照、清单和 `SHA256SUMS`。

管理台侧栏仅显示版本号。`frontend/vite.config.js` 每次构建以北京时间生成 `vYYYYMMDDHHmmss` 并嵌入制品；开发服务使用启动时版本。后续系统更新须重新构建前端并在发布后回读侧栏版本，避免继续显示旧版。版本显示用于辨识前端制品，API 与 Worker 仍以发布清单核对。

组件独立增量发布例外：生产 API、Worker 和前端本来就可能处于不同版本。若本次前端不在批准
范围，不得因构建发布制品而带入工作树中的其他 UI 变化，也不重写侧栏版本。先把已验收生产
前端完整复制到受限本地目录并逐文件记录摘要，再设置
`PRODUCTION_FRONTEND_SOURCE_DIR=<该目录/frontend>` 和
`PRODUCTION_FRONTEND_VERSION=<已验收前端版本>` 运行构建脚本。脚本将原字节复制进新发布
目录，并在 manifest 记录 `frontendSourceMode=preserved-production-bytes`、前端版本与完整树摘要；新
`releaseId` 只标识本次制品／API／工具，不声称前端已升级。候选仍执行 `prepare`、实际全部
Nginx 身份 `check`、带 `expected-current` 的 `switch` 及 `verify`。未提供该变量时才构建当前
源码前端；两种模式都必须在计划中分别记录各组件版本。

制品输出到 `release-artifacts/<release-id>/`。`manifest.json` 同时记录 commit 和 tree hash；若 `workingTreeClean=false`，发布记录必须以 tree hash 为准，不能只写 commit。

构建源必须包含 `vendor/xlsx-0.20.3.tgz`。运行和迁移镜像的依赖安装阶段先执行 `npm run security:verify-vendor`，制品缺失或 SHA-256 不匹配立即失败；不得临时从旧 npm registry 版本补装。公开依赖来源与许可见[第三方制品说明](../../vendor/README.md)。前端依赖审计同时纳入现有 CI，不能用构建成功替代安全检查。

## 源码与生产能力收敛

生产增量必须合入构建所用的 main，禁止只修生产压缩包而让下一次完整构建再次覆盖。首次接入时应对照现有前端、实际 API／各 Worker 和独立采集运行目录，区分故障回退与有意的组件独立版本；不能用一个整仓 commit 冒充所有组件版本。

`config/productionCapabilities.json` 维护已发布能力的源码要求及前端行为标识。能力新增时同步实现、回归与清单；不能通过删除清单项绕过失败。`scripts/productionSourceGuard.py` 提供三层校验：

1. `source` 校验关键实现并记录全部业务源码摘要，输出 `source-capabilities.json`。
2. `runtime` 在断网只读容器读取实际镜像的 `src`，要求与已校验源码逐文件一致，输出 `runtime-source-proof.json`。
3. `frontend` 只从 HTML 可达的真实 JS/CSS 中核对能力标识，将资源摘要与能力绑定到发布目录私有的 `capabilities.json`。

构建入口强制执行以上检查；CI执行源码检查、构建检查和 `npm run test:release`。标识检查用于发现代码／制品来源退化，不能替代标签权限、版本冲突、代抢取消释放、付款码及跨天日志等行为测试。

前端门禁在切换前核对上版与候选的能力及源码清单。已登记版本不得换成无清单版本，不得移除能力编号或原有行为证明；即使前端保持原字节，新增后端能力也独立受源码清单保护。API／Worker差量来源、目标源码摘要和行为证据仍须纳入统一冻结计划。

仅 API 发布保全前端时，须连同其父目录的 `capabilities.json` 一起保全；新源码证明与被保全的前端证明分别留档。私有证明不得放入公开前端目录。

有意回退使用 `switch --rollback`，但当前版本必须事先保存 `rollback-target.json`，包含精确的 `releasePath`、入口 HTML 的 `indexSha256` 和全部可达资源的 `assets` 摘要。目标缺证、路径不符或内容变化均拒绝；该标志不是任意跳过能力检查的开关。自动切换失败仍恢复旧指针并复验；API／Worker由执行器反向回退。

```bash
npm run check:production-source
python3 scripts/productionSourceGuard.py runtime --image <候选镜像> \
  --manifest <发布目录>/source-capabilities.json --output <发布目录>/runtime-source-proof.json
```

首次接入的旧生产树可以没有能力清单，但候选必须生成完整证明，并在冻结计划绑定首次核对证据。首次接入后不再允许清单退化。

## 发布前备份和演练

2026-10-05 用户明确调整发布边界：生产发布不备份 AOS 监控日志数据，不执行这些日志及相关原始文件的恢复演练，也不把其恢复作为发布门槛。数据库备份排除 `public.monitor_log_entries`、日志旧副本 `public.monitor_log_entries_*`、共享文件目录 `public.monitor_log_files`、压缩块 `public.monitor_log_blocks` 及其日分区 `public.monitor_log_blocks_*`、账号目录 `public.monitor_log_block_accounts` 及其日分区 `public.monitor_log_block_accounts_*`、全局回执 `public.monitor_log_receipts` 的数据；保留表结构及索引定义，并继续备份订单、账号、资金、库存、权限、配置及运行游标等业务数据。原始 AOS 日志文件不纳入发布备份和恢复清单。此规则不授权删除生产日志或改变现有保留期；历史报告中的整库恢复证据仍按当时范围解读。

下文生产发布中的“完整备份”指上述范围内的完整业务备份，须记录日志排除项，不能称为包含 AOS 日志的整库数据备份。

在服务器执行任何 Migration 前必须：

1. 用下列 `pg_dump -Fc` 排除命名明确的日志数据，备份 `apple_order_mgr` 的业务数据与结构；
2. 记录备份 SHA-256；
3. 保存当前站点配置、容器 inspect 和旧镜像信息；
4. 把业务备份恢复到隔离 PostgreSQL 容器，不恢复 AOS 监控日志数据或相关原始文件；
5. 在隔离库执行全部待处理 Migration 和敏感数据转换；
6. 检查迁移表、核心表行数、非空约束和敏感字段转换统计。

以下示例中的通配仅覆盖约定的日志副本及日分区，不能改成 `monitor_*` 排除其他监控业务。日志采集状态 `monitor_log_states`、范围模式 `monitor_log_storage_scopes`、迁移／运行指标 `monitor_log_storage_metrics` 仍作为配置与运行游标保留。

```bash
pg_dump -Fc \
  --exclude-table-data=public.monitor_log_entries \
  --exclude-table-data='public.monitor_log_entries_*' \
  --exclude-table-data=public.monitor_log_files \
  --exclude-table-data=public.monitor_log_blocks \
  --exclude-table-data='public.monitor_log_blocks_*' \
  --exclude-table-data=public.monitor_log_block_accounts \
  --exclude-table-data='public.monitor_log_block_accounts_*' \
  --exclude-table-data=public.monitor_log_receipts \
  apple_order_mgr > business.dump
```

只有隔离演练通过，才进入生产切换。健康接口通过不能替代数据库与业务校验。

### 发布准备与轻量预检（2026-10-31经验）

以下是现有发布保护的执行清单，不改变A/B/C/D等级、备份范围或校验强度。开始全量数据库/文件备份前人工逐项核对；本清单尚未接入自动阻断，不能只因文档存在就声称已检查。

1. **先完成候选，再开始重型保护。** 先收敛生产源码、完成已知修正、相关回归及最终制品构建。准备独立候选目录、传输和解包；不覆盖已有发布目录。记录源码/制品摘要和回退目标后再开始备份。若后续源码或制品变化，重新核对分类及受影响证据，不能机械复用或机械全量重跑。
2. **冻结文件快照覆盖的目录和父目录。** 文件清单也记录选中路径的祖先目录元数据；即使新候选目录本身不在备份范围内，在扫描期间新建、删除或重命名同级目录也可能改变父目录并触发 `SOURCE_TREE_CHANGED`。先完成这些准备动作；按现行方式排空并暂停相关写入者，finally恢复。失败时保存具体变化路径及字段，定位后重新取一致性证明和快照，不移除二次目录核验。
3. **在相同执行环境预检UTF-8。** `PYTHONIOENCODING`只影响标准流，不能修复Python 3.6的文件系统解码；`C.UTF-8`也不保证在服务器存在。先用 `locale -a` 选择实际存在的UTF-8 locale；在将运行备份工具的用户、解释器和环境中核对 `sys.getfilesystemencoding()`、`locale.getpreferredencoding()`，并用临时中文文件验证目录枚举、`json.dumps(..., ensure_ascii=False)`及UTF-8字节化。此前服务器验证可用的是 `en_US.utf8`；只为本次命令及子进程设置 `LC_ALL`/`LANG`，不修改系统全局locale，不改名业务文件规避错误。
4. **恢复隔离证明随用随生成。** 不在长时间完整恢复之前一次性生成后续所有容器证明；各步骤开始前按现行工具核验实际隔离状态并生成新鲜证明，避免前序恢复超过有效期。已过期时保留旧证据并重新生成，不放宽时效或伪造时间。
5. **门禁传规范化绝对路径。** 先核对原始路径及祖先没有不允许的符号链接，再规范化候选/输出目录；不能用 `resolve()` 隐藏原始非法链接。Python使用 `Path(...).resolve()`，不把 `.absolute()`当成消除`..`或验证无符号链接的替代品。预检与正式门禁使用相同入口、解释器及权限，保留原有路径和链接保护。
6. **CI失败先定位，再限定复验。** 对比相同失败是否存在于发布前源码/CI，保存精确提交与运行记录；环境缺项在隔离环境补齐验证，不假定“都是旧问题”，也不将局部通过写成远端CI全绿。候选无变化且相关检查已通过时，不重复整套构建/回归；代码变化、失败或未解决问题才触发相称复验。
7. **分开计时与业务验收。** 分别记录准备、备份、恢复、失败重跑、受锁切换和上线回读；并行阶段不相加，不承诺未经实测的总耗时。生产只读冒烟提前准备：HTTP缓存指令按大小写及逗号列表的实际语义核对（重复`no-store`有效），shell变量避免zsh只读变量`status`，且保留真实退出码；不为验收新增/修改生产业务记录。

本次证据及可避免耗时见[代抢费用发布耗时复盘](../archive/2026-10/2026-10-31-代抢费用发布耗时复盘与预检改进.md)。

### 统一备份与恢复工具（REL-01 至 REL-04）

发布制品内的 `productionReleaseBackup.py`、`productionReleaseFiles.py` 和
`productionReleaseDatabaseValidation.sql` 使用 Python 3.6 标准库，兼容生产 Python 3.6.8。
每次发布先按[生产发布分级执行规范](生产发布分级执行规范.md)生成并绑定分级证据。A级纯静态
前端和B级严格无写入变更可复用24小时内满足全部失效检查的完整恢复证明；没有有效证明时自动
升级到C级。C级业务写入及D级Migration／数据转换必须生成本次完整业务数据库备份并完成本次
完整隔离恢复，D级还必须在恢复库执行正式迁移演练。不得凭“改动小”或历史备份目录存在降级。

数据库工具保持一个 `SERIALIZABLE READ ONLY DEFERRABLE` 导出事务，取得
`pg_export_snapshot()` 后让 `pg_dump -Fc --snapshot` 与源库摘要使用同一快照。正式摘要统一
使用 UTC，覆盖全部 `public` 业务表的逐表行数和稳定行摘要、列／UDT／enum／长度与精度／
约束／索引／序列定义、序列 `last_value` 与 `is_called`，以及 `SequelizeMeta` 数量和摘要；
只排除本节列明的 AOS 日志表数据，配置与运行游标仍然保留。

PostgreSQL 序列不受 MVCC 快照约束，因此源库现场 `last_value/is_called` 只作观察值，不参与
源快照与恢复结果的相等判定。恢复端单独核对 dump 恢复出的序列状态、拥有列最大值和下一次
`nextval` 安全性；不得把序列现场值描述为与表数据同一快照。

恢复端必须是网络模式 `none`、无公开端口、带专用隔离标签的 PostgreSQL 15 容器，dump
精确只读挂载到 `/restore-input/`。空库检查、实际 PostgreSQL 主版本查询、`pg_restore` 和
恢复后摘要全部通过已证明的同一 `containerId` 执行；工具拒绝 `PGHOST` 或外部连接参数绕过
容器。最后用 `compare-validations` 比较源快照与恢复摘要，仅返回 `passed: true` 的弱校验不
予接受。

源库可能因历史 `DROP COLUMN` 的 `attnum` 空洞、PostgreSQL 对 ARRAY cast 的原生重新解析及
分区派生对象创建顺序，与 `pg_dump` 重放后的原始定义文本不同。遇到这种差异不得用正则删除
cast、括号或约束名来放宽比较。应在无 DDL 窗口用 `schema-source-archive` 生成独立的
`--schema-only` archive，要求导出前后原始 schema 摘要都等于业务备份的源快照摘要，并用
`pg_restore --list` 证明不含 `TABLE DATA` 或 large-object data。随后把该 archive 恢复到第三个
全新无网 PostgreSQL 15 reference 容器，与业务 dump 的 schema-only 容器及完整恢复容器运行
同一套 catalog inventory；schema、dense 列、类型、序列及 ownership、约束的递归 parent 图、
索引完整属性、分区树、函数、非内部 trigger、relation 属性和注释必须逐对象严格相同。另用三库
共同的精确 PostgreSQL 15 镜像及同一 `--restrict-key` 执行完整 `pg_dump --schema-only
--no-owner --no-privileges`，三份原始 SQL 必须逐字节一致；禁止删除版本 header、cast 或任何
正文后比较。原始失败结果和任何被判无效的比较 attempt 均保留，新证明以 HMAC 绑定两个 dump
摘要、archive list、三个容器、客户端镜像 ID、完整 SQL 摘要和各组件摘要。

业务文件可从单一受控根按重复的 `--include-path` 白名单纳入多个目录和文件；以 `/` 为源时
强制要求 include，禁止全机扫描。范围至少包含 uploads 导入文件、共享环境与 Worker 配置、
库存密钥、采集器更新、官网订单／收据／取货回填证据、当前发布配置与前端、本站 Nginx 配置
及本次队列 unit；原始 AOS 日志仍排除。运行中官网证据快照前必须停止领取并等待在途任务和
所核对的 queue／collector 写入归零，再生成认证 `consistency-proof`；该字段只证明证据列明
的检查范围，不表示全机不存在 writer，该过程不得发起新的 Apple 请求。文件散列后还要对
include 闭包做第二次完整 `lstat` 枚举，发现新增、删除、替换或重命名即失败。没有一致性
证明的清单不能登记为完整可恢复集合。

文件清单是 HMAC-SHA256 认证的完整逻辑视图，内容对象按 SHA-256 寻址。可变文件每次完整
散列；只有上次认证清单、文件系统身份均一致，且文件及源内全部父路径对任何身份都不可写、
不含符号链接时，才允许复用不可变对象摘要，否则回到完整散列。恢复只进入新建空目录，完整
读取并复核每个对象，拒绝缺对象、坏摘要、路径穿越、越界链接和特殊文件。候选清单不等于
恢复证明；数据库和文件都完成完整恢复后才能生成认证恢复组合证据及 `backup-set.json`。
选中子树内的相对目录链接原样保留，但禁止借链接父目录追入 include 后代。绝对链接必须同时
把每一级 target 加入白名单；清单保留原始 target，隔离恢复将已入清单的绝对 target 重映射
为恢复根内等价相对链接，创建全部链接后再严格解析，任何缺 target 或越出恢复根都失败关闭。
使用 `--source /` 时对象库可以位于源树下，但必须完全处于 include 闭包之外，工具会拒绝自备份。
每个目录、文件和链接还以 `lstat` 记录 `uid/gid`，owner 变化纳入扫描前后身份复核。真实 Linux
恢复默认使用 `preserve`，由 root 对普通项 `chown`、对链接本身 `lchown` 后逐项复核 owner 和
mode；隔离 Mac 演练只能使用限定到当前 manifest 摘要的 HMAC 认证 `ownership-map`。映射不全、
跨 manifest 复用、非法 uid/gid 或任一 chown 失败都不能生成完整恢复证明。

`cleanup-plan` 仅识别精确受限根中的认证备份集合：保留最近 7 天全部集合且至少两套完整可
恢复集合，并递归保护 current、rollback、base、dependency 引用。未知目录、活跃写入、
符号链接、状态或引用变化都阻断；一次计划最多删除一个集合，`cleanup-apply` 还需显式确认
计划摘要。工具不创建定时任务、不自动删除历史官网证据或生产文件；安全候选为 0 时不得为
释放空间强删。

通过 `ssh ... bash -s` 输送多步脚本时，非交互迁移使用 `docker compose run --interactive=false -T --rm migrate`，避免 Compose 消费后续脚本的标准输入；需要输入校验脚本时显式重定向对应文件。每步单独核验退出码与状态，不能因 SSH 返回 0 就推断后续启动和版本切换已执行。

## 生产切换顺序

正式发布使用 `productionRelease.py` 的冻结 JSON 计划。计划绑定源码摘要、只读生产基线摘要，
以及 API、各 Worker、前端各自的 expected/target 版本，不得把生产异构组件误写成同一版本。
数据库、文件、制品准备最多并行两个只读重 I/O 步骤；前端实际身份 `check`、迁移、API／
Worker 更新、`switch`、`verify` 和失败回退由同一个发布锁覆盖。锁内再次读取基线、迁移台账、
组件版本和 current。

含并行准备步骤的计划必须配置 `resourceGuard`，并行步骤必须声明只读且可串行降级。执行器在
开工前、并行组启动前和组内任务完成后调用真实资源探针，保存磁盘余量、回环 readiness 延迟和
数据库锁等待毫秒数。磁盘低于安全线或探针失败／超时直接失败关闭；API 延迟或锁等待超过阈值
后停止启动新的并行任务，把剩余可暂停任务改为串行。发布锁内的维护窗口步骤始终禁止并行；
监控错误不得被解释为“指标正常”后继续切换。

每个变更步骤执行前先落盘 `pendingMutation`。进程在动作完成与状态落盘之间中断时保持
unknown，必须提供锁内独立核对证据后显式解决，禁止自动重放非幂等动作。成功回退的 attempt
标记为 `rolled_back`，只能新建 attempt，不能 resume 后把已回退发布标为成功。前端后续验证
失败时，先用同一门禁和反向 `expected-current` 恢复旧指针，再反序执行 API／Worker 独立回退。
每个可变步骤应分别提供 `reconcileCompleted` 与 `reconcileRolledBack` 只读核对命令；
`resolve-unknown` 在锁内先重读基线、执行 pending 步骤所选结果的核对命令并原子保存已知结果，
再执行全部 `resumeChecks`；后置检查失败时保留已认证 resolution、标记失败并停止，不能让仍按
旧 `completedSteps` 推断的检查提前阻断实际结果对账，也不能只凭人工 JSON 声明解除 unknown。
执行任何对账命令前，state 的 release、attempt、plan、source 和 baseline 摘要必须与传入计划
全部相同；对账证据还须绑定 `planDigest` 与 `sourceDigest`，避免复用 evidenceDir 注入另一计划。

执行器默认丢弃命令原始 stdout/stderr，只记录 0600 的退出状态、摘要和计数；不得把
`images.override.yml`、Compose 展开配置、Docker inspect 原文、环境值或凭据写入普通日志。
候选在任何服务变更前进入锁，依次执行 `frontendPrepare`（现有门禁 `prepare`）和全部实际 Nginx
身份 `check`；计划的 `nginxUsers` 逐一检查，`switch` 使用实际入口对应的主身份，最后仍由同一
锁覆盖 `verify`。`--permissions-only` 仍只限本地制品，不能代替生产检查。

发布目录创建和复制完成后统一运行 [`productionFrontendGate.py`](../../scripts/productionFrontendGate.py)；标准构建脚本已调用 `prepare`，增量发布也必须调用。保留 `umask 077` 保护业务备份、环境与验收文件；`prepare` 只把公开发布根目录和 `frontend` 子目录设为 `0755`、前端普通文件设为 `0644`，拒绝符号链接和特殊文件，不递归修改发布根目录中的私密文件。不能依赖 `mkdir(mode=0o755)`，它仍受 umask 影响。标准制品将门禁脚本一同打包，上传解包后须再次检查，因为归档和目标父目录权限也可能影响访问。 生产统一安装入口为 `/var/www/apple-order-mgr/shared/tools/productionFrontendGate.py`（root 专属工具目录）；下列命令使用该实际路径。后续更新门禁时先校验制品 `SHA256SUMS`、备份现有工具，再将制品根目录的 `productionFrontendGate.py` 以 `0600 root:root` 安装到此处。不要假设生产发布目录存在仓库的 `scripts/` 子目录。

```bash
python3 /var/www/apple-order-mgr/shared/tools/productionFrontendGate.py prepare /var/www/apple-order-mgr/releases/<发布ID>
python3 /var/www/apple-order-mgr/shared/tools/productionFrontendGate.py check /var/www/apple-order-mgr/releases/<发布ID> --nginx-user nginx
```

`check` 必须在任何正式 API 切换前执行：检查公开目录／文件的明确权限，并以实际 Nginx Worker 用户验证全部前端文件的可读性（含父目录穿越）。本机构建使用 `--permissions-only` 仅验证制品模式；此选项不能代替生产用户检查。容器内 Nginx 运行身份与宿主机 `nginx` 账号不一致时，先核对实际 Worker 的 UID/GID，再用 `--nginx-user 33:33` 这类明确的非 root `UID:GID`，门禁通过 `setpriv` 清空补充组并降权读取全部文件；不能用同名宿主机账号替代实际身份。私密文件如 `shared/app.env` 继续保持 `0600`。现有业务备份恢复、候选 API、Migration、Worker 保全门禁继续执行。

完成正式 API 健康与业务检查后，版本指针统一通过下列命令原子切换，禁止用临时脚本直接 `ln`／`os.replace` 绕过门禁：

```bash
python3 /var/www/apple-order-mgr/shared/tools/productionFrontendGate.py switch /var/www/apple-order-mgr/releases/<发布ID> \
  --current /var/www/apple-order-mgr/current \
  --expected-current /var/www/apple-order-mgr/releases/<旧发布ID> \
  --nginx-user nginx --base-url https://apple.godp.me
```

`switch` 加发布锁并核对预期旧版本；切换前再次检查新旧前端权限，递归解析 HTML 入口、Vite 静态／动态导入及依赖预载表，并拒绝候选版本用同一 `/assets/` URL 提供与当前版本不同的字节（`IMMUTABLE_ASSET_REUSED`）。增量发布不得把任务名、固定名或旧内容哈希当作新资源名；Nginx 已对该目录使用长期 `immutable` 缓存，同 URL 换内容会使已有浏览器混用新旧模块。

切换后使用正常 TLS 校验、禁止跳转的请求验证首页、订单页、登录页、全部可达 JS/CSS 的内容类型及逐字节摘要，以及 API readiness 的成功／数据库健康字段。失败自动恢复旧 `current` 并复验，返回非零；调用方还必须执行原有 API／Worker 回退，不能把恢复指针当作整个发布回退。只读复验用 `verify <发布目录> --base-url https://apple.godp.me`。门禁不能代替浏览器表格与业务验收。排障见[前端 Nginx 500](故障排查.md#前端-nginx-500但-api-健康)及[页面加载后的白屏](故障排查.md#页面加载后的白屏)。

在发布目录执行，命令中的发布 ID以实际值为准：

```bash
shasum -a 256 -c SHA256SUMS
gzip -dc images.tar.gz | docker load
set -a
. ./release.env
set +a
docker compose --env-file release.env -f docker-compose.prod.yml config --quiet
```

涉及官网爬虫退役时，维护窗口上限为 15 分钟，并按以下无中断顺序执行：

1. 保持 API、邮件、订单邮件和企微服务运行，只停止旧爬虫 Worker；
2. 做最终数据库备份，并执行扩展 Migration；
3. 在临时回环端口启动新 API，健康后原子切换本站 Nginx upstream；
4. 替换正式 API 和前端，再将 upstream 切回正式端口；
5. 执行最终归档 Migration；
6. 滚动替换邮件和订单邮件 Worker；企微 Worker 先启动新版重叠实例，确认心跳后再替换旧实例；
7. 核对新订单和企微投递游标、Worker 日志及旧接口 410，再结束维护窗口。

普通结构迁移命令仍为：

```bash
docker compose --env-file release.env -f docker-compose.prod.yml --profile tools run --rm migrate
```

首次启用字段加密时才执行 `security-migrate`；爬虫退役发布不重复执行。每次替换 API 后都必须等待回环 readiness 成功，再切换 Nginx。

邮件 Worker 启动会按持久化 UID 游标扫描，首次以固定的最近 24 小时范围引导，此后每 30 秒扫描并由邮件事件即时触发；已读邮件也参与去重检查。发布时需确认 `IMAP_MARK_SEEN`、`IMAP_ALLOWED_SENDERS` 和 `IMAP_ALLOWED_SENDER_DOMAINS` 来源策略；地址与域名白名单任一命中即可通过，域名只按 `@` 后完整值精确匹配。两项白名单均为空时所有发件人都会进入主题与严格内容校验。主题命中但 From 未授权的邮件进入 `manual_review` 并保留加密原文；主题未命中的普通邮件记录原因后最小化为 `ignored`。应通过积压、失败率和人工处理队列监控误匹配风险。

## 验收标准

- `api` 为 healthy，且只监听宿主机回环地址的 3001 端口。
- `email-worker` 独立运行，无配置校验、IMAP 或数据库连接错误。
- 不存在旧 `crawler-worker` 容器；旧爬虫历史表位于只读 `archive` schema。付款官网核对通过现行独立官网队列运行，只有生产显式配置 `PAYMENT_OFFICIAL_REFRESH_ENABLED=true` 才由 API 每三分钟调度。
- 宿主机 PostgreSQL、共享 Nginx 和其他站点/容器未重启。
- `SequelizeMeta` 包含目标版本全部 Migration；核心表行数与备份前一致。
- HTTPS 首页和静态资源正常，`/api/health/ready` 通过 Nginx 和本地回环均可访问。
- 核对历史付款截图链接；当前兼容路径仍是公开 URL，属于后续安全闭环项。
- 至少完成登录和一个只读业务查询，并核对新订单入库与企微投递游标连续。真实新邮件业务验收已完成，本次只做回归。

## 回滚

若新服务在数据迁移前失败，停止新服务并恢复旧容器即可。若已经执行字段加密或不向后兼容的 Migration，旧应用不能直接连接新数据库；必须停止新服务、恢复发布前数据库备份、恢复旧 Nginx 配置和旧容器，再验证数据窗口。

```bash
docker compose --env-file release.env -f docker-compose.prod.yml down
```

不要默认执行 `db:migrate:undo`。生产回滚以已验证的完整备份恢复为准，并记录切换后可能丢失的数据窗口。

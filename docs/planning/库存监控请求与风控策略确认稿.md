## 二、当前请求策略

| 项目 | 生产实际行为 |
| --- | --- |
| 启用范围 | 16 个 iPhone 18 Pro Max SKU × 49 家门店，共 784 个组合；不根据接口少返回门店而缩小分母 |
| 周期 | 每 300 秒一个自动计划轮次；单轮截止时间为计划时间加 300 秒 |
| 请求拆分 | 每组最多 5 个 SKU，分别查询 6 个固定区域邮编；当前每轮 24 个基础库存请求，响应按 SKU＋门店去重 |
| 正常并发 | 最多 3 个在途采集任务；并发数不等于每秒请求数 |
| 实际发起间隔 | PostgreSQL 库存模块门控统一预留下一次发起时间，间隔 1,000～1,150 毫秒；库存、目录、出口验证等共享该门控 |
| 其他请求 | 出口核验、目录请求也经过门控并计入预算；存在并发互斥与恢复期限制 |
| 请求时限 | 单次网络超时 20 秒；网络租约 45 秒、采集任务租约 90 秒；迟到结果受租约及恢复代次校验 |
| 重试 | 普通临时故障单任务最多 3 次尝试；整轮额外重试不超过基础任务数的 20% 向下取整，当前最多额外 4 次；重试间隔至少 5 秒 |
| 541／429 | 不作为普通重试处理，进入风控冷却与恢复流程 |
| 重叠和漏跑 | 不积攒历史轮次后突发补跑；前轮占用、冷却等造成的未完成继续记入计划统计 |
| 手动查询 | 进入同一调度、代理、风控与预算体系；不构成绕过保护的直连入口 |
| 新鲜度 | 成功观测有效期为观测时刻加两个配置周期，当前 10 分钟；失败不生成“无货”事实 |

限流口径需要纠正：健康接口中的 `taskRps=1`、`globalRps=5` 是静态展示字段。当前库存生产路径实际使用上述约 1 RPS 门控；校验模式中的 5 RPS 参数，不能作为“所有业务模块已共享同一个 5 RPS 限流器”的生产证明。

当前预算：每小时 1,200 次、每天 25,000 次请求、每天 512 MiB、每天 400 次代理提取／核验计数。预算桶按 UTC 切日，即北京时间 **08:00**；代理提取计数也包含出口核验，并非只计算供应商接口调用。失败请求同样消耗相应预算；重启及人工恢复不清零预算。

## 三、当前代理与风控策略

### 3.1 十分钟隧道

当前配置为一个网帆隧道来源，IP 粘性 600 秒；套餐允许 10 条并发，程序正常采集并发仍为 3。套餐有效期至 2026-11-06 15:13:01，来源标签继续沿用原标签。没有配置第二个独立来源，也不自动回退直连。

会话到期或必须更换出口时，程序等待在途请求释放，再申请候选会话并通过出口核验服务确认实际出口。实际 IP 仅保存哈希用于去重／拒绝判断；不会仅凭改变会话名认定换 IP 成功。候选更换有最多 3 次的限制，拒绝出口列表保留最近最多 20 个哈希。会话状态持久化，重启不会天然清除风险历史。

正常十分钟到期换会话是代理维护事件，本身不意味着库存中断或重新到货。出口核验成功只证明代理链路可用，不能解除 Apple 库存恢复状态。

### 3.2 故障分类与当前动作

| 故障 | 当前动作 | 业务含义 |
| --- | --- | --- |
| 目标端 541 | 至少冷却 60 秒；进入恢复；要求不同实际出口，记录拒绝出口 | Apple 拒绝本次访问，不能推断库存 |
| 目标端 429 | 至少冷却 60 秒；进入恢复；遵守更长的 `Retry-After` | 限流；不自动等同于必须换出口 |
| 风险累计达阈值 | 冷却至少 10 分钟 | 下述三项满足任一即触发 |
| 401／403 挑战、阻止的重定向、无效响应、商品映射不符 | 设置全局人工核查暂停原因 | 不继续自动尝试挑战页面或错误结构 |
| 代理鉴权失败／拒绝 CONNECT／明确连接失败 | 暂停对应代理来源；当前单来源可能因此无法采集 | 先修复代理，不报 Apple 无货 |
| 网帆 CONNECT 631 | 仅 `.fanproxy.com` 且状态文本为 `Internal Server Error` 时视为隧道临时故障 | 其他来源或不匹配响应仍按原拒绝策略处理 |
| CONNECT 502／503／504、超时、响应读取失败、上游临时错误 | 普通临时故障，有界重试；连续 5 次临时失败触发 10 分钟冷却和恢复 | 不计为目标端 541／429 风险 |
| HTTP 200 但缺失／不可解析 | 校验响应结构；缺失组合保留最后观测并标异常 | HTTP 200 不等于有效库存 |

541／429 升级至十分钟冷却的三个条件：连续风险响应至少 3 次；最近 5 分钟至少 20 条相关结果且风险比例至少 20%；最近 5 分钟至少 2 个不同实际出口出现风险。窗口最多保留 300 条记录，目录等相关结果也可能进入统计。

因此，间隔十分钟出现一次 541，可能反复落在五分钟窗口之外；三次成功探测又会重置部分恢复计数，目前缺少跨多次短暂恢复的较长时间窗口约束。

### 3.3 当前恢复流程

1. 等待冷却、预算、任务和网络租约允许；541 还需完成不同实际出口验证。
2. 恢复阶段仅允许一个库存请求在途；有效探测之间等待至少 5 秒。
3. 累计 3 次符合当前恢复代次的有效库存响应，即退出 `recovering`，清除恢复失败计数；**不要求完整一轮成功**。
4. 恢复请求失败后，第 1 次退避 20 分钟，第 2 次 40 分钟，第 3 次进入 `RECOVERY_EXHAUSTED` 人工暂停。新风险会更新恢复代次，迟到成功不得解除新风险。
5. 探测仍依赖调度机会，60 秒冷却不意味着恰好第 60 秒就发请求。人工“已核查，恢复探测”也不是强行宣告成功；预算、既有冷却与拒绝出口历史继续保留。

当前任务层只将部分门控原因当作可等待状态；`ALTERNATE_EGRESS_REQUIRED` 等路径可能直接结束待处理任务。这会把尚在等待出口恢复的轮次提前变成部分失败，需在修复时统一等待与截止语义。

## 四、当前库存与通知逻辑

成功响应逐组合更新快照，普通失败只给受影响且本轮尚未成功的组合标记错误，保留最后成功值和时间。这部分符合局部失败原则。

但另一条全局路径会在 `TARGET_REJECTED`、`TARGET_RATE_LIMITED`、`TARGET_CHALLENGE`、`INVALID_RESPONSE`、`CATALOG_MISMATCH` 后给全部快照设置 `interrupted`／`hardInterrupted`，覆盖了上述局部保护效果。

| 事件 | 当前主要判定 |
| --- | --- |
| 首次有货 `first` | 没有之前的成功观测，本次有货 |
| 到货 `arrival` | 之前有效、新鲜且未中断的无货观测，本次变成有货 |
| 恢复有货 `recovery` | 中断、异常或过期后再次有货；前后均有货，只要被标为硬中断仍可触发 |

库存事件按门店和事件类型合并，约 10 秒聚合，消息正文限 1,600 字节；通知有效期 120 秒，群发送上限每滚动 60 秒 18 批。发送前会再次检查库存新鲜度、启用范围和风控状态。静默时段为 00:30–08:30，不补发过期提醒。

运行健康提醒另有“两分钟确认、同类三十分钟合并”规则；该规则**不约束按门店发送的恢复有货消息**。当前健康状态还可能因少量成功清除错误、退出恢复而转正常，不能证明 784 个组合完整可用。发送接口 `accepted` 也不等于已核实群内收件。

## 五、应分开的三类状态

| 状态 | 应回答的问题 | 禁止混用 |
| --- | --- | --- |
| 请求与风控状态 | 是否允许继续请求、是否要冷却或核查代理 | 一次 541 不应抹掉其他商品刚完成的观测 |
| 组合数据状态 | 该商品该门店最后一次有效结果是什么、何时取得、是否过期 | 未知、失败和过期不能变成“无货” |
| 通知状态 | 是否观测到补货，还是恢复采集后重新得知库存 | 前后有货不能包装成到货；一次恢复不应扩散为几十条门店提醒 |

| R2 风控保留并补长窗口 | 保留现有 541 换实际出口、至少 60 秒冷却、五分钟阈值、有限候选和 20／40 分钟退避；新增滚动 30 分钟内至少 3 次目标 541／429，则至少冷却 10 分钟 | 长窗口计数跨短暂恢复和重启保留，过期自然滑出；不因三次成功抹掉反复风控。每次风险都重新计算，更多冷却可能降低完整率，必须如实记录 |

| R4 库存状态 | 取消因单次全局风险而给全部快照设置硬中断；全局健康单独记录，失败只影响对应尚未成功的组合 | 已成功组合保留真实结果、观测时间和原有效期；未知不报无货。间隔出现漏采时记录连续性缺口，重新查到有货不能擅自推断期间发生补货 |
| R5 通知降噪 | 停止逐门店推送“恢复后检测到有货”；恢复事件保留在历史，恢复通知合并成一条运行健康摘要，附覆盖数、有货数量和页面链接 | 短暂或长时间中断均不逐店刷屏；仅连续有效且新鲜的无货→有货触发到货通知。首次启用采用初始库存摘要；保留现有静默、有效期、限流及未知发送结果不盲重发规则 |
| R6 恢复验收 | 三次请求成功只标为“请求通道恢复”；一轮完整且数据新鲜标为“本轮数据完整”；连续 3 个完整自然轮次且最近 30 分钟无目标风险，才显示稳定恢复并发送一次健康恢复摘要 | 恢复阶段保持 R1 的低频参数，不自动升频；新故障、漏跑或范围改变中断完整轮次连续性。短期正常与 48 小时稳定性验收分别展示 |

R6 延续原[需求方案](库存监控需求草案.md)对“三个完整轮次且三十分钟无风险”的恢复约束，纠正生产实现仅三个请求成功的差距。恢复健康摘要只对应之前已经报告的故障，重复故障沿用合并策略；采集过程中确认的新到货仍可按独立库存条件发送，不应等待三十分钟而全部过期。

通知示例：

> 库存监控已稳定恢复。当前覆盖 784/784，连续 3 轮完整，最近 30 分钟无目标风险。有货组合 N 个，详情见库存页面。中断期间是否发生补货无法确认。

示例中的覆盖、有货数量和轮次必须取当时实际值；不满足条件不发送该文案。故障持续时保留故障提醒，不反复“故障—正常”刷屏。

## 七、确认后实施与验收

确认后的规则先同步库存设计、API 状态说明、涉及的数据库契约和测试用例，再实现。若需要持久化新窗口或状态，通过正式 Migration 演进；不直接改生产状态凑出恢复结果。通知语义、保护历史和旧待发事件需有兼容处理，避免发布后补发旧恢复队列。

| 验收场景 | 必须达到的结果 |
| --- | --- |
| 有货→另一请求 541→仍有货 | 成功组合不被全局标错；无到货通知、无逐门店恢复通知；稳定后仅一条健康摘要 |
| 无货→采集中断→有货 | 保存恢复观测与数据缺口，不宣称确认补货 |
| 连续新鲜无货→有货 | 正常产生一次到货事件与有效通知 |
| 十分钟会话自然到期 | 有界换会话并核验实际出口；不凭到期产生库存中断／恢复通知 |
| 541 与代理 631 | 目标拒绝和特定供应商临时错误分别分类；未知 631 不扩大白名单 |
| 同一出口被换会话名复用 | 实际出口哈希仍被识别，不能绕过 541 换出口要求 |
| 出口、冷却等待跨轮次截止 | 准确记录等待和未完成，计入计划分母，无补跑突发 |
| 五次临时故障／恢复三次失败 | 分别进入既定冷却／人工暂停；预算和候选上限有效 |
| 30 分钟三次目标风险 | 即使中间短暂恢复也升级冷却；重启不清空窗口 |
| 旧请求迟到成功 | 不清除新恢复代次、暂停或冷却 |
| 三次请求成功但轮次缺失 | 不能显示完整数据或稳定恢复 |
| 真到货发生在健康观察期 | 组合证据有效且已允许发送时及时通知；不被健康三十分钟窗口一概压住 |
| 静默、超时、未知发送结果 | 不补发过期库存事件、不盲目重发未知结果、不突破群限流 |
| 固定全量自然观察至少 48 小时 | 至少 95% 计划轮次全量完成，轮次 P95 不超过 300 秒；冷却／漏跑留在分母，另报数据年龄、代理失败、目标风险及消息实际送达 |

本轮交付为策略审阅稿；上述用例尚未执行。生产修复、发布和真实观察在确认后的执行范围内另行留证，不能将文档检查通过当成业务验收。

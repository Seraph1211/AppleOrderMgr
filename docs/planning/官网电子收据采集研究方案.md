## 目标和试验范围

验证“原始订单链接 → 该订单的 AppleID 登录 → 商城会话交接 → 查看电子收据”的完整链路。首批选择系统 ID 1093（用户截图对应订单）、1357、1356，均在只读查询时为邮件状态 `picked_up` 且已有官网状态 `PICKED_UP`，分别属于不同账号。旧状态不计为本次官网核实。

另加入已有历史收据的订单 208 作为对照，分别记录历史原文离线复核和本次新会话结果。不得将历史两条 SN、既有设备记录或登录后的订单详情计作新收据。

研究只读业务库，不写订单状态、日期、设备或库存，不恢复旧批次，不提交 Git 或部署管理台。账号密码仅传送至 Apple 官方认证域；代理从已登录 IPRoyal 平台提取。每单本轮最多三次实际运行，沿用共享 PostgreSQL Gate 的账号互斥、历史次数、登录冷却和请求许可；失败历史不清零。验证码、双重认证、协议确认、密码重置转人工。

## 待验证链路

1. 独立 HTTP 会话读取原链接和明确的访客 action，保存完整响应与订单身份。
2. 先区分访客与登录态。本次访客详情确实缺少 `orderHeader.d.invoiceUrl`，却含有 `orderDetail.d.signInURL`；优先跟随这个经过订单身份核对的登录入口。已有收据链接却重定向到登录时，保存官方 Location 和目标上下文，不猜测 token。
3. 同一代理与 Cookie 会话执行官方登录；优先验证订单来源的登录入口。认证接口成功、商城交接成功和收据取得分别记录。
4. 登录后回到目标订单，重新读取其收据链接，在同一会话获取原始 HTML／JSON；如真实来源是 PDF 则另行建立文件解析路径。
5. 结构为 `orderInvoices → orderInvoice-* → invoiceOrderSummary.d.orderNumber` 和 `invoiceLineItems → invoiceLineItem-*.d.lineItemSerialInfo`。已使用 2026-10-07 的真实历史收据校验：一张收据、两个 SN，含商品名和料号；本次新鲜获取结果独立记录。
6. 核验订单一致、商品数量、SN 明确字段、重复 SN 和来源摘要。缺字段或认证页面不能记为收据成功。输出受限本地 JSON 与脱敏研究报告。

## 材料取舍

- [官网 HTTP 技术说明](../design/官网订单HTTP采集技术说明.md)：复用只读详情、来源封存、代理与共享 Gate；其当前入口关闭收据，不提供 AppleID HTTP 登录能力。
- 用户的 AOSHelper 报告和伪代码：用于理解 TLS／Cookie、Shld、认证与代理模块；未运行未知程序，未把静态复原视为当前可用性证明。
- 手机截图：证明该目标订单在用户已登录会话中显示“查看电子收据”；不证明匿名 HTTP 会话可访问，也没有给出收据正文或 SN。

## 验收和下一阶段

逐单记录前后出口、请求数、密码是否提交、IDMS／商城／详情／收据各阶段状态、返回格式、订单身份、收据及序列号数量和业务库前后摘要。至少三单完整成功才可开始讨论批量接入；小样本通过仍不代表长期稳定。

后续产品接入应独立设计收据来源、设备绑定冲突、权限、审计和幂等性，并按数据库／API 级联要求实施；本研究不预先扩大写入边界。


## 采集状态和字段契约

| 状态 | 成功证据 | 不能替代的下游证据 |
| --- | --- | --- |
| `GUEST_DETAIL_VERIFIED` | 完整详情、目标订单号、逐商品数量及原始状态 | 不代表已登录，不代表收据存在或不存在 |
| `IDENTITY_AUTHENTICATED` | 本次 `signin/complete` 返回 200 | 不代表 Apple 商城交接通过 |
| `STORE_SESSION_READY` | 商城 `authx` 交接与登录后的目标详情 | 不代表电子收据取得 |
| `RECEIPT_CAPTURED` | 原始收据响应、来源链接、HTTP 状态及摘要 | 不代表订单／商品／SN 已通过一致性校验 |
| `RECEIPT_VERIFIED` | 收据订单号一致、显式 SN 字段、数量与商品对应、无重复 | 不自动授权设备／库存回写 |

| 输出字段 | 预期来源／校验 |
| --- | --- |
| `systemOrderId` | 系统只读输入，不从页面猜测 |
| `orderNumber` | 每张 `invoiceOrderSummary.d.orderNumber`，必须等于输入与详情 |
| `invoiceCount` | 按 `orderInvoices.c` 枚举，不假设只有一张 |
| `items[].serialNumber` | `invoiceLineItem-*.d.lineItemSerialInfo[]` 的原文，不做 OCR 猜字或截取任意十位文本 |
| `items[].partNumber` | 同一行的 `partNumber` |
| `items[].productName` | 同一行的 `productName` |
| 商品数量 | `quantityShipped`、`quantityOrdered`、SN 数量与详情完整数量交叉核对 |
| `source` | 采集时间、主机、脱敏路径、原文 SHA-256、研究 run、详情关联与前后出口摘要 |

解析器对多张收据、重复模型、订单不一致、缺少行、重复 SN、不完整发货、纯数字／空格／小写 SN、登录页及 PDF 非 HTML 正文作独立区分。当前严格解析器遇到“部分行没有序列号”会拒绝整单；未来存在配件、分次履约或更换设备时，应先定义逐行状态，不能将部分提取误记为整单完成。

## 实现路线和取舍

- **短期验证路线**：由官网提供的订单入口建立会话，浏览器完成官方 AppleID 认证，商城详情和收据维持同一 Cookie／代理上下文。针对商城交接，比较原生浏览器传输与 HTTP 会话传输，结果分别计量，不预设哪种网络特征一定有效。
- **纯 HTTP 路线**：在既有访客采集器旁新增独立认证模块，完整覆盖 Apple 下发的 SRP `s2k`／`s2k_fo`、`signin/init`／`signin/complete`、会话头、HC 与商城 `authx` 交接。三份材料没有给出可直接复用的完整实现，不能把静态伪代码补成已经可用的无浏览器登录。
- **有限人工协助路线**：遇到额外认证时转人工；只在授权且同账号、同代理和短时有效窗口内继续使用已认证会话。不把 Cookie 长期保存、共享给其他账号或作为可公开链接交付。

本轮实验采用“官方浏览器认证＋同一 HTTP 会话承接商城请求”：浏览器运行官网认证脚本，商城登录交接和详情交给保持存活的 `curl_cffi` 会话。1356 已观察到 IDMS 200、商城 `authx` 200 和登录后详情 200，但交给 HTTP 会话的收据请求仍失败。208 后续点击可见链接，由原生浏览器新窗口取得 200 收据并解析出两条 SN。不同试验同时存在账号、代理、浏览器模式和最后一跳传输差异，不能据此断言 HTTP 桥接或点击动作单独解决了问题。

该混合路线不是纯 HTTP AppleID 登录实现。审计确认成功新窗口的首个请求未经过现有 CDP `Fetch` 拦截：收据 run 1525 有新鲜 200 正文，但请求许可为 0。因此数据取得成功与运行保护验收分开；这份实验代码不得直接用于批量采集。

## 后续实施顺序

1. **先补齐新窗口请求保护**：在新窗口产生网络请求前安装整个浏览器上下文的请求拦截，或使用经过验证的预建受控页面方式；每个出站请求必须先取得共享 PostgreSQL 许可，并保持目的地址、方法和停止状态检查。使用本地合成新窗口验证首个请求、重定向、资源请求和取消均无漏计／重复计数，再恢复真实验证。不能把事后补记当成事前限流。
2. **解决收据最后一跳及统一结果**：固定账号、出口和登录会话，对照官方可见链接点击、同页导航和 HTTP GET，逐项比较 Cookie、Referer、重定向及会话连续性。统一顶层 `receiptOutcome`；详情 `SUCCEEDED` 与收据失败可以并存。分别记录数据验证与运行保护验收，分开统计登录运行、收据运行和链路总请求，避免重复求和。
3. **建立新鲜样本验证**：建议至少三笔不同账号订单完整取得收据，核验前后出口、订单号、SN 数量和原文摘要，再评估分次履约、多张收据及失败恢复；这只是进入后续研发的门槛，不证明批量稳定。
4. **确定生产契约后接入**：先定义设备已存在、SN 冲突、部分收据、账号权限和来源保留策略，再按项目要求更新设计、数据库／API 契约、实现与测试。研究阶段不回写设备或库存。

新窗口拦截候选可参考 [Playwright `page.route` 文档](https://playwright.dev/docs/api/class-page#page-route)：页面级路由不覆盖新窗口首请求，官方建议使用 `browserContext.route`。这是后续实现依据，不是本轮 CDP 适配已修复的证明；还需验证重定向与既有 CDP 拦截并存时的覆盖和计数。

## IPRoyal 提取方式

本轮使用已登录平台的“特定格式的代理列表”，提取 6 条中国区、24 小时粘性配置，没有购买或充值。长期实现可使用官方 `POST /v1/access/generate-proxy-list`，显式设置地区、`rotation=sticky`、`lifetime` 和少量 `proxy_count`，认证材料仅留在私密配置。接口参考 [IPRoyal Access](https://docs.iproyal.com/proxies/residential/api/access)。

粘性会话时长不是出口稳定保证；供应商明确住宅节点可能提前离线。本轮对每次实际运行做前后出口核验，但它只证明两个观测点相同。参考 [IPRoyal 粘性会话说明](https://help.iproyal.com/en/articles/7215287-how-long-does-a-sticky-ip-session-remain-the-same)。不应将多个会话配置计为同数量的独立出口。

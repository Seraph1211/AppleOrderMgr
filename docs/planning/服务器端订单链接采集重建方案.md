## 已确认目标

- 输入系统已有订单 ID，由服务器读取链接并取得本次有效官网响应。系统订单号、链接订单号、响应订单号必须一致。
- 日常采集、代理使用、会话建立和任务恢复都在服务器侧完成，关闭用户电脑后仍能执行。
- 目标服务器为 `PP_CloudServer`。首期手动单笔和批量刷新，每批最多 100 单，不做定时刷新。
- 至少 10 个不同订单实际同时采集；排队、仅创建浏览器上下文和重试休眠不能代替采集并发证据。
- 每单最多 5 次尝试，包含首次；这是本次用户对旧规范三次上限的明确调整，仅适用于新验证及后续确认的新能力。重启和换出口不重置次数。
- PostgreSQL 全局请求限流初始 5 RPS，配置硬上限 10 RPS，保留小幅随机抖动；订单执行并发和请求速率独立控制。
- 已批准验收目标：五次内最终成功率至少 95%，首次成功率独立统计；单单总耗时 P95 不超过 3 分钟，100 单批次不超过 30 分钟。未实测前不承诺达标。

## 字段与业务边界

核心必采字段为订单号、完整商品列表、逐项数量及官网原始状态。付款状态、金额、下单时间和取货信息按有效响应实际提供程度记录；不从邮件补齐官网结果，不推断缺失值。

字段至少区分有效值、官网未提供、无法判定和解析失败。失败、空值、身份不符、超时和迟到结果不能覆盖旧正确值；沿用旧值时必须保留其观测时间，不能冒充本次结果。

## 首轮批准的受限单订单验证

1. 在目标机创建隔离验证程序、临时容器、专用 PostgreSQL 和受控证据目录；不连接生产数据库进行写入。
2. 只读选取一个已有且链接身份合法的真实订单，预先保存脱敏样本标识及行摘要。
3. 候选顺序为 HTTP 直连、服务端浏览器直连、服务端浏览器加网帆。跨路径累计最多五次尝试，任一路径成功即停止。
4. 每次尝试最多 100 次外部请求；订单请求最多 500 次，额外连通性检查最多 20 次，合计上限 520 次。初始 5 RPS，重定向和页面子请求同样计数。镜像／依赖下载不属于订单采集请求，另记录环境准备开销。
5. 每次尝试最多 90 秒，真实单订单验证阶段总执行上限 10 分钟；环境准备时间单独统计。
6. 使用现有网帆包月套餐，新增采购预算为零；发现额外计费则停止。未经授权不使用其他付费套餐或新增资源。
7. 人工验证、身份不符、费用或请求预算耗尽、代理鉴权失败、现有服务健康异常立即停止；429 不立即重试，541 更换已授权出口并计入累计尝试。
8. 资源保护：宿主机可用内存低于 1.5 GiB、OOM、持续 60 秒 CPU 超过 85%，或连续三次现有 API 健康失败时终止验证容器。

单单成功要求本次完整响应、匹配订单号、有效商品及数量和原始状态。HTTP 200、页面加载完成、任务入队、历史缓存或邮件数据均不构成成功。

证据包括程序和镜像摘要、请求时间线、响应状态、加密响应文件、解析字段、身份判断、尝试数和资源指标。普通日志不含链接、个人信息、代理凭据或 Cookie；密钥和原始输入仅在服务器受限目录保存，不进入 Git。

## 后续阶段的门禁

单订单取得身份匹配的有效结果后，按现有授权验证三批十并发：每批十个不同订单，优先覆盖三十个不同样本；固定清单，不替换失败样本。取得实际请求重叠、全部样本结果、首次／最终成功率、重试和耗时分布后，再推进百单批次验收。一次单单成功不代表该阶段通过。

至少一个完整批次由服务器定时触发、在用户电脑关闭时运行；另测新会话和进程重启。等效环境通过后仍在目标机复验。新增服务器、托管浏览器或其他付费资源另行给出必要性、报价和替代方案。

## 可行性通过后的实施方向

新建独立持久化队列、任务尝试、官网观测和审计记录，不解封旧归档、不重放旧队列。任务使用幂等键、每单去重、租约和心跳；进程重启回收过期租约，失败隔离且尝试预算持久化。

网络采集与业务落库分离。落库短事务校验订单身份、链接版本、任务租约和结果新旧，观测与审计同事务提交。权限包含功能操作权限与订单 TAG 范围，逐笔校验；付款任务权限不能成为订单详情访问旁路。

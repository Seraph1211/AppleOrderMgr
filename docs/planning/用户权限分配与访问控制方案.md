> 状态：关键契约已定稿，实施中；复用 users、不新增业务角色、由管理员给用户分配权限
>
> 最近核对：2026-09-07
>
> 基线：main@d000d03 与当前工作树；覆盖当前已挂载业务路由、前端认证和导航入口
>

## 一、目标和明确边界

复用现有 `users` 和登录体系，不增加付款工作人员角色，也不另建付款账号。管理员在用户管理中逐人勾选功能权限；相同账号可以同时具有订单、付款任务、取机人等多个模块的权限。

本文负责全系统权限目录、授权管理、接口与数据边界、迁移和权限验收；付款任务的业务规则统一见[订单付款任务分配与处理方案](订单付款任务分配与处理方案.md)。本页权限名称、管理员保留能力、依赖和存量迁移规则已经定稿，并同步进入[API 契约](../design/API设计.md)及[数据库架构](../database/数据库架构.md)。后续实现不得在不更新权威契约和验收用例的情况下改变这些规则。

### 1.1 授权模型（已定稿）

- 保留原 `admin/operator/readOnly` 字段兼容现有账号，不新增角色。`admin` 表示平台管理身份，保留受保护的管理员能力；非管理员的业务能力由管理员显式保存的权限集合决定，不再每次按旧角色自动叠加 `write/export/refresh`。
- `operator/readOnly` 对已有用户保留历史标签。新界面统一显示“普通用户＋实际权限”，不再把 readOnly 标签当成不可增加业务权限的硬门禁；旧角色切换不应隐式清空或增加权限。
- 非管理员有效权限 = 已登记且未撤销的权限集合及其经过显式确认的依赖；空集合只能登录、查看本人账号、改密和退出。新用户默认空集合，管理员可在创建时一并配置。
- 管理员默认拥有当前注册的业务权限，并受账号锁定、单会话校验、资源状态、敏感字段环境门禁等共同约束。界面明确展示“管理员拥有全部已注册权限”，不提供看似可撤销却实际无效的复选框。
- 权限目录由代码维护，管理员只能分配目录中有效权限，不能在 UI 任意新增权限键或授予通配符。新权限默认不授予普通用户。
- 权限控制能否使用功能；付款接单开关和承接上限控制是否参与调度。二者独立，必须同时满足，不以角色名判断谁可以处理付款。

### 3.1 依赖和授予限制

- 本模块创建／编辑／删除／导入／导出／刷新依赖本模块 read；导入还依赖对应 template.read，模板下载不依赖导入能力；取机人绑定额外依赖 apple_ids.read；channels.rename 依赖 channels.read。
- 所有本人任务动作依赖 payment_tasks.read_own，不依赖 orders.read。本人付款权限组合可一次勾选，展开后显示其中的五项权限；这只是表单快捷选择，不创建新角色或隐式继承。待处理、处理中、已完成、异常四种状态均可在权限与归属范围内登记订单付款人，第一版每单一名当前付款人并保留修正历史。
- `payment_tasks.payer.edit_own` 只允许员工在本人任务内手工填写、修改或清空外部付款人姓名，不开放付款人候选目录、付款人账号或其他业务数据。付款人不会登录系统；可登录用户均为内部员工，员工自行组织其负责的外部付款人完成付款。
- email.process 依赖 email.content.read 和 email.read；email.content.read 本身不得给普通用户勾选。system 管理动作依赖相应 read。
- UI 勾选时显示必需依赖；取消基础权限时展示将一并取消的下游权限，由管理员在同一保存动作确认。API 收到依赖不完整、未知键或管理员保留键授予普通用户时拒绝，不能默默补权。
- 普通业务权限集合不能赋予管理身份。创建、提升或降级管理员仅经管理员专用账号接口，保护最后一名可用管理员；不允许通过普通用户编辑请求夹带 role 或权限字段提权。

## 四、页面、API 和数据范围闭环

### 4.1 管理员分配权限

用户列表新增“权限摘要／已授予项数”和“配置权限”。配置抽屉按模块分组，显示读取、动作、数据范围、依赖与管理员保留项；提供清空非管理员权限、复制另一普通用户权限和“仅处理本人付款任务”等快捷组合。复制必须展开最终集合并确认，不形成持续绑定。

保存前显示新增与撤销项、受影响模块、本人在途付款任务数量。支持同一次创建账号时设置权限；普通用户不能编辑自己的授权。撤销付款处理权限会使该用户停止新增接单，并展示需交接的存量任务；不因有存量任务阻止紧急撤权，也不自动转派可能正在支付的任务。

接单配置页面仅允许选择满足付款执行权限组合、账号正常的用户。仅给予权限不会自动开启接单或提高上限；管理员自己参与付款沿用相同开关和上限。

### 4.2 资源和字段边界

- 任务列表、详情、状态／备注、付款人关联、历史、商品筛选候选、统计、链接及刷新分别执行 permission + assignee_user_id 检查。全局订单 read 不自动带来全局任务、备注或链接权限。
- 只有本人任务权限时返回订单最小投影：内部订单 ID、订单号、商品、金额币种、官网订单／支付状态、期限及新鲜度、登记付款人。Apple ID 密码、身份证、完整地址、取货码、无关联系信息不返回。
- 全局 orders.read 会明确扩大订单可见范围；这是管理员授权的结果，不伪装成“仍只能看本人”。但订单详情仍不通过联表带出他人任务备注或链接。
- 刷新 job/batch 查询按关联订单范围判定；仅本人权限不能因 requestedBy=null、本人曾发起、任务转派前的旧 ID 或混合批次，读到他人订单。混合批次拒绝，不返回可推断全局规模的统计。
- 导入预览／执行必须按 type 校验相应模块 import 权限，模板下载校验对应 template.read。预览成功不代表执行获永久授权，执行时按服务端会话保存的 type 和当前权限复查，不信客户端改 type。预览前先通过不上传文件的路径或请求头声明 type 并授权，再接收文件；正文和服务端会话类型须一致，防止无权限用户先触发磁盘上传。
- 通用订单更新接口不再接受付款人姓名旁路写入；付款人变更由专用关联服务执行并审计。前端旧订单详情同步改造，不保留另一套无权限限制的写入口。
- 未登记权限的 API 默认拒绝。健康检查、登录、当前用户、改密、退出等例外建立显式列表，不能以任意 GET 为公开业务查询。

### 4.3 权限即时生效与并发

每次业务请求从数据库加载当前账号与权限版本；第一版不依赖 JWT 内长期有效的权限快照，不使用未失效的多进程内存缓存作授权依据。登录和 /auth/me 返回 `permissions`、`permissions_version` 与管理员身份。

敏感发放及写操作在事务执行点再次核对权限版本；撤权事务已提交后，旧页面或旧 Token 发起的后续操作必须失败。已经在线性化顺序上先于撤权完成的操作保留审计，不承诺收回已复制链接或已下载数据。

权限变更与接单资格更新、账号锁定、分配使用统一锁顺序：先调度互斥锁（涉及接单时），再用户／权限行，再任务／订单行。撤销任务执行权限时同事务关闭该人的自动接单并记录审计；存量任务保留负责人并提示管理员交接，恢复权限不自动恢复接单开关。

前端页面加载、恢复前台、收到 403 后刷新 /auth/me；显示当前授权的导航和按钮，不采用旧 isAdmin 作为普通业务授权判断。失去页面权限后关闭对应数据视图、清除敏感临时状态，保留非敏感未提交草稿供用户了解失败原因。

## 五、候选数据结构与接口

| 结构                   | 建议                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------ |
| users                  | 继续使用既有主键、账号、认证字段；增加 `permissions_version` 整数版本                                  |
| user_permissions       | `user_id`、`permission_code`、授予者、时间；用户＋键唯一；未知代码拒绝，不删除用户后级联清空追溯       |
| user_permission_events | 被授权用户、操作管理员、前后集合／差异、理由、前后版本、请求幂等键与时间，追加写；管理员身份变更也留痕 |
| 代码权限目录           | permission_code、中文名、模块、动作、数据范围、依赖、是否管理员保留；由版本化代码维护，无动态建权限 UI |

| 候选接口                             | 行为                                                                   |
| ------------------------------------ | ---------------------------------------------------------------------- |
| GET /api/permissions/catalog         | 管理员查看全部可分配目录、依赖及保留项                                 |
| GET /api/users/:id/permissions       | 管理员查看显式授权、有效权限和版本                                     |
| PUT /api/users/:id/permissions       | 管理员提交完整权限集合、expected_version、幂等键；依赖检查与审计同事务 |
| GET /api/users/:id/permission-events | 管理员分页查看授权历史                                                 |
| GET /api/auth/me                     | 增加当前服务端有效权限、版本及可用首页；不接受客户端传入的权限集合     |
| POST /api/users                      | 复用新增用户，支持管理员显式给出的初始权限；账号和授权创建原子化       |

用户通用 PUT 不接受 permissions 字段，防止绕过专用授权接口；新账号支持初始授权是唯一明确例外。401 未认证、403 无权限／保留能力、409 版本冲突、400 非法权限集合。普通用户权限缺失与账号锁定错误分开；请求日志只记权限代码和 ID，不记录敏感业务载荷。

| /api/import                                      | 模板按相应 template.read，预览／执行按对应 import 检查；接收上传前授权、执行重新授权      |
| /api/dashboard、/api/stats                       | dashboard.read、stats.read；筛选项与汇总也受保护                                          |
| /api/channels                                    | channels.read／rename；渠道订单额外 orders.read                                           |
| /api/email-processing                            | read、content.read、process 分离并保留管理员身份限制；GET 详情中的正文必须走 content.read |
| /api/users                                       | users.read／manage／permissions.manage；普通账号编辑不能修改管理员身份或权限              |
| /api/system                                      | logs、refresh、proxy 的 read／manage 分开，保持管理员边界                                 |
| 新付款任务与付款人入口                           | 见付款任务专项方案；本人任务权限不能旁路访问全局订单或主数据敏感字段                      |

授权检查不仅在 Router：Service 需要资源范围参数，防止其他 Router 复用业务服务时丢失范围；序列化器按字段权限输出。页面守卫、导航、按钮统一用 `can(permission)`，管理员保留身份仅用于真正受保护的操作。

## 七、存量迁移与回退

1. 先生成存量用户权限预览，不写生产。按当前实际合法行为映射：operator 保留现有全局常规读取、写入、脱敏导出、刷新和对应导入；readOnly 保留现有常规查询及模板下载；admin 保留管理员身份并通过代码目录获得全部有效权限。
2. 当前 readOnly 可下载模板但不可执行导入，因此将模板下载独立兼容为 `apple_ids.template.read`、`recipients.template.read` 两个目录键，import 依赖同模块 template.read；不得为了保留模板下载而给 readOnly 导入权限。目录与接口实现阶段必须包含这两个键。
3. 系统 requestedBy=null 刷新资源公开等旁路按新资源规则关闭，作为修正差异明确列出，不把漏洞当作必须保留权限。付款人专用写权限对应旧合法 payerName 编辑能力的迁移，历史姓名数据本身不猜测归并。
4. 新付款任务和接单权限不因为用户原来是 operator 就自动授予；管理员按需配置。完整映射以逐用户 diff 复核，不以“旧角色全权”批量扩大。
5. 正式 Migration、权限映射、服务端门禁和前端权限消费按一个兼容发布计划实施；不得先创建空集合使全部存量用户失去业务能力，也不得失败时 fallback 到全部权限。
6. 版本切换后数据库授权是唯一来源。迁移可重入，不能重跑覆盖管理员已修改的权限；迁移记录版本，已有显式权限跳过并报告。
7. 保留至少一个未锁定、能登录并管理授权的管理员，禁止删除／降级最后一个；锁号策略及临时失联的恢复按管理流程保留审计。
8. 回退先关闭新的自动分配和业务写入入口，再校验旧版本按角色授予是否会重新扩大已经收紧的权限。不能直接回退旧 ROLE_PERMISSIONS 使仅付款用户重新看全局数据；须保留新授权门禁或暂停受影响账号业务访问。备份与正式 Migration 回退另行授权，不销毁审计。

## 八、开发与验收

| 编号   | 交付                                           | 依赖和退出条件                                    |
| ------ | ---------------------------------------------- | ------------------------------------------------- |
| ACL-01 | 权限目录、接口矩阵、现有用户映射评审           | 已定稿；保留能力及敏感边界明确                    |
| ACL-02 | 权威数据库／API 更新、权限表与正式 Migration   | ACL-01；隔离库约束和 up/down/up，通过幂等迁移测试 |
| ACL-03 | 服务端逐用户授权、全部端点及字段范围门禁、审计 | ACL-02；默认拒绝、撤权与并发验证通过              |
| ACL-04 | 用户权限配置、/me、导航／路由／按钮改造        | ACL-03；可创建仅付款账号和跨模块账号              |
| ACL-05 | 全量权限矩阵、存量迁移和回退演练               | ACL-03、ACL-04；技术结论及实际管理员验收分别记录  |

付款任务 PD-03 依赖 ACL-02；PD-05 和 PD-06 的可交付版本依赖 ACL-03／ACL-04，不允许先用旧 operator 全局权限伪装完成。

最低权限用例：

- PA-01：新普通用户零权限；直接 URL／API 不能读取任意业务数据，登录／本人资料／改密／退出可用。
- PA-02：同为 operator 的两名用户授予不同权限，读取、写入、导出和按钮表现不同；不受旧固定映射影响。
- PA-03：仅付款任务权限可以查本人商品筛选项、登记订单付款人，不能读取他人任务、渠道订单、统计、模板、订单导出或邮件。
- PA-04：管理员给用户增加／撤销权限，原 Token 的后续请求立即执行新权限；多 API 副本一致。
- PA-05：用户伪造 permissions、role、assignee、请求他人 ID 或直接调用旧更新入口均不提权。
- PA-06：任意模块 write／import／export 不等于其他模块权限；模板下载不等于导入执行；预览后撤权执行失败。
- PA-07：依赖缺失、未知键、普通用户获管理员保留项、最后一名可用管理员降级等请求失败且不部分写入。
- PA-08：并发授权保存返回版本冲突，幂等重试无重复审计；新建用户与权限中途失败整体回滚。
- PA-09：撤回付款执行权限时关闭自动接单；与自动分配竞态不把新任务派给已撤权用户；存量交接可见。
- PA-10：当前系统任务、本人旧 job、转派后的 job 和混合 batch 查询均按最新订单范围校验，无 requestedBy=null 旁路。
- PA-11：普通导出不输出敏感字段；管理员敏感权限不绕过生产字段门禁；领取付款链接和看订单密码不是同一权限。
- PA-12：存量映射有证据、重跑不覆盖新授权；readOnly 模板兼容不变成导入权限；回退不恢复已撤销的访问能力。
- PA-13：权限按钮隐藏与 API 实际拒绝分别验证；轮询、浏览器刷新和恢复前台后不继续展示已失权数据。

## 一、已确认的要求与待确认事项

### 已确认

1. 多台 Windows 电脑运行抢购软件，可以在每台电脑运行采集程序。
2. 只接入 `AOS订单记录-*.txt`；本轮不接入含二维码和证件信息的 AOS 成功记录。
3. 每天生成新文件，文件名包含日期；抢购成功后更新文件。
4. 入库来源全局二选一：邮件或 AOS，不提供双来源同时自动入库模式。
5. 首次启用或切回数据源时，补录当天订单，按 Apple 订单号去重。
6. 原文件第 9 列是抢购软件账号，不用于系统员工、付款人、渠道或业务归属。
7. 第 13 列是完整的取机人 TAG；第 15 列是下单时间。
8. 本轮先提交方案，用户确认后才实施代码、接口和数据库变更。

### 2026-09-10 实施确认

- 既有订单采用 `keep_existing`：仅去重关联和留痕，不覆盖任何既有订单字段。
- 3～4 台 x64 Windows 电脑，有管理员安装权限；每台一个本机普通目录，目录必须可在 GUI 配置。每日约百单，峰值每分钟几十至上百单。
- 已重新读取附件：11 行、15 列，UTF-8 **无 BOM**、CRLF；兼容有 BOM。实际追加／整体重写方式未知，须同时兼容并在实机验证。
- 取机人仅在姓、名、手机号唯一一致且其他联系资料无冲突时关联；未建档 Apple ID 只保存快照。
- AOS 启用期间已发现并持久化到本地队列的订单，断网跨天后自动恢复，仍按订单号去重、检查当前来源与设备状态。
- 独立人工补单和 Excel 导入沿用既有权限及规则，不受此来源开关约束。
- Windows 安装包、配置 GUI、托盘、后台服务及本地目录配置均在本次范围。用户已授权一台 Windows 电脑用于测试；连接凭据不进入项目文件。
- 用户截图确认测试环境为 Windows 10 专业版 22H2（19045.6456）、x64。保留真实文件写入、Windows 安装与业务验收边界。

### 跨天恢复的协议补充

服务器在已启用 AOS 的设备 context 中签发并持久化当天采集许可，返回 `capturePermitId`、业务日期和设置版本。采集器发现当天完整行时，将此许可与原事件一并保存；批量接收允许附带 `capturePermitId`，重传不可修改。服务器验证许可属于本设备、许可日期与订单下单日一致且签发时 AOS 启用；此前已获得许可的本地积压可跨天恢复。许可只是限定设备已获授权的日期范围，不把设备时钟或上传时间当作订单时间证据。当前来源及设备禁用仍阻止最终入库。未获得许可的旧日期记录保留待处理，不静默扩展历史导入。

## 三、总体结构

Windows 抢购软件更新文件后，由同机采集器读取；采集器经 HTTPS 向服务器提交记录；服务器持久化接收结果，再根据当前全局来源设置决定是否进入公共订单入库服务。邮件保留现有接收流程，也通过同一来源开关和公共入库服务。

订单保存后继续进入当前官网首次刷新、订单状态同步和付款调度链路。

### Windows 采集器

- 每台电脑独立登记设备 ID、设备名称及可撤销的专用接入凭证。设备身份与 AOS 文件内抢购账号无关。
- 交付“安装包、配置窗口、系统托盘图标、后台服务”四部分；包含 .NET 10 运行依赖，目标 Windows 10 专业版 22H2 x64。
- 配置一个或多个本机文件目录；仅监控指定目录下符合规则的文件，不扫描整盘。
- 只读源文件，通过出站 HTTPS 上传；不在 Windows 暴露入站端口，不配置数据库连接凭据。
- 将已发现记录先保存到本地持久化待发送队列，再上传。网络失败采用退避重试，重启恢复待发送记录。
- 本地敏感载荷和令牌使用 Windows 系统提供的凭据／数据保护能力，按服务身份配置文件权限；运行日志不输出密码和完整原始行。

### Windows 呈现形式与使用流程

| 组成 | 用户看到的内容 | 行为边界 |
| --- | --- | --- |
| 安装包 | 安装、修复、卸载向导和版本信息 | 一次安装配置后台服务；升级保留目录、设备身份和待发送队列；卸载默认保留本地待发送数据，并提示数量 |
| 配置窗口 | 设备名称、一个或多个 AOS 目录、服务器地址、设备接入凭证 | 提供浏览目录、检查目录、测试连接和保存；凭证保存后只显示是否已配置，不回显全文 |
| 系统托盘 | 状态图标、文字说明、打开窗口、退出托盘 | 托盘在用户登录后显示；退出托盘或关闭窗口不停止服务，不用颜色作为唯一状态提示 |
| 后台服务 | 在窗口中显示运行、停止、异常状态 | 开机启动；用户注销、窗口关闭后继续采集；本机管理员可显式停止／启动服务 |

配置项建议：`deviceName`（1–100 字符，本机显示名；服务器登记名称由网页管理员维护）、`serverUrl`（HTTPS 服务地址）、`credential`（专用设备凭证）、`directories[]`（1–20 个绝对目录，每项含稳定 `directoryId` 和显示名称）。路径只在本机选择和保存；首版不允许网页远程下发任意文件路径或执行命令。

首次流程：管理员在网页登记设备并取得凭证 → Windows 安装 → 填写服务器与凭证 → 选择 AOS 目录 → 测试连接和服务身份的目录读取权限 → 保存 → 开始后台采集。连接测试只验证设备身份和协议版本，不提交真实订单。

日常窗口分为：

1. 运行概况：本机服务、服务器连接、当前全局来源、最近成功扫描时间、最新错误及恢复情况。
2. 文件列表：目录、文件名、修改时间、已识别记录数、待完成尾行和读取异常。
3. 传输概况：今日发现、服务器已接收、待上传、上传异常；服务器处理结果另外显示已入库、重复、暂停、待人工处理。
4. 常用操作：测试连接、检查目录、立即扫描、重试可重试上传、导出脱敏诊断。立即扫描仍遵守当天补录范围，不能隐式导入历史订单。

传输计数与入库计数使用不同标签：重传不重复增加“已接收”；后台状态过期时显示“上次同步时间”，不把缓存数当作实时状态。故障图标包括断网、目录异常、凭证失效、服务停止；“邮件模式，AOS 暂停入库”属于业务状态，不表示采集器故障。

全局来源只能在网页管理后台切换，Windows 端只读展示；本地“停止服务”与全局“停止 AOS 入库”是不同动作。服务与窗口通过限定本机身份权限的本地通信通道交互，不新增对外监听端口。保存配置先校验再原子替换；新服务器或凭证验证失败时保留旧有效配置。存在待发送记录时禁止直接更换服务器或设备身份，先处理旧队列或执行明确的迁移流程，不能把队列静默发给另一套系统。

### 服务器

- 接入 API 独立验证设备凭证、请求大小、结构版本、记录字段、订单链接与订单身份。
- 每条记录有持久化接收结果；批量请求逐条返回结果，单条格式错误不丢失其他有效订单。
- 接收成功与订单入库成功分别展示。服务器可靠保存后可确认已接收，Windows 才结束该条传输重试；服务器负责后续重试和人工异常处理。
- 重复投递只返回已存在的接收结果；服务器响应丢失后重传不会重复创建订单。
- 后台执行器按数据库租约领取记录，支持中断恢复；复用现有 PostgreSQL，不额外引入消息队列基础设施。

## 四、文件监听、跨天与恢复

### 监听目录和识别新订单

1. 监听目录中的新建、修改和重命名事件，匹配 `AOS订单记录-*.txt`，排除成功记录及临时文件。
2. 文件事件只触发读取任务，同一文件串行处理并合并短时间重复事件；建议等待约 0.5–1 秒的稳定窗口。
3. 同时每 5 秒扫描目录进行补漏；周期性内容核对处理元数据未可靠反映的变化。事件溢出、服务重启或目录恢复后重新核对候选文件。
4. 首版优先采用“变化文件重新解析、按订单号和内容指纹识别新记录”，兼容追加和整体重写。文件大小和单量上限待量级确认；必要时分块读取，偏移量只用于优化，不能成为唯一防漏依据。
5. 每条完整有效记录独立加入持久化发送队列；同订单、同内容再次扫描不生成新的上传任务。内容改变生成新版本交给服务端重复／冲突策略处理。

### 跨天规则

- 持续发现新文件，不绑定 `0909`、固定文件名或固定抢购账号。
- 当天按 `Asia/Shanghai` 计算，以记录内完整下单日期为业务依据；文件名中的 `MMDD` 仅用于发现候选文件，不能承担年份和订单日期判断。
- 首次启用或切回时，扫描当天候选文件并提交当天记录；文件命名日期与记录日期不一致时提示异常并校验，不能仅按名称静默漏单。
- 跨午夜后发现新文件，同时继续处理已登记的旧文件、未完成尾行和待发送队列；不能因日期变化删除昨天尚未发送成功的记录。
- 切换时的当天补录范围，与此前已取得入库资格的失败任务恢复分开：前者不自动扩展到历史日期，后者不会仅因跨天丢失资格。旧日期但从未取得资格的待处理记录可见并计数，不默认历史回填。
- 重启后结合本地队列和源文件重扫恢复；若磁盘文件被外部删除且该记录从未被采集，无法凭空恢复，管理台必须显示目录／文件异常与未完成数量。

### 文件正在写入和异常格式

- 保留制表符分隔的空列，按照 15 列处理；不使用按空白分割或直接 trim 整行导致列位移。
- 支持 UTF-8（含有／无 BOM）和 Windows 换行；其他编码需明确配置或经验证识别，不容忍乱码后继续入库。
- 不完整尾行留待下一次读取。最后一行没有换行符时，仅在完整字段校验和连续稳定读取后接收。
- 文件占用、暂时消失、重命名替换或截断后重建均重试／重扫；不能因文件缩短自动删除已入库订单。
- 永久格式错误显示文件、行号和稳定错误码，原始敏感内容仅受控查看；允许修正后重试。坏行不阻塞后续独立订单。
- 字段数或商品语法变化时进入待处理，不猜测新的列定义。

文件事件可能重复或丢失，因此事件监听必须配合周期核对，见 [Microsoft FileSystemWatcher 文档](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemwatcher?view=net-10.0)。Windows 服务和独立可执行文件部署参考 [Microsoft 官方说明](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service)。

## 五、AOS 字段落库与资料匹配

| 原列 | 已确认含义 | 建议处理 |
| --- | --- | --- |
| 1 | Apple 订单号 | 标准化为大写并校验，作为订单去重键 |
| 2 | 订单联系邮箱 | 保存来源联系邮箱；与订单链接中的邮箱核对，不能被基础档案邮箱静默替换 |
| 3、4 | 下单 Apple ID、密码 | 匹配已有 Apple ID，密码保存为加密订单快照；不自动修改基础账号密码 |
| 5、6 | 联系人姓、名 | 使用文件显式姓和名，保存完整姓名及来源分列，不重新按第一字拆姓 |
| 7 | 门店代码 | 保存 `pickupStoreCode`；有字典则补名称，无字典保留代码，等待官网补充 |
| 8 | 未知空列 | 不赋予业务含义；保留格式兼容 |
| 9 | 抢购软件账号 | 不进入业务字段或人员关联逻辑 |
| 10 | 联系手机号 | 保存来源手机号 |
| 11 | 商品信息 | 转换为当前 `products` 结构，保留 SKU、完整名称、数量；颜色和容量可提取但不丢失原文 |
| 12 | 支付方式 | 保存“微信”；不据此推定付款状态 |
| 13 | 取机人 TAG | 完整保存为订单来源 TAG，不拆成姓名和付款方式，不当作人员唯一键 |
| 14 | Apple 订单查询链接 | 严格验证 HTTPS、Apple 域名、路径、订单号和联系邮箱；保留当前敏感链接访问权限 |
| 15 | 下单时间 | 明确按北京时间解析并保留毫秒，不使用文件修改时间、上传时间代替 |

### 缺失资料和关联原则

- AOS 订单文件没有证件号或尾四位，新增订单可以先保存快照并让 `recipientRef` 为空。
- 建议仅在显式姓、名、手机号与现有档案一致、且只命中一个候选时自动关联；其他联系资料出现冲突则暂不关联。TAG 只用于显示和辅助核对。
- 零匹配或多匹配不阻止订单保存，在页面提示“取机人待关联”；不能自动建立缺少必需身份证资料的取机人档案。
- Apple ID 未建档也允许保存账号和加密密码快照，外键暂空；不会为了接单批量新增或修改基础档案。
- 本轮不以接入 AOS 为由修改所有历史订单的 TAG 展示规则；新来源 TAG 必须可见，档案 TAG 不一致要明确展示差异。

### 初始状态与后续处理

- 新订单初始为待官网确认的内部状态，不声明已付款或已具备付款资格。
- 金额、支付状态、取货状态和付款截止来自官网，缺失保持未知；不使用 AOS 下单时间推算付款截止。
- 订单、来源成功结果、首次官网刷新任务和符合既有条件的付款任务登记在同一事务提交。
- 历史补录单也先走身份及官网有效性检查，不能因刚刚入库就被当成刚刚下单并立即自动派付。
- 已付款及终态订单仍按现有规则停止自动刷新；更换入库来源不重置付款记录、分配记录或官网状态。

## 六、全局来源切换和重复处理

### 全局开关

新增管理员“订单数据源”入口，仅提供“邮件”“AOS 文件”两个选项，初始默认邮件。服务端数据库中的配置是最终依据；设备本地配置过期不能绕过开关。

建议开关只控制创建订单及来源补充写入，接收与入库分离：

| 当前选择 | 邮件来源 | AOS 来源 |
| --- | --- | --- |
| 邮件 | 符合规则的记录可入库 | 可可靠接收，等待启用，不创建或修改订单 |
| AOS | 可可靠接收，等待启用，不创建或修改订单 | 全部已授权设备的有效记录可入库 |

停用来源不会破坏已有接收游标、待发送队列和审计记录。停止整个采集器或邮件 Worker 属于独立运维动作，不是本次页面切换的必要步骤。

### 切换流程

1. 后台显示目标来源就绪情况、设备／邮箱最近扫描时间、待处理数量和当天补录范围。
2. 管理员保存切换，记录操作者、旧值、新值、配置版本和服务端生效时间。
3. 入库事务与切换操作使用统一数据库锁边界。已进入提交阶段的旧来源事务先完成；页面只有在切换提交后才显示生效。生效后旧来源任务在最终写订单之前必须重新校验并暂停。
4. 新来源开始处理当天记录，按订单号去重；切换不批量删除、重建已有订单。
5. 自动重试、人工修正后入库、补录和设备重传均遵守同一开关；不存在人工入口绕过全局选择的隐含例外。
6. AOS 故障时提示异常，由管理员手动切回邮件；首版不自动切换，避免改变用户选择而不知情。

邮件停用期间可保留可靠接收能力，但不能因切换直接将未完成订单记录标为成功、忽略或确认已处理。邮件的已读确认遵循持久化业务处理结果；UI 区分“已接收”“因来源停用暂停”“已入库”。

切回邮件时，IMAP 查询需覆盖北京时间当天并按解析后的下单日期判断补录资格，不能只依赖未读或最近新增 UID；当日邮件的晚到投递仍可通过持续接收进入处理。自动回填历史订单不在首版默认范围内。

### 三层防重复

1. 设备层：持久化扫描结果与待发送队列，识别同一订单的相同内容。
2. 接收层：稳定事件 ID 保证超时重传幂等；同事件 ID 携带不同内容拒绝处理。
3. 订单层：全来源统一订单号锁和数据库唯一约束；多台电脑、邮件和 AOS 先后提交都只保留一个订单。

来源文件名、行号、设备和接收时间只用于追溯，不能替代订单号作为业务去重键。

### 既有订单的字段策略（已确认）

本次选定第一项“仅去重”，后两项仅保留为未启用的历史备选；不创建第二个订单，保留后到来源记录。

- 仅去重：关联已有订单，记录来源，不自动改字段。
- 仅补空：在身份一致后，只补明确缺失的来源字段；非空冲突进入人工处理。
- AOS 下单资料优先：对批准的下单资料白名单应用 AOS 值并保存字段审计；不覆盖人工锁定字段、官网状态和金额，也不重置任务。密码、身份资料、链接变化需要单独校验。

第三种策略还必须确保晚到的旧文件版本不覆盖较新内容；AOS 文件没有可靠修改版本时间，无法判定新旧的差异进入人工确认。不能以上传时间代替业务新旧顺序。

## 七、管理页面与拟议数据结构

### 页面

- 全局来源选择、切换状态及审计。
- 采集设备表：设备名称、启停、在线状态、目录就绪、程序版本、最近成功扫描、最近新订单、待发送／待处理数量、失败原因、凭证撤销。
- AOS 处理记录表：文件名、行号、订单号、下单时间、设备、接收时间、处理结果及关联订单。
- 异常详情：校验错误、字段冲突、重新处理和关联已有订单；敏感查看有权限和审计。
- 订单详情提供创建来源和来源记录入口；同单可关联多条来源记录。

“采集器有心跳”不等于“文件读取正常”，“上传成功”不等于“订单入库成功”。当天文件尚未产生显示“等待文件”，已有文件突然不可读、队列积压或长时间扫描失败显示异常。

### 数据与接口责任（已实现的职责）

| 对象 | 职责 |
| --- | --- |
| 全局入库设置 | 当前来源、配置版本、生效时间；切换审计复用现有操作日志体系 |
| AOS 采集设备 | 设备身份、凭证摘要、启停、心跳与扫描指标 |
| AOS 接收记录 | 稳定事件 ID、结构版本、来源文件位置、加密载荷、错误与重试状态、关联订单 |
| 订单来源标识 | 首次创建来源及可追溯关联；不能把当前全局设置当作历史订单来源 |
| 门店字典 | 代码、名称、城市、来源与核对时间；未知代码可持续入库 |

新增接入 API 仅授权设备上报、读取本机接收结果及心跳；设备不能读取全量订单或切换全局来源。接口已同步至 API 权威文档，本地实现包含正式 Migration，生产尚未部署。

既有邮件订单可由邮件关联记录回填创建来源；不能推断的历史订单标记未知，不伪造来源。现有非敏感 `sourceSnapshot` 仍服务官网冲突核对，不存放明文密码或整行 AOS 内容。

## 九、实施顺序与验收

### 实施顺序

1. 确认待决规则，更新正式数据库、API、匹配和邮件流程文档；为统一入库服务增加现有邮件回归保护。
2. 实现公共入库服务、AOS 解析／接收记录、数据源设置及事务内互斥。

4. 完成设备／处理记录管理页、门店字典及来源显示。
5. 隔离环境验证后，在实际 Windows 抢购软件上完成文件写入联调，再进行用户业务验收。生产迁移与部署单独执行当前会话授权流程。

### 验收清单

| 场景 | 预期结果 |
| --- | --- |
| 用户样本 11 行导入、重复提交 | 得到 11 个唯一订单、22 台商品；重复提交不增加订单和付款任务 |
| 新成功记录追加 | 目标：健康网络和正常负载下，完整行稳定写入后通常 5 秒内、兜底 10 秒内完成订单入库；官网补全耗时单独计量，需实际验收 |
| 整体重写、重命名替换、文件截断 | 已有订单不删除、不重复；新增有效记录被识别 |
| 半行、无末尾换行、BOM、空列和坏行 | 无字段错位；半行等待；坏行明确记录且其他订单正常处理 |
| 跨午夜、多个账号文件、跨年文件同名 | 自动发现新文件；按记录完整日期处理，不漏未完成的旧队列 |
| 断网、服务器重启、Windows 重启、响应丢失 | 本地／服务端持久化恢复；已接收记录可追溯；不重复建单 |
| 多设备同时报告同单 | 同一订单仅创建一次，各来源可追溯 |
| 邮件先入库后切 AOS，或顺序相反 | 同一订单仅一条；字段处理严格采用确认后的策略 |
| 切换时已有上传、重试、人工提交和入库事务 | 生效点明确；非当前来源不能在生效后新增或修改订单 |
| 当天补录、旧日期记录和跨天失败恢复 | 仅补规定范围；既有失败任务不因跨天静默丢弃；范围外数量可见 |
| 无身份证、资料不匹配或重名 | 订单保存，关联留空并提示；不误绑定取机人 |
| TAG 与档案不同、未知门店代码 | 来源 TAG 和门店代码保留且可见，冲突不被隐藏 |
| 付款与官网刷新回归 | 首次刷新不丢；不重复登记任务；无截止不擅自派付；已付／终态不被恢复为待付 |
| 凭证撤销、越权、非法链接和结构版本错误 | 拒绝未授权请求；日志不泄露密码，拒绝数据可追溯 |

后端解析和事务测试、真实 PostgreSQL 并发／Migration 测试、Windows 文件事件与恢复测试、管理页面验收分别记录；本地技术测试不能代替实际抢购软件与生产业务验收。

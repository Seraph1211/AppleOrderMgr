## 目标与已确认规则

完整商品名称固定为 `机型 完整颜色 容量`，分隔使用单个空格。例如 `iPhone 18 Pro Max 黑色 256G`。容量展示为 `256G`、`512G`、`1T`、`2T`；兼容来源中的 G／GB、T／TB、1024G／1024GB、2048G／2048GB 等明确等价写法。Pro Max 的完整颜色为黑色、银色、勃艮第酒红色、冰川蓝色；Duo 为星光白色、夜空色。用户明确允许代抢中的“酒红色”在 iPhone 18 Pro Max 下映射展示为“勃艮第酒红色”，不补写 SKU、不建立关联、不改代抢原颜色字段。

本次最终授权包含业务名称批量修改，取代前一轮“只映射、不改业务名称”的建议。原始来源和历史事实继续保留，不因规范化名称改写原始证据。

## 身份识别与统一映射

1. 建立单一版本化规范目录及纯映射规则，前后端使用同一来源，避免两份手写词库分叉。完整 SKU 与已知目录匹配时核对明确规格，缺失部分可由该 SKU 补足；来源出现明确机型、颜色、容量冲突时保留原值并标记待核对，不静默覆盖。
2. 无 SKU 时只有完整规格唯一且无冲突才生成标准名。显示映射不会补写 SKU、订单、设备或商品关联。机型允许 ProMax／Pro Max 的明确等价空白写法；颜色别名须按机型限定，酒红色别名仅限已确认 Pro Max。
3. 其他现有机型也接入同一入口：优先使用已有已核实目录，完整结构化规格可按统一顺序显示；未知或歧义内容保持原文并提示核对，不冒充已核实的 24 SKU，不凭模糊文字创建商品。
4. 不通过全局字符串替换改写非商品文本。容量内部数值 storageGb、SKU、productId、productKeys、计价版本、导入协议和业务身份保持；不因展示名相同合并不同 SKU 或冲突记录。
5. 接口按兼容方式提供 displayName／映射状态，既有原始资料读取契约保留。所有业务页面及新生成的复制、导出、通知使用标准名；编辑预览与原始输入分开，查看或保存无关字段不产生隐式来源改写。

## 业务字段与原始证据的边界

| 数据 | 本轮处理 |
| --- | --- |
| orders.products[].name（当前有效业务商品） | 分批改成标准名；仅修改可唯一确认的名称，保留原产品其他字段、项顺序、数量、SKU、时间和金额 |
| inventory_products.body.title（当前监控商品目录业务标题） | 规范可确认标题；保持 body 的其他字段及 enabled／supported／代理／范围／采集状态 |
| stock_products 的分列机型／颜色／storageGb | 不需要拼出一个名称写回；所有业务展示和选择使用标准名 |
| proxy_orders 的分列规格 | 仅显示映射，原“酒红色”保持；不补写 SKU 或关联 |
| AOS payload／draft／safe_preview、邮件 parsed_data／draft／final_data、原始行及附件 | 保留原始或人工修订事实；派生业务预览统一名称，不批量改原始记录 |
| orders.source_snapshot、official_products、校验诊断及历史审计 | 保留来源证据；业务摘要经映射展示，原文查看明确标注原文 |
| 库存销售快照、库存监控 samples／hourly／events／deliveries 等历史证据 | 保留原快照和已投递事实，业务历史页面摘要统一显示；不重发历史消息 |
| 冻结目录、历史 Migration、历史价格及报价源库 | 不修改历史版本和外部原始来源，增加现行显示规范 |
| 已导出的文件、已发送通知 | 不回写；重新导出及后续新通知使用规范名 |

每个被覆盖的业务名称必须有持久、可核对的原名留存。新增正式 Migration 建立专用名称变更审计表（具体列定义先更新数据库文档），逐条保存批次、实体、字段定位、原值与新值／身份保护信息。审计与修改在同一事务中提交，不以临时文件或易变 source_snapshot 作为唯一原名备份。审计表不存账号凭据或整行敏感资料。

后续新订单或业务商品更新时同样经过映射：来源接收和证据保留原文，进入当前业务商品时规范名称。采集器／解析器仍接受旧格式，未知或冲突记录不自动修正；原始名称变化的留存和业务写入须原子完成。

## 筛选、搜索、统计与金额保护

现行商品筛选键包含名称身份哈希。此次纯词序和单位规范化不重建持久化历史键、不删除旧别名；现有筛选标签更新显示名。批处理保存旧键与旧名称别名，规范名可检索；旧 productNames 精确查询兼容原值与标准名；现有 productKeys 保持可用，列表、候选、分页、筛选全选、导出和官网刷新范围一致。

同一已确认身份的名称变体展示汇总时不重复计数。不能按新 displayName 单独合并不同商品；保持订单数去重与件数原义，聚合后再排名／分页，避免先截断再合并漏算。原始计价协议与冻结价格版本保持，批处理不得触发普通 Order 保存钩子而重算金额、更新订单时间或联动邮件／付款／库存状态。后续正常业务保存仍执行原有合法校验与计价，显示映射不参与价格身份推断。

## 历史批处理与回退

实现可重复运行的 dry-run／apply／verify 工具：先仅输出脱敏汇总和异常清单，带规则版本、原名／新名及实体定位；apply 使用事务、咨询锁和原值／身份一致性条件，分批有界读取，冲突跳过并记录，不使用全仓库 ORM save。保护订单／产品所有非目标字段、金额、SKU、SN、销售结算、原始证据和筛选键。第二次运行无新增修改，异常不被清空。

生产前按部署指南备份全部业务数据（明确排除 AOS 监控日志明细及原始文件、不删除生产日志），校验 SHA-256；隔离 PostgreSQL 15 完整恢复、核对全部业务表计数与摘要，运行实际候选 Migration／批处理，独立核对允许字段外的数据与原始证据不变、审计原名完整、幂等和并发保护。不得使用虚构业务记录换取生产验收。

应用回退保留审计和已规范的业务名称，旧业务仍需接受 G／T 写法。不得整体回灌数据库或自动运行破坏性 down；如需撤销具体名称，只在当前值／商品身份仍与本批次一致时从审计恢复，不覆盖后续合法编辑和新增事实。Migration down 在已有审计事实时拒绝删除。

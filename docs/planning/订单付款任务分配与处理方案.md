# 订单付款任务分配与处理方案

> 状态：关键契约已定稿，实施中；按 2026-09-07 开发授权锁定首版安全来源
>
> 最近核对：2026-09-07
>
> 适用范围：用户权限分配、内部账号付款任务分工、订单付款人登记；外部付款人继续线下协作
>
> 基线：main@d000d03 与当前工作树
>
> 验证范围：账号、现有权限及路由、订单与商品字段静态核对；未验证新功能、真实付款链接或 30 分钟业务目标

## 一、复核摘要

采用“统一付款任务池 → 自动或手动分配给具备权限的用户 → 用户自行付款或自行联系他人付款 → 手动维护处理状态、备注及订单付款人 → 管理员调度和核对”的流程。

### 1.1 用户已明确的要求

| 编号 | 当前要求                                                                                                                         |
| ---- | -------------------------------------------------------------------------------------------------------------------------------- |
| U-01 | 复用 users 和现有账号，不新增付款角色；管理员能够按用户配置权限，并拆分现有系统功能权限。                                        |
| U-02 | 新待付款订单自动或手动分配给内部账号；管理员设置允许接单的用户、承接上限并查看当前任务数量。                                     |
| U-03 | 付款任务页面显示官网订单／付款状态、人工处理状态、备注；处理状态固定为待处理、处理中、已完成、异常，由工作人员手动维护。         |
| U-04 | 每个有相应任务操作权限的人，包括管理员，都可以自己付款；页面不要求选择“本人支付／外部分发”。                                     |
| U-05 | 所有处理状态都能登记付款人，第一版每张订单关联一名当前付款人，允许修正并保留历史；不能只存为任务备注，也不能只有完成时才能登记。 |
| U-06 | 付款任务页面支持根据订单商品筛选、根据订单号搜索；每条记录都有剩余付款时间。                                                     |
| U-07 | 管理员自己可以接单付款，也可把链接交给他人付款；内部负责人和实际付款人分别记录。                                                 |
| U-08 | 当前只优化可执行方案，复核后再安排开发。                                                                                         |

### 1.2 首版定稿契约

- 用户权限改造独立见[用户权限分配与访问控制方案](用户权限分配与访问控制方案.md)，本方案不再引入 paymentOperator 或按旧 operator/readOnly 名称决定付款能力。
- 用户已确认保留“待处理、处理中、已完成、异常”四种处理状态；未分配是负责人为空，不增加第五种处理状态。
- 删除付款模式选择、分发类型、强制分发登记和完成结果选择器。任务围绕官网状态、人工处理状态、备注、归属、时限及审计；实际付款人通过订单关联独立登记。
- 用户已确认第一版每张订单关联一名当前付款人，允许任何任务状态下补录／更正并保留历史；本版不建设多人付款关联。
- 官网状态不自动改变人工处理状态；人工已完成也不改写官网支付状态，不等同于款项已到账。

本页权限、算法、阈值、关联结构和接口均作为首版开发契约。后续若真实 Apple 页面证明付款入口或截止来源不同，必须先更新权威契约和兼容方案，不在实现中静默改变语义。

首版来源规则固定如下：

- 付款入口唯一来源是订单已经保存的 `orderUrl`，该值来自严格邮件解析或管理员邮件人工处理；只有通过 Apple 中国 `vieworder` 域名、路径、订单号一致性校验，并由管理员确认当前链接可继续付款后才可发放。系统不拼接新链接、不返回 Apple 密码，来源码固定为 `order_url`。
- 付款窗口固定为官网订单创建时间起 30 分钟。爬虫从官网订单 JSON 获取包含时分的创建时间并写入 `official_order_created_at`，付款任务 `deadline_at` 固定派生为该时间加 30 分钟；官网只返回日期时保持未知，不以当天 00:00、邮件接收、抓取或数据库创建时间冒充。
- 只有付款入口存在、官网订单创建时间明确、30 分钟付款窗口未结束且官网状态未明确已付／退款／取消的任务才可自动或手动分配。缺失官网时间的任务仍可留痕和刷新，但不具备分配资格；已经分配的当前负责人复制订单链接不受这些业务条件限制。
- 本人任务的付款人候选使用全局最小目录，只返回内部 ID、`payer_code` 和 `display_name`；联系方式、资金资料、创建人和关联订单始终不返回。
- 阈值固定为官网成功同步 90 秒后标记状态陈旧、付款窗口 30 分钟、分配后待处理 2 分钟提醒，以及截止前 10 分钟／5 分钟两级临期提醒。

## 二、目标、范围与现状

### 2.1 目标和业务衡量

支持百余单集中到达，每张任务有一名当前负责人，快速分配、持续可见、可处理异常。30 分钟内完成全部付款仍依赖真实付款时限、订单到达延迟、人员与资金能力和支付渠道，需要峰值演练及真实业务验收，不能由后台任务完成率证明。

分别记录“下单→入库→可分配→已分配→人工处理反馈→官网付款核实”耗时。没有可信付款时间时，截止后抓到已付款不能证明其在截止前付完。

### 2.2 第一版范围

包括逐用户权限配置、付款任务、管理员调度、接单设置、手动状态与备注、订单外部付款人姓名及审计、复制本人任务订单链接、商品／订单号查询、逐行倒计时、站内提醒、交接历史、并发与验收。

不建设外部付款人登录、系统代付、银行／支付 API、付款方式选择、分发渠道台账、自动向他人发消息、资金转账、应结金额、佣金和内部结算。登记付款人不表示认定其垫付了资金或产生应归还款。

### 2.3 当前静态核对事实

| ---------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |

## 三、用户权限与管理员自处理

### 3.1 权限集合

管理员在用户管理页面按模块勾选权限；普通用户是否能付款由有效权限决定，不再检查其 role 是否属于某个付款角色。管理员管理身份仍保留，未登录、锁号和会话有效性校验限制适用于所有人。

付款执行快捷组合包含以下五项，表单展开可见，不形成角色：

| 权限                         | 范围                                                 |
| ---------------------------- | ---------------------------------------------------- |
| payment_tasks.read_own       | 本人任务、详情、历史、商品候选及关联订单必要信息     |
| payment_tasks.handle_own     | 手动修改本人任务处理状态和备注                       |
| payment_tasks.payer.edit_own | 在本人任务的任意状态登记／更正订单付款人             |
| payment_tasks.link.read_own  | 复制本人任务订单链接，自己付或自行转发均使用同一动作 |
| payment_tasks.refresh_own    | 本人关联订单的受控刷新及进度查询                     |

所有动作依赖 read_own。仅有本人任务权限不等于获得 orders.read；商品候选、计数、历史、链接、付款人关联也必须检查当前归属。

管理员全局调度按 payment_dispatch.read/assign/configure/correct 控制，第一版为管理员保留权限；全局订单付款人修改按 orders.payer.edit 控制。权限目录、旧端点改造、授权实时生效、用户 UI 和迁移统一见[权限专项](用户权限分配与访问控制方案.md)。

### 3.2 接单资格与撤权

接收新任务须具备完整付款执行组合、账号正常；自动分配还要求管理员开启自动接单且有剩余容量。权限授予不自动开启接单。

移除任一执行权限时停止该用户新增接单；已有任务保留负责人，管理员看到需交接数量。紧急撤权可以立即生效，不因有任务而强制继续保留权限；不自动把结果不明的付款任务发给别人。重新授权不自动恢复接单开关。

### 3.3 管理员和工作人员支付操作一致

- 所有人在有权限且当前负责的任务上使用同一个“复制付款链接”入口，页面不要求声明自己支付还是交给别人支付。
- 实际支付后，员工手工登记真实付款人姓名；自己付款时也明确填写实际姓名，不自动使用账号用户名或 user_id。
- 管理员有“付款任务”和“付款调度台”；自己参与自动分配时按相同负载算法计数，不享优先级。
- 管理员关闭本人自动接单时可手动“分配给我”，但仍须配置上限且有容量。
- 管理员处理他人任务前先执行接管交接，不产生并行付款安排；代改状态／备注留审计，但不自动改变负责人。

## 四、状态、备注与订单付款人

### 4.1 状态分离

| 维度         | 来源及行为                                                                                |
| ------------ | ----------------------------------------------------------------------------------------- |
| 官网订单状态 | 沿用订单同步结果，只读展示                                                                |
| 官网付款状态 | 沿用 payment_status，已付款／未付款／未知等；显示最近成功同步时间和新鲜度                 |
| 处理状态     | pending 待处理、processing 处理中、completed 已完成、exception 异常；用户已确认，手动维护 |
| 分配情况     | assignee_user_id 是否为空；与处理状态独立                                                 |
| 提醒         | 临期、过期、同步过期、信息缺失、人工已完成但官网未确认等自动派生，不是新增状态            |

任务创建默认待处理；工作人员实际开始后手动标记处理中。官网更新、复制链接、付款人登记、到期、转派都不自动改变处理状态。

| 手动转换                | 规则                                                                             |
| ----------------------- | -------------------------------------------------------------------------------- |
| 待处理 → 处理中         | 工作人员明确提交，不因领取链接或登记付款人自动开始                               |
| 待处理／处理中 → 已完成 | 用户明确提交；官网未确认付款时提示差异并要求写备注，不要求选择付款方式或完成结果 |
| 待处理／处理中 → 异常   | 异常原因写入备注／事件，不能为空                                                 |
| 异常 → 处理中           | 填写恢复说明，仍由用户主动提交                                                   |
| 异常 → 已完成           | 必须补充处理说明；官网是否已付独立显示                                           |
| 已完成 → 异常           | 管理员重开并填写原因，保留原负责人和历史；本人可补备注申请处理                   |

“已完成”仅表示人工认为任务处理结束。取消、已过期、已退款等订单由人工在备注说明后结束或保持异常，不另外新增结果选择器。统计取消／退款来源于官网值，过期来源于截止时间与证据，不能从自由文本猜测付款结果。

### 4.2 备注

处理备注与 orders.notes 分开，建议纯文本最多 2,000 字符。全部处理状态均可维护备注；修改或清空保留前后内容、操作者及时间。异常、转派、重开等必填原因持久化为事件，不因以后清空当前备注消失。

备注不存密码、验证码、完整付款链接或银行卡明文；按现有敏感字段方式加密，页面纯文本渲染，普通运行日志不记正文。轮询和版本冲突不能覆盖未保存草稿。

### 4.3 所有状态都允许登记付款人

付款人登记与处理状态共享当前任务行的“保存”动作，但服务端仍按独立权限和版本写入：待处理、处理中、已完成、异常均允许新增、补录或更正，官网已付款／取消／退款、任务已过期也不阻止真实信息补录。写付款人不得自动完成或重开任务，不影响接单容量。

系统用户与付款人是两类主体：可登录用户均为内部员工；付款人是员工在线下组织的外部实际付款者，不创建系统账号，也不建立候选下拉或付款人主数据。第一版已确认每单一名当前付款人，员工直接在 `orders.payer_name` 手工填写姓名，可留空，最长 100 个字符。

- 员工按实际付款结果输入姓名，不默认把当前账号用户名写为付款人。
- 相同姓名不代表同一身份，系统不自动合并、推断关联或生成内部编号。
- 有权限者可在任意任务状态修正或清空；每次变化通过订单版本锁和审计事件保留前后姓名、操作者、可选说明与时间。
- 登记位置：付款任务页面、付款任务详情、具有 orders.payer.edit 的订单详情共用关联服务；订单列表与详情显示同一付款人。
- 转派后：原负责人失去任务入口的登记权限，新负责人可补录；旧付款人关联保留，转派不能清空订单事实。
- 历史订单已有 `payer_name` 时直接作为当前登记值显示，不自动按同名关联到任何账号或实体。

付款任务自身不再存 payment_mode、payer_label 或 distributed_at，也不把付款人只放进备注。付款人姓名变更记录到订单审计，同时在相关任务历史中展示，包含前后名称、操作者、可选说明和时间。全局订单更新与任务登记采用相同订单版本锁，防止互相覆盖。

本版不建立多人付款关联，不在姓名字段拼接多名付款人，不根据付款人登记推导分摊金额。将来如有多人实际付款需求，作为独立需求调整订单关联和验收口径。

## 五、任务生成、付款入口与时限

### 5.1 生成与补偿

1. 功能默认关闭；首次启用保存 scope_started_at。默认纳入本范围后新建且下单时间属于本场范围的订单，历史订单不全量回填。
2. 新订单事务内创建唯一任务或持久化待办事件；order_id 唯一，重复邮件、人工纳入和重试不重复建任务。
3. 已明确付款、退款、取消或无需付款的订单不新建任务；其余先建待处理任务。付款状态未知、链接或时限缺失时显示待核实原因，不伪造未付款。
4. 每 10 秒补偿持久化待办和未分配任务。下单时间缺失、迟到或疑似历史转发进入管理员纳入待核实列表；纳入／忽略都留痕。
5. 手动模式停止自动分配但继续建任务；全局功能关闭停止自动建任务与分配，保留已有任务人工操作。再次开启沿原范围补查，不能重新给过期订单 30 分钟。

### 5.2 每条任务的剩余付款时间

每行固定提供“剩余付款时间”，所有状态都显示该列。服务端返回 deadline_at、deadline_source、server_time、remaining_seconds 及官网付款状态／可信付款时间（若可获得）；前端以服务端时间校准，不用浏览器时钟直接决定是否过期。

| 情况                           | 展示规则                                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| 截止时间已知且官网未付款／未知 | HH:mm:ss 倒计时；10 分钟、5 分钟阈值分别显示临期、紧急                                                         |
| 已到截止时间但仍未确认付款     | “已到付款时限／超时 X 分钟”，不显示负数倒计时；不自动改处理状态                                                |
| 人工已完成但官网未确认付款     | 仍显示剩余时间或超时提示，附“人工已完成，官网待核实”，不能隐藏风险                                             |
| 官网已付款                     | 显示“已付款”；若有可信付款发生时间，可显示“付款时剩余 X”，否则显示“付款时间待核实”，不能以抓取时间代替支付时间 |
| 官网取消／退款                 | 显示相应结果及原截止时间，避免继续显示可付款暗示；若有时间差只说明距原截止，不表示应再次付款                   |
| 时限未知                       | 明确显示“等待官网时间”，不留空、不以日期 00:00 或其他本地时间伪造                                             |

付款截止固定由官网订单创建时间加 30 分钟计算，来源码写 `official`。管理员不能手工修改截止；转派、补录付款人、重开、备注、邮件重发和后续刷新均不重置已确认的官网创建时间。历史 `manual_verified` 值只为兼容旧记录，新页面不再提供维护入口。

到时停止自动和手动分配；已经分配的当前负责人仍可复制订单链接，付款人补录及状态／备注维护仍允许。官网创建时间只能由后续官网刷新补齐或纠正，管理员不能手工延长付款窗口。

### 5.3 真实付款入口

现有 `orderUrl` 是复制按钮的唯一来源；接口在专用权限和当前任务归属通过后直接返回，不再检查 URL 结构、付款资格、有效期、截止时间或订单状态。链接缺失时不能构造替代值，也不开放 Apple 密码；复制动作本身不代表系统确认链接有效或已经付款。

领取接口从订单链接字段读取，经服务端再次校验后短暂返回；数据库、任务事件、普通接口和日志不复制链接值。领取时只检查当前权限、负责人和链接存在，记录不含链接的领取事件；复制不自动改变人工状态。订单链接已被复制后，系统不能保证撤销外部访问。

## 六、自动分配规则

### 6.1 配置、当前任务数量与容量

管理员配置全局开关（默认关）、自动／手动模式（首次默认手动），逐用户 auto_assign_enabled（默认关）及 max_active_tasks（默认 0，整数 0–1,000；1,000 是输入保护而非推荐单量）。

active_count = 当前负责且状态为待处理、处理中或异常的任务数。已完成释放容量，但“人工完成／官网待核实”另列数量；过期、官网已付但人工未完成的任务仍占容量。remaining_capacity = max(0, 上限 - active_count)，load_ratio = active_count / 上限，上限 0 不参与候选。

调低上限不回收存量，超额时停止新增；管理员重开任务允许真实负载临时超额，保留负责人并告警。手动分配和管理员自己接单同样检查上限。

管理员开启接单表示本场确认该用户可参与，不等于技术上证明在线；第一版不根据登录或心跳自动开关。员工暂离联系管理员暂停。账号锁定／撤权等自动停止新增并告警存量，不静默转派。

### 6.2 候选与确定性排序

任务满足：已纳入范围、无负责人、待处理、付款入口存在、官网订单创建时间精确到分钟且 30 分钟付款窗口未结束，并且没有已付款／退款／取消等明确冲突。官网创建时间未知的任务保留在队列中并允许人工刷新，但不参与分配；最新官网否决结果优先，不回写伪造官网状态。

按 deadline_at、任务创建时间、任务 ID 升序取任务。候选人员满足执行权限、账号、自动接单和容量条件。按 load_ratio 最低者选择；并列时最久未获分配者优先，再按用户 ID。每派一单重算，不先选一人再整批塞单。

示例：甲上限 10 已有 5 单，乙上限 20 已有 6 单，负载分别 50% 和 30%，下一单给乙。算法不代表付款人金额能力，真实资金和付款速度仍需人工准备。

无合格人员保留队列并显示无人接单／容量不足；不丢任务、不忙循环、不自动超限。条件补齐、释放容量、启用接单／提高上限、切换自动模式及重启触发调度，另每 10 秒补偿。

### 6.3 一致性与故障恢复

调度器运行在现有 API 进程，多个副本通过 PostgreSQL advisory lock 协调，独立于邮件／爬虫开关。自动与手动分配、转派、容量修改、重开、接单资格和权限变更使用统一锁顺序：调度锁→用户及权限／配置行→任务／订单行。

数据库事务中复查并写归属、状态与审计；建议每事务最多分配 20 张后释放锁继续。任务 order_id 唯一，不正常超额、不重复归属；提交前失败回滚，提交后退出由持久化状态恢复。持锁期间不访问 Apple 或外部消息服务。普通备注和付款人登记使用对应任务／订单版本检查，不以 UI 计数作为分配依据。

## 七、手动分配、交接与提醒

- 管理员可对合格未分配任务指定用户或分给自己，自动接单关闭不阻止手动分配；仍检查有效权限、账号和容量。
- 批量最多 100 条，按截止排序，逐项返回结果；已分配任务返回冲突，不当作覆盖分配。超限时先显式调整上限再操作。
- 无链接领取记录且确认没有线下付款安排的待处理任务，可以转派或撤回未分配池，状态保持待处理。
- 已领取链接或已经联系付款人、处于处理中／异常、支付在途或结果不明时，不直接撤回自动队列。转派须说明原因，并确认原执行方停止、没有支付在途／结果不明；管理员紧急接管也一样。
- 没有强制分发登记，因此“没有领取日志”不能证明外部从未拿到链接。交接确认必须明确询问当前负责人，不能由系统日志替代；确认作为一次交接审计，不增加付款方式选择。
- 转派保留状态、订单付款人、备注与历史；新负责人手动继续。已完成任务先管理员重开为异常才能转派。
- 分配 2 分钟后仍为待处理时提示负责人及管理员；备注或付款人登记不压制此提醒，链接领取单独显示，不当成已开始或付款成功。该阈值只用于提醒，不自动换人或改状态。
- 临期 10／5 分钟、账号不可操作却有存量任务、超额和人工完成但官网未付款持续提醒。所有提醒不自动改人工状态。
- 有任务、订单付款人审计或权限审计引用的用户不得物理删除；停用／锁定与交接保留历史。

## 八、页面、商品筛选与搜索

### 8.1 付款任务

侧边栏中“付款任务”紧随“付款调度”显示；账号没有付款调度权限时不显示该项，但仍按自身 `payment_tasks.read_own` 权限显示“付款任务”。

浅色表格列表，遵循[前端设计规范](../development/前端设计规范.md)。默认显示本人待处理、处理中和异常任务；有“全部／待处理／处理中／已完成／异常”筛选，已完成仍可查、改备注、登记付款人。

| 区域／列 | 内容                                                                                       |
| -------- | ------------------------------------------------------------------------------------------ |
| 顶部     | 待处理、处理中、异常、已完成、临期、人工完成待核实数量；当前任务数／上限、自动接单开关     |
| 查询     | 订单号搜索、商品型号、商品关键词、官网订单／付款状态、处理状态、下单日期、临期／时限待核实 |
| 订单     | 订单号、商品型号及名称、各项数量、官网金额币种；缺失值不猜测                               |
| 时间     | 每行付款倒计时、官网最后更新时间；下单时间独立成列，分配时间可展开                                     |
| 状态     | 官网订单／付款状态和新鲜度、独立人工处理状态                                               |

不显示付款方式选择或分发类型；开始处理仍由工作人员明确手动改为处理中，付款人登记无需先改状态。仅因任务已完成或异常而禁用付款人按钮属于验收失败；权限丢失或已转派则必须禁用并由 API 拒绝。

### 8.2 商品和订单号查询契约

- 订单号：order_number，去首尾空格并统一大写，支持完整号和部分号包含查询；参数化查询并转义 %、_，输入它们不作为任意匹配通配符。建议最多 32 字符，空串等同无筛选。
- 商品型号：product_models，支持多选，按现有 products[].model 精确匹配，选项显示实际数据；不能只在当前分页中过滤。
- 商品关键词：product_keyword，建议最多 100 字符，在 products[].name 和 model 中忽略大小写包含匹配。颜色、容量现在属于名称，因此用户可输入“蓝色”“256GB”等真实商品文字；第一版不伪造独立颜色／容量下拉或强行拆词推断。
- 多个型号之间 OR；型号与关键词之间 AND，并要求同一商品项同时满足。例如一单含蓝色 256GB 型号甲和黑色 512GB 型号乙，筛选型号甲＋512GB不能因不同商品项各自命中而误匹配。
- 订单内任一商品满足组合条件即返回该订单一次，展示完整商品列表并高亮命中项；不把订单拆成多条任务，不把未命中商品藏掉。
- 商品数据以邮件 products 快照为第一版筛选依据，与页面展示一致；不混用爬虫 official_products 做另一套不可解释筛选。model 缺失时关键词仍可查 name，并支持“型号未提供”选项。
- 型号候选从当前用户有权访问的全部任务关联商品计算（不局限当前页），不返回他人商品信息；候选权限与主列表相同。候选接口按去重值输出，关键词输入用于补充名称查询。
- 订单号、商品、状态、日期等不同维度按 AND 组合；条件变化回到第一页。排序默认截止最早优先，无时限记录单列待核实提示且保留可筛选入口。
- 支持清空筛选、匹配总数、空结果提示。所有筛选在服务端执行并在分页前应用，统计与列表使用相同范围；使用 JSONB 元素查询和订单去重，评估索引，避免 N+1。

两个付款页面复用订单管理的分页组件，默认每页 20 条，可选 10/20/50/100，支持首页、上一页、下一页、末页和输入页码跳转。筛选或调整每页条数回到第一页；翻页、筛选、调整条数清空勾选，全选仅作用于当前页。数据减少造成页码越界时回到有效末页。本人页面状态徽章明确为“本页统计”。

下单时间优先使用接口 `orderDate`，与订单管理展示同一订单字段，按本地时区显示 `YYYY/MM/DD HH:mm:ss`；缺失时回退已确认的 `officialOrderCreatedAt`，两者均无值显示“待核实”。这一展示回退不参与官网付款截止或分配资格计算，不使用本地任务创建时间替代。

### 8.3 刷新与交互

活跃页每 5 秒刷新本站数据，隐藏降频、恢复立即同步；逐行倒计时本地每秒显示并按 server_time 校准。不得每秒抓 Apple。失去网络显示最后更新时间，付款时限未知显示原因，草稿不被轮询覆盖。

保存只提交实际变化，并使用任务版本和订单付款人版本分别防覆盖；同一行同时修改状态／备注／付款人时在一个事务内全部提交或全部回滚，不产生无变化的版本和审计记录。页面展示保存中、成功或失败反馈，失败保留草稿并说明原因；任务被转派／撤权后清除无权数据视图。复制按钮在权限和当前归属通过后直接复制关联订单链接，不按截止时间或业务状态限制；剪贴板失败不报告复制成功，链接不常驻 DOM／本地存储。

两页支持先勾选本页订单再批量刷新。页面以最多五个并发请求逐项调用既有刷新接口，每项独立鉴权、合并队列和反馈；一项失败不阻断其他订单，不会刷新未勾选订单。刷新按钮展示提交中并防止连续提交；入队后展示排队或运行状态，终态在对应行展示成功／失败并静默重新加载当前页，保留付款任务未保存的备注、状态和付款人草稿。调度单行刷新不再显示顶部入队成功横幅；刷新超过 30 秒仍跟踪队列，连续三次进度查询失败时明确结果未确认并允许重试。刷新进度只能查询本人当前任务关联订单的 job；本地未启动爬虫 Worker 时保持“已进入队列，等待后台处理”，不能冒充已完成。

### 8.4 管理员调度台

全局队列和人员表显示：用户、是否接单、上限、待处理／处理中／异常／未完成合计、剩余容量、已完成待核实、最近分配与配置修改时间。任务队列支持订单号、商品信息、负责人、官网订单状态和人工处理状态组合筛选；显示付款倒计时、官网状态、最后官网更新时间，提供逐行刷新和批量刷新。手动分配先批量勾选任务，再点击分配并在弹窗选择人员确认；服务端原子提交整批，转派批次必须确认交接并填写原因。

显示最近调度扫描／故障；总任务数 = 未分配数 + 各负责人任务总数；四种处理状态互斥，风险标签可重叠不能相加作为总数。不提供一键将全部任务标成已付款。每日收尾分别核对官网付款、人工完成待核实、取消／退款、过期和未完成。

新增付款接口采用 camelCase 请求／响应，与当前 JavaScript 前端和服务层一致；既有订单 DTO 的 snake_case 不做隐式全局转换。每项写操作使用版本和 `Idempotency-Key` 请求头，同用户同操作同键绑定目标；重复请求不覆盖成功项。

付款人可通过 `payerName=null` 清空并留痕；登记付款人不受截止时间或处理状态门禁，但仍受实时权限、任务归属、乐观锁和幂等控制。

复制订单链接只校验权限、当前归属和链接是否存在，不再检查 URL 来源、任务完成、截止时间或官网支付／订单状态。日志、导出、错误信息和权限审计不得回显原始链接。

### 11.2 技术与业务验证

隔离环境以 150 单为首轮高峰、300 单为余量，记录人员容量、API 副本与数据库配置。建议目标为条件具备且容量足够的 150 单在 10 秒内持久化分配，活跃页在变更后 10 秒内可见；不包含邮件、官网和真实支付耗时。商品筛选要在多商品和跨页数据上验证准确性、权限范围与耗时。

业务按本场经确认需要付款的原始订单集合计算，未分配、超时不从分母删除，取消／退款／排除项逐单可核对。分开显示官网确认付款数、人工处理完成数、两者不一致数、时限待核实数、异常和过期数。只有可信付款发生时间才能支持按时付款结论；未知不能算成功。

记录任务各环节耗时、最大积压、每人峰值负载、临期和转派次数；真实资金不到位、支付渠道异常、人员失联、官网同步失败分别记录。技术通过不替代人员和真实付款业务验收。

## 十二、与付款人及内部结算规划的关系

本次纳入订单付款人姓名和变更审计，满足用户“所有状态可登记且关联订单”的要求；付款人姓名是订单事实，不放在任务临时备注中。内部负责人是可登录 user，实际付款人是不会登录的外部主体，不自动互相映射。

[付款人与内部结算方案](付款人与内部结算方案.md)中的完整垫付归还、金额、币种、退款和结算责任仍待确认。最小付款人实体与该规划统一主键和命名，避免日后重复创建两套 payers；同名和历史映射不猜测，任务完成／付款人登记不自动产生债权或资金记录。

### 下单时间精度与时区（2026-09-09 修复）

`orderDate` / `order_date` 保留邮件或人工录入的来源下单时间，官网只有日期时禁止覆盖，官网精确时间独立保存在 `officialOrderCreatedAt`。日期冲突提示核对，不用官网日期补造时分秒。页面和导出统一北京时间（Asia/Shanghai）；日期筛选包含北京时间的完整起止日。仅有日期时仅展示日期，未知时间不使用入库时间或付款截止倒推。人工录入必须包含时分；无时区输入按北京时间解释。付款截止仍只使用官网截止或精确官网时间。历史修复只恢复可核验来源快照，不将来源时间宣称为官网精确时间。

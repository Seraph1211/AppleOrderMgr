# 官网订单链接爬虫下线与邮件状态接替方案

> 状态：待实施；用户已确认范围，本轮仅编制开发交接文档
>
> 最近核对：2026-09-22
>
> 适用范围：AppleOrderMgr 管理台、API、订单入库、付款业务、后台 Worker、数据库与部署配置
>
> 代码基线：`main@b3cbb1b` 及当前未提交工作树；开发人员接手时必须重新核对差异
>
> 验证范围：本地源码、依赖及现行文档静态梳理；本方案尚未编码、执行 Migration 或部署，不代表下线完成

## 1. 已确认目标与交付边界

用户已确认：删除所有官网订单链接爬虫相关功能和逻辑，浏览器采集一并删除；保留原始订单链接；历史数据归档保留；按邮件状态调整日常业务。必须保留 Apple 订单邮件解析及订单状态更新，不能误删无关代码。

本次交付为实施方案。后续开发人员依据本文编码、测试和提交验收结果；本次文档确认不等于生产发布、真实数据写入、提交或推送授权。

下线完成后，业务链路应为：

```text
AOS／既有收单邮件 → 订单入库 → 付款任务登记、已有邮件关联、通知登记
Apple 订单邮件 → 归档 → 解析与订单号匹配 → 邮件状态／取货信息 → 页面与统计
                                             └→ 符合原有条件的付款任务完成及审计
人工操作 → 复制订单链接／付款码、处理本人任务、既有授权核定
```

系统不再自动访问订单链接，不再通过浏览器或代理获取官网详情。用户主动复制、打开链接不属于爬虫；系统内业务页面、邮件 Worker、AOS 采集器不能依赖爬虫模块存在才能启动。

## 4. 邮件状态接替规则

### 4.1 来源与展示

不将旧官网数据改名冒充邮件证据，不把邮件值反写到官网专用字段以兼容旧调用。接口和查询直接使用现有邮件字段：

| 字段                                                 | 现有枚举／含义                                           | 接替后的用途                                     |
| ---------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------ |
| `emailOrderStatus`                                   | `unknown`、`confirmed`、`processing`、`ready_for_pickup` | 三张订单／付款页面的订单阶段、筛选及对应汇总     |
| `emailPaymentStatus`                                 | `unknown`、`paid`                                        | 邮件付款确认及符合现有规则的任务联动             |
| `emailStatusNeedsReview`、`emailStatusReviewReasons` | 邮件待复核与原因                                         | 保留复核提示和既有人工核定流程                   |
| `emailPickupInfo`、`emailPickupDate`                 | 邮件归并的取货信息                                       | 详情、列表和取货导出                             |
| `emailLifecycleUpdatedAt`、`emailStatusEvidenceAt`   | 应用时间、邮件证据时间                                   | 分别展示／用于证据追踪，均不是实际付款或取货时间 |

`unknown` 显示“待确认”，不是“未付款”；确认邮件不等于付款证据；可取货不等于已取货。当前邮件枚举不支持的已取货、取消、退款、配送等阶段不能在本次删除任务中靠推断补齐。相关实时筛选／指标退出或明确显示“邮件未提供”，不能默认填 0，也不能继续拿冻结的官网值充当最新状态。

商品、来源支付方式、下单时间、金额映射继续使用现有入库／业务规则。历史已合并商品保留，不批量还原来源商品、不重新命名或清空金额；邮件取货信息缺失时明确待确认，不静默回退历史官网结果。保留来源快照用于追溯。

### 4.2 Apple 订单邮件更新必须完整保留

保留 `orderMailSync`、`orderMailService`、`orderMailLifecycleParser`、`orderMailLifecycleService`、`orderMailWorker` 及各自归档／事件／任务模型。现有收单 `emailWorker`、`emailProcessingService`、`emailParser` 同样保留，两条邮件处理链不能互相替代。

下列现行规则不因删除爬虫而改变：

1. 归档、重新解析和系统订单的完整订单号精确匹配；邮件先到时等待订单入库后关联。
2. 保留模板正文、商品范围及歧义复核；不重新引入 DKIM 通过作为应用硬门槛。
3. 重复邮件／重复重放幂等；乱序邮件不使已确认阶段倒退；后续空字段不清空已知取货安排。
4. 未知模板、订单号不符、商品范围不符等异常不能自动更新成成功状态。
5. 仅符合现有已付款证据且无需复核的邮件结果联动付款任务；任务更新、版本和 `mail_payment_confirmed` 审计保持事务一致，不改负责人或付款人。
6. 保留 HTML、原始 `.eml`、附件、脱敏、保留期、查看／转发／重解析／核定权限和 TAG 范围。
7. 邮件解析、订单应用、付款任务联动的现有独立开关保持原配置；不得因清理环境变量而关闭，也不得将关闭环境自动开启。

### 4.3 付款分配与历史限制

新日常判断以邮件付款结论、人工任务状态、链接校验、来源截止、权限／归属、容量和版本为依据。截止仍为来源 `orderDate + 30 分钟`，缺失不回退官网或入库时间。保持自动分配仅未过期、授权手工分配可处理过期任务的既有规则。

删除“官网尚未核实”、旧官网新鲜度、官网身份比对等提示和依赖；原始付款链接的协议、域名及订单号校验仍须保留。邮件没有付款证据不自动阻断全部新订单，也不自动把人工已完成任务重开。

历史防重复付款采用一次性迁移的独立业务限制，不能继续从官网字段动态判断：

- 迁移前按当前 `isAssignmentBlocked(order, true)` 及自动分配规则生成逐单对照，区分“仅自动过期限制”和“已付／退款／终态限制”。
- 对旧官网已付、退款、明确终态等限制且不能仅由现有邮件／任务状态承接的订单，建立中性的历史付款限制。建议在 `orders` 新增可空 `paymentAssignmentHoldReason`（STRING(50)）和 `paymentAssignmentHoldEvidence`（JSONB），正式结构先写入数据库架构后实施 Migration。
- 本次限制原因统一为 `legacy_payment_restriction`；证据仅含迁移标识、原判断分类、归档记录引用和时间，不保存链接、邮箱或原始页面。该字段是待实现设计，当前数据库没有此字段。
- 运行时只读取邮件状态、任务状态和独立限制；历史归档不参与在线 JOIN。历史限制阻止自动和手工重新分配并显示“历史付款限制，待核对”，不将订单改为邮件已付款，不伪造付款任务完成记录。
- 单纯过期不写入永久限制，不破坏手工处理过期任务；迁移不重新分配任务、不修改负责人、不自动关闭或重开任务。
- 首版不增加批量解除限制功能。解除涉及真实付款判断，应另行核定并审计，不能让通用订单编辑接口直接清除此字段。

开发交付须提供迁移前后资格差异报告：不得出现原受已付／退款／终态限制的订单无依据变为可自动分配；无相关证据的新订单也不得被批量误拦截。

### 4.4 统计、筛选与导出

- 日常订单阶段按 `emailOrderStatus` 分组；付款确认按 `emailPaymentStatus=paid` 统计；人工任务完成数仍为独立指标。
- 金额继续使用现行商品目录映射 `orderAmount`，未知金额不补 0；映射金额不表述为银行实扣。
- 渠道及仪表板原有“官网或邮件已付”联合口径改为邮件确认口径，历史官网独有付款不自动计入邮件确认；提供受影响数量／金额差异，说明统计变化来自口径切换。
- 邮件不支持的已取货／取消等指标退出日常实时统计，历史证据仅在归档中保留。标签、SQL、API、表格和导出保持一致。
- 更新对应查询参数和允许值；旧官网筛选参数不能被静默当作邮件参数。建议返回明确 400 参数已退休错误，前端清除旧持久化筛选。
- 日常导出移除官网刷新时间／校验等专用选项，保留邮件更新、取货和业务字段。归档导出与日常导出区分，不默认开放敏感历史信息。

## 5. 历史归档与数据库迁移

### 5.1 归档对象

| 对象                                                                                                                  | 处理原则                                                                           |
| --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `order_refresh_jobs`、`order_refresh_batches`、`order_refresh_schedules`、`order_refresh_system_states`、`crawl_logs` | 完整归档，退出在线模型、查询和调度；保留原任务状态与时间，不把积压任务伪装成成功   |
| 官网专用观测／校验字段及来源快照                                                                                      | 保存逐订单下线快照；原字段可暂时冻结保留作为回滚兼容，但从在线 DTO 和业务判断退出  |
| `status`、`payment_status`、`pickup_status` 等历史混用字段                                                            | 逐字段核对人工／入库用途；不能按名称盲删或全量覆盖。旧官网值不能成为新日常状态来源 |
| 商品、订单链接、金额、邮件字段、付款任务与事件                                                                        | 保留现有数据，不因“爬虫曾经更新过”而删除                                           |
| 旧爬虫权限记录、列配置和发布信息                                                                                      | 归档必要映射；仅处理已退休键，不重置无关设置                                       |

建议使用独立 `archive` schema 归档上述五张表和下线快照，运行账号不具有归档写权限，应用代码不加载归档模型。备份／审计角色受控读取；如果实际部署的数据库账号权限不支持隔离，由开发人员在迁移说明中给出等效只读归档措施并验证，不能只改表名声称只读。

归档必须包含清单、数量、关键时间范围、校验摘要及恢复方法。停止所有生产者／消费者后再完成最终快照。核对序列、索引、外键及 `ON DELETE CASCADE`：业务订单／用户后续变更不能级联删除历史证据；归档改用保留 ID 的快照关系，完整登记原约束以便回滚。

### 5.2 迁移约束

1. 先更新[数据库架构](../database/数据库架构.md)的目标设计，再写新的 `up/down` Migration；禁止编辑已执行历史迁移、启动时 `sync/alter` 或直接清空旧表。
2. 先建立归档与业务限制、校验完整性，再退休在线结构。推荐分扩展和收尾两阶段，避免旧 API／Worker 在滚动替换期间查询已移走的表。
3. 邮件相关表、AOS 表、付款表及用户业务授权不得被连带删除；不强制重放全部历史邮件、不发送通知、不改变任务归属。
4. 迁移前后比对订单、付款任务、邮件事件数量和关键业务字段摘要；按订单核对历史限制，验证无意外新增分配。
5. 回滚不能覆盖下线后新产生的邮件、付款和人工操作数据。恢复归档结构时处理 ID／序列／外键冲突，不能直接用旧全库快照覆盖已有新业务数据。
6. 旧爬虫表恢复不等于恢复爬取：回滚默认保持爬虫 Worker 停止和暂停状态，禁止积压任务自动重放。

## 6. 实施顺序与文档级联

| 阶段          | 工作                                                                             | 交付门槛                                               |
| ------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------ |
| A：基线与边界 | 记录 Git 差异、线上实际镜像／前端版本；形成删除／迁移／保留三类清单              | 每个共用文件有具体修改范围，无关未提交内容有保留证据   |
| B：契约与数据 | 完成 API 退休、邮件筛选、归档及付款限制的规范和 Migration 设计                   | 当前枚举、权限、回滚方法和统计差异口径明确             |
| C：业务脱钩   | 先提取共用工具，改入库／付款／统计和前端为邮件驱动，再删除爬虫模块               | 删除目录后 API 和其余 Worker 可加载，邮件更新测试通过  |
| D：配置清理   | 清理 Compose、配置、脚本、权限和当前下载制品                                     | 无可用爬虫入口或隐式恢复路径，其他代理／采集能力保留   |
| E：验证交付   | 执行第 7 节用例，审查最终差异                                                    | 提供测试结果、未验证项、迁移演练及发布／回滚清单       |
| F：授权后发布 | 依据实际生产版本构建，备份，在 15 分钟维护窗口内仅停止爬虫并分阶段迁移、无中断切换 API 与前端 | 新订单入库和企微推送持续运行；生产页面与邮件链路回归，不以 health 代替业务验证 |

发布只停止会写入待归档表的旧爬虫 Worker。扩展迁移期间保留旧 API、邮件 Worker、订单邮件 Worker和企微 Worker；新 API 健康后通过 Nginx 双端口切换，再执行最终归档。邮件 Worker 采用可补偿的短滚动替换，企微 Worker 使用新旧实例重叠和数据库幂等领取保持推送连续。整个维护操作不超过 15 分钟，不使用笼统的全栈删除、卷清理或 `--remove-orphans` 处理其他服务。

真实新邮件业务验收已在本方案实施前完成，本次发布只做链路连续性和回归核对，不重复发送真实通知或制造真实订单。

开发人员实施时同步维护：API 设计、数据库架构、系统架构、邮件处理／解析、AOS 入库说明、渠道／仪表板说明、付款任务／分配相关文档、测试指南、部署／本地开发／运维文档、开发进度及优化计划。爬虫说明、爬虫改造计划和本机并发刷新说明在实际下线后转历史并修复导航；AGENTS 和提示词中的爬虫专用强制规则一并更新，其他编码规则保留。

历史报告保留原事实。本规划仅取代今后的爬虫开发／恢复方向，不把当前尚在运行的代码或生产能力提前写成已删除，也不删除邮件规划中的有效规则。

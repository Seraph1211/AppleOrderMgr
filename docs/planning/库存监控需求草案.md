## 全国与多商品覆盖规则

### 商品和门店目录

- 门店以 [Apple 中国大陆零售店列表](https://www.apple.com.cn/retail/storelist/)为基础，核对门店代码与可取货查询返回的门店集合；按当前名单核验覆盖，不写死历史门店数量。
- 首批建议覆盖 Apple 中国大陆官网当前在售、且能验证门店可取货查询的 iPhone 型号及全部有效颜色／容量组合；上线前形成明确 SKU 清单。小程序商品标签、订单商品名称和市场报价不作为 SKU 权威来源。
- 不支持或暂未验证的组合显示原因，不能用“无货”替代；不存在的颜色／容量组合不生成监控任务。
- 目录每日检查变化；新门店、新 SKU 展示为待启用，确认覆盖和运行容量后纳入。商品暂时无货不会自动停监控，下架也不因一次请求失败而认定。
- 一期不包含港澳台、其他 Apple 产品、第三方经销商、线上配送或自有仓库库存。

### 采集策略

- 全国统一轮询所有已启用的商品与门店组合，不依赖个人关注或订阅。关闭网页不影响运行；重启后恢复持久化进度，避免重复启动一轮或重复提醒。
- 优先验证按地域覆盖多门店、按接口能力合并多个 SKU 的请求方式；同一门店因多个地域结果重复出现时去重，按 SKU 与门店代码精确对应。
- 以“一轮覆盖全部启用范围”为调度单位，先保证各组合公平获得检查机会，再优化速度。手动检查复用同一队列、限流和去重机制，不能挤占所有后台任务。
- **建议首次全国试运行以 300 秒一轮为候选起点**，还须满足请求预算与实测耗时；不能完成时继续拉长周期。稳定后再逐档评估 180／120／60 秒，60 秒只是后续优化方向，不是交付前提或稳定性承诺。触发风控时自动降速或暂停，不为维持刷新周期缩小全国覆盖。
- 页面读取库存快照建议每 10 秒刷新；这不表示每 10 秒向 Apple 重新采集。每个结果始终展示自己的采集时间。
- 单独记录“计划开始时间、实际轮次耗时、数据年龄、通知排队时间”，不以网页刷新动画宣称秒级库存。
- 部分请求失败时，成功组合正常更新，失败组合保留最后成功值与时间并标记异常；全局覆盖显示不完整，不能把失败组合计为无货或把本轮标为完整成功。
- 采用有界并发、PostgreSQL 跨进程全局限流、任务请求预算和分级恢复，具体规则见下节。全局限流器继续遵循项目初始 5 RPS、配置上限 10 RPS；这不是 Apple 允许的调用额度，也不要求任务持续跑满。验证／恢复阶段用更低的任务发起预算，建议不超过 1 RPS、并发不超过 2；不修改现行规范默认值。

## Apple 风控与采集可靠性

### 前置结论与已有证据

风控处理是本模块的核心交付条件，先验证能否持续获取有效数据，再确定全国刷新周期；不能用“有代理”“换了浏览器”或一次请求成功证明稳定可用。

- 当前参考路径是 Apple 购买流程使用的 `pickup-message` 库存查询端点；本轮没有取得 Apple 对该路径的第三方调用配额或服务稳定性承诺。库存接口与带订单身份的详情接口分别验证，不能相互推定成功率。
- 已重新阅读本地 PPSpider 历史记录：旧任务曾因 541、重复换代理和轮次重叠放大消耗，随后通过减少重复地域请求、延长间隔和互斥调度改善。这是历史单商品经验，不是当前全国多 iPhone 的验收结果。
- 当前 PPSpider 代码将全部 `429/5xx` 合并处理，不能直接复制为新模块的错误分类；AppleOrderMgr 现行规则要求 541 切换出口，新模块按该规则做受限切换，同时保留整体冷却与重试预算。
- [IANA 状态码注册表](https://www.iana.org/assignments/http-status-codes/)中 541 没有标准化定义；本项目将来自 Apple 路径的此类响应记为“疑似风控／拒绝”，保留脱敏诊断，不断言唯一原因是 IP 被封。429 的限流语义及可选 `Retry-After` 见 [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)。

### 请求规模、出口与会话

1. **先算请求成本**：按实际 SKU 批次和覆盖地域计算全轮请求数 Q，平均基础速率约为 Q／周期秒数，还要预留失败重试、手动查询和目录检查。示例仅用于预算：30 个 SKU、8 个覆盖地域、每请求 1 个 SKU，约 240 次／轮；300 秒约 0.8 RPS，60 秒约 4 RPS，后者尚未计算重试。真实地域数和多 SKU 批量能力需要实测，不能套用历史 6 个位置。
2. **减少重复请求**：合并同一时段的相同查询、按地域批量获取门店、有效支持时才合并 SKU；网页和多用户共享服务端结果。随机小幅错开请求启动时间，但不恢复逐订单固定串行等待。
3. **独立采集出口**：建议先验证一个库存专用主出口和一个备用出口的真实库存请求成功率；不通过员工浏览器、个人网络或已登录 Apple ID 承担常驻采集。独立出口需要实际网络路径核验，独立容器本身不代表出口隔离。
4. **保持受控请求上下文**：使用必要且一致的请求参数／头部；确需 Cookie 时只使用库存会话独立 Cookie 容器，不混用订单、付款或 Apple ID 登录会话。代理失效不能静默回退到业务服务器公共出口，不关闭 TLS 校验。
5. **统一预算**：自动、手动、重试、恢复探测及重定向都计入全局限流和小时／日预算；换出口、多开 Worker、服务重启不重置额度。单逻辑查询最多 3 次实际尝试，批次重试还受独立预算约束；建议全轮重试请求预算不超过基础 Q 的 20%，达到任一上限停止剩余重试。
6. **限制费用扩张**：记录请求数、代理提取／切换数、带宽和有效结果数；按清单与实测设定小时／日预算，达到上限暂停并告警。不得因风控自动无限提取出口或新增付费服务。

### 按错误类型处理

| 信号 | 处理方式 |
| --- | --- |
| Apple 429 | 识别为目标限流；有效 `Retry-After` 到期前不再请求受限路径；缺省时使用冷却与退避。不能通过换出口立即重试来清空限流状态 |
| Apple 路径 541 | 标记当前出口在该目标上需冷却，停止其库存派发；按现行项目规则改用已配置备用出口，但必须先经过目标级冷却，只做小样本探测。仍失败则进入全局暂停，不轮换大量 IP 连续请求 |
| 403、验证码／挑战页、登录或交互验证要求 | 暂停受影响数据源或配置并通知人工核查；不将页面当作库存、不自动解验证码、不把批量浏览器采集当作即时兜底 |
| 普通 500／502／503／504 | 单列为服务端／链路异常，尊重适用的等待指示并有限退避；不把所有 5xx 都认定为 IP 风控，持续异常同样降级或暂停 |
| 代理 407、提取鉴权或额度错误 | 暂停该供应商／出口并提示配置或额度问题，不通过不断换 IP 重试同一无效账号 |
| 已确认代理隧道／连接失败 | 标记出口不可用，在整体预算内切换健康备用；和 Apple 拒绝分别统计 |
| 普通超时／连接重置 | 原出口允许有限重试，超过预算再隔离排查；不因单次超时认定 Apple 风控 |
| HTTP 200 但 HTML、空结果、错误结构、SKU／门店不匹配 | 标记挑战／解析／覆盖异常，保存脱敏诊断；不得写成有货或无货，不因状态码成功就恢复正常状态 |
| 商品参数失效或目录变化 | 只隔离受影响 SKU，进入目录核对；与全站风控区分，不反复请求确定无效的参数 |

来源无法判定时记为“来源未确认的失败”，保存状态码、内容类型、耗时、请求编号及脱敏错误摘要；不记录 Cookie、代理密码或完整敏感头部。

### 降级、暂停与恢复

下面是待确认的首版保护参数，不是 Apple 官方阈值；应通过合成测试和真实试运行校准：

- **单次风险信号**：429／541 使受影响路径进入冷却，缺省至少 60 秒；若服务器给出更长有效等待时间，采用更长值。541 的出口切换不取消这段等待。
- **全局熔断（自动暂停）**：连续 3 次风险响应，或最近 5 分钟至少 20 次尝试且风险响应占比达到 20%，或 5 分钟内主备两个出口都出现目标拒绝时，暂停全部库存外部查询 10 分钟。手动“立即检查”同样受保护；页面仍可查看带时间标记的历史结果。
- **有限恢复探测**：以有效 `Retry-After`、目标冷却、出口隔离和全局暂停截止时间中的最晚时间为准，到期后在全局预算内最多做 3 个间隔请求，必须取得有效 SKU／门店库存结构才算通过。HTTP 200、代理连接成功或首页能打开都不够。
- **逐步恢复**：探测通过后按不超过 1 RPS、并发不超过 2 恢复；连续至少 3 个完整轮次且 30 分钟无风险响应后，才逐档恢复已批准周期，始终受全局上限约束。
- **恢复失败**：再次冷却 20／40 分钟；连续 3 次恢复探测失败后转为“需人工处理”，停止自动外部探测。显示原因与建议处理，不无限轮询或自动采购更多代理。
- **状态持久化**：冷却截止时间、失败计数、预算和暂停原因存入数据库，多 Worker 共用；进程重启不能绕过暂停。恢复时不追赶堆积的过期轮次，只按当前范围生成下一轮。

暂停和冷却是正常保护动作，但意味着监控存在空窗，应进入实际可用性指标，不能从验收分母中删除。采集预算不足时增加周期，不能把未采到的数据标成“全国成功”。

### 前台、数据与企微联动

- 显示“正常／降速／冷却／恢复探测／需人工处理”，附影响范围、最近成功时间、风险占比、当前速率、冷却截止时间和最近错误原因。
- 受影响组合立即显示异常；旧有货／无货只作为“上次结果”。到期后标记过期，停止依赖这些旧结果生成到货通知。
- 因风控降速不能延长旧样本的有效期，让过期数据重新变新鲜；有效期基于成功采集时记录的正常周期，后续改周期只作用于新成功样本。
- 风控期间的历史和热力图显示数据缺口；恢复后的有货按“恢复后观察”处理，不凭空生成中断期间的补货次数。
- 当库存群通知已启用时，只在开始降级／暂停、升级为需人工处理和恢复时发送合并的运行告警。同一事件不逐请求刷屏，恢复只发一次；内容包含影响范围、最后成功时间、下次恢复动作。仍使用库存专用群，不借用现有订单群。

### 数据源验证是开发前置工作

先验证少量明确 SKU 的有效有货／无货响应，再扩为固定的全国多 SKU 清单；按 300 秒候选周期和低任务预算开始，测量实际首发成功率、有效 SKU×门店覆盖率、429／541 比例、数据新鲜度、轮次耗时和代理成本。不能通过无限重试只展示“最终成功率”。

全国固定范围稳定性观察由原建议 24 小时调整为**至少连续 48 小时**，覆盖白天与晚间；生产机、出口和真实计划商品应与拟上线方案一致。保护行为通过合成故障注入验证，不刻意提高对 Apple 的负载以制造封禁。

如果需要持续大量换 IP、频繁人工验证，或在可接受周期与成本内仍无法稳定覆盖，就先交付“数据源验证未达标”的明确结论及证据，调整周期／出口／数据接入方案。不能把界面开发完成当成库存监控已交付，也不能在验证前保证解决所有 Apple 风控。

## 库存与统计口径

库存含义是“该 SKU 在该门店本次查询可取货”，不是精确剩余台数；最近成功的有货结果也不保证下单时仍有货。

| 数据类型 | 口径 |
| --- | --- |
| 最新状态 | 最新有效结果为有货／无货；首次未成功、异常或过期明确标记。未启用监控与不支持查询单独展示 |
| 有货检测记录 | 一次有效采集观察到可取货；同一轮同一 SKU、门店的重复返回不重复计数；持续有货可以有多次检测记录 |
| 到货变化事件 | 同一 SKU、门店从有效且未过期的无货结果转为有货；持久化去重，不因多页面、多任务或重试重复计数 |
| 首次／恢复观察 | 没有有效基线、暂停恢复或长时间失联后首次看到有货，单独标记；不能称为已确认发生一次补货 |
| 事件时间 | 系统发现时间，按北京时间显示；不是 Apple 实际放货时间 |
| 当前有货门店 | 当前筛选内至少一个配置有新鲜的有货结果，按门店去重 |
| 历史有记录门店 | 所选时段内有过有效有货记录的门店，不能代替当前有货门店 |

数据超过**成功采集时记录的 2 个正常检查间隔**没有成功刷新时标记过期；因风控临时延长调度不改变旧样本有效期。暂停监控立即标记已暂停，最后结果作为历史参考。一次失败即显示查询异常；即使旧结果尚未超过时限，也要同时展示失败与最后成功时间。

统计默认采用“到货变化事件数”，可切换“有货检测记录数”，两类不混加。首次／恢复观察单独统计，用户可按来源过滤。小时、配置、热力图、城市榜、门店榜共用筛选与口径，必须能回查明细。

热力图支持 10／20／30 分钟及 1 小时时间桶。所有图表标明采集覆盖情况；未监控、失联和缺数据的时段显示缺口，不补成 0 次，也不推算销量、库存数量或精确在库持续时间。榜单只反映本系统实际观测，不表述为购买成功概率。

## 独立企业微信群提醒

### 接入方式

- 一期使用一个专门的企业微信内部库存群及独立机器人 Webhook，目标群名称由用户确定；建群与机器人配置在实施后的接入阶段完成，本轮不执行。
- 库存通知拥有独立配置、开关、队列、限流与投递记录，和现有订单通知隔离；不替换现有订单群，不改变其消息格式或发送顺序。
- 默认提醒全部启用范围的到货变化，可按城市／门店／型号／容量／颜色限制群提醒范围；这是全局通知设置，不建立用户订阅体系。
- 建议 24 小时采集并提醒；可配置仅提醒的静默时段，静默期间继续采集与统计，过期消息不在静默结束后集中补发。
- Webhook 在后台加密保存、不回显；测试消息与正式到货消息分别标识。上线后先向新群发送一条明确的合成测试消息，核对群内收到后再启用自动提醒。

### 触发与防刷屏

| 场景 | 建议行为 |
| --- | --- |
| 首次启用且已有货 | 首轮完成后发送一条“初始库存摘要”，数量多时按长度拆分；不逐项冒充新到货。部分成功则标记覆盖未完整 |
| 有效无货转有货 | 创建一个到货事件并排队提醒；连续有货不重复触发 |
| 有货转无货 | 留历史，不发普通群提醒；此后再明确转有货可创建新事件 |
| 暂停／过期后恢复有货 | 汇总提示“恢复后检测到有货”，不计为确定的到货变化；连续短暂失败后恢复原有货不重复提醒 |
| 手动与自动同时发现 | 共用状态判断与事件唯一性，最多登记一次，不分别推送两条 |
| 停用通知后重新启用 | 从启用后的新事件开始，不回放停用期间历史；可手动查看当前库存摘要 |

同 **10 秒窗口**的到货事件按城市／门店合并商品行；超长内容分批并带详情链接。建议沿用现有发送实现的保守速率，每个库存机器人最多约 18 条／分钟，测试与重试计入；这是本系统建议值，接入时复核官方限制。全国大量到货时展示队列积压，不承诺无限吞吐。

发送前读取最新本地库存：明确已无货、暂停、数据过期，或事件超过 **120 秒**的普通到货消息跳过并记录原因。120 秒为建议通知有效期，可配置；实时采集与推送压力测试后再确认。企微超时或回执丢失标记结果未知，不盲目重发；只对明确未发送成功、且仍在有效期内的失败做有限重试。接口接受不等于群内已读。

消息示例（模板示意，非真实库存）：

```text
【iPhone 到货提醒】
城市：上海
门店：Apple 浦东
商品：<型号> · <容量> · <颜色>
状态：检测到可取货
发现时间：2026-10-02 14:32:08（北京时间）
取货提示：<Apple 原始提示>
详情：<AppleOrderMgr 库存详情链接>
```

一个批次可包含多个商品行。详情链接打开后需要现有系统登录；只放商品和门店信息，不包含订单、客户或付款资料。

## 项目接入与数据保存

- 前端增加独立库存模块，建议入口 `/inventory-monitor`；使用现有登录、权限、标准按钮／表格和 H5 导航，默认只对管理员开放。
- Express API 负责查询与配置，PostgreSQL 保存目录、监控计划、采集轮次、最新快照、检测历史、变化事件、汇总和通知投递；具体表结构与接口在方案确认后先更新权威文档，再执行正式 Migration 和实现。
- 新增独立库存采集 Worker 与库存通知执行链路，通过显式 profile 启动。当前源码中的官网订单爬虫与代理模块已经下线，本功能不恢复旧订单刷新链路；当前规范要求的限流及所需代理能力须在库存模块中独立实现和验证。
- 可评估复用已有企微底层发送、校验、加密和结果分类，但不能直接复用单一订单通知配置／队列；库存任务不影响订单邮件、付款、AOS 或现有通知的运行。
- PPSpider 现有 `pickupDisplay`／SKU 解析实现只作为参考；库存能力最终接入本项目，不依赖旧 Mac mini 调度是否运行。跨地区结果、门店覆盖和新商品需要重新验证。
- 建议检测明细保留 7 天、变化事件与投递记录保留 90 天、小时级统计保留 365 天；较旧统计页面标明明细已超保留期，不能提供虚构下钻。超过 90 天仅提供已保存的小时粒度汇总，不展示虚构的 10／20／30 分钟分布。到期策略可配置，实施前按实际日增量校准容量。
- 数据量估算采用“启用 SKU 数 × 门店数 × 每日检查轮数”，不能按商品型号数估算。优先保存必要结构化数据，对无变化状态使用时间桶汇总，避免长期保存全部原始响应。

## 实施顺序与验收

所有阶段均属于本期计划，数据分析和全国榜单不因分阶段开发被删去。

1. **数据源与风控验证**：先用最小验证采集器固定首批 SKU 与全国门店清单，验证有货、无货、不支持、超时、部分失败、重复门店及 SKU 一致性；完成限流预算与保护规则的合成测试，再做至少 48 小时固定全国范围观察，确定可持续间隔及成本。此阶段未达标，不把全国监控作为可交付能力。
2. **基础闭环**：正式数据结构、独立采集、全国列表、任务配置、历史和运行状态；实现重启恢复、过期标记及覆盖审计。
3. **独立企微提醒**：独立配置／队列、变化事件去重、合并、过期跳过、失败分类；先模拟验收，再验证新群真实送达。
4. **统计与双端验收**：完成全部图表／榜单、筛选下钻及导出，验证 PC 与 375px H5 的完整流程。
5. **全量试运行与发布验收**：完整系统对明确启用的全量组合连续运行至少 48 小时，记录首发与重试成功率、覆盖、P50／P95 轮次耗时、数据年龄、风控／代理失败率、冷却时长、费用、队列延迟及存储增量；发布后单独验证真实数据与群内送达。前置数据源验证与完整系统验收分别留证，不能用单商品旧记录替代。

建议验收标准：

- 配置清单覆盖大陆所有目标直营店及全部启用 SKU；不能因为接口少返回门店而缩小分母。未验证项逐项列明，不能标记为全国完整覆盖。
- 已知有货／无货样本与同时间附近的官方查询结果一致；窗口间发生变化时记录时间差，不能只用 HTTP 200 判断成功。
- 全量至少 48 小时试运行中，至少 95% 的计划轮次完成全部目标组合，轮次 P95 耗时不超过选定正常检查间隔；风控冷却／暂停导致的计划未完成继续计入分母，不能删去失败或缩小范围。另报告首发成功率与新鲜组合占比的时间分布；未达标时先调整或提交实际可持续间隔确认。
- 风控专项覆盖：429 等待指示、541 冷却后受限切换、403／挑战页、普通 5xx、代理鉴权／链路错误、200 伪成功、重试预算耗尽、多 Worker／重启保持冷却、手动请求不能绕过、恢复失败停止探测、降速不把旧数据变新鲜。保护测试使用合成响应；真实运行独立报告是否触发过各类保护，不虚称全部真实场景已发生。
- 网络失败、部分成功、过期、重启、同时手动／自动查询、通知停启及状态来回变化均有自动化回归；无货误报与重复事件是阻断问题。
- 通知高峰下遵守速率，持续有货不刷屏、已过期不补发、结果未知不盲重试；至少一次独立新群真实消息确认，不能以接口 accepted 替代。
- 同一筛选下图表、榜单、明细和导出一致；首次／恢复观察、重复观测与真实状态变化计数可区分；北京时区跨日边界正确。
- PC、375px H5 和短屏可完成查询、筛选、任务启停、历史／统计、群设置与错误恢复；现有订单、邮件、AOS 和企微订单通知回归通过。

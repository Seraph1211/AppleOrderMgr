#### 建议方案：官网不可用时仍可筛选（已批准并实现）

- 入库即依据 AOS／邮件已有商品生成独立的筛选标识和展示名，不等待官网抓取、不要求 `validation_status=valid` 或已有抓取时间。筛选只查询本地数据，不触发官网请求；付款任务仍遵循当前任务归属、权限和分配规则，不因可筛选而绕过分配校验。
- 明确的完整商品 SKU（如 `MJYD4CH/A`）优先作为同款归组依据。当前 AOS 校验只保证 `model` 非空，不能将任意系列名／通用型号直接当 SKU。名称仅作为标签与搜索别名；同一 SKU 的 AOS／官网名称归为一个选项。型号相同但商品属性明确冲突时标记待核对，禁止把冲突字段直接当作可信别名。
- 缺 SKU 时保留可筛选的名称回退项，仅归一化空白、大小写、明确容量单位等无歧义差异；不凭模糊包含、数组位置或剩余单项猜测同款。能够从本订单来源快照唯一且无冲突地匹配的才恢复已知 SKU，无法确定的保留独立选项并提示型号待核实。不能据此改写业务商品原值。
- 筛选标识与原始商品／官网展示名分开保存，名称变化不改变已选条件。无 SKU 项后续确认 SKU 时保留旧筛选键的受控映射；真实商品身份被官网纠正时显式提示变化，不为了维持结果而强行归入原商品。别名匹配必须落在同一商品项，不能将同一订单的不同商品拼成一次命中。
- 三页共用候选与匹配规则，服务端分页前筛选，同维度 OR、跨维度 AND；任一商品命中时订单只返回一次并保留完整商品明细、高亮命中项。候选按当前权限及其他条件从完整范围生成，移除 5000 单截断，排除自身已选商品条件；选项数量以去重订单／任务数计。别名及计数同样遵守权限，不能通过全局商品目录泄漏其他范围的数据。

## 一、背景与总体判断

当前项目已经实现了后端 API、用户认证、Apple ID 与取机人管理、订单管理、邮件监听与解析、Apple 官网爬取、自动刷新、仪表板、渠道管理、Excel 导入、前端管理页面及基础部署文件。

项目现阶段的主要矛盾不是“功能数量不足”，而是以下问题尚未收口：

1. 仓库中存在真实敏感数据和硬编码凭据，安全风险高于普通功能缺陷。
2. 状态枚举、接口字段、数据库迁移和前端调用之间存在多处契约不一致。
3. 部分页面仍使用 Mock 数据或演示逻辑，不能代表真实业务结果。
4. 邮件和爬虫主链路已有实现，但缺少可靠补漏、失败重放、并发控制和持久化调度能力。
5. 测试、Lint、构建、依赖锁定、部署和文档没有形成统一质量门禁。

因此，本计划坚持“先止血、再修主链路、随后重构、最后扩展”的顺序。现阶段不建议推倒重写，也不建议在关键契约修复前继续增加大量页面或业务字段。

## 二、优化目标

### 2.1 核心目标

- 清除仓库中的敏感数据暴露，建立凭据、隐私字段和权限治理基线。
- 修复已确认会阻断新增、编辑、导入、导出、筛选和订单刷新的问题。
- 建立统一、可追踪的 API、状态枚举和数据库迁移契约。
- 使“邮件到达 → 解析 → 入库 → 官网同步 → 前端查询”形成可重试、可审计、可验证的闭环。
- 将 Web API、邮件监听和爬虫调度的运行职责逐步解耦。
- 建立可复现安装、自动测试、构建、迁移和发布门禁。
- 修订文档，使文档、代码和实际运行状态保持一致。

### 2.2 本计划暂不包含

- 未经需求确认的新业务模块。
- 大规模 UI 改版或品牌视觉重做。
- 移动端、小程序或多租户能力。
- 为追求技术新颖而全面替换 Express、React、PostgreSQL 或 Sequelize。
- 未经单独审批的生产数据迁移、生产凭据轮换、生产发布和历史数据清理。

## 三、执行原则

1. **安全问题优先**：P0 安全问题未关闭前，不继续导入真实账号、密码、身份证或邮件数据。
2. **权威文档先行**：涉及表结构或 API 契约的变更，先更新 `database/数据库架构.md` 或 `design/API设计.md`，再修改代码和测试。
3. **迁移优先于自动同步**：数据库结构只通过正式 Migration 演进，正常开发和部署不依赖 `sequelize.sync({ alter: true })`。
4. **单一契约**：状态枚举、字段命名、错误码和分页格式集中定义，前后端不再各自硬编码。
5. **小步交付**：每批变更只解决一个可独立验收的问题，避免安全整改、架构重构和业务扩展混在同一批次。
6. **证据分层**：单测通过、构建通过、接口联调、测试环境业务验收和生产验收分别记录，不互相替代。
7. **可回滚**：数据库迁移、凭据轮换、调度切换和部署变更都必须有回滚方案。

## 四、优先级定义

| 优先级 | 含义                                     | 处理规则                     |
| ------ | ---------------------------------------- | ---------------------------- |
| P0     | 已存在数据泄露、越权或可能造成不可逆损失 | 立即处理，阻断其他开发和发布 |
| P1     | 核心业务无法完成或会产生错误数据         | P0 后优先完成，阻断业务验收  |
| P2     | 可靠性、架构、性能和可维护性问题         | 在核心业务恢复后分批处理     |
| P3     | 文档、体验和一般工程优化                 | 不阻断业务，但纳入质量收口   |

#### 数据迁移门禁

1. 迁移前生成备份并在隔离环境验证可恢复。
2. 对存量数据运行只读预检，统计异常值但不输出隐私原文。
3. 在测试数据库执行 `up → 校验 → down → up`。
4. 记录预计锁表时间和受影响行数。
5. 生产迁移与应用发布分别审批，失败时优先停止继续写入而不是强行推进。

## 六、目标架构

建议在不改变主要技术栈的前提下逐步演进为：

```text
邮件服务器
    │
    ▼
邮件 Worker ──► 持久化任务/失败队列 ──► 订单领域服务
                                         │
Apple 官网 ◄── 爬虫 Worker ◄─────────────┤
                                         │
                                         ▼
前端 ──► Nginx ──► Web API ─────────► PostgreSQL
                         │               │
                         ├──────────────► 文件/对象存储
                         └──────────────► 指标、日志与告警
```

职责边界：

- **Web API**：认证、授权、查询、人工操作和任务提交，不直接承担长期监听任务。
- **邮件 Worker**：连接邮箱、过滤、解析、幂等入队和失败重放。
- **爬虫 Worker**：代理、限速、抓取、解析、校验和结果提交。
- **订单领域服务**：统一执行状态转换、数据权威性和写入规则。
- **持久化任务层**：保存任务状态、重试次数、租约和失败原因。
- **文件存储**：保存付款截图等二进制文件，数据库只存元数据。
- **可观测性层**：统一请求 ID、任务 ID、结构化日志、指标和告警。

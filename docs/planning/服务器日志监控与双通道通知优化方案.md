## 目标和已确认范围

保留现有邮件通知，在服务器监控中增加独立的企业微信群通道。两条通道可以单独开启，也可以同时开启；共享告警事实和人工处理状态，分别安排发送时间、记录结果及重试。

用户已确认：本次提供的新群接收服务器／实例异常、恢复和监控健康通知；AOS 放货提醒继续发送到原库存群。新群不自动订阅订单、付款、库存到货或放货信号。Webhook 已由用户提供，作为部署配置密钥处理，本文和仓库不保存其明文或可调用链接。

本地 `main` 已包含 2026-10-19 的 AOS 放货提醒：首次立即、后续三分钟汇总、首条不重复计入摘要、一个空窗口后重新开始。该能力已在发布记录中标记启用，本轮未重新检查线上状态。实施须保留它的独立开关、库存群目标和现有规则；本方案的异常提醒频率不覆盖放货提醒。

首期在现有“服务器监控 → 通知设置”中完成双通道配置和统一投递列表。跨订单、库存模块的独立“通知中心”列为后续工作，避免把新增一个告警通道扩大为全部业务重写。

## 现状和需要修复的问题

| 项目 | 已核对的现状 | 方案处理 |
| --- | --- | --- |
| 日志与规则 | 完整日志保留 90 天；关键词规则支持任一／全部、排除词、窗口、阈值和级别；有效扫描连续两次不命中可恢复 | 保留检测口径，新增通知路由和健康事件；规则恢复只表示条件解除 |
| 邮件频率 | 严重立即、警告延迟 10 分钟合并、提醒下一整点、恢复延迟 10 分钟 | 保留原节奏，补可靠性、状态查询和人工重试 |
| 收件人变更 | 待发记录保留旧 `recipientSnapshot`，只改收件人不会取消旧队列 | 目标版本隔离；变更收件人取消尚未出站的旧目标任务，不把旧消息转发给新收件人 |
| 邮件重复风险 | 五分钟超时的 `sending` 直接回到 `pending`，无法区分 SMTP 已接受后的进程崩溃 | 增加租约、出站标记和 `unknown`；明确未发送才自动重试 |
| 邮件失败处理 | 重试耗尽后失败，页面没有人工重试、队列积压和专属发送心跳 | 增加重试及取消操作、队列健康指标和告警 |
| 恢复关联 | 邮件恢复事件独立入队，未限定原告警已经通知；短暂异常可能只发恢复 | 按事件、通道和目标记录通知关联；只为已接受或结果未知的原告警发送恢复 |
| 检测故障 | 设备离线、缺文件、读取／解析失败、规则未同步主要靠页面查看；长期无新增日志未检测 | 持久化健康事件，按下文观察窗口和运行时段通知 |
| 推送进程 | 监控邮件发送依赖邮件 Worker；API readiness 只证明 API 和数据库可用 | 独立监控通知 Worker 和健康指标；再增加独立进程看门狗 |
| 轮询审计 | 操作审计等待数据库写入后才结束响应，普通监控查询也会写入 | 将机器轮询从业务审计中排除，保留敏感读取和用户写操作 |
| 企微复用能力 | 订单企微已有加密目标、租约、未知结果、人工重试及限速；库存还有健康事件降噪 | 复用底层传输与可靠性规则，各业务事件和队列保留独立语义 |
| 机器人限速 | 订单与库存预算分别维护；相同机器人若被多个模块配置，模块限速可能叠加 | 增加按实际机器人身份共享的数据库发送预算 |
| 日期状态 | `dates` 校验格式和数量，但未与服务端查询窗口分离 | 本机发现日期不等于可查询日期；展示取保留窗口交集，不因旧客户端报告历史日期拒收整批状态 |
| 容量和清理 | 90 天真实累积容量仍缺验收；操作审计与订单企微历史未发现明确的清理任务 | 增加有界统计、容量预警和保留政策；不根据旧行存储基线推断当前生产存储模式 |

## 通知内容和默认频率

### 通道规则

| 事件 | 企业微信群建议默认值 | 邮件建议默认值 |
| --- | --- | --- |
| 严重告警首次触发 | 立即入队；正常负载下入队后 30 秒内首次出站 | 延续立即发送 |
| 警告首次触发 | 从该服务器首条事件起固定 3 分钟合并；后续事件不延后窗口 | 延续固定 10 分钟合并 |
| 普通提醒 `info` | 默认只在站内显示；可打开下一整点摘要，仅非空时发送 | 延续下一整点摘要 |
| 严重告警持续 | 首次接受／未知后 15 分钟提醒一次，再间隔 30 分钟，之后每 60 分钟一次 | 默认不增加周期重复，保留首次和静默到期提醒 |
| 警告持续 | 首次接受／未知后每 60 分钟一次 | 默认不增加周期重复 |
| 告警恢复 | 检测已恢复并保持 2 分钟后合并发送一次 | 延续恢复后 10 分钟合并，但增加原告警通知关联 |
| 人工静默到期仍异常 | 按新鲜状态发送一次；同一时刻的周期提醒合并 | 延续一次到期提醒 |
| 每日运行摘要 | 可选，默认关闭；开启时每天北京时间 09:00 一条 | 首期不新增定时报表 |

“立即”从服务端有效事件落库起计算；日志产生到被采集仍受现有扫描与同步周期影响。外部网络异常、机器人限流和告警风暴须明确展示排队原因，不承诺所有场景 30 秒到群。

持续提醒只对当前仍异常、观测新鲜、未人工静默的事件生效；计时与已发送次数持久化，Worker 重启不清零。`unknown` 后的周期消息必须标为新的“持续异常提醒”，不能偷偷重试原消息。失败／未知投递另外进入待处理列表。

关键词规则的检测级别不由通知次数自动升级。确需把持续警告升级为严重时，应有单独可配置规则及验收。

### 降噪和聚合

1. 采用现有实例＋规则的一次异常周期作为事件身份。持续命中只更新当前窗口次数，不每行推送，也不把重叠窗口次数相加成“累计错误数”。
2. 合并键包含通道、目标版本、服务器、严重级别、事件类别和窗口。不同目标、首次告警与恢复不混成一条；到点后窗口固定封闭。
3. 首次已经立即通知的事件不再作为“新告警”放入下一摘要。恢复与持续提醒都引用同一事件编号。
4. 合并窗口内自行恢复、且该通道从未接受／未知的告警，不再发异常或孤立恢复；站内保留短暂异常记录。
5. 同一设备离线时先发设备级事件，合并列出受影响实例；暂缓派生的实例缺日志／规则未同步提醒。设备恢复后用新观测重算，避免逐实例爆发。
6. 同一群 60 秒内出现超过 5 个不同异常事件时进入聚合模式，后续最多每分钟一条故障摘要；连续两个一分钟窗口低于阈值后退出。当前严重事件排在摘要前部，详情全部保留在网站。
7. 本监控通道所有实际请求默认最多 6 次／滚动 60 秒，测试与重试也占额度；同一机器人所有业务总计最多 18 次／滚动 60 秒，出站间隔至少 3334 毫秒。聚合及限速不删除事件，页面显示合并数和等待原因。
8. 待发的严重新事件优先于普通摘要；业务内部既有顺序保持。共享机器人预算需具备公平调度，避免一个高频模块长期饿死其他模块。

建议全天 24 小时接收严重和警告通知，不默认静默凌晨时段。保留实例人工静默 15／30／60／120 分钟、延长和提前结束，作用于邮件与企微的实例业务告警。静默不会隐藏网站记录，也不屏蔽通知 Worker 故障。静默到期只判断当前状态，不批量补发历史。

### 健康事件

| 事件 | 触发条件建议 | 恢复条件和限制 |
| --- | --- | --- |
| 设备失联 | 已启用设备连续 3 分钟没有有效在线心跳，严重 | 连续 2 分钟收到有效心跳；展示最后心跳及受影响实例 |
| 监控报告中断 | 设备在线，但启用实例超过 3 分钟没有新鲜扫描结果，警告；持续 10 分钟升级严重 | 连续 2 分钟新鲜有效扫描 |
| 读取失败／解析失败／超限 | 状态持续 2 分钟，警告；持续 10 分钟升级严重 | 有效扫描连续正常 2 分钟；历史累计错误数不作为当前故障条件 |
| 缺文件 | 在已配置运行时段内持续 5 分钟，警告 | 文件存在且扫描恢复；跨日轮转有 3 分钟宽限 |
| 规则未同步 | 最新规则发布后 5 分钟仍未得到匹配版本的有效报告，警告 | 新版本有效报告连续正常 2 分钟 |
| 上传积压 | 待上传大于 0 且持续 5 分钟无确认进展，警告；持续 15 分钟严重 | 有确认进展且稳定 2 分钟；正常历史补采不因队列非空告警 |
| 程序长期无新日志 | 默认关闭；为应持续运行的实例开启后，在运行时段内源文件连续 10 分钟无追加，警告 | 重新观察到可信源文件追加；扫描健康和补传完成是前置条件 |
| 通知发送异常 | Worker 心跳超过 90 秒、严重事件最老待发超过 2 分钟、一般待发超过 10 分钟 | 心跳与队列恢复稳定 2 分钟；只按一次故障周期提醒 |

已停用、已移除、维护中的设备／实例不产生运行故障。新加入或刚启用监控的实例有 3 分钟初始化宽限；宽限结束仍未上报应显示“未就绪”，不能显示正常。

健康时间以服务端接收时间和单调前进的扫描序号／报告身份判断，历史补传和未来设备时间不刷新在线健康。仅凭当前 `observedAt` 不能防止时钟偏差，需补接收时间和有效进展字段。

“无新日志”需要采集器提供源文件最近追加观测和扫描完成状态，不能用“最近收到历史日志的时间”代替。旧版不支持时显示“检测能力未接入”，不开启该规则；此项在采集器兼容升级阶段交付。

### 消息格式

按2026-10-19用户反馈，监控通知改用 `text` 纯文本，避免当前微信入口对Markdown显示“不支持此消息类型”。正文不超过2048 UTF-8字节，字段分行，完整HTTPS详情链接单独成行。超长时优先省略低优先级明细并显示剩余条数，保留事件编号、关键时间和完整网站链接，不增加拆条请求。限制按字节校验，不能用字符数代替；机器人共享预算和聚合频率保持。参考[企业微信消息推送配置说明](https://developer.work.weixin.qq.com/document/path/91770)。

恢复标题改为“恢复通知 · 告警条件已解除”，明确仅对应规则恢复，显示解除时间；持续提醒、当前摘要、风暴摘要分别显示“异常仍在持续”“当前异常汇总”“集中告警汇总”。邮件能力、恢复判定、原库存群及投递状态机制保持。

消息只发送服务器别名、实例别名、规则显示名、聚合计数、时间、事件编号和系统详情入口；不附原始日志、账号密码、代理认证、付款链接或完整身份信息。自定义名称也要清理控制字符、Markdown 标记、URL 和敏感格式，避免将凭据或伪造提及带入消息。网站详情链接只使用受控 HTTPS 源和非敏感事件 ID，继续要求登录及权限，不带访问令牌。

默认不 `@所有人`。后续如启用值班人提及，仅用于严重告警首次及一次升级；使用受控成员名单，普通名称不能生成 `<@...>`。首期不增加群内确认／处理按钮，用户进入网站完成处理，避免把 Webhook 发送能力误当作双向回调能力。

每日摘要若启用，包含过去 24 小时新异常／恢复数、当前未解决数、失联实例数和双通道失败／未知数；明确统计事件而非日志行，不宣称“全部正常”时忽略未知实例。

## 投递可靠性和配置行为

事件落库与待发登记保持同一数据库事务，外部发送在事务外完成。邮件与企微使用独立任务和独立通道执行循环；一边失败、暂停或限流不影响另一边。

| 状态 | 页面含义 | 自动处理 |
| --- | --- | --- |
| `pending` | 排队中，显示计划时间及等待原因 | 到期且通过最新状态校验后领取 |
| `sending` | 已领取，显示开始时间 | 租约和领取令牌限制并发 |
| `accepted` | 对方接口／SMTP 已接受 | 不等于用户已读或最终到达邮箱 |
| `unknown` | 已开始出站但结果无法确认 | 不自动重发原消息，人工核对后确认可能重复才重试 |
| `failed` | 明确拒绝、参数错误或安全重试用尽 | 可人工重试；永久配置错误先修复目标 |
| `skipped` | 已恢复、已静默、目标变更、失效或人工取消 | 保留原因，不复活旧任务 |

持久化 `leaseToken`、`leaseUntil`、`dispatchStartedAt`、尝试次数及版本。领取后未出站的过期任务可回到待发；已经标记出站的过期任务转未知。设置关闭和出站授权在事务内串行核对，已进入网络请求的任务继续记录真实结果，不伪称已撤回。

企微只对明确未连接或明确限流自动重试，最多 3 次重试：未连接退避 10／30／60 秒，限流每次至少等待 60 秒，均受共享预算及事件有效性约束。超时、连接重置、无法解析回执、出站后的进程崩溃按未知处理。明确目标无效暂停该通道，网站和另一健康通道报告一次。

邮件保留总计最多 5 次尝试及 1／5／15／60 分钟退避，但仅在能够确认未被 SMTP 接受、且属于临时故障时自动执行。永久拒绝直接失败；SMTP 可能已接受却丢失回执时转未知。多收件人的部分接受要逐收件人记录结果，只重试明确未接受的地址，不能因一个地址拒绝向全部地址重发。

人工重试校验最新版本、目标、开关和事件状态；已恢复的首次异常、旧目标和已停用通道不允许重发。每次尝试附固定错误码和脱敏摘要，不保存 Axios 原始错误对象或 SMTP 认证内容。

启用企微只订阅启用后的事件；不扫描 90 天日志补发。提供单独的“发送当前异常摘要”操作，展示预览后一次入队，便于接入时了解存量。通道自动开关关闭时也允许发送固定合成测试，测试请求用唯一 `requestKey` 去重。

替换机器人必须先停用该通道；变更邮件收件人则原子生成新的目标版本，取消旧目标未出站任务。群名称等纯展示变更不换目标身份；频率变更只重新计算尚未出站且仍有效的任务，不能跨旧新策略混合批次。重新开启不复活已取消任务，不把旧群消息转移到新群。

初始告警及周期提醒在出站前复核新鲜状态、规则版本、实例状态及人工静默；不可用观测转健康事件，不用旧关键词命中冒充当前异常。超过计划时间 10 分钟的企微待发消息取消旧内容，若异常仍有效，则生成最多一条“服务恢复后的当前异常摘要”；恢复消息超过 30 分钟只留站内。邮件待发最长保留 24 小时，发送前同样复核，不能无期限排队发送陈旧异常。

恢复关联按通道和目标分别建立。旧群已收到异常不使新群自动收到恢复；某通道首次告警失败且未被接受，不为该通道发孤立恢复。`unknown` 关联的恢复应标注“原提醒回执未知”。规则停用、实例移除或配置变化使用“已终止”记录，不冒充业务恢复。

## 技术和页面设计

### 服务和数据演进

优先演进现有监控通知表和服务，并复用企微传输安全校验。订单与库存的业务队列、模板、开关和聚合窗口保留；只抽取经过回归的传输、租约和机器人预算能力。

| 对象 | 规划变化 |
| --- | --- |
| 监控邮件设置 | 保留现有设置；增加目标版本、策略版本及测试结果，SMTP 凭据继续由现有服务端配置管理 |
| 监控企微设置 | 新增独立设置：开关、群名称、加密 Webhook、目标 ID、策略、版本、启用时间、测试和暂停状态 |
| 监控投递 | 增加 `channel`（旧记录默认 `email`）、目标版本、优先级、有效期、领取与出站字段；邮件增加收件人结果 |
| 通知事件 | 增加可跨通道关联的事件键；幂等约束包含事件键、通道和目标版本；周期提醒带持久化序号，避免原 `sourceKey` 唯一约束阻止另一通道入队 |
| 健康事件和观察状态 | 持久化故障周期、首次／最新观测、恢复观察、升级、维护范围和每通道通知关联 |
| Worker 状态 | 分别记录调度、邮件和企微执行心跳、最近成功、错误码、待发和最老到期时间 |
| 机器人发送预算 | 使用规范机器人密钥的服务端 HMAC 指纹归并真实目标，不以模块内随机目标 ID 当限流键；密钥本身不进入指标 |

新结构通过正式 Migration 演进，旧已发送记录保持原 ID、次数和时间，原 `sent` 展示映射为“SMTP 已接受”，不重发历史。迁移前核对旧 `sourceKey`，确保历史与新键不会重复登记。旧待发邮件仅在确认目标一致后承接；不确定的已领取旧任务转人工核对。

为服务器监控新增独立通知 Worker，邮件和企微有各自的有限并发与超时；邮件收信 Worker 继续负责收信。发布切换时停止旧监控邮件领取、等待在途完成或归类未知，再启用新发送者，使用数据库所有权／版本闸门避免旧新进程同时发送。

机器人预算在现有订单、库存及新监控传输调用处统一预约，同一真实机器人共享 18 次／滚动 60 秒，重启和多进程不重置。未完成共享适配前，新监控设置应阻止复用其他模块正在使用的机器人；不能假定本次新提供的 URL 一定与存量不同。

### 接口和权限

以下为目标契约，实施时先更新 [API 契约](../design/API设计.md) 和 [数据库架构](../database/数据库架构.md)，不将规划端点当作当前已可调用接口。

| 接口建议 | 用途 |
| --- | --- |
| `GET /api/server-monitor/notifications/channels` | 返回两通道脱敏配置、版本、测试状态与策略 |
| `PUT /api/server-monitor/notifications/channels/:channel` | 单通道保存，使用 `expectedVersion`；Webhook 空值保留，不回显密文 |
| `POST /api/server-monitor/notifications/channels/:channel/test` | 合成测试，携带 `requestKey`，返回异步投递 ID |
| `POST /api/server-monitor/notifications/channels/:channel/current-summary` | 显式发送当前异常摘要，支持预览和请求幂等 |
| `GET /api/server-monitor/notifications/deliveries` | 按通道、状态、设备、事件和时间筛选；每页最多 100 条，使用游标 |
| `POST /api/server-monitor/notifications/deliveries/:id/retry` | 版本保护；未知结果要求 `acknowledgeUnknown` |
| `POST /api/server-monitor/notifications/deliveries/:id/cancel` | 取消未出站任务，记录操作人和原因 |
| `GET /api/server-monitor/notifications/health` | 两通道心跳、到期积压、最老待发、未知／失败数及暂停原因 |

首期保留旧邮件设置、测试和历史接口作为兼容适配，内部调用同一服务；未传新字段的旧客户端不能清空企微设置。过渡完成后再另行决定旧接口退役。

保留已发布的 `monitor.logs.read`。新增 `monitor.notifications.read`、`monitor.notifications.configure`、`monitor.notifications.retry`：分别控制查看、配置／测试／当前摘要、重试／取消。管理员默认拥有；现有 `monitor.manage` 在兼容期派生这些权限，已有角色不意外失权。完整权限矩阵须覆盖 API，不能仅隐藏按钮。

Webhook 使用现有字段加密机制，限制官方 HTTPS 主机、固定发送路径、唯一 key 参数，拒绝重定向和任意外部地址。浏览器保存后只显示“已配置”和目标名称；预览接口不发送外部消息。通道健康读取不返回密钥、原始日志或收件人认证信息。

### 操作页面

保留“流量统计、实例监控、告警规则、通知设置”的主结构。通知设置中使用两行通道表格，分别显示启停、目标、策略、测试结果、最近接受时间和状态，并提供配置、测试和投递记录入口。

投递列表显示事件／批次编号、通道、目标名称、级别、状态、计划时间、尝试次数和失败原因；事件详情可并排查看邮件和企微结果。`unknown` 操作明确提示可能重复，`accepted` 不显示“用户已收到”。监控概览增加离线／采集异常／规则未同步等可筛选状态。

前台可见时每 15 秒刷新健康摘要，投递历史按需或每 30 秒刷新；后台标签页暂停普通轮询，回到前台立即刷新。刷新不覆盖未保存表单，冲突展示版本提示。PC/H5 使用项目现有蓝白表格样式及统一加载、空数据、失败和重试状态。

## 审计 容量和独立看门狗

轮询审计调整采用精确接口和用途清单：监控健康、概览、流量及投递列表自动刷新不记业务操作；登录、失败鉴权、配置、测试、重试、取消、敏感日志读取与导出继续审计。敏感日志查询必须留下访问记录，可按一次查询会话归并自动分页，但保留目标范围和页面计数。现有 API 对读取审计有约定，实施时同步调整，不能简单删除所有 GET 审计。

监控事件与投递终态保留 90 天。操作审计建议保留 180 天，订单企微投递终态建议 90 天；这些是新增治理建议，须按计划启用清理。活动事件、待发任务、未处置未知任务及其关联不按创建时间直接删除，先过期或人工处置再计保留期。清理每批最多 1000 条、每轮最多 5 秒，使用独立数据库锁，记录删除数、最早剩余日期和预算耗尽情况。

容量统计使用 PostgreSQL 系统目录与索引范围聚合，不全量读取日志正文。查看实际 `rows/shadow/blocks` 模式、日志／索引／回执占用、每日增长、清理进度及磁盘空间。建议磁盘剩余低于 20% 或按近 7 天增长预计不足 7 天时警告，低于 10% 或不足 3 天时严重；预计天数不足有效样本时显示未知。保持 90 天保留，不以新增群通知为理由缩短或删除生产日志。

独立看门狗分两层实施：独立于通知 Worker 的进程每 30 秒检查心跳与积压；另由独立于应用宿主机的探测器检查公开 readiness 和通知健康。通知进程停机时，进程看门狗使用独立备用投递记录和目标预算发送一次故障／一次恢复；整机、数据库或公网出口故障需要外部探测器自身的通道。后者需要部署位置和目标配置，列为后续交付条件，不能将同进程定时器视为整机故障保护。

健康告警自带来源和故障周期，限制递归：发送健康告警失败只更新原故障，不继续生成“健康告警发送失败”的无限链。邮件坏时优先企微、企微坏时优先邮件；两边都不可用时保留站内显著状态，并由外部探测器通知。

## 实施阶段与验收

| 阶段和任务 | 内容与依赖 | 通过标准 |
| --- | --- | --- |
| 第一阶段 `MON-NOTIFY-01` | 从最新发布基线实施；先同步设计、数据契约和 API，修复邮件目标版本、租约、未知结果、恢复关联和人工重试 | 旧邮件配置与节奏保持；换收件人不向旧地址出站；崩溃／回执丢失不自动重发；两通道事件键可独立去重 |
| 第一阶段 `MON-NOTIFY-02` | 新增企微通道、模板、聚合、持续提醒、共享限速及双通道页面；依赖 01 | 邮件或企微可单独开关；新群仅收已确认范围；合并窗口和优先级确定；Webhook 全链路脱敏 |
| 第一阶段 `MON-NOTIFY-03` | 独立监控通知 Worker、心跳和积压；上线前完成旧发送者切换 | 多 Worker 无双领取，重启不重置节流／提醒；一通道故障不阻塞另一通道；可诊断最老待发 |
| 同批治理 `MON-AUDIT-01` | 精确排除机器轮询、保留敏感审计、增加保留政策和有界清理 | 普通轮询不增加操作记录；写操作、失败鉴权和敏感读取仍可追溯；清理不会删除活动依赖 |
| 第二阶段 `MON-HEALTH-01` | 设备／采集／规则／积压健康事件、父子抑制、进程看门狗；依赖 01—03 | 稳定窗口、恢复关联、维护排除均通过；停止通知 Worker 可经备用路径报警 |
| 第二阶段 `MON-COLLECTOR-01` | 采集器补源文件追加与扫描进展协议，开启按时段的无日志检测 | 旧采集器兼容；补采、跨日轮转、时钟偏差、程序正常空闲均不误判 |
| 后续 `MON-OPS-01` | 外部探测器、容量预测、真实 90 天滚动清理与跨模块通知中心 | 应用／DB／整机不可用有独立验证；容量与清理以实际趋势验收；统一中心不改变现有业务通知规则 |

第一阶段是最小可发布版本；检测健康事件和无新日志能力分阶段启用，页面不能在对应采集与看门狗未交付时显示“已覆盖”。

实施验收至少覆盖以下场景：

| 范围 | 必测场景 |
| --- | --- |
| 频率与降噪 | 严重首次、固定三分钟合并、整点边界、持续提醒、跨午夜、空摘要、窗口内恢复、快速复发、人工静默及到期；重叠窗口计数不累计失真 |
| 配置与目标 | 单通道启停互不影响；旧客户端保存不覆盖新配置；目标变更与领取／出站并发；已停用目标不重试；测试幂等；启用不补历史 |
| 可靠性 | 事务回滚不发消息；领取前后和出站前后崩溃；明确限流、DNS 故障、超时和未知响应；SMTP 部分接受；迟到 Worker 回写不能覆盖新租约 |
| 限速与公平 | 多进程和不同业务配置同一机器人，任何滚动 60 秒不超过 18 次；监控自身不超过 6 次；重试／测试共用；订单 FIFO 和放货三分钟规则保持 |
| 恢复与健康 | 未发异常不发恢复；未知关联有说明；离线不假恢复；父设备故障不逐实例刷屏；规则变更不冒充恢复；未知观测不显示正常 |
| 安全与权限 | Webhook 明文不出现在响应、日志、审计、异常及测试快照；名称不能注入提及或外链；日志读取权限不授予通知写权限；详情必须登录 |
| 容量与性能 | 队列查询与清理使用索引及有界批次；无 N+1；最大摘要 UTF-8 字节校验；普通轮询不写审计；日志正文不被全量载入内存 |
| 迁移与回归 | 隔离数据库 up/down/up；历史投递数量与状态保全；有数据时 down 拒绝破坏性删除；邮件收信、订单企微、库存与 AOS 放货提醒不回归 |
| 页面 | PC、375px H5、短屏；保存冲突、输入草稿、失败／未知和重新加载；链接登录后能定位事件及对应日志 |
| 真实验证 | 经实施／发布阶段授权后发送明确标记的合成测试；分别记录接口接受和人工群内／邮箱收件确认，不互相替代；再观察 24—48 小时错误和积压 |

发布遵循[生产部署指南](../deployment/生产环境部署指南.md)：业务备份和隔离恢复排除 AOS 监控日志明细及原始文件，其他业务与新增通知配置／历史纳入；迁移先于新发送者启动。先验证迁移和只读页面，再验证邮件兼容、配置新群、执行合成测试，最后启用企微。机器人替换、自动启用和真实发送在实施／发布阶段执行，本规划阶段不调用用户 Webhook。

回退优先关闭新企微通道并保留新数据；新 Worker 停止出站后再切换经过兼容验证的旧邮件发送者。新增列／历史优先保留，不能直接运行会删投递事实的 down，也不能恢复整库覆盖上线后业务。已进入外部网络的任务按真实回执或未知保留，禁止回退时全量重置为待发。

## 本轮交付和下一步

本轮完成现状问题、已确认群范围、消息示例、频率、可靠性、接口／数据候选、实施批次和验收条件。邮件节奏兼容与新群范围为方案基础；其余建议参数在确认实施时作为可配置默认值落地。

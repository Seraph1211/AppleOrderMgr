## 使用前定位

在已确认的项目目录操作，先核对 Compose 服务和部署版本。本文命令面向 api、email-worker、crawler-worker，历史单容器名称不作为当前默认值。完整发布流程只在[部署指南](生产环境部署指南.md)维护。

## 只读检查

```bash
docker compose ps
docker compose logs --tail=100 api
docker compose logs --tail=100 email-worker
docker compose logs --tail=100 crawler-worker
curl -i http://localhost:3000/api/health/live
curl -i http://localhost:3000/api/health/ready
```

live 只说明 API 存活；ready 检查数据库，不能证明邮件、代理、官网同步可用。日志可能含业务信息，分享前脱敏。

## 定位顺序

| 症状          | 优先检查                                           |
| ------------- | -------------------------------------------------- |
| 前端打不开    | Nginx 静态目录、证书、前端构建版本                 |
| API 502       | Nginx upstream 与 API 3000 端口是否一致            |
| readiness 503 | DB_*、数据库连通性、TLS、迁移状态                  |
| 邮件未入库    | email-worker、IMAP 白名单、未读状态、解析/事务失败 |
| 官网未更新    | crawler-worker、自动刷新开关、代理、暂停和订单终态 |
| 导入令牌失效  | 是否超时、已消费、服务重启或跨 API 实例            |

## 受控恢复

先确定原因与影响，再在已有授权范围内仅重启受影响服务。例如爬虫问题已经处理后：

```bash
docker compose restart crawler-worker
```

独立 Worker 模式下 API 的恢复接口返回 409；重启只是进程操作，还需验证开关、代理及订单实际刷新。不要把 API 返回的日志观测状态当作 Worker 实时心跳。

数据库备份、恢复、密钥和敏感数据转换遵循[数据库指南](../database/数据库初始化与迁移指南.md)。磁盘问题先查项目日志和上传目录占用，再界定清理对象；本文不提供跨项目清空命令。

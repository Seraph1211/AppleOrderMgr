# 基于订单邮件的信息更新方案

> 状态：已生产发布并开启影子解析；订单应用、付款任务联动与历史回放均保持关闭。
>
> 最近核对：2026-09-21。
>
> 已确认范围：新增独立“订单状态”“付款状态”，仅根据官方订单邮件更新；获取门店和取货时间；确认已付款后自动完成付款任务；不判断已取货，不使用或交付电子收据。
>
> 验证基线：本地 HEAD `5daea97` 加当前工作树；生产 API、收单邮件 Worker 与订单邮件 Worker 为 `20260921-order-mail-lifecycle-shadow`。
>
> 验证范围：1,494 封生产归档原文分析、全邮箱 UID 对账、217 封取货邮件离线提取；生产备份恢复、Migration、影子开关、健康与页面只读技术验收。尚无真实新邮件影子解析业务验收。具体证据见[只读核对报告](../archive/2026-09/2026-09-21-订单邮件样本与收信完整性只读核对.md)和[生产发布记录](../archive/2026-09/2026-09-21-订单邮件生命周期影子解析生产发布记录.md)。

## 一、目标和范围

复用 vvv8.net 现有订单邮件归档，将同一订单的多封邮件合并为订单阶段、付款结果和取货安排。订单链接是否可抓取不再是这些信息更新的前提。

订单录入继续由 AOS／原建单邮件负责，生命周期邮件独立于 `email/aos` 建单开关。邮件先到而订单尚未录入时等待关联，不擅自创建没有归属的订单。

本期只判定订单已确认、处理中、可取货，以及是否已有付款确认依据。用户已明确邮件无法判断已取货，因此不提供邮件自动“已取货”结果，不根据预约时间已过、个人设置辅导或电子收据推断取货完成。退款、取消、配送等没有本轮有效模板依据的分支不纳入首批自动更新，相关疑似邮件保留待核对。

不更改账号密码、TAG、订单归属、人工付款人、备注、截图或结算记录。门店、日期和时段是本期核心字段；账单联系人不能直接当成取货人。

## 二、两个独立状态字段

| 页面名称 | 建议技术字段／数据库列                       | 首期状态                                                                                 |
| -------- | -------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 订单状态 | `emailOrderStatus`／`email_order_status`     | `unknown` 待确认、`confirmed` 订单已确认、`processing` 处理中、`ready_for_pickup` 可取货 |
| 付款状态 | `emailPaymentStatus`／`email_payment_status` | `unknown` 待确认、`paid` 已付款；`unpaid` 待付款仅在未来取得明确有效模板后启用           |

两个字段初值均为待确认。它们只接受官方邮件的解析结论，不能从官网字段、人工付款任务完成状态、AOS 或历史系统默认值回填。原 `status/paymentStatus/pickupStatus`、`official*` 和 `lastCrawledAt` 保留原官网含义，作为独立对照信息。

“待核对”是单独的证据质量标记：已有可靠值时保留并提示冲突，没有可靠值时维持待确认。可取货表示收到过可取货确认，不表示用户至今没有提货；页面应展示邮件证据时间。

## 三、真实邮件映射规则

标题用于识别候选模板，必须同时核对正文、订单号、商品范围和来源。不能在全文搜索“付款”“取货”“取消”等词就决定状态，正文底部的帮助说明和条件句不构成事件。

| 邮件类型                      | 当前样本 | 订单状态                       | 付款状态                         | 取货信息处理                               |
| ----------------------------- | -------: | ------------------------------ | -------------------------------- | ------------------------------------------ |
| 你的 Apple Store 在线商店订单 |      488 | 订单已确认                     | 待确认                           | 可保存初始门店和预约线索；不能据此标可取货 |
| 我们正在处理你的订单          |      402 | 处理中                         | 建议按当前预付到店流程判为已付款 | 可补门店／时段；空取货日期不覆盖旧值       |
| 关于你的 Apple 订单的更新信息 |      215 | 正文明确“已可取货”才更新       | 按同一预付流程判为已付款         | 提取正式门店、取货日期和到店时段           |
| 订单的取货信息                |        2 | 正文明确“已备好并可取货”才更新 | 按同一预付流程判为已付款         | 保存门店和营业时间内到店说明，不补造时段   |
| 电子收据、个人设置辅导、广告  | 本期排除 | 不更新                         | 不更新                           | 不参与取货信息提取                         |

### 付款判定依据

确认邮件明确说明“确认你的付款后，我们会开始处理你的订单”；处理邮件明确说明“你的订单正在处理中”。结合用户明确邮件可以判定已付款，本方案建议对当前已验证的预付到店模板采用“进入处理中或可取货＝付款已确认”的业务映射。

这是跨邮件流程推定，不是邮件逐字包含“已收到付款”。解析记录须保存所用规则、对应确认／处理／取货邮件及商品范围；不能扩展到未知模板、货到付款、部分付款或其他业务渠道。仅收到确认邮件时，正文中“如果你尚未付款”不是明确未付款结论，付款状态保留待确认。

同一订单没有匹配到预付业务依据、邮件真实性未通过验证、部分商品范围不明、出现冲突或未来未知取消／退款通知时，不自动完成付款任务，进入待核对。该细化映射在实现前作为明确业务规则定稿。

### 同一订单归并

每封邮件独立归档并保留解析结果；订单状态由该订单所有有效邮件归并，不以最新一封邮件的标题直接覆盖。迟到确认邮件不会将可取货改回已确认；设置辅导等无关邮件不会改变结果。

已验证模板支持 `confirmed → processing → ready_for_pickup`，缺少中间通知但取货正文与预付业务依据完整时可以直接进入可取货。已知付款证据不被旧确认邮件撤销；未发现付款邮件不等于未付款。新的实质矛盾进入待核对，不用状态排序掩盖冲突。

## 四、门店与取货时间

建议使用独立 `emailPickupInfo` 保存邮件取货信息，并让需要检索的日期具有结构化列或索引；正式结构在实现前进入数据库权威文档。

| 字段               | 来源与规则                                                              |
| ------------------ | ----------------------------------------------------------------------- |
| 门店名称           | 正式取货通知的“取货零售店”块，规范化为 Apple＋门店名；保留原文          |
| 门店地址           | 同一门店块的地址，不取账单地址或联系人地址                              |
| 取货日期           | 通知中的明确年月日；与邮件发信、接收时间分开                            |
| 取货开始／结束时间 | “到店时间”“取货时间”中明确的时段，AM/PM转换为24小时制                   |
| 到店方式           | 固定预约时段，或营业时间内到店；后一种不强行补具体时段                  |
| 时区               | 当前已核定中国大陆门店使用 `Asia/Shanghai`；其他地区需独立模板规则      |
| 保留说明           | “最长保留7天”等原文仅保存为说明，未明确起算点则不计算精确截止时间       |
| 证据               | 逐字段关联邮件 ID、邮件发信时间、实际收信时间、解析／应用时间和规则版本 |

正式取货通知是主要依据。确认邮件可提供“预约待确认”的初始信息，处理邮件只补明确字段；本次402封处理邮件的商品取货日期均为空，不能清空原预约日期。更晚的明确变更通知可更新原预约；新的营业时间内到店安排与原固定预约不一致时，要更新到店方式、撤销旧时段的当前有效性并保留历史，不能拼成混合安排。

“明天”等相对日期只有在模板参考时间及年份可唯一确定时转换，否则保留原文并待核对。邮件发送时间、收到时间不能代替预约或实际取货时间。不会生成 `pickedUpAt`，不会回填原 `actualPickupDate`。

用户指定订单 `W1688354674` 的更新邮件在北京时间2026-09-18 06:44:46发出，正文明确“已可取货”：

| 字段 | 结果                               |
| ---- | ---------------------------------- |
| 门店 | Apple 重庆北城天街                 |
| 地址 | 重庆市两江新区北城天街8号          |
| 日期 | 2026-09-18                         |
| 时段 | 16:00–16:15，原文04:00 PM–04:15 PM |

全部217封可取货通知完成离线提取：217封门店、215封确定日期／时段、2封营业时间内到店；这不是已实现的生产解析器验收。

### 多商品

真实确认邮件中452封列两条商品、每条数量1。首期必须逐项解析商品和数量，不能只取第一项，也不能把多封通知的商品数量累加。若整封明确针对整单且商品范围可与已有订单核对，可汇总为整单结果；部分商品、数量不符或无法确定对应关系时保留逐项证据并转待核对，不判整单可取货或已付款。部分履约扩展待真实样本后另行定稿。

## 五、收信、更新和防漏机制

```text
vvv8.net 邮箱
  → 后台只读收信并可靠归档
  → 持久化解析任务
  → 验证来源、订单号、模板和商品范围
  → 按订单归并多封邮件
  → 事务更新两个邮件状态、门店／预约信息、付款任务及审计
  → 页面自动获取最新结果
```

现有生产基础已核实：新邮件事件触发＋每30秒主动扫描，连接恢复立即扫描，失败后30秒重连，持久UID断点；不依赖网页是否刷新，不依赖未读标志。2026-09-21 04:28只读对账未发现现有回查范围内的可关联邮件漏归档，但仍需防范异常和业务处理积压。

| 层次     | 实施方案                                                                                                    |
| -------- | ----------------------------------------------------------------------------------------------------------- |
| 快速接收 | 复用独立订单邮件Worker和30秒扫描；原文与解析任务可靠保存后才推进接收游标                                    |
| 异常留存 | 疑似订单邮件解析失败、订单号冲突或数量不明时留存受限证据及原因；不只增加忽略计数                            |
| 任务恢复 | PostgreSQL持久任务、有限重试、租约和失联恢复；解析异常不阻塞正常接收                                        |
| 周期对账 | 建议每5分钟核对近72小时、每日核对近30天；按邮箱／文件夹／UIDVALIDITY／UID逐封核对，不按总数相减             |
| 范围治理 | 核实别名归集、路由和监控文件夹，各自独立游标；UIDVALIDITY改变或超长停机时建立有范围的恢复任务               |
| 业务补偿 | 扫描已归档未解析、已解析未应用、等待订单和任务关联的记录，补齐遗漏                                          |
| 独立监控 | 由独立监控方检查最后成功扫描、Worker存活、对账和最老待处理记录；建议90秒未扫描标红，持续3分钟或积压超时报警 |
| 页面更新 | 建议页面可见时每15秒拉取，切回立即更新；保留筛选、分页及未提交输入                                          |

对账分页限流，独立进度，不回退正常收信游标，不让历史扫描阻塞新邮件。旧邮件如果已在邮箱删除且从未归档，不能承诺恢复。正常条件下建议邮箱收到到业务应用P95不超过60秒，页面刷新延迟单独计量；该目标需要真实验收。

### 来源验证

本轮1,494封归档邮件均有DKIM签名，但无标准收件认证结果头，本次未密码学验签。实施时必须选定并验证可信收件服务认证结果或服务端DKIM验证；签名存在和From白名单不能视为验证通过。验证不足的邮件可人工核对官方邮件证据，不能自动触发任务完成。

唯一完整订单号用于关联，邮箱仅作辅助。主题、正文和可信链接号码矛盾时拒绝自动更新，不通过猜测或仅按邮箱关联。

## 六、数据库、API和付款任务联动

复用现有`OrderMailMessage`和邮件原文180天保留机制，新增解析任务／订单邮件事件；订单表增加两个邮件状态及配套证据、版本、取货信息和冲突标记。未知模板与人工核对状态不能混作业务结果。结构讨论定稿后先更新[数据库架构](../database/数据库架构.md)，再正式Migration（含up/down）、模型、[API契约](../design/API设计.md)及调用方。

### 已确认：邮件判为已付款后自动完成任务

同一事务完成以下操作：追加有效邮件事件、更新 `emailPaymentStatus=paid`、锁定并完成既有付款任务、记录系统完成来源和审计、递增相关版本。任务未分配或处理中均适用；已完成任务不重复变更完成时间。人工旧页面提交必须检测版本冲突，不能覆盖系统已确认结果。

保留原归属、付款人、截图和备注；系统完成时间与实际付款时间不同，没有实际付款时分则不补造。自动完成不是付款人业绩或内部结算确认。

邮件先到、订单或任务后到时，后续创建流程必须读取同一邮件结果，避免先派发待付款任务再补完成。按已确认业务流程为整单付款才触发联动，部分范围或冲突进入待核对。

订单列表、详情、付款任务、分配服务及直接SQL候选筛选、导出、渠道／仪表板统计必须使用一致的邮件字段。分配增加邮件已付排除条件，同时保留现有明确已付等限制；旧官网结果只影响其既有操作限制，不反写邮件字段。邮件未知本身不新增既有人工分配禁令。原`officialPaymentConfirmed`保留官网语义。

### 权限和人工核定

邮件状态摘要按订单读取与TAG范围开放；付款任务页仅显示本人任务必要摘要，不成为完整订单详情或邮件的访问入口。原文／附件仍由`order_mail.manage`和订单范围保护，解析重放、纠正、开关操作设管理权限。

人工核定只能依据关联官方邮件修正解析结果，必须有原因、邮件ID和版本；不得凭口述或人工任务状态填入两个新字段。复读相同邮件不得撤销有效人工核定。敏感正文、取货码、邮箱和联系人不进入普通日志。

## 七、页面与实施步骤

订单列表新增“订单状态”“付款状态”，说明来源为官方订单邮件；取货信息展示门店、预约日期／时段或“营业时间内到店”，并显示证据时间与待核对标记。旧官网状态作为独立辅助列；“付款任务状态”单独命名。

订单详情和邮件抽屉展示同一订单邮件时间线、识别类型、应用结果、门店／时间来源和未更新原因。不能把“最近成功收信”当成“最近订单更新”，两者分别展示。

| 阶段               | 当前状态与交付                                                                          |
| ------------------ | --------------------------------------------------------------------------------------- |
| 真实样本核定       | 已完成本轮归档分析、收信对账和217封取货信息离线提取；已明确本期不判断已取货、不使用收据 |
| 规则及契约定稿     | 已固化预付流程付款映射、服务端 DKIM 验签、正式字段与 API 契约                          |
| 影子解析和影响预览 | 已生产发布并开启新邮件解析；应用和付款任务开关关闭，既有归档未回放                    |
| 受控上线           | 技术及真实样本验收通过后，按授权范围启用订单和付款任务应用                              |
| 历史回放           | 尚未执行；须按单汇总完整邮件历史、预览差异再应用，不逐封制造错误中间状态                |

归档、解析、订单应用、任务联动独立开关；关闭订单应用时不得单独完成付款任务。生产部署、启用和历史回填遵循各自授权，不因只读核对自动开放写入。本期不增加企微通知或自动转发。

回滚先关闭应用和任务联动，保留接收及证据；保留已付阻止重复分配的兼容读取，不能因旧代码忽略新字段而重新派付。错误结果用有版本前提的补偿事件纠正；有后续人工操作时转核对，不整库覆盖，也不自动批量重开已完成任务。

## 八、验收和待闭环事项

- 真实样本：确认邮件条件式催付不判未付款，处理通知未来取货说明不判可取货；更新邮件正文明确可取货才更新；收据和辅导不改变状态。
- 字段：门店不取账单地址；215封固定时段与2封营业时间内到店场景；AM/PM、跨日期、相对日期和空值；不生成实际取货时间或精确保留截止。
- 多封／多商品：重复、乱序、UID重编号、两条同型号商品、商品范围冲突、邮件先到和任务后到。
- 一致性：订单应用、任务完成和审计原子提交；与人工修改、分配、官网刷新并发时版本和字段范围正确；金额、归属、付款人等保持。
- 收信与页面：不靠未读、不靠网页触发；漏事件、断线、停机、数据库失败、文件夹路由、处理积压和长期打开页面各有验收。

# 官网更新服务离线修复发布

> 日期：2026-10-05；环境：PP_CloudServer。用户授权定位、修复并部署此前官网更新问题。
>
> 状态：生产修复已部署，真实单笔查询及窄范围落库验收通过。

## 根因

截图“官网更新服务暂未就绪，请稍后重试”来自 `POST /api/orders/official-refresh/batches` 的 503 / `OFFICIAL_WORKER_OFFLINE`。API 正常，但执行器最后心跳为 10 月 3 日 17:57:00，临时批量保护在 17:57:55 遇到多个账号验证未完成后调用 systemd 停止了整个查询服务。保护只存在于外部脚本，业务 API 不区分批次暂停与进程离线，也没有自动恢复路径；重试页面无法解决。

发布前业务库共有 1197 单、1926 个账号、67 个迁移。历史批次 `45d8f2b7-9d73-4dd7-87f8-2df234122ce1` 为 6 成功、6 失败、1157 排队，另有两笔单项补充批次排队。直接启动旧 Worker 会重新领取旧任务；重新启动旧守护又会因历史失败停掉服务，因此仅重启不足以修复。

## 修复

1. 正式 Migration `20261005000001-add-official-refresh-batch-pause.js` 增加批次 `paused_at` / `pause_reason`，成对约束；有暂停历史时 down 拒绝。
2. 登录拒绝、认证失败、人工验证、HTTP 541/429/407、代理连接失败、代理冷却和请求预算耗尽，立即暂停当前批次；领取跳过暂停批次但持续写心跳。
3. 人工新请求在同一事务和全局咨询锁下，仅替代所选订单在本人／管理员可操作的暂停批次中的 queued 项。旧项以 cancelled / `REQUEUED_MANUALLY` 留痕，不重写批次成员。请求键重放不重试；其他活动项仍去重。
4. 页面展示暂停原因、服务在线或离线、逐单“已暂停”；真正离线提示管理员检查，不再建议无效等待。未清空账号或代理暂停、请求预算、历史失败及研究证据。
5. 上线前把上述三个历史批次全部标记 `LEGACY_SAFETY_HOLD`，停用临时批量守护；启动正式 Worker。旧积压不会因进程重启自动运行。

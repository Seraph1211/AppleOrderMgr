## 使用方式

管理员进入侧栏“企微订单通知”，填写目标群名称及 Webhook 后保存。新配置默认关闭；可先点击“发送测试消息”，观察投递记录并核对目标群实际收到的合成消息，之后再启用新订单自动通知。Webhook 保存后不回显，输入框留空表示保留，替换前须先停用。

仅支持企业微信内部群。设置、测试和重试使用独立管理员保留权限，不将付款任务权限扩展为群通知权限。WebHook 按字段加密密钥加密存储，发送内容及完整支付地址不写入投递记录。若接收服务异常，页面显示发送暂停原因或服务未就绪；修复配置后重新保存可恢复。

## 消息与时效

```text
系统订单ID || TAG || 商品及数量 || 支付方式 || 付款截止时间 || 支付链接
```

- TAG 只增加到群消息；原付款页面单条／批量复制不变。AOS 使用来源 TAG 优先，其他来源使用订单 TAG；空值为 `-`。
- 截止时间为来源下单时间加 30 分钟，北京时间 `YY/MM/DD HH:mm`。不冒充官网再次核实的有效期。
- 微信订单优先读取已关联付款码并在本地识读。缺码或坏码等到登记后 60 秒仍不可用，则回退原订单链接；所有非普通微信方式（含微信分付）直接使用原订单链接。排队过程中二维码已到达则优先使用，不重新开始等待。
- 一单一条、不 @ 成员、不补历史，单群按登记时间与 ID 顺序发送；等待码的队首不会被后续订单越过。
- 全局发送间隔至少 3334 毫秒，约每分钟 18 条，测试与重试共用。积压可能导致订单超时；实际发送前按最新本地订单状态跳过已付款、退款、取消或超时订单，不额外抓取官网。
- 缺准确截止时间、缺两种链接或超过 2048 UTF-8 字节时，记录失败供处理，不伪造时间或截断付款链接。

## 投递状态与操作

| 状态 | 含义与处理 |
| --- | --- |
| 排队中 | 等待轮到此消息或安全重试 |
| 等待付款码 | 最多等待登记后 60 秒 |
| 发送中 | Worker 已领取；短租约防止多进程重复领取 |
| 接口已接受 | HTTP 与企微业务返回均成功；仍需在群内核对 |
| 失败 | 输入不完整、明确拒绝或自动重试已用尽；可人工重试 |
| 结果未知 | 网络回执丢失或发送中服务退出；先核对群记录，确认后才可重试 |
| 已跳过 | 已付款、超时、停用或更换目标；不补发 |

仅明确未连接及明确限流自动重试，最多 3 次；网络超时、重置、未知响应和发送已开始后的崩溃均不会自动重发。结果未知时不存在可靠的自动去重送达保证。

停用会取消尚未进入网络发送的任务；在途请求无法撤回，保留实际结果，在途失败也不会复活关闭的队列。重新启用只登记此后的新订单，更换 Webhook 不迁移旧群消息。页面轮询保留未保存草稿；配置版本变化需要重新载入。

## 本地与部署

正式 Migration：`20260920000004-add-wecom-notifications.js`。先迁移，再发布 API、入库 Worker 和企微 Worker，避免新入库代码查询未建立的通知表。该迁移创建两张表、索引和默认关闭配置；down 删除通知表，已有配置和历史会丢失，生产回滚前须备份。

本地依赖随 `package-lock.json` 安装 `jsqr` 与 `pngjs`。修改依赖后重新构建开发后端镜像。启动发送服务需要显式 profile：

```bash
docker compose -f docker-compose.dev.yml --profile wecom up -d wecom-worker
```

生产编排也提供 `wecom` profile，运行命令为 `npm run start:wecom-worker`。Worker 只访问现有 PostgreSQL 和官方 HTTPS 地址，不需常驻桌面或新增入站端口。需要现有字段加密配置；群配置通过后台保存，不能写入仓库环境示例。

源码入库接点是 `orderIngestionCore.createOrderInTransaction`，与订单同事务登记，通知开关独立于付款调度。API 契约和表结构分别见[API设计](API设计.md#企微新订单通知接口2026-09-20)、[数据库架构](../database/数据库架构.md#企微订单通知2026-09-20正式迁移新增)。

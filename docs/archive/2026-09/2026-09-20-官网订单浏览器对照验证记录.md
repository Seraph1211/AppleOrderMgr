## 环境与边界

开始 01:27、结束核查 01:34，生产均未暂停、active_proxy_provider=fanproxy_tunnel，无 pending／running 任务。未切换 Provider、恢复队列、触发批量刷新、回写订单、修改配置或部署代码。独立诊断进程复用生产 Provider 配置及 PostgreSQL 全局限流游标；除时隙预留外不写业务状态，不调用 fetchWithRetry／crawlAndUpdateOrder。生产容器只读根目录阻止临时脚本复制，改为独立 node -e 进程执行，不改容器文件系统。

浏览器运行于本机已安装 Chrome，通过生产配置返回的代理账密连接固定当次代理；Cookie 仅属于新建 Context，结束立即关闭。没有复制个人 Chrome Cookie／存储、没有复用截图中的临时访客令牌。每次浏览器对照最多 90 秒、100 个受控请求；原生校验与 fetchOrder 可执行，订单修改／取消／付款等动作不执行。只保存枚举、计数、状态码与结构摘要，不保存原始页面、响应正文、Cookie、联系方式或完整访客 URL。

前两轮采用 Playwright 路由时隙控制，但自动重定向不能按同一计数口径保证逐跳拦截，其计数不视为全部网络请求精确值。后续有窗口对照改用 CDP Fetch.requestPaused，记录重定向并逐请求调用全局限流；同时处理 Fetch.authRequired 的代理鉴权，避免将诊断器自身的 407 当成业务故障。协议依据：[Chrome DevTools Protocol Fetch 定义](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)。本机截止检查时约 0.5 秒的观察清理开销计入耗时，未继续发送超预算请求。

成功门禁为实际页面／fetchOrder 返回匹配订单号的 orderDetail，再交给现有 extractOrderJson／parseOrderData，要求非空商品；本轮所有独立会话均未过门禁，没有将 HTTP 200、页面标题或固定等待标记为成功。

另只读查看用户已经打开的同单 Chrome 页面，没有重载或产生新的抓取：可见两条 iPhone 18 Pro Max 256GB 黑色商品，均显示“正在处理订单”和已完成的“已收到付款”阶段，取货地点为 Apple 南京东路。用户确认当时为本机普通网络或常用 VPN。此证据证明该既有浏览器页面显示有效详情；不能证明生产代理或新建浏览器也能取得同样结果，也不能确认此前加载的精确时间。

本地脱敏证据：`test-artifacts/order-browser-compare-20260920/`。侧边任务此前三次 HTTP 200 加载页为转交证据，未混入本轮实测统计。

## 判断与未完成工作

1. 当前 HTTP 客户端不执行页面脚本，无法仅凭加载页获得最终数据；但正常浏览器原生脚本执行也未使已测代理会话通过详情请求。因此不能把“改为 Playwright”视为已验证修复。
2. 既有用户会话成功、全新会话未成功，仍混有网络出口、会话历史、环境及时间差；未建立单变量对照，不能断言只是 IP、Cookie 或无头标识导致，也不能用个人会话令牌替代根因分析。
3. 本机新会话未观察到详情阶段，结论限于本次 90 秒预算；不能把它与代理 fetchOrder 541 混为同一错误。
4. 本轮修正的是实验限流与代理鉴权工具，没有修改或发布未经验证的业务兜底。后续需要在用户成功环境中明确有效出口及正常加载时序，再验证一个可重现的隔离环境。达到该门槛前，不扩建浏览器服务、不重复放量、不宣称抓取已修复。

## 一、结论摘要

项目不是“第 0 阶段、只有文档”的空工程。当前已经形成 React 管理台、Express API、PostgreSQL/Sequelize 数据层、邮件 Worker、爬虫 Worker、导入导出、统计和基础部署配置，主要 MVP 功能均有代码入口。

现有技术栈适合当前规模，不建议为了重构而整体替换。当前更迫切的问题是：历史敏感数据、前后端和数据库契约漂移、邮件可靠消息语义、爬虫任务租约和持久化状态、付款截图存储、真实数据库集成测试，以及文档和运行状态不一致。

本轮已经修复一批无需业务猜测的确定性问题，但不能据此宣布系统已可生产使用。真实数据库迁移、真实邮箱、Apple 官网、代理、Telegram、浏览器业务流程和生产发布均未验证。

## 三、当前架构与演进判断

### 3.1 当前实际数据流

```text
NULL AOS 邮件
  → email-worker / emailService
  → emailParser
  → orderService 事务写入 Apple ID、取机人快照、订单和邮件日志
  → crawler-worker / crawlerService
  → 代理访问 Apple 订单页
  → 解析、身份校验、邮件/官网数据合并
  → 短事务更新订单与爬虫日志
  → Express API
  → React 管理台
```

### 3.2 建议保留的方案

- **React + Vite**：页面和组件已经齐全，现有问题主要是契约、状态和分包，不值得重写框架。
- **Express**：当前 API 规模可控，中间件、路由和控制器结构已经存在；应补领域服务和契约测试，而不是换框架。
- **PostgreSQL + Sequelize**：关系、事务、JSONB 和索引适合订单场景；应统一 Migration/Model/文档，避免运行时 `sync({ alter: true })`。
- **axios + cheerio**：官网数据位于 HTML/脚本时比浏览器自动化轻量。只有确认官网必须执行 JavaScript 后才考虑浏览器降级通道。
- **JSONB 商品数组**：适合每单商品结构不完全一致的现状；统计查询和字段约束应通过专用投影、索引或后续明细表治理。
- **独立 Worker 入口**：方向正确，API 不应承担永久监听和调度。需要补持久化任务层，而不是重新塞回 API 进程。

### 3.3 应渐进演进的边界

1. 将邮件监听、解析、订单入库拆成可持久化任务，保存幂等键、尝试次数和失败原因。
2. 将爬虫拆成 Fetch、Parse、Validate、Persist、Schedule 五个可独立测试的模块。
3. 增加 PostgreSQL 任务表或成熟队列，保存租约、心跳、冷却、暂停和恢复指令。
4. 付款截图迁移到私有对象存储，数据库只存对象键、摘要、类型、大小、上传人和审计信息。
5. 建立版本化 DTO 或 OpenAPI 契约，逐步消除 `camelCase`/`snake_case` 混用。
6. 增加独立测试数据库、脱敏邮件/HTML Fixture 和浏览器 E2E，不以单元测试替代业务验收。

因此结论是：**保留技术栈，重构职责和可靠性边界；不做一次性全面重写。**

## 五、邮件链路剩余风险及触发条件

### 5.1 当前已有保护

- 生产邮件必须同时满足主题规则和发件人白名单。
- 订单号唯一性可以避免同一订单重复创建。
- 成功订单在同一数据库事务中创建订单和成功邮件日志。
- 临时失败会在当前进程内保留未读并重试；主动停止不会误触发重连。

### 5.2 尚未完成及其实际影响

| 缺口                     | 触发条件                                                     | 用户影响                                                                           |
| ------------------------ | ------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| 没有时间回溯             | 服务停机或 IDLE 事件丢失期间，邮件被其他客户端标记为已读     | 启动时只搜索 `UNSEEN`，该订单不会被自动补录，形成静默漏单                          |
| UID 幂等键不稳定         | 邮箱迁移、UIDVALIDITY 变化、多个邮箱出现相同 UID             | 当前全局唯一 `email_uid` 可能把新邮件误判成冲突；有效订单事务可能回滚              |
| 重试次数仅在内存         | 进程在失败重试之间重启                                       | 次数清零，邮件可能无限重复；相反，进程内达到三次后会标记已读，缺少可持久化重放入口 |
| 解析失败没有统一持久记录 | 邮件在 `saveOrderFromEmail` 之前解析失败，随后被判定永久失败 | 邮件可被标记已读，但数据库没有完整失败任务，后续只能依赖应用日志人工排查           |
| 没有失败队列/人工重放    | 数据库或解析规则长期异常                                     | 无法按任务状态查询、修复后重放或证明所有邮件最终处理完成                           |

因此 MAIL-03～MAIL-06 不是一般优化，而是“是否会漏单、重启后能否恢复”的业务可靠性门禁。建议幂等键至少包含邮箱标识、`UIDVALIDITY`、UID 和 Message-ID；订单号继续作为业务唯一约束，二者不可互相替代。

## 六、独立 Worker 状态说明

默认 `RUN_WORKERS_IN_API=false` 时，API 与 `crawler-worker` 是不同进程。API 进程内调用 `resumeAutoRefresh()` 不能修改另一个进程的内存，因此当前行为是：

- 状态接口从 `crawl_logs` 返回最后一次可观测事件；`isRunning=null` 表示无法证明进程此刻存活。
- 页面不展示可用的恢复按钮。
- 恢复接口返回 `409 WORKER_CONTROL_UNAVAILABLE`，提示授权运维人员在确认风控/代理问题后处理 Worker。

这是对原有“假成功”的修复，是**诚实降级**，不是跨进程恢复功能。完整方案需要持久化 `worker_instances`/`scheduler_state`、心跳超时、暂停原因、恢复命令、租约所有者和命令消费审计。

## 七、隔离 PostgreSQL 集成验证的准确环境结论

本轮只做只读检查，没有执行数据库连接写入、建库或 Migration：

- 本机已安装 `psql` 和 `pg_isready`。
- `127.0.0.1:5432` 当前没有 PostgreSQL 响应。
- Docker CLI 可用，但本轮没有取得可用的 Docker daemon 服务版本；不能把它视为已可启动容器。

- Jest 没有数据库 `globalSetup`/`globalTeardown`；当前自动测试主要是 Mock 或模型元数据测试。旧数据库脚本不属于默认 Jest 测试集合。

缺少的是**项目自带的隔离测试基础设施**，而不是用户提供生产数据库：

1. `compose.test.yml` 或等效脚本，提供 PostgreSQL 14+、临时卷和健康检查。

4. Migration 演练：`up → 结构/约束/密文验证 → down → up`。

这些基础设施补齐后才应执行隔离数据库写入测试；不得使用当前开发库或任何生产凭据代替。

## 八、付款人和“垫付归还”结算方案

### 8.1 已确定的业务边界

- 付款人是实际垫付资金、等待归还的主体，不等于取机人、Apple ID 拥有者或系统操作员。
- Apple `payment_status` 只表示官网支付状态，不能代表系统已经向付款人结算。
- 结算必须可追溯、可部分归还、可冲正，确认后不能直接覆盖历史。

### 8.2 建议数据模型

#### `payers`

| 字段                | 建议                                 |
| ------------------- | ------------------------------------ |
| `id`                | 主键                                 |
| `payer_code`        | 内部唯一编号，不以姓名作为唯一键     |
| `display_name`      | 付款人显示名称                       |
| `payer_type`        | `person` / `organization`            |
| `status`            | `active` / `inactive`                |
| `contact_encrypted` | 可选密文联系方式，不参与普通列表响应 |
| `notes`、审计时间   | 备注和创建/更新时间                  |

#### 订单付款责任

第一版建议在 `orders` 增加：

- `payer_id`：当前付款人外键。
- `payer_name_snapshot`：订单发生时的名称快照，不参与唯一性。
- `payable_amount DECIMAL(14,2)`：经确认应归还金额。
- `payable_currency CHAR(3)`：币种。
- `payable_amount_source`：`manual_confirmed` / `official_suggested` / `adjusted`。
- `payable_confirmed_by`、`payable_confirmed_at`：金额确认审计。

`official_order_amount` 只可作为录入建议，不能自动覆盖 `payable_amount`。

#### `settlement_batches`

| 字段                               | 建议                                |
| ---------------------------------- | ----------------------------------- |
| `id`、`batch_no`                   | 主键和业务批次号                    |
| `payer_id`、`currency`             | 同一批次只处理一个付款人和一种币种  |
| `status`                           | `draft` / `confirmed` / `reversed`  |
| `idempotency_key`                  | 唯一，防止重复确认                  |
| `created_by`、`confirmed_by`、时间 | 操作和确认审计                      |
| `evidence_objects`                 | 对象存储元数据引用，不保存 Data URL |

#### `settlement_items`

| 字段                         | 建议                                     |
| ---------------------------- | ---------------------------------------- |
| `id`、`batch_id`、`order_id` | 明细和关联                               |
| `amount DECIMAL(14,2)`       | 本次归还金额                             |
| `item_type`                  | `settlement` / `reversal` / `adjustment` |
| `reverses_item_id`           | 冲正时指向原明细                         |
| `reason`、`created_by`、时间 | 原因和审计                               |

订单内部结算状态不建议直接存布尔值，而由有效台账派生：

```text
已结金额 = settlement - reversal ± confirmed adjustment
待结金额 = payable_amount - 已结金额
unsettled: 已结金额 = 0
partially_settled: 0 < 已结金额 < 应结金额
settled: 已结金额 = 应结金额
disputed/void: 由付款责任状态单独表达
```

超额结算默认拒绝；取消、退款或金额调整生成追加记录，不修改已确认明细。

### 8.3 页面表现

- 订单列表新增“付款人、应归还、已归还、待归还、内部结算状态”，与 Apple 支付状态分列。
- 订单详情展示付款责任确认记录、结算明细、凭证和冲正链。
- 付款人详情展示按币种汇总的待结金额和异常订单。
- 批量结算先按付款人和币种筛选，确认页展示订单、应结、已结、本次金额和异常项。
- `operator` 可创建草稿；`admin` 确认、作废和冲正；`readOnly` 仅查看。若将来需要双人复核，再增加审批角色，不阻塞表结构。

### 8.4 最少的真正阻塞决策

实施前只需要确认两项会改变核心数据结构或金额语义的问题：

1. **一张订单是否永远只有一个付款人？** 若可能由多人共同垫付，应改用 `order_payer_obligations` 关联表，不能在 `orders` 上只放一个 `payer_id`。
2. **应归还金额的权威输入是什么？** 默认建议“人工录入并由管理员确认，官网金额只作建议”；若必须自动包含佣金、服务费或汇率差，需要先给出公式和样例。

部分结算、单批次单币种、追加式冲正、历史文本不自动归并均可采用上述安全默认值，不必阻塞第一版设计评审。

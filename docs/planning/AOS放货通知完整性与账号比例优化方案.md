>
> 最近核对：2026-10-28。
>
> 任务：AOS-SIGNAL-COMPLETE-1028。
>

>
> 验证范围：生产通知记录、索引状态、限定时间 Worker 日志只读核对，以及现有查询的 `EXPLAIN`（未执行 `ANALYZE`）。性能改进和完整性机制均为拟实施内容。

## 目标与已确认问题

用户接受有货通知存在一定延迟，要求展示数据全面、准确。本方案建议把“尽快发送可用部分”改为“统计范围核验完整后发送”，并将无法完成核验的原因明确暴露。

2026-10-28 16:34:09～16:34:17 的广州 Apple 天环广场／iPhone Duo／星光白色／512G 信号，16:37:25 的汇总记录为：US_10／10号实例 `3/—`，US_02／02号实例 `5/—`。两项保存原因均为 `INDEX_READ_FAILED`；16:37:23～16:37:28 的 Worker 记录四次 `57014`。相关读取设置单 SQL 超时 1500ms。两实例索引均已在10月26日完成，不能把此次问题解释为仍在等待回填。

源码还存在以下影响新目标的行为：

- 比例查询在库存全局锁事务及发送前复核中执行，同一窗口可能重复查询；读取失败允许降级后发送。
- 信号入口清理、消费过滤、窗口结算和投递有效期均有三分钟相关限制；只延长分母等待会引入丢信号或通知过期。
- 分母读取包含历史事件筛选、两层窗口函数及排序；本次 `EXPLAIN` 确认该查询形状，但未据此断言生产实际耗时由某个执行节点单独造成。
- 正文达到字节限制会省略门店、来源或商品分组；这不满足完整展示要求。
- 当前分母保护会拒绝配置缺失、覆盖不全及窗口内账号集合变化；新方案继续保留这些保护，不能通过去掉未知账号来得到一个数字。

| 超长消息     | 按商品／城市／来源拆成有批次号和页码的多条消息，保留全部条目，遵守共享机器人限速。                                                                       |

## “全面、准确”的具体口径

1. **命中次数与账号数分开。** 门店次数为去重后的原始信号次数；账号数按服务器、实例、原始账号编号去重，保留前导零。同账号同城多店命中不重复计入分子。
2. **分母仍限定同城同规格。** 按实例、城市、型号、颜色、容量，取该统计段首次命中之前各编号最近一次启动配置；停止本身不改变设置。未来配置不能回填过去，也不能用全实例账号总数充当分母。
3. **最新启动缺失不借旧配置。** 某账号有较早完整配置、较新启动却不完整时，依然待核验；真实未知门店、冲突、缺口必须保留。
4. **分子必须属于分母。** 保存分子及分母的编号集合、证据位置和摘要，检查集合包含关系及 `N <= D`。历史原文不完整时，已有命中数不等于完整分子。
5. **窗口内换配置分段展示。** 某来源的有效账号集合变化时，按变化前后区间分别计算并标时间；即使分母数量相同但成员不同，也要分段。不强行给变化窗口一个比例，不跨段相加去重账号数。
6. **来源范围明确。** 以窗口开始时已启用并纳入监控的来源清单为基线；窗口中启用、停用、实例更换均记录生效边界。不能只检查已命中的实例，否则未上传的来源可能被漏掉。全来源覆盖未闭合时，整窗不标为完整；离线来源不能自动当作零命中。
7. **可证明范围有边界。** 完整指已登记并纳入监控来源的该窗口，不代表所有 Apple 门店或未接入服务器。AOS信号表示当时观察到放货相关日志，不保证送达时仍有库存。

## 实现方案

### 1. 将计算从发送事务中拆出

接收日志、生成统计任务、计算比例、发送通知分成独立阶段。任务和窗口持久化，具有唯一标识、输入版本、租约、重试时间、阻塞原因和输出摘要；进程退出可恢复。

建议状态为“收集 → 等待覆盖 → 计算 → 已核验 → 待发送 → 已接受”，另设“阻塞”“发送结果未知”等状态。计算任务只占用独立、有界资源，默认一个并发；不在库存全局锁内执行历史查询，也不在每次领取发送任务时重新计算。

在一致的数据版本上读取配置与信号，计算完成后短事务核验输入版本并保存；若出现相关晚到数据，旧结果失效并重算。发送阶段只读取通过完整性检查的冻结结果，并复核版本和通知开关。

### 2. 优化分母查询并预先维护配置

- 先在隔离环境以真实规模副本采集执行计划、实际行数、耗时和缓冲区读取，区分扫描、排序、I/O或锁等待；不能只把1500ms调大作为修复。
- 第一层优化：按账号有界读取最近启动及其后相关事件，提前限制范围，消除同一窗口／来源在生成和发送阶段的重复扫描。必要索引通过正式 Migration 创建，并验证写入成本和回退。
- 第二层优化：在日志入库后增量维护“账号启动轮次及配置有效区间”，保留版本、未知状态和原始证据位置。通知读取对应历史时点的区间快照；不能只保存一份当前配置。
- 以输入版本和统计时点作为复用结果的条件；晚到旧事件、解析规则版本变化、配置变化使相关结果失效。不同时间或配置版本不得复用旧分母。
- SQL和任务继续保留预算。超时后保存进度、分页或缩小批次；大来源不能导致无限扫描或阻塞实时接收。

第一层能否满足性能目标由测量决定；完整性门槛、持久任务和失败重试不因查询变快而省略。

### 3. 用采集进度证明完整，不靠固定多等几十秒

每个参与来源需证明：相关文件清单已枚举、文件代际已区分、所需字节区间已连续上传并入库、配置派生处理已追平，且覆盖窗口结束。心跳正常或某个索引状态为 `ready` 不能单独作为完整依据。

优先复用现有采集状态；如不足以证明上述条件，补充采集器协议及服务端确认进度，作为严格模式上线前置条件。处理重传、乱序、轮转、截断、替换、跨日、断线补传和新文件；稳定等待时长只用于吸收常态迟到，不能替代覆盖证据。

按事件时间归窗前必须验证来源时间可信度及偏差范围；时间异常的来源进入待核验，不能暗中改写时间后计数。应以完整采集屏障、文件位置及服务端接收记录结合证明窗口边界，不能仅用客户端最新时间戳推断无遗漏。

### 4. 取消会丢待处理数据的三分钟硬删除

三分钟只作为统计窗口长度，不能同时充当待处理数据寿命。未结算窗口、未消费信号、所需上下文、相关配置基线及关联证据，在完成或明确处置前不得因普通TTL清理。

未完成任务保留；执行重试有界并监测积压，超过容量或证据保留边界要显式告警和记录不可恢复状态。已完成数据按正式保留策略清理，避免以“永不丢失”为由无限堆积。

近期原文回查继续遵守既有最近三天范围；优先复用可信配置基线并保留未来计算所需的最近启动快照。若缺失证据只能从更早日志取得，单独列出最小需要范围待确认，不自动扩大为全历史扫描，不拿今天配置补历史。

### 5. 完整分片与投递核验

全部分片共用窗口ID、结果版本和总页数；单片按 UTF-8 字节计算上限，不截断有效门店、商品和来源。接收方可通过页码识别缺片，后台只有全部分片均被接口接受才标记整批发送完成。

投递幂等覆盖内部任务和分片；外部接口超时的“是否已送达”可能无法确认，应保持“发送结果未知”并进入核查，不能盲目重发后声称绝不重复。明确成功、明确失败可重试、结果未知分别处理。

若发送后出现此前覆盖证明未涵盖的有效迟到证据，保存原版本，生成明确关联原批次的更正版本；同时标记完整性检查缺陷，不静默改写历史或把更正当新一轮放货。

## 实施顺序与交付

1. 确认本方案的通知时机、时间口径、异常及补发规则；检查当前 `main` 与生产差异，建立明确实施基线。
2. 更新现行业务说明、数据库架构、必要API／采集协议和测试用例，再实现正式迁移、任务状态、配置索引及查询优化。
3. 补齐覆盖证明和待处理数据保留，最后接入严格发送门槛、分片及告警。未具备可靠覆盖证明时不能上线宣称完整。
4. 完成回归、隔离真实规模验证、历史样本对照和不发送消息的生产并行计算，提交可审阅差异和验收证据。
5. 经生产发布授权后，按既有业务备份与恢复演练、`productionFrontendGate.py` 门禁部署；备份继续排除AOS原始日志及日志明细。回退须保留待处理任务和已发记录，暂停严格通知优于自动退回发送不完整结果。

交付包括正式实现、必要迁移、完整性与性能测试、生产对照证据、故障可见状态以及文档更新。本轮只提交待确认方案，未修改数据库、Worker、采集器或通知配置。

## 用户确认项

建议整体确认以下四点：

1. 取消立即首报，只发送核验完整的三分钟汇总，常态首次通知目标约3分30秒～4分30秒。
2. 窗口按核验后的日志事件时间归属；配置集合变化时分段展示，所有来源覆盖未闭合时等待。
3. 窗口结束10分钟仍未完成时发一次异常提示，继续补齐；恢复后以历史补发形式发送完整结果。
4. 不省略条目，超长拆成多条；真实缺证据时明确阻塞，不用未知比例或估算总数冒充完整统计。

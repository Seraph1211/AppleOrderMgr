# 服务器监控双通道通知验收

> 状态：当前有效；第一阶段独立验收用例，执行结果另行记录。
>
> 最近核对：2026-10-19。
>
> 适用范围：`MON-NOTIFY-01`、`MON-NOTIFY-02`、`MON-NOTIFY-03`、`MON-AUDIT-01`。
>
> 基线：`main@d3baf4b`；当前实施分支的实际提交和差异以执行报告为准。
>
> 验证边界：隔离 PostgreSQL、真实本地 HTTP、合成 SMTP／企微传输；真实群、邮箱、生产及长期观察必须单独记录。

## 环境与执行约束

先阅读[已批准方案](../planning/服务器日志监控与双通道通知优化方案.md)、[测试指南](测试与验收指南.md)和[API 契约](../design/API设计.md)。使用独立 Compose 项目、可销毁 PostgreSQL 容器与固定合成数据库。不得对共享开发库、研究库或生产库执行清空、迁移回退或清理验收。邮件、爬虫、库存等真实 Worker 不启动；只显式调用一次调度／领取／出站／清理入口。

默认禁止真实 Webhook、SMTP、Apple 或代理出站。传输必须注入合成响应。环境门控未启用、容器不可用和未运行的用例记为跳过或阻塞，不能计为通过。并发和事务用例使用真实 PostgreSQL，不以模型桩替代。跨模块共享预算必须调用订单、库存、AOS 与监控实际业务入口，而非仅重复调用预算函数。

## 独立验收矩阵

| 编号    | 场景与操作                                  | 必须断言                                                                                 |
| ------- | ------------------------------------------- | ---------------------------------------------------------------------------------------- |
| MIG-01  | 正式迁移 up/down/up                         | 默认关闭、列和索引正确、旧业务摘要前后一致                                               |
| MIG-02  | 写入新投递事实后 down                       | 原子拒绝破坏性回退；数据和结构均保留                                                     |
| EVT-01  | 同一告警在事务内重复登记与回滚              | email／wecom 各一次；回滚无待发或残留事件                                                |

| CFG-01  | 单通道关闭、旧接口保存与重新开启            | 另一通道保留；旧客户端不清空企微；不复活取消任务                                         |
| CFG-02  | 领取后、出站授权前换目标／关通道            | 未出站旧任务跳过；原子目标版本生效                                                       |

| RATE-01 | 同机器人订单＋库存＋AOS＋监控滚动发送       | 任意滚动 60 秒总计 ≤18、监控 ≤6、间隔 ≥3334ms；测试与重试占额                            |

| RATE-03 | 高频模块、严重监控事件与普通摘要并存        | 严重新事件优先；各模块获得发送机会；订单 FIFO 保持                                       |

## 结果记录

自动化入口为 `test/monitorNotificationsIndependent.test.js`、`test/monitorNotificationsIndependentMigration.test.js` 和 `test/browser/monitorNotificationsIndependent.cjs`。前两者只有 `MONITOR_NOTIFICATIONS_INDEPENDENT=1` 才启用，并强制要求 `DB_HOST=127.0.0.1`、`DB_NAME=monitor_notify_independent` 且未设置 `DATABASE_URL`。迁移专项另连接同一隔离实例的 `monitor_notify_migration`，该库先执行至本次迁移的前一份正式 Migration。测试包含清空合成表、慢 SQL Trigger 和迁移回退，不能连接业务数据库。

本轮可重复执行的隔离配置、HTTP 合成身份入口和混合镜像脚本放在 `.tmp/monitor-notifications-independent/`，使用 `monitor-notify-isolated-db` 容器；只有该隔离 PostgreSQL 使用合成凭据。重新执行前先确认容器归属及专库名称。核心套件命令：

```bash
docker compose -f .tmp/monitor-notifications-independent/compose.yml run --rm -T test \
  npx jest test/monitorNotificationsIndependent.test.js \
  test/monitorNotificationsIndependentMigration.test.js --runInBand --coverage
```

浏览器使用专用临时 Chrome、工作树前端 `127.0.0.1:5188` 及真实隔离 HTTP `127.0.0.1:5194`；通知 API 转发至真实后端路由／隔离 PostgreSQL，其余外部请求阻断。身份为合成身份，不能当作真实登录验证。后台测试模拟 `visibilityState` 与 `visibilitychange`，记录隐藏期间不轮询、恢复可见立即读取和草稿保留；真实系统切换标签页另行验收。

既有 AOS／库存数据库专项通过 `test/helpers/monitorNotificationBudgetFixture.js` 从正式迁移提取预算 DDL，并按场景重置本轮隔离库预算。必须保留真实共享预算调用；受新增 3334 毫秒最小间隔影响的场景推进合成时钟，不能通过禁用限速让旧断言通过。混合镜像验收使用旧生产基线镜像及最小文件绑定：邮件入口只替换 `emailWorker.js`，并注入合成收信启动；订单企微只替换 Sender、Transport、预算服务和预算模型，验证旧模型注册闭包仍能完成一次实际排队、合成接受和预算登记。

每次执行保存实际命令、提交及差异、数据库／容器标识、通过／失败／跳过数量、失败用例和证据路径。合成传输接受仅证明系统记录接口接受，不能证明真实群成员收到或邮件最终投递。生产发布后另测明确标记的合成通知，并分别记录接口接受、人工收件和 24—48 小时观察。

第二阶段的设备健康检测、源文件追加协议、独立看门狗和外部探测器不因第一阶段通过而标记完成。

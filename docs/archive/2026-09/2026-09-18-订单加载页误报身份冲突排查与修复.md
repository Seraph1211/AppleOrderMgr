## 现象与证据

系统订单 170 的网站手动刷新提示“官网返回的订单身份与本地订单不一致”。18:54 手动任务 5733 的接口返回 202、入队、领取、结果查询均正常；Worker 取得空订单号、0 商品和 unknown，却先记录成功，再在重试循环外报 IDENTITY。最多 3 次配置实际只抓取 1 次。该失败没有证明返回了另一订单。

页面引用的 [Apple 订单前端脚本](https://store.storeimages.cdn-apple.com/8756/store.apple.com/static-resources/rs-olss-5.18.5-9a078/dist/order-detail.js)显示：访客加载组件等待浏览器校验完成事件，再执行 fetchOrder。程序没有执行页面 JavaScript，所以只能解析当次实际返回的 HTML。没有证据支持把生产差异归咎于某个特定出口；18:16／18:54 历史响应未保存，也不能断言每次历史失败都来自相同页面。

## 根因与修复

1. 将 HTTP 200 且 JSON 可解码误当作订单加载完成。修复后先识别 guestOrderSpinner，缺失／无效订单号也按 PARSE 处理。
2. 身份检查位于重试循环外。修复后每次尝试内完成解析与身份校验，通过后才记录成功；解析失败切换下一代理会话并有限重试，每次仍经过全局限流器。最多 3 次，保留 541 和 407 既有策略。
3. 缺失订单号与明确不同订单号混用 IDENTITY。修复后仅明确返回不同有效订单号立即停止并标记身份冲突；URL 来源限制仍保留。
4. 增加白名单诊断：状态码、字节数、Apple 最终主机、路径类别、标题类别、组件与关键结构存在性。HTTP 失败页同样支持安全摘要，不记录动态路径、查询、Cookie、令牌、正文、联系方式或另一个订单号。

解析失败保留旧业务字段与既有校验结果。历史身份误标不自动批量清除；后续真正成功同步才重新计算校验并更新官网状态。真实同单成功已取货的合成持久化回归覆盖这一过程。没有改动付款任务人工处理状态或周期自动刷新规则。

后续完整方案的实施顺序与验收门槛：

1. **保留已发布的严格判定和有限重试。** 有效详情才进入统一解析器；身份、商品和状态校验后才能落库。缺失身份不可从 URL 填充，加载页不可当成功，失败保留旧值和观测时间。
2. **先验证可重复的详情获取方式。** 在当前代理下分离验证单次会话的重定向、Cookie 作用域、校验完成事件与 fetchOrder 响应，使用脱敏时序证据和固定请求预算。不要仅凭一次成功新增生产依赖，也不要将有校验脚本的完整页面一律改走浏览器。
3. **浏览器兜底只有取数实验通过后才实现。** 如能证明原生浏览器稳定取得详情，采用独立受限进程／服务、订单级隔离 Cookie、固定当次代理、全局限流与超时；只读取页面原生返回的详情，复用同一解析与身份门禁。必须覆盖正常详情、加载后详情、541、超时、真正错单及全部商品一致性。现有 Worker 资源限制下不直接增加 20 个浏览器实例。
4. **无法取得详情时准确报告失败。** 541／校验阻断没有通用的解析器修复；不伪造校验结果、不增加无界请求、不自动跨供应商切换。需要针对真实订单详情而非首页做受控线路比较后，才能决定线路方案。

# 邮件解析规则

> 状态：当前有效
>
> 最近核对：2026-09-07
>
> 基线：main@79e83e0 与当前工作树
>
> 验证范围：合成 MIME Jest 与隔离 PostgreSQL 集成；未验证真实邮箱、真实订单或生产环境

## 实现入口与职责

邮件 Worker 使用[emailParser.js](../../src/services/emailParser.js)。`parseMimeEmail` 对每封 MIME 只调用一次 mailparser；来源过滤和订单字段解析复用同一个解析对象。解析器不写数据库，接收留痕、来源过滤、失败状态和订单事务由[邮件处理流程](邮件处理流程.md)负责。

MIME 输入只接受 Buffer 或 UTF-8 原始 MIME 字符串，统一转为 Buffer 后计算 SHA-256 和 Base64。空 MIME、超过 10MB、无法解析或正文为空分别返回稳定错误码，不将元数据解析异常降级成“非订单”。

## 正文与订单信息块

HTML 和纯文本分别转换成保留换行边界的文本行，再从完整行定位订单信息块：

```text
型号1-产品名称 x 数量1@型号2-产品名称 x 数量2/取机人/身份证后四位/付款方式/-/-/标签
```

- 商品仅在已定位的商品段内按 `@` 分隔，Apple ID 中的 `@` 不参与商品分割。
- 型号可包含 `/`，名称也可包含 `/`；不得对全文直接按 `/` 分割。
- 标签只取订单信息行最后一个字段，不得吞入链接、领取说明或页脚。
- 商品执行全有或全无校验：1–50 行，每行必须有 2–50 位型号、1–300 位名称和 1–999 的正整数数量；任一行失败即整封邮件进入 `manual_review`。
- HTML 实体、MIME Base64、CRLF、连续空格和换行会规范化，但不会先把全文压成一行。

## 字段契约

| 输出                               | 来源与规则                                                                              |
| ---------------------------------- | --------------------------------------------------------------------------------------- |
| `appleId`                          | 称呼中 `***` 后的完整邮箱，规范化为小写并校验                                           |
| `orderNumber`、`orderUrl`          | 仅允许 `https://www.apple.com.cn/xc/cn/vieworder/W##########/...`，URL 内订单号必须一致 |
| `orderDate`                        | 正文 `YYYY/M/D HH:mm:ss` 明确按中国 `+08:00` 转为 Date，不使用容器本地时区猜测          |
| `products`                         | `model/name/quantity/image`；颜色和容量仍属于名称，`image` 初始为 null                  |
| `recipient`                        | `name/idLast4/tag`；姓名、后四位和标签均执行字符、空值和长度校验                        |
| `paymentMethod`                    | 订单信息行中的付款方式，必填且不超过 50 字                                              |
| `emailSubject/emailFrom/emailDate` | MIME 元数据                                                                             |
| `rawContent`                       | 原始 MIME Buffer 的 Base64；写入 `EmailLog` 后由模型层 AES-256-GCM 加密                 |

邮件商品数量用于初始入库；官网身份一致后采用官网有效数量（包括取消时的 0），邮件原值保留供冲突核对。官网缺失型号或其他字段时保留已有有效值。公共入库流程（含人工确认和 AOS）将新订单官网状态初始化为 pending（待处理），来源提供的状态不直接当作已确认官网状态；同事务登记 initial 刷新任务，异步官网抓取后再更新。基础资料匹配与敏感快照规则见[快照匹配](../database/快照匹配.md)。

## 错误与验证

解析错误使用[emailErrors.js](../../src/services/emailErrors.js)中的稳定错误码，例如 `MIME_TOO_LARGE`、`MIME_PARSE_FAILED`、`BODY_MISSING`、`ORDER_BLOCK_MISSING`、`APPLE_ID_INVALID`、`ORDER_URL_INVALID`、`ORDER_DATE_INVALID`、`PRODUCT_INVALID` 和 `TAG_INVALID`。错误文本不拼接外部字段原值，运行日志只记录内部邮件记录 ID、错误码和商品数等必要指标。

## 订单归档邮件生命周期解析

[orderMailLifecycleParser.js](../../src/services/orderMailLifecycleParser.js)只处理已由独立订单邮箱归档的 MIME，不创建订单。确认、处理、可取货更新或取货信息模板的标题与正文事件句必须同时匹配。标题精确为“个人设置辅导，帮你上手新 iPhone。”的邮件映射为 `personal_setup` 和 `picked_up/paid`；必须仍提取到唯一完整订单号。缺句号或其他相似标题不能触发推定。电子收据和广告继续排除，未知模板仅生成待核对事件。规则版本为 `apple-cn-pickup-v4-personal-setup`。

解析结果包括完整订单号、逐项商品及数量、邮件订单／付款候选、门店、地址、取货日期、24小时制开始／结束时间、预约方式、`Asia/Shanghai` 时区和原文保留说明。取货日期优先读取“取货日期”字段；当该字段为空时，允许从明确的“有货：YYYY/MM/DD. 你订购的商品可以取货……”通知句提取同一天，不读取订购日期或其他普通日期。门店只取“取货零售店”块，不取账单联系人地址；没有固定时间而明确“营业时间内前往”时使用 business_hours，不补造时段。确认邮件不因条件式催付判未付款，处理邮件不因未来取货说明判可取货。辅导邮件没有商品明细，只对 `personal_setup` 跳过商品范围比对并保留证据原因；输出的 picked_up 是邮件推定，`actualPickupAt` 固定为 null，不伪造实际取货时间。

生命周期业务应用不再以 DKIM 作为门槛。归档时提取的完整订单号、重放时从邮件重新解析的完整订单号与系统 `orders.order_number` 必须三者精确一致；邮件先到时保持 `waiting_order`，订单建立后再按相同规则关联。DKIM 可保留为诊断信息，但失败、缺失或历史签名变化不阻断订单号匹配的生命周期事件。商品用现有名称归一化后按整单汇总数量比较，名称集合或数量不一致仍为 `PRODUCT_SCOPE_MISMATCH`，不能把部分通知提升为整单已付款或可取货。

解析器自身无数据库写入；持久任务、追加事件、订单号核对、单调归并、人工核定和付款任务事务由[邮件处理流程](邮件处理流程.md)定义。自动化用例见 `test/orderMailLifecycleParser.test.js` 和 `test/orderMailLifecycle.integration.test.js`；`test/orderMailAuthentication.test.js` 仅保留底层 DKIM 诊断模块回归，不再代表生命周期应用门禁。

[emailParser.test.js](../../test/emailParser.test.js)及其 Fixture 覆盖单商品、多商品、HTML、纯文本、MIME Base64、HTML 实体、换行、含 `/` 型号和名称、标签边界、`+08:00`、未知模板、非法数量和部分商品失败。历史 `test/test_email_parser.js` 已删除，不再使用返回 0 的 `console.assert` 脚本作为门禁。

## 设计目的

基础 Apple ID 或取机人资料尚未导入时，仍能保存订单。订单保存必要快照，外键允许为空；关联用于追踪和补充，不应使订单展示依赖基础资料永远存在。

## 当前匹配规则

| 对象     | 当前查找条件                                                      | 成功时填充                                 | 未匹配时                         |
| -------- | ----------------------------------------------------------------- | ------------------------------------------ | -------------------------------- |
| Apple ID | appleId 精确匹配邮件地址                                          | appleIdRef、applePassword 快照             | 保留邮件 appleId，关联和密码为空 |
| 取机人   | 邮件姓名第一字作为 lastName，其余为 firstName，再匹配 idCardLast4 | recipientRef、身份证、邮箱、手机、地址快照 | 保留邮件姓名，其余资料为空       |

实现见[orderService.js](../../src/services/orderService.js)。当前使用 findOne，没有复姓识别、同名后四位冲突的显式人工消歧流程；这些是现状限制，不是新的业务规则。

## 数据一致性

订单保存和邮件日志处于同一事务；订单号存在时返回已有订单。邮件商品数量是权威数量，官网数据只补充状态、取货、图片、金额等字段，详见[爬虫说明](../design/订单爬虫.md)。

快照不是实时 JOIN 的别名；不能假定修改基础资料会自动重写历史订单。渠道改名是明确的跨表 tag 更新，见[渠道管理](../design/渠道管理说明.md)。

## 安全与字段

密码及身份证快照由模型 setter 加密，getter 解密仅供受控服务处理。API 另行脱敏，隐藏前端列不能替代服务端权限控制。字段、类型、索引以[数据库架构](数据库架构.md)为准，本页不复制 SQL 建表与明文插入示例。

## 待验证

多匹配、事后关联、补齐范围和真实数据库并发行为需独立验收；历史“自动匹配不会丢单”不作为可靠性承诺。

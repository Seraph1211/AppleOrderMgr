### 第一阶段：分类、会话与交互修正

1. **统一结构化错误。** 将加载／校验未完成、未知页面结构、网络超时、响应中断、主动取消、HTTP 631、541／429、身份冲突分开；任务层保留可信内部错误码，HTTP 200 不等于详情成功。记录实际尝试次数；当前最多三次是首次加两次重试，文案应改为“已尝试 3 次”，提前终止时不能仍显示 3 次。
2. **补全会话健康管理。** 有界槽位增加租用／释放、匿名槽位标识、最近成功、连续失败和冷却状态；同一详情获取流程固定代理会话，跨订单隔离 Cookie。网络失败按阈值冷却槽位，541 按现行切换出口规则处理；通过供应商正式能力和套餐约束换会话，不能无限扩张 sid。加载页单独计数，不能等同于线路死亡，也不能永久封禁隧道入口。进程内限制不能冒充多 Worker 全局并发保障。
3. **按原因执行有限重试。** 保留每订单最多三次尝试、PostgreSQL 全局限流初始 5 RPS／上限 10 RPS、少量抖动。网络失败可以更换健康槽位重试；加载页不继续把重复下载同一类 HTML 当作完整加载方案；407 继续停止并提示配置问题，631 先归因。不同故障分别记录退避和实际收益。较长冷却可通过任务 scheduledAt 延后并释放执行槽，需保存跨领取的累计尝试预算，不能每次重新从三次开始；这属于待确认实现，不恢复周期自动刷新。
4. **建立任务总时限与阶段耗时。** 分别记录排队、限流等待、连接、首字节、正文接收、解析与全任务耗时；对重定向也计入请求预算。请求 timeout 之外设置可取消的任务总时限，取消原因单独保存。具体超时值由成功样本耗时分布决定，先不统一拉长 30 秒，也不预设缩短一定有效。Axios 支持 AbortController，见[官方说明](https://github.com/axios/axios#cancellation)。
5. **页面准确展示当前结果。** 操作区显示简短中文状态，完整错误、失败时间、实际尝试数放详情；并列展示最后成功更新时间和“本次未更新，仍为上次数据”。按任务 ID／完成时间协调本地与服务端状态，后续成功清除旧错误，旧轮询不能覆盖新任务。临时失败用明确文字和辅助色，真正身份冲突保留醒目提示；权限过滤及敏感数据保护保持。可增加“重试本批失败项”，服务端重新校验每笔权限并去重。

第一阶段可以改善可诊断性、资源使用和显示准确性；能否提升真实详情成功率需要下述实验，不能直接作出成功率承诺。

### 第二阶段：受控验证详情获取方式

先只读分析已有任务／日志，将首次成功率、三次内成功率、加载页率、541／631、超时／中断、P50／P95 耗时、队列等待及每成功订单的请求数分开。按时段、代理 Provider、匿名槽位和失败阶段比较；新加指标从上线后开始积累，不从没有记录的历史日志反推。

建议首轮挑选 10 条用户授权订单，兼顾加载页与正常详情，交错执行两组对照以减少时间偏差：

- A 组：当前 HTTP 获取方式作为基线。
- B 组：相同 Provider 下，保留单次会话重定向与 Cookie 的 HTTP 方式；Cookie 仅内存、订单隔离、不跨单共享。每条／每组最多三次尝试，两组合计最多 60 次顶层尝试；重定向也纳入全局限流和额外网络预算，建议总计不超过 180 次网络请求，达到预算即停止。请求额和套餐占用须在执行前核实。

只有仍存在加载页、且前两组不能说明问题时，才追加最多 3 条失败样本的浏览器原型：每条一次原生加载、并发 1、每条最多 90 秒／100 次网络请求。保留正常校验请求，禁止订单修改、取消和支付动作；预算耗尽或访问拒绝时记录失败，不增加绕过校验逻辑。每个订单独立 BrowserContext，并固定当次代理；Playwright 官方支持[隔离 Cookie 和存储](https://playwright.dev/docs/browser-contexts)及[按上下文设置代理](https://playwright.dev/docs/network)。这些能力只证明隔离方案可实现，不证明 Apple 会返回详情。

9 月 18 日完整 Chromium 对照已出现校验请求 200、fetchOrder 541，因此浏览器兜底尚未得到真实验证；不据此直接建设浏览器集群。若原型在多个时段反复取得此前失败样本的完整详情，再考虑独立低并发浏览器服务：只在明确加载页时进入，复用原解析器、身份与商品校验、全局预算及落库门禁。浏览器尝试占用同一订单预算，不能在三次 HTTP 失败后再叠加三次浏览器重试。

若同一 Provider 的 HTTP 与正常浏览器均不稳定，再对已有可用线路做同订单集、交错时段的受控比较，按有效详情率、耗时与单次成功成本决策，不凭首页 HTTP 200 或旧试用结果采购／切换线路。

| 阶段 | 验收条件 |
| --- | --- |

## 一、已确认需求

1. 支持自动刷新和手动刷新；手动刷新包括刷新单个订单和刷新全部订单。
2. 邮件解析出订单号和订单链接后，继续根据订单链接访问 Apple 中国官网；身份校验保持严格；解析、官网字段权威和冲突规则按[生命周期方案](真实订单生命周期与官网数据映射优化方案.md)的最新批准决策执行。
3. 2026-09-13 已批准改为首次入库刷新后仅手动刷新。付款窗口只有 30 分钟，同一时间可能存在上百条待付款订单。
4. 已付款订单仅由用户手动刷新；打开页面不自动请求官网（2026-09-09 最新决定）。
5. 允许完整重构爬虫业务模块，但不能把待实施方案写成已实现能力。

## 二、目标与边界

### 2.1 目标

- 保留新订单首次官网刷新，之后仅用户手动提交；不再生成分钟级周期任务。
- 使用持久化任务和租约，保证 API 或 Worker 重启后任务不丢失，多 Worker 不重复处理同一订单。
- 统一自动、手动单个和手动全部入口；page_open 仅保留空结果兼容入口。
- 在上百个待付款订单下控制并发、代理频率和重试放大，避免单条失败阻塞整批。
- 前端明确展示待付款订单、数据新鲜度、刷新进度和失败原因。
- 按最新官网数据权威规则解析和合并，并建立脱敏结构 Fixture 回归保护。

### 2.2 本方案不包含

- 改变邮件模板识别和订单链接提取规则。
- 本方案本身不另行定义解析口径；相关变化由已批准的生命周期方案承接。
- 把 Apple 官网支付状态用于推导内部付款人结算状态。
- 未经单独授权购买代理、执行生产 Migration、部署、重启或访问真实订单。

实施默认口径如下：

- 邮件成功创建订单后立即提交首次刷新任务。
- 2026-09-09 收紧历史空支付状态资格：未知支付不再无限等同未付款，仅待核实阶段且付款窗口内允许自动核实；付款后阶段即使支付字段为空也停止。时间优先级与队列执行复核见[爬虫说明](../design/订单爬虫.md#同步流程)。不批量回填历史业务状态。
- 2026-09-13 取消后续周期刷新：首次（initial）资格沿用既有校验；成功或失败后均由人工刷新，历史 auto/page_open 任务执行前跳过。
- 识别为已付款后立即取消后续定时计划，仅保留手动刷新能力。
- 打开订单列表与详情只读取缓存；不会自动访问官网。
- 手动“刷新全部”默认包含所有具有合法 Apple 订单链接的订单，不按付款或终态排除。
- 同一订单已有待执行或执行中任务时，新的手动触发与现有任务合并，不重复访问 Apple。

## 四、目标架构

```mermaid
flowchart TD
    A[邮件解析产生订单] --> B[提交首次刷新任务]
    D[持久化刷新队列]
    E[打开订单页面] --> Cache[读取缓存，不访问官网]
    F[手动刷新单个] --> D
    G[手动刷新全部] --> D
    B --> D

    D --> H[任务去重与优先级]
    H --> I[PostgreSQL 租约领取]
    I --> J[有限并发 Worker 池]
    J --> K[全局请求限速]
    K --> L[代理 Provider]
    L --> M[Apple 中国官网]

    M --> N[现有页面与 JSON 解析]
    N --> O[现有身份与商品校验]
    O --> P[短事务锁行与旧结果检查]
    P --> Q[更新订单、任务和日志]

    Q -->|成功| R[不再定时刷新]
    Q -->|已付款或终态| S[不再定时刷新]
    Q -->|失败| T[保留旧状态并标记数据过期]
```

核心原则是触发与执行解耦：API 和页面只提交任务，独立 Worker 负责限速、代理访问、解析、校验和写入。

## 五、任务模型

采用 PostgreSQL 持久化队列，当前规模不新增 Redis。正式字段和索引须在开发前先写入[数据库架构](../database/数据库架构.md)，再通过 Migration 实现。

### 5.1 `order_refresh_schedules`

每个订单一条调度状态，避免调度字段改变订单业务行的 `updatedAt`。

| 字段                   | 用途                                   |
| ---------------------- | -------------------------------------- |
| `order_id`             | 订单主键，一对一                       |
| `next_auto_refresh_at` | 下一次未付款自动刷新时间；已付款时为空 |
| `last_attempt_at`      | 最近一次实际发起请求时间               |
| `last_success_at`      | 最近一次成功写入时间                   |
| `last_failure_at`      | 最近一次最终失败时间                   |
| `consecutive_failures` | 连续失败次数                           |
| `freshness_status`     | `fresh/stale/refreshing/failed`        |
| `updated_at`           | 调度状态更新时间                       |

### 5.2 `order_refresh_jobs`

每次实际执行对应一条任务记录。

| 字段                 | 用途                                       |
| -------------------- | ------------------------------------------ |
| `id`                 | 任务 ID                                    |
| `order_id`           | 目标订单                                   |
| `trigger`            | `auto/page_open/manual_single/manual_all`  |
| `status`             | `pending/running/succeeded/failed/skipped` |
| `priority`           | 调度优先级                                 |
| `scheduled_at`       | 最早执行时间                               |
| `lease_owner`        | 领取任务的 Worker                          |
| `lease_expires_at`   | 租约到期时间                               |
| `attempt_count`      | 已执行请求次数                             |
| `last_error_code`    | 结构化错误码                               |
| `last_error_message` | 脱敏错误摘要                               |
| `batch_id`           | 手动全部刷新批次，可为空                   |
| `requested_by`       | 人工触发用户，可为空                       |
| `started_at`         | 开始时间                                   |
| `finished_at`        | 结束时间                                   |

数据库应保证同一订单最多只有一个 `pending/running` 任务。重复请求不创建第二次官网访问，而是关联现有任务或提升优先级。

### 5.3 `order_refresh_batches`

记录手动刷新全部的总数、待执行、执行中、成功、失败、跳过和完成时间。运行中再次点击“刷新全部”时返回现有批次，不重复创建全量任务。

### 5.4 `crawl_logs`

继续承担抓取执行审计和排障。任务状态与抓取日志职责分离：任务表回答“是否排队和完成”，日志表回答“请求、解析或写入为什么成功或失败”。原始响应和错误信息继续遵守敏感数据最小化与脱敏要求。

## 六、调度、优先级与去重

Scheduler 每 5 秒领取到期任务，但不会每 5 秒抓取所有订单。任务使用数据库事务和 `FOR UPDATE SKIP LOCKED` 领取，并写入带期限的 Worker 租约。

优先级由高到低：

1. 手动刷新单个订单。
2. 入库首次刷新任务 initial。
3. 历史 page_open 任务仅兼容读取，执行时跳过，不更新最后成功时间。
4. 手动刷新全部产生的批量任务。

调度规则：

- 周期自动调度取消；首次刷新与手动刷新共用现有有限并发和全局限流。
- Worker 异常退出后，其他 Worker 可在租约过期后重新领取。
- 页面重复加载、用户重复点击、自动任务与人工任务同时到达时，按 `order_id` 合并。
- 手动刷新单个订单可提升现有待执行任务优先级；已有请求正在执行时直接观察该任务结果。
- 单次任务保留既有最多三次请求尝试；任务最终失败后由人工重试，不安排下一分钟刷新。

## 九、页面行为

### 9.1 订单列表

- 先展示数据库缓存，不阻塞首屏等待 Apple。
- 默认支持“仅看待付款”，待付款订单优先排序。
- 显示待付款总数、最后成功刷新时间及 `排队中/刷新中/最新/已过期/失败`。
- 打开页面只读取数据库；未付款订单由独立调度器刷新。
- 后台任务完成后局部更新对应行，不能把“任务已提交”提示成“官网已更新”。
- 超过 90 秒没有成功结果的未付款订单标记为过期，并显示失败原因摘要。

### 9.2 订单详情

- 打开订单详情不提交刷新任务。
- 已有任务时复用并展示其进度。
- 手动刷新按钮始终可用，但继续经过权限、去重、限速和审计。

### 9.3 刷新全部

- 点击前明确提示目标数量和可能耗时。
- 提交后展示批次总数、待执行、成功、失败和完成状态。
- 单个失败不终止其他订单；失败项可以进入明细并单独重试。

付款倒计时优先使用官网付款截止 Epoch，回退准确官网创建时间加 30 分钟，不使用本地创建时间猜测。

## 十、代理、并发与重试

### 10.1 容量基线

100 个未付款订单每分钟产生 100 次正常请求，平均约 1.67 次/秒；若每个订单最多尝试 3 次，理论上可能放大到每分钟 300 次。建议初始参数：

- Worker 并发数：8–10。
- 代理产品能力：至少 10 次/秒。
- 应用内部请求上限：先以 5–8 次/秒压测，根据 Apple 实际成功率调整。
- 单订单最多尝试 3 次，所有重试都经过全局限速器。
- 删除订单之间固定 5–10 秒的串行等待，改用全局限速和小幅随机抖动。

### 10.2 代理 Provider

系统支持快代理隧道 Pro、快代理私密代理和网帆国内隧道三种 Provider。三套凭据预先配置到 Worker 环境后，管理员可在管理页面请求切换；Worker 只在当前批次结束后初始化候选 Provider，并在 Apple 中国首页健康检查通过后原子切换，失败继续使用旧 Provider。切换状态只保存非敏感元数据，新增或更换凭据仍需单独更新运行配置并重建 Worker。

Apple 订单入口存在跨主机重定向，因此“每次 HTTP 请求换 IP”会破坏同一次订单抓取的出口一致性。快代理隧道 Provider 使用固定 Host、端口和鉴权，每次抓取尝试生成独立 `sid`，通过 `period-0.5` 在 30 秒内固定出口；网帆隧道 Provider 为每次尝试生成 `acc/cty/reg/sid` 账密用户名，由相同 `sid` 保持单次尝试的会话出口。两种隧道模式均在发生重试时生成新 `sid` 请求切换出口，并关闭连接复用。快代理默认选择兼容性优先的企业池 `type-std` 和质量优先 `pool-q10`；私密代理继续使用提取 API 和坏 IP 冷却池。

动态隧道请求需关闭连接复用并验证“单次尝试出口固定、重试出口切换”。保持 Axios 原生代理传输并使用 gzip；真实订单对照实验未证明自定义 `HttpsProxyAgent` 有收益，不引入并行传输实现。最终产品、带宽和并发规格以真实 Apple 订单试用结果为准，不能用供应商对其他网站的可用率代替业务验收。

### 10.3 错误分类

| 错误类型                 | 处理方式                                                       |
| ------------------------ | -------------------------------------------------------------- |
| Apple `541/429`          | 目标风控；更换出口、退避重试并统计比例                         |
| 快代理 `441`             | 代理频率超限；降低速率，不修改订单状态                         |
| 代理 `407`               | 鉴权或配置故障；停止领取新任务并告警                           |
| 快代理 `517`             | 代理建链失败；更换会话和入口后受控重试                         |
| 连接超时、隧道错误       | 网络/代理错误；更换出口后受控重试                              |
| 页面 JSON 缺失或结构变化 | 解析错误；不把正常代理永久废弃                                 |
| 订单身份不匹配           | 禁止写入并告警，不增加普通业务失败计数                         |
| 商品校验异常             | 采用官网有效值，保留来源差异并显示行首冲突；身份异常仍拒绝覆盖 |

同一订单第一次失败可更换出口重试；后续重试增加短随机退避。单次 541 不直接暂停全局 Worker，只有连续订单均在三次尝试中全部收到 541 时才累计断路阈值；任一订单后续重试成功会清零计数。触发全局断路后系统必须把未付款数据标为过期并告警，不能继续显示为最新。

## 十一、数据处理保持项

以下当前正确行为在重构中必须保留：

- 只接受与本地订单号、Apple ID 完全一致的 `www.apple.com.cn` 订单链接。
- 官网返回订单号缺失或不匹配时禁止更新。
- 使用 Cheerio 从 script 中提取订单 JSON，不默认引入浏览器执行。
- 订单状态以订单项 JSON 的 `currentStatus` 为第一权威来源，清理后的可见订单文本只作兼容回退。
- 已观测的 `PICKED_UP` 映射为 `picked_up`；`PAYMENT_EXPIRED_STORED_ORDER` 映射为 `payment_expired/unpaid`，保留商品原始状态。
- 保留付款、取货、商品和门店解析；官网没有总计标签和金额时记录为未提供，不伪造金额或解析错误。
- 官网有效商品数量为权威，含取消后的 0；导入值保留在来源快照，差异可查看。
- 网络请求在数据库事务外执行。
- 写入时锁定订单，并拒绝爬取期间产生的旧结果。
- 失败保留旧业务状态，成功后才更新 `lastCrawledAt` 和官网字段。

## 十三、验收标准

### 13.1 业务验收

- 新订单在邮件入库后立即进入首次刷新队列。
- 首次刷新结束后等待超过 60 秒不再产生自动任务，人工刷新仍可提交和完成。
- 已付款订单在后续观察周期内不产生定时任务。
- 打开列表和详情均不触发官网刷新，旧 page_open 兼容入口不创建任务。
- 手动单个和手动全部均可执行并展示真实进度。
- 付款状态变化后，订单及时移出待付款集合。
- 刷新失败时保留旧状态，并明确显示最后成功时间和已过期状态。

### 13.2 一致性与可靠性验收

- 自动、页面和人工触发同时发生时，同一订单只访问 Apple 一次。
- API、Worker 重启后，待执行任务、批次和暂停原因不丢失。
- 两个 Worker 并行运行时不重复领取或覆盖同一订单。
- 单条失败不阻塞其他订单，刷新全部可以部分成功。
- 并发爬取期间发生人工修改时，旧结果不会覆盖新数据。

### 13.3 错误与安全验收

- 541、429、441、407、代理传输、解析、身份和数据库错误分别记录。
- 日志不包含 Apple 密码、完整订单链接、代理密码或不必要的个人信息。
- 权限不足不能提交单个、全部或恢复调度操作。
- 代理、Apple 或数据库异常时不能伪造刷新成功。

### 13.4 测试边界

- 单测和模拟服务证明内部规则，不证明真实 Apple 或代理兼容性。
- PostgreSQL 集成测试证明租约、事务、索引和并发行为，不证明生产运行。
- 真实订单、代理购买、生产 Migration、部署、重启和业务观察分别需要明确授权和验收记录。

## 十四、开发开始前检查

1. 先更新数据库架构和 API 契约，再编写模型、Migration、Controller 和前端调用。
2. 冻结一组脱敏 HTML/JSON Fixture，保证原解析规则在重构前后结果一致。
3. 明确快代理测试账号、隧道规格、测试订单和允许的请求窗口。
4. 定义一分钟时效、数据过期、最终成功率和 541 比例的业务验收阈值。
5. 为 Migration、调度切换、Worker 扩容和代理切换准备回滚方案。
6. 每个实施批次更新[开发进度](../development/开发进度.md)，区分开发自测、集成测试、真实官网验收和生产验收。

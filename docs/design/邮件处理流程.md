## 进程与事实来源

[邮件 Worker](../../src/workers/emailWorker.js)独立运行[emailService](../../src/services/emailService.js)。跨进程状态、重试、幂等、人工处理和 IMAP 确认均以 PostgreSQL 为事实来源；API 进程不使用自己的内存状态代表 Worker。

```text
启动并打开邮箱
  → 按邮箱身份和 UIDVALIDITY 恢复接收游标；首次回查最近 24 小时
  → 下载完整 MIME
  → 以邮箱身份哈希 + UIDVALIDITY + UID 先写 received
  → MIME 只解析一次并保存元数据、Message-ID、Authentication-Results
  → 主题关键词过滤
      → 未命中：记录 SUBJECT_NOT_ALLOWED，清除正文和可识别元数据，保留最小 ignored 审计
  → 可选 From 精确地址／精确域名白名单
      → 未命中：记录 SENDER_NOT_ALLOWED，保留加密 MIME 并进入 manual_review
  → 严格解析订单字段
      → 永久错误：manual_review
      → 临时错误：retry_wait，每分钟重试一次，最多自动重试 3 次
  → 同一事务创建/确认订单、邮件终态和首次刷新任务
  → succeeded / superseded / manual_review / ignored 持久化后按 IMAP_MARK_SEEN 确认已读
```

`mail` 事件立即触发 UID 扫描，独立的 30 秒计时器兜底扫描；两者均不使用 UNSEEN。邮箱身份 + UIDVALIDITY 对应持久化游标，初次固定 24 小时起点；每批最多 20 封，整批 MIME 可靠入库后才推进游标，下载或持久化失败不越过缺口。忽略 UIDNEXT=0，UID 范围返回结果再次按下界过滤。重连恢复游标，进程重启也保留未完成范围；UIDVALIDITY 变化建立独立游标。`IMAP_MARK_SEEN=false` 时记录为 `not_required`，不会通过 500ms 递归搜索形成处理循环。

## 来源与身份

主题关键词为 `NULL`、`预订助手`、`预订成功` 之一。`IMAP_ALLOWED_SENDERS` 配置标准化完整地址精确匹配，`IMAP_ALLOWED_SENDER_DOMAINS` 配置标准化域名精确匹配；两者任一命中即通过，只有两者都为空时才接受任意标准化 From。域名规则只接受地址中 `@` 后的完整域名相等，例如 `lanu.cn` 不接受 `evil-lanu.cn` 或 `sub.lanu.cn`。主题命中但 From 未命中的邮件进入 `manual_review` 并保留加密 MIME，避免动态发件地址误判后不可恢复；无订单关键词的普通邮件继续最小化为 `ignored`。

From 地址／域名白名单只是业务过滤，不是密码学身份验证。仅主题或域名相似仍不能绕过严格订单信息块、字段 Schema、Apple URL/订单号一致性和订单事务校验。`Authentication-Results`（含服务端提供的 DKIM/SPF 结果）原样记录，当前不作为阻断条件。

邮箱身份由 IMAP host、账号和邮箱文件夹规范化后 SHA-256，运行日志不输出账号。主幂等键为 `(mailbox_identity_hash, uid_validity, email_uid)`；Message-ID 和 MIME SHA-256 辅助识别重新编号、跨邮箱或相同内容投递。相同订单号由 PostgreSQL 事务级 advisory lock 串行化，不同邮件分别留痕，后到事件关联已有订单并进入 `superseded`，不覆盖订单。

## 状态、重试与恢复

| 状态            | 含义                                       | IMAP 已读确认 |
| --------------- | ------------------------------------------ | ------------- |
| `received`      | 原始 MIME 和稳定身份已提交                 | 否            |
| `ignored`       | 主题未命中的普通邮件或获授权用户有理由关闭 | 是            |
| `parsing`       | 正在 MIME/字段解析                         | 否            |
| `retry_wait`    | 临时错误或中断恢复，等待数据库调度         | 否            |
| `manual_review` | 永久错误或第 3 次自动重试仍失败            | 是            |
| `processing`    | 正在执行订单事务                           | 否            |
| `succeeded`     | 新订单、邮件结果和首次刷新任务全部提交     | 是            |
| `superseded`    | 重复事件或已有订单已关联，不覆盖已有订单   | 是            |

数据库连接、锁冲突等临时错误初次失败后等待 1 分钟；之后在约第 1、2、3 分钟各自动重试一次，第三次仍失败转 `manual_review`。永久 MIME、格式或业务校验错误直接转人工。`attempt_history` 加密记录尝试开始、失败、成功、重复和中断恢复事件，不通过中文错误文本判断是否重试。

多个 Worker 使用 `FOR UPDATE SKIP LOCKED` 领取到期记录。停留在 `parsing/processing` 超过 5 分钟，或 `received` 超过 1 分钟尚未开始处理的记录恢复为立即可领取的 `retry_wait`。未提供已校验 MIME 的自动重试先重新提取元数据并检查来源，不能因中断恢复绕过主题／From 校验。连接命令及 FETCH 正文接收限时 30 秒；断线取消该连接的网络等待，旧连接事件与回调不影响新连接。补查计时不因重连重置，繁忙时合并触发并继续扫描。Worker 关闭时取消网络等待，最多等待 10 秒让在途处理到安全点，再关闭数据库；已保存的未完成记录由持久化重试恢复。

终态提交后才调用 IMAP `\Seen`；确认失败写入独立的确认状态和下一分钟重试时间。邮件处理成功与 IMAP 确认成功是两个不同结论。

## 人工处理与保留

`/email-processing` 页面和 `/api/email-processing/*` API 按逐用户邮件权限开放，普通用户也可获授权。`email.read` 查看全局处理列表和运行指标；`email.content.read` 依赖前者，查看未脱敏的订单邮件 MIME、字段及审计；`email.process` 依赖前两者，可修正 Apple ID、密码、订单号/链接/时间、商品、取机人、完整身份证号、联系方式/地址、付款方式、标签和订单内部状态；提交仍须通过完整 Schema、Apple 域名/路径/订单号一致性、订单唯一性、乐观锁和事务校验。

获授权用户完整查看、重新解析、保存草稿、入库和人工关闭均写入加密 `audit_history`。人工忽略或关联已有订单必须填写原因。原始 MIME、解析结果、人工草稿和最终数据保留 180 天，到期清除内容但保留状态、错误码、订单关联、尝试历史和操作审计。主题未命中的普通邮件立即清除 MIME、Message-ID、Authentication-Results、From 和 Subject，只保存稳定 IMAP 身份、时间、`SUBJECT_NOT_ALLOWED` 和 `ignored` 状态。主题命中但 From 地址／域名白名单未命中的疑似订单邮件进入 `manual_review`，保留加密 MIME、元数据和 `SENDER_NOT_ALLOWED`，允许持有 `email.process` 的用户重新解析、修正、入库或有理由关闭。

不自动授予任何用户邮件权限。这组权限不按订单 TAG 过滤，独立于订单级 `order_mail.manage`；仅有查看权限的用户不显示处理按钮，详情字段只读。

详细 API 见[API 契约](API设计.md)，严格字段规则见[邮件解析器](邮件解析器.md)，数据库字段见[数据库架构](../database/数据库架构.md)。

## 收信时效与诊断

扫描起止、耗时、匹配数、新接收数、连接代际与脱敏断线原因分别记录。指标区分心跳和最近一次成功扫描：心跳正常但成功扫描超过 90 秒、从未成功扫描或最近扫描失败时，不显示收信正常。最近收信仅由新持久化邮件更新，重复回查不会刷新它。正常邮箱／数据库下 60 秒内入库是业务验收目标，必须单独进行真实邮件验收。

独立权限 order_mail.manage（查看及转发）依赖 orders.read；普通用户默认不授予，管理员沿用固定全权。订单列表入口及所有邮件接口验证权限与 orders.tag 范围。原管理员邮件解析页面不变。

邮件MIME及元信息加密保留180天。过滤邮件仅计数不保存内容。前端区分未启用、尚未开始、同步中、异常与最近成功；无关联邮件不代表邮箱无邮件。正文默认显示安全HTML原始排版，并保留纯文本切换：服务端移除脚本、表单、事件属性、危险URL、SVG等主动内容，浏览器在无脚本权限的沙箱和严格内容安全策略中渲染。CID图片通过现有鉴权附件接口读取后以内存data URL显示；远程图片默认阻止，用户明确点击后才允许HTTPS图片加载；附件继续强制认证下载。纯文本优先从去除head/style后的HTML提取，HTML不存在时才回退MIME的text/plain，避免直接显示CSS源码。

可选择一个或多个邮件联系人，并可补充一个手动输入的目标邮箱，单次最多50个不同邮箱，可附备注；转发采用普通正文转发：有 HTML 时保留原邮件的表格排版、样式、链接、远程图片引用和 CID 内嵌图片，并提供纯文本备用；无 HTML 时发送纯文本。保留原有 PDF 等附件，并按用户要求继续附加原始 EML 文件；EML 是额外保留的原件，收件人无需打开附件即可直接阅读排版正文。备注与原发件信息安全转义后置于正文顶部；系统内预览和转发共用服务端HTML清理规则，移除活动脚本、事件属性及危险链接，服务端不下载远程图片。发件地址固定为授权账号。队列以操作人和幂等键去重并绑定完整请求。发送前重新验证用户状态、权限、TAG范围及内容有效期。明确SMTP临时拒绝可重试；网络超时、进程中断或接受后落库失败标记结果不明，不自动重发；accepted只表示已提交邮件服务器，不代表最终送达。

## 官方订单邮件生命周期归并（2026-09-21）

订单归档成功后，在同一数据库事务幂等创建 `order_mail_processing_jobs`。订单邮件 Worker 独立领取任务并执行 MIME 解析、模板正文识别、唯一订单号和整单商品范围核对，再追加 `order_mail_events`；解析失败不会回退收信游标，也不会阻塞后续邮件。任务使用 PostgreSQL 行锁和 `SKIP LOCKED`、60秒租约、30秒递增等待及最多5次尝试，Worker 重启后可恢复超时任务。


生命周期接受七类已核定模板：确认邮件得到 confirmed，处理邮件得到 processing/paid，正文明确已可取货的更新／取货信息邮件得到 ready_for_pickup/paid；标题精确为“个人设置辅导，帮你上手新 iPhone。”且归档／重解析／系统订单号一致的邮件得到 picked_up/paid。辅导邮件本身不列商品，因此只对该精确模板记录 `not_required_personal_setup` 并跳过整单商品比对；新增过期与取消模板分别得到 `expired` 与 `cancelled`，要求完整订单号、标题和明确正文事件一致；Apple 可逐件发送终态通知，因此这两类模板记录 `not_required_terminal_notice` 并跳过单封商品数量门槛，不同取消邮件按消息 ID 计数，同一封重放不重复计数。其他模板仍必须完整核对商品范围。电子收据和广告继续排除；未知或相似标题、正文事件不匹配、订单号不唯一、其他模板缺商品或商品范围不完整均留存事件并标记待核对。DKIM 结果只作诊断，不参与应用资格。

同一订单按全部当前有效事件单调归并：unknown → confirmed → processing → ready_for_pickup → picked_up，乱序旧邮件不能回退；paid 不能由确认、过期或取消邮件撤销。归并优先级为普通阶段 → `partially_cancelled`（部分取消）→ `cancelled`（已取消）→ `expired`（已过期），旧邮件不能回退。取消邮件数按不同归档消息 ID 计数，与订单商品总件数比较；两件订单一封取消为部分取消、两封取消为已取消，一封取消加一封过期为已过期。过期优先与发信／收信顺序无关。单封取消不要求商品数量覆盖全单，重放只取同一消息当前有效修订；商品总件数缺失或非法时标记 `ORDER_QUANTITY_UNKNOWN` 待核对，保留部分取消。人工核定状态仍按既有权限、原因与版本要求应用。正式取货通知优先，其次按邮件发信时间选择当前门店／日期／时段；营业时间内到店不补造日期或具体时间。picked_up 是邮件的单向履约推定，邮件发信时间只作证据时间，不生成实际取货时间，不修改人工取货记录、结款或收据结论。没有该邮件也不能反推未取货。

三个开关相互约束：`ORDER_MAIL_LIFECYCLE_PARSE_ENABLED` 控制解析，默认 true；`ORDER_MAIL_LIFECYCLE_APPLY_ENABLED` 控制订单字段应用，默认 false；`ORDER_MAIL_PAYMENT_TASK_APPLY_ENABLED` 控制付款任务完成，默认 false，且只有订单应用同时开启时才生效。应用时锁定订单，在同一事务更新邮件字段、标记事件、锁定并完成未完成的付款任务及追加 `mail_payment_confirmed` 事件；保留任务负责人、付款人、备注、截图和结算数据。邮件先到时任务保持 waiting_order，公共订单创建事务会在付款任务建立后关联并应用已有结论。

### 订单关联邮件的查看与转发授权（2026-09-21）

普通用户仅需查看和转发时，授予 `orders.read`、`order_mail.read`、`order_mail.forward` 并配置订单 TAG 范围。`order_mail.read` 包含邮件列表、完整正文、附件和转发记录；`order_mail.forward` 只增加转发能力，不允许重新解析、人工核定或收单入库。`order_mail.manage` 为兼容既有授权仍包含全部订单邮件操作，权限名称明确包含管理能力；截图中的 `email.*` 是独立的收单处理权限，不用于转发。发送队列在真正发信前重新检查转发权限，撤权后不继续发送。

### 邮件联系人与批量转发（2026-09-22）

管理员在“邮件联系人”表格页新增、编辑、删除及搜索全局联系人（姓名＋邮箱，邮箱唯一）。有转发权限的用户可在订单邮件抽屉通过可搜索的多选下拉框选择：点击展开，按姓名/邮箱过滤，选中项以标签显示，点击外部或按 Escape 收起，支持跨搜索保留多选；候选项显示“姓名 <邮箱>”；保留手动邮箱。选中的邮箱去重，确认完整收件人列表后，在同一事务排队，再逐收件人独立发送并记录结果；一个收件人发送失败不影响其他任务，彼此不暴露其他收件人的邮箱。提交超时可用原请求重试，避免重复排队。联系人修改或删除不改变已提交任务的邮箱快照，既有正文、附件、原始 EML 和发送前权限复核继续保留。

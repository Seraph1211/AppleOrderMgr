## 二、实施前基线与数据边界

### 2.1 实施前链路

```text
邮件 Worker 启动
  → 校验 IMAP、数据库和加密配置
  → 连接 IMAP 并打开邮箱
  → 启动时及 mail 事件搜索 UNSEEN
  → 下载整封 MIME
  → 解析 From、Subject 并执行主题和白名单过滤
  → 再次解析 MIME，提取订单字段
  → 在事务中校验并创建订单、快照、邮件日志和首次刷新任务
  → 根据 IMAP_MARK_SEEN 与处理结果标记已读
  → 批次结束约 500ms 后再次搜索 UNSEEN
```

`isProcessing` 只避免同一进程重复进入批次，不是数据库级幂等锁；同一批中的邮件实际可以并发处理。邮件 Worker 与爬虫 Worker 是独立进程，邮件成功入库只负责创建持久化刷新任务，不直接执行 Apple 官网请求。

### 2.2 数据权威

| 数据                                 | 当前权威来源与处理                           |
| ------------------------------------ | -------------------------------------------- |
| Apple ID                             | 邮件正文中的称呼字段                         |
| 订单号、订单链接                     | 邮件中的 Apple `vieworder` 链接              |
| 商品型号、名称、数量                 | 邮件；商品数量不得被官网普通结果覆盖         |
| 取机人、身份证后四位、付款方式、标签 | 邮件订单信息行                               |
| 联系方式、地址、Apple 密码快照       | 由基础资料匹配补充                           |
| 官网订单状态、支付状态、金额、图片   | 后续官网刷新，不由邮件估算                   |
| 原始 MIME、解析结果                  | 邮件处理记录；敏感正文和解析数据必须加密存储 |

### 2.3 实施前已有能力

- 邮件 Worker 独立入口、IMAP TLS 默认校验和生产必填配置校验。
- 主题关键词与标准化 From 地址白名单过滤。
- 单商品、多商品、Apple ID、订单号、链接、时间、取机人、付款方式和标签的基础提取。
- 新订单、基础资料快照、邮件日志和首次官网刷新任务的事务写入。
- 订单号和 `email_uid` 提供的局部重复保护。
- `raw_content` 与 `parsed_data` 通过模型层加密存储。
- 主动停止不重连，连接异常共享单一重连定时器。

### 3.1 已复现证据

使用仓库现有两个合成 HTML 邮件执行解析：

- 单商品和多商品主体字段能够提取，但都会先产生一个由称呼和 Apple ID 截断形成的“商品解析失败”片段。
- 两个样例的标签断言均失败；实际标签包含 Apple 订单链接和后续邮件正文。
- 脚本最终仍报告 `2 通过, 0 失败` 并返回退出码 0，证明当前脚本不能作为回归门禁。
- `emailService.test.js` 的两个 Jest 用例通过，但只覆盖“合法发件人 + 主题”和“伪造发件人 + 主题”两种过滤场景；对应服务 Statements 覆盖率为 9.42%。
- 样例正文写明中国本地时间，当前容器结果却保留同一时钟值并标记为 UTC，未正确表达 `+08:00`。

以上仅为合成样例和静态证据，未据此推断生产历史数据已经污染。历史订单标签、邮件失败和漏单情况需要另行授权后进行只读审计。

## 四、已确认的目标规则

1. 商品解析采用全有或全无原则：任一商品无法识别时不创建订单，整封邮件进入待人工处理队列，禁止只保存部分商品。
2. 标签只能取订单信息行最后一个字段，不得包含链接、领取说明、页脚或其他后续正文。
3. 相同订单号、不同邮件事件分别保留审计记录，但默认不覆盖已存在订单；未来若有订单变更邮件，另行定义允许更新的字段和优先级。
4. 临时错误使用数据库持久化重试；无法通过原样重试解决的格式或业务校验错误进入待人工处理队列。
5. 首次建立邮箱代际游标时回查最近 24 小时，之后按可靠 UID 续扫；mail 立即扫描，每 30 秒兜底，不依赖 `UNSEEN`。
6. 主幂等键使用“邮箱身份 + UIDVALIDITY + UID”，同时保存 Message-ID 和 MIME SHA-256，用于识别重新编号、转投或跨邮箱重复邮件。
7. 原始 MIME 加密保存并设置保留期限；运行日志只记录内部邮件记录 ID、状态、脱敏错误码和必要指标。
8. 第一阶段先修复解析正确性并建立正式 Jest Fixture；后续阶段再增加 Migration、状态机、持久化重试、人工处理页面与人工重放。
9. 必须新增邮件人工检查和处理页面，并以快速重新入库为核心目标；不得要求管理员直接修改数据库。

## 五、目标处理状态与流程

### 5.1 建议状态

| 状态            | 含义                                           | 是否允许确认邮件已读                 |
| --------------- | ---------------------------------------------- | ------------------------------------ |
| `received`      | 原始 MIME 与幂等标识已经持久化                 | 否                                   |
| `ignored`       | 主题未命中的普通邮件或管理员有理由关闭         | 是                                   |
| `parsing`       | 正在解析和校验                                 | 否                                   |
| `retry_wait`    | 临时错误，等待下次自动重试                     | 否；补漏不以未读状态作为唯一依据     |
| `manual_review` | 自动重试无意义或已达到上限，等待人工处理       | 是，但必须先持久化原始邮件和失败状态 |
| `processing`    | 正在执行订单事务写入                           | 否                                   |
| `succeeded`     | 订单处理与审计记录已经提交                     | 是                                   |
| `superseded`    | 重复邮件或相同订单的后续事件已留痕但不覆盖订单 | 是                                   |

“待人工处理”替代面向用户的“死信”称呼。标记已读只表示 IMAP 不再反复投递；邮件原文、错误和重放能力仍保存在系统中。

### 5.2 目标链路

```text
发现邮件
  → 读取邮箱身份、UIDVALIDITY、UID、Message-ID
  → 计算 MIME SHA-256
  → 先写入 received 记录及加密原始 MIME
  → 检查稳定幂等键和内容指纹
  → 执行来源过滤
      → 主题未命中：记录 SUBJECT_NOT_ALLOWED 后最小化为 ignored
      → 主题命中但 From 地址／域名未授权：记录 SENDER_NOT_ALLOWED 后进入 manual_review
  → MIME 只解析一次
  → 精确定位订单信息块
  → 严格解析并校验所有字段和全部商品
      → 临时错误：retry_wait
      → 永久错误或超过重试上限：manual_review
  → 事务创建或确认订单、快照、处理结果和首次刷新任务
      → 同订单不同邮件：保留记录，不覆盖订单
  → succeeded / superseded
  → 在终态持久化成功后确认 IMAP 已读
```

### 5.3 错误分类

| 类型         | 示例                                                            | 处理                                                            |
| ------------ | --------------------------------------------------------------- | --------------------------------------------------------------- |
| 临时错误     | 数据库暂时不可用、连接超时、事务锁冲突、IMAP 短暂中断           | 写入 `retry_wait`、持久化次数和下次执行时间，按退避策略自动重试 |
| 永久解析错误 | MIME 无法解析、订单信息块不存在、商品格式未知、标签边界无法确定 | 写入 `manual_review`，不反复原样重试                            |
| 永久业务错误 | 订单号、Apple ID 或数量不合法，必填字段缺失                     | 写入 `manual_review`，等待人工核对或规则修复                    |
| 重复事件     | 稳定幂等键或内容指纹已处理                                      | 返回既有结果或写入 `superseded`，不重复建单                     |

错误类型必须使用稳定错误码，错误描述脱敏。不得依赖中文 `error.message` 片段判断是否重试。

## 六、解析器优化设计

### 6.1 MIME 与正文处理

- 每封邮件只调用一次 mailparser，过滤元数据和业务正文共享同一个解析结果。
- 保留正文结构和边界，不先把整封邮件压缩为一行再用跨全文贪婪正则提取。
- 优先从明确的 HTML 节点或完整文本行定位订单信息块；HTML 与纯文本分别使用适配器，并输出统一的标准化输入。
- 对邮件大小、字符集、正文缺失、附件和异常 MIME 设置明确限制与错误码。
- 原始 MIME 使用 Buffer 计算哈希和 Base64，不允许字符串与 Buffer 产生不同存储语义。

### 6.2 字段提取与验证

- Apple ID、订单号、订单 URL、订单时间、商品、取机人和尾部字段分别提取，最后通过统一 Schema 验证。
- Apple URL 必须限制为允许的域名和 `vieworder` 路径，并校验 URL 中订单号与输出订单号一致。
- 订单正文时间按明确时区解析；邮件头 `Date` 与正文时间分别保存或明确选择规则，不用容器本地时区猜测。
- 商品信息只在已经定位的商品段内按 `@` 分隔，禁止把 Apple ID 中的 `@` 当成商品分隔符。
- 每个商品必须满足型号、名称和正整数数量要求；任一商品失败即整封邮件失败。
- 不把颜色和容量拆成独立保证字段；它们仍属于商品名称，除非未来有单独批准的业务契约。
- 取机人姓名、身份证后四位、付款方式和标签必须有长度、字符和空值限制。

### 6.3 标签边界示例

原始订单信息行为：

```text
MG0A4CH/A-iPhone 17 Pro Max 星宇橙色 1T x 2/李浩/603X/支付宝/-/指定信息/天津
```

即使下一行紧接订单链接和领取说明，解析结果也只能是：

```json
{
  "recipientName": "李浩",
  "recipientIdLast4": "603X",
  "paymentMethod": "支付宝",
  "tag": "天津"
}
```

禁止把“点击此处查看订单详情”、Apple URL、领取说明或页脚拼入 `tag`。

## 七、持久化、幂等与重试设计

### 7.1 数据模型原则

优先演进现有 `email_logs`，避免建立另一套重复的邮件事实来源。正式字段、类型和索引需在实施前先写入数据库架构，候选能力包括：

- 邮箱身份的不可逆标识，不在普通日志中输出原始邮箱账号。
- `uid_validity`、`email_uid`、`message_id`、`mime_sha256`。
- `status`、`error_code`、脱敏 `error_message`。
- `retry_count`、`next_retry_at`、`last_attempt_at`。
- `resolved_at`、`resolution_type`、`resolved_by`。
- 加密原始 MIME、加密解析结果和加密人工修正草稿。
- “邮箱身份 + UIDVALIDITY + UID”复合唯一约束；Message-ID 和 MIME SHA-256 使用适合缺失值与重复值的辅助索引。

历史 `email_uid` 数据没有邮箱身份和 UIDVALIDITY，Migration 不得猜测生成具有虚假语义的幂等键。需要保留 legacy 状态，并通过只读预检确认转换策略。

### 7.2 重试和确认

- 自动重试由数据库状态和调度时间驱动，不以进程内 Map 或邮件是否未读作为唯一事实来源。
- 重试次数、每次错误码、开始和完成时间必须可审计；退避间隔和最大次数配置化。
- 达到上限后进入 `manual_review`，不会自动丢弃，也不会继续高频扫描。
- 标记已读必须在终态记录提交后执行；确认失败需要记录并进入可恢复的确认重试，而不是只写日志。
- Worker 关闭时停止领取新邮件，并等待已领取邮件到安全停止点后再关闭数据库连接。

### 7.3 回溯补漏

- 首次回查最近 24 小时；游标和初次起点持久化，重连／重启续扫，每 30 秒补查。
- 回溯条件使用时间、UID 范围或可验证的服务器能力，不只使用 `UNSEEN`。
- 所有回溯结果先经过稳定幂等检查；重复扫描不能重复创建订单、重复增加重试次数或重复生成刷新任务。

## 八、人工检查与快速重新入库页面

### 8.1 页面目标

新增“邮件处理”管理页面，默认进入“待人工处理”列表。目标是在不查看数据库、不复制原始邮件、不重新录入全部字段的情况下，快速完成重新解析、少量修正、预览和入库。

页面不等同于普通订单新增页面：它必须保留原邮件、解析尝试、错误、修正和最终订单之间的审计关系。

### 8.2 列表设计

默认展示：

- 接收时间、完整邮件主题和完整发件人；本页面仅 admin 可访问，不做字段脱敏。
- 已识别订单号、错误类型、错误摘要、尝试次数。
- 状态：待重试、待人工处理、处理中、已入库、已忽略。
- 推荐动作：重新解析、补充字段、查看已有订单、忽略。

支持按状态、错误类型、接收日期和订单号筛选；默认把最新、可直接重新解析和字段缺失较少的记录排在前面。列表行直接提供“重新解析并预览”快捷操作，并支持对同一解析错误批量重新解析。

### 8.3 快速处理交互

1. 点击“重新解析并预览”后，后台使用当前解析器生成新预览，不立即写订单。
2. 解析完整时，页面突出显示订单号、商品数量和目标标签；管理员可一键确认入库。
3. 仍有异常时，打开侧边抽屉或详情页，并预填已经可靠提取的字段。
4. 商品使用可增删的表格行，支持型号、名称和数量的行内校验；不得要求输入 JSON。
5. 标签字段旁展示“仅限订单信息行最后字段”的来源提示，并提供原始片段对照。
6. 提交前展示入库预览和与既有订单的重复检查结果。
7. 相同订单已存在时显示既有订单入口，允许将邮件标记为“已有订单”，但不提供默认覆盖按钮。
8. 确认后调用统一订单领域服务，在事务中创建订单、邮件处理结果和首次刷新任务。
9. 成功后自动从待处理列表移除，并提供“查看订单”和“处理下一封”快捷入口。

### 8.4 安全与审计

- 页面、详情、重新解析和确认入库均必须经过后端权限校验；仅隐藏菜单或按钮不构成权限保护。
- admin 打开详情时展示完整解密原文和全部人工字段，不做字段脱敏；每次完整查看必须记录操作审计。

6. 临时错误初次失败后等待 1 分钟，随后每分钟重试一次，最多自动重试 3 次，即约第 1、2、3 分钟分别重试；第三次仍失败进入 `manual_review`。

### 14.1 发现规则与调度

- `mail` 事件立即触发扫描，每 30 秒触发独立的兜底扫描；两条路径都按邮箱身份、UIDVALIDITY 和 UID 发现新邮件，不以 `UNSEEN` 为资格。已读与未读只影响 IMAP 确认，不代表系统是否处理过邮件。
- 游标仅在对应邮件原文与接收记录已可靠入库后推进；不能直接取最大的成功订单 UID，不能越过下载或持久化失败的 UID。解析失败但已经可靠入库的邮件由现有持久化重试／人工队列接续。
- 初次连接保留有界启动回查；重连从可靠接收进度续扫。若 UIDVALIDITY 变化，按新的邮箱代际重新建立进度；进度已通过正式 Migration 保存到 email_mailbox_cursors。当前实测 UIDNEXT 为 0，不得依赖它推断没有新邮件。
- UID 范围搜索可能包含低于请求起点的已有 UID，结果需再按数值下界过滤；同一邮箱、UIDVALIDITY、UID 沿用数据库唯一约束，不能靠读写 Seen 标记去重。
- 补查计时随 Worker 生命周期运行，断线只暂停网络执行，不重置计划到期时间；重连后合并并执行到期扫描。并发请求保留扫描类型、最早下界和覆盖范围，不能降级为 UNSEEN。

### 14.2 连接与超时

- 保留已验证可用的 NOOP 保活，但不把保活等同于业务发现；当前邮箱未声明 IDLE 支持。每 30 秒的 UID 搜索同时提供业务扫描进度证据。
- SEARCH、FETCH、正文接收及 STORE 确认均设置有界的命令／批次截止时间；当前单命令 30 秒，批次按数量有界分片，不让单封邮件无限占用批次。超时进入现有重试策略并受控重连。
- 连接使用代际标识；旧连接的 error/end/close 和迟到回调不能修改新连接状态。断线时拒绝旧连接未完成的网络等待、释放扫描占用、保留未完成范围，再建立唯一重连任务。
- 停止服务先停止领取并有界等待已持久化处理，取消未完成网络等待，避免 SIGTERM 因 Promise 未结束而永久等待。

### 14.3 诊断与验收

- 日志记录扫描原因、起止与耗时、匹配数量、新接收数量、连接代际、断线类型及脱敏原因；不记录账户、密码、邮件正文和订单链接。心跳与最近一次成功扫描分开，不再仅凭 connected=true 判断收信正常。
- 本地必须覆盖：邮件立即变已读、没有 mail 事件、批次中到来补查、连续重连、SEARCH/FETCH 不回调、旧连接迟到事件、UIDVALIDITY 变化、UIDNEXT=0、范围返回旧 UID、同一封重复扫描、批次中部分下载失败。
- 建议业务验收目标：邮箱与数据库正常时，从 IMAP INTERNALDATE 到邮件持久化／订单创建不超过 60 秒；断线恢复后 60 秒内补回断线期间邮件。超时或解析异常必须明确显示，不用健康心跳掩盖积压。该目标尚未在真实邮箱实测达标。
- 用授权的真实新订单分别验证未读、立即已读和断线补回场景；核对订单、首次刷新和付款任务各只生成一次。官网刷新时效另行记录，不能混入邮件入库时效结论。

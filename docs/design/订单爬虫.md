>

>
> 验证范围：Jest、本地隔离 PostgreSQL、快代理隧道／私密代理／网帆国内隧道、Apple 中国首页及用户授权的 83 条真实订单只读对照；未验证真实订单写库、邮箱、完整浏览器业务流程和生产环境

## 入口和数据来源

兼容抓取入口为[crawlerService.js](../../src/services/crawlerService.js)，独立调度入口为[crawlerWorker.js](../../src/workers/crawlerWorker.js)。持久化任务、策略、限流与代理 Provider 位于 `src/services/crawler/`；现有抓取、解析、校验和短事务写入仍由兼容门面维护，后续再完成 Parse、Validate、Persist 的物理拆分。

使用 axios 获取 Apple 订单页，通过 cheerio 读取 script 中的订单 JSON。直接返回完整 orderDetail 时无需执行网页 JavaScript；2026-09-18 真实复现的部分响应仅含 guestOrderSpinner，页面脚本会等待浏览器校验后调用 fetchOrder。当前 HTTP 爬虫不执行该浏览器校验，遇到加载／校验页按解析失败有限重试，不能承诺每次取得详情。HTTP 541 仍按 Apple 风控处理；不绕过校验、不因局部失败自动切换代理供应商。

请求仅接受 `https://www.apple.com.cn/xc/cn/vieworder/{订单号}/{订单联系邮箱}` 对应的合法来源与身份；校验协议、主机、端口、路径、URL 用户信息及订单号，返回结果的订单号也必须匹配。订单联系邮箱可以与邮件提取的下单账户 Apple ID 不同，不做相等校验，不用联系邮箱覆盖入库 Apple ID（2026-09-09 用户确认）。有合法订单链接时不依赖关联 Apple 账号；仅缺少链接的历史兼容路径才尝试用已有 Apple ID 构造入口。

## 同步流程

### 浏览器取数接入（2026-09-21，API 已发布、全局暂停保持）

内部 `crawlAndUpdateOrder` 支持由受信任的本机采集实现提供 `acquireOrderPage` 函数。它接收已校验的原始订单链接、订单号和取消信号，返回正常官网页面的 `pageUrl`、`orderJson` 与可选 `html`；服务器仍自行解析和校验身份，然后复用原有短事务、并发保护、字段合并和审计。该函数仅为服务内部依赖，不接受 HTTP 请求体指定函数或直接提交已归一化的业务状态。

2026-09-21 用户收窄浏览器刷新范围：只采集订单号、逐商品官网阶段与状态说明、商品名称／型号规格／明确数量。订单号仅用于身份校验，不改写订单身份。金额、支付方式、日期、门店、地址和付款截止均不作为成功必填，也不通过本入口更新。服务器仅合并状态、商品及对应观察／校验／审计元数据；保留已有支付与取货派生字段、非商品校验问题和人工付款任务。状态变化仍参与既有自动刷新停止判断。商品不完整时保留已有商品并提示待核对；不会按条目数猜测数量。此为当前实现契约，生产版本与真实验收状态见开发进度。

浏览器结果只接受 HTTPS、无 URL 用户信息／自定义端口、Apple 中国 `secure数字.www.apple.com.cn` 主机及匹配订单号的访客订单路径。加载页、无订单项、错误身份及超时结果均不进入业务合并；结果审计标识 `acquisitionMethod=browser`，不保存页面正文、访客令牌或 Cookie。取数预算仍为 `CRAWLER_TASK_TIMEOUT_MS`，迟到结果不能更新订单；采集实现必须响应取消信号并关闭自己创建的任务页面。

回传 API 已随 `20260921-browser-batch` 发布，最小字段边界随 `20260921-browser-query-fix` 生效，生产仅 API 配置 `BROWSER_ORDER_REFRESH_ENABLED=true`，全局暂停保持；代码默认 false。扩展和单行入口仍为本地实现，此次未发布前端。扩展历史首次实机采集 46 请求后超时，未取得有效详情。本地订单管理行提供“浏览器刷新”，通过当前登录会话取得 120 秒专用票据；扩展仅接收订单链接／订单号／截止时间，每个请求和重定向通过管理台向现有 PostgreSQL 限流器申请许可。扩展最多运行 90 秒、100 个请求，只附加自己创建的临时标签页，接收正常 Document／fetchOrder 响应并在本机及服务器两次执行业务字段白名单；发现独立子页面时终止任务，避免漏计子页请求。登录令牌、任务票据、Cookie 和访客令牌不传给扩展或写入采集日志；访客 URL 回传前保留来源和订单号，令牌段替换为 `redacted`。

扩展 0.1.1 在失败结果附带有界诊断：主文档／fetchOrder 状态码（各最多 10 个）、请求数及正文读取／解析／缺少详情等计数。管理台再次按白名单裁剪，只供诊断，不改变订单更新契约，不包含原始 URL、正文或 Cookie。

2026-09-21 真实请求复测发现详情动作位于查询参数。浏览器采集端统一识别可信 HTTPS Apple 中国主机上的主文档、`fetchOrder` 路径段以及 `_a=fetchOrder` 查询动作；不能只检查 pathname，也不能把其他参数里碰巧包含该字符串的请求当作详情。HTTP 541／429 立即按官网拒绝处理；HTTP 200 的详情响应仍必须通过完整结构与订单身份校验。此修复不改变官网响应，也不代表已经解决 Apple 541。

成功结果仍使用既有订单事务，额外核验任务开始时订单版本，并在事务内利用 CrawlLog 的随机任务标识拒绝重放。该接入信任已授权管理员使用的本机采集端，服务端校验结构与身份不等于独立证明客户端数据来自官网。Chrome `debugger` 权限本身范围较广，安装必须明确确认；当前实现只操作自身临时订单页。构建命令为 `npm run collector:package:browser`（需要系统 `zip` 命令），生成 `frontend/public/browser-collector.zip`，操作说明随制品提供。

现有 Worker 默认仍执行原 HTTP／代理流程。独立数据库和合成界面通过不代表个人 Chrome、生产或多订单稳定性通过；必须以新取得的真实详情完成系统更新验收，不能用历史导出文件冒充当前观测。协议参考：[Chrome debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger)。

### 本机隔离浏览器批量刷新（2026-09-21，本地实现，真实官网待验收）

API 已发布且管理员入口启用，全局暂停仍生效；具体证据见[发布记录](../archive/2026-09/2026-09-21-本机十并发刷新API生产发布记录.md)。并发目标为 10，采用本机独立执行器与 Playwright 隔离上下文，不将个人 Chrome 的共享 PAC 改成逐标签页代理。每个在途订单独占代理节点，整个尝试固定出口；重试释放原上下文并选择不同节点。现有单标签页扩展保留作为单笔入口，不承诺个人浏览器中的多个普通窗口具有代理隔离能力。

批次输入仅为明确的系统订单 ID 清单，最大 1000 笔，拒绝重复；默认 10 并发、可配置 1–10。代理数量不得少于并发数；每单最多三次采集尝试，541／429、传输与超时允许换节点重试，身份或结构异常转为待核对。每个请求和重定向仍通过生产已有许可接口取得 PostgreSQL 全局时隙，默认 5 RPS、最大 10 RPS，不乘以任务数；不自动解除全局暂停、不绕过权限、不改变供应商套餐。

代理池按轮转游标选择空闲节点，并排除该单上次失败节点，避免配置了大量备用节点却反复复用列表前部。节点数量不足时仍遵守独占和三次上限，不并发共享节点或突破尝试预算；不同端点是否对应不同公网出口仍需供应商及实测确认。

仅在空闲槽位取得代理后签发任务票据，避免队列排队消耗有效期。新增 `mode=isolated_batch` 的票据有效期 330 秒，采集预算 300 秒、每次最多 100 请求；单笔扩展的 120 秒票据／90 秒预算保持。超时覆盖上下文创建、导航、许可等待和取数，取消关闭所属上下文；不允许 WebSocket、弹窗或未受限流的独立子目标继续访问。只接收与订单身份、官网来源一致的完整结构化详情，自动投影白名单后复用现有事务；仅 DOM 文字、验证码、加载页、混合或未知结构仍保留原值并标记待核对，不将可见文本伪造成官网 JSON。

本地检查点采用受限权限文件、原子替换和独占锁，不保存登录令牌、任务票据、代理凭证、访客 URL 或完整采集结果。持久化尝试计数；成功单重启跳过，采集中断可在三次总预算内续跑，提交中断／提交回执不明转为待核对，不自动重放。明确服务器拒绝的提交同样不重新采集并写入。批次正常或取消均关闭浏览器，恢复不改变个人系统代理。运行入口、配置和分级验收见[本机并发刷新操作说明](../deployment/本机并发刷新操作说明.md)。

### 2026-09-19 可靠性优化（本地实现，未发布）

刷新失败区分 `PAGE_LOADING`、`PARSE`、`REQUEST_TIMEOUT`、`RESPONSE_STREAM`、`REQUEST_CANCELLED`、`TASK_TIMEOUT` 与既有 HTTP／身份错误；内部错误码跨重试包装保留。最多三次是实际发出的顶层抓取次数，错误摘要使用“已尝试 N 次”，提前停止按实际次数记录；队列 `attemptCount` 仍表示领取次数，不冒充网络次数。

网帆抓取使用有界会话租用，单进程同槽不并行使用，完成或异常均释放。网络／传输连续失败两次冷却 60 秒，541 立即冷却并在冷却结束后更换该槽 sid；加载页和解析／身份错误不作为线路故障。冷却不永久禁用固定隧道入口，不扩大会话槽数量，不自动跨供应商切换；更换 sid 不保证不同出口。冷却配置必须不短于套餐粘性周期；默认 60 秒，多 Worker 的套餐总并发仍需按部署实例分配，进程内租用不等于全局租用。

抓取流程总预算默认 120 秒（`CRAWLER_TASK_TIMEOUT_MS`），覆盖会话等待、限流等待、请求和重试；Axios 请求保持原单次超时并接受取消信号，超时后不再解析落库。数据库操作与最终事务仍使用数据库自身超时，不宣称抓取预算是数据库硬截止。每次记录实际请求数、会话等待、限流、请求和解析耗时及匿名槽位；无法测量的 TCP／首字节阶段不估算。所有失败保留原业务数据和上次成功观测时间；页面按最新任务与成功／失败时间协调，旧结果不能覆盖新提交，简短中文提示可展开查看脱敏错误。

1. 加载订单与来源快照，校验 Apple URL 和本地身份；网络请求在数据库事务外执行。
2. 优先解析 `script#init_data`；该节点损坏时报告解析失败，不能借其他脚本静默替代。旧结构才兼容其他 JSON script 和已清理的可见正文。HTTP 200 不等于订单加载完成：只有 `guestOrderSpinner` 的加载页归类为 PAGE_LOADING，缺失或格式无效的订单号归类为可重试解析失败（PARSE），保留旧业务数据与既有校验结果，不新增身份冲突。解析与身份校验须在单次尝试内完成，失败按全局限流和最多 3 次尝试规则切换代理会话重抓。
3. 按 `orderItems.c` 及合法订单项键遍历，动态键仅作本次定位，不作为跨阶段商品身份。保存商品级状态、场景码、履约文案；相同阶段汇总整单，不同阶段显示状态待核对并暂停新付款分配，全部商品终态才派生整单终态标记。
4. 校验响应订单号。明确返回不同的有效订单号才属于响应身份异常，立即拒绝并停止重试；保留原业务数据，仅写入身份异常提示，禁止自动改号和跨单覆盖；该身份提示不再阻止付款分配。URL 来源／身份校验保持不变。抓取成功日志只在解析和身份校验通过后记录。
5. 短事务锁定订单，拒绝请求期间版本或身份已变更的旧结果；保留首次合并前的非敏感导入来源快照，采用官网有效字段并记录差异。商品一对一匹配优先非空型号，再语义名称；只接受双方唯一的匹配，单项剩余配对可以纠正名称，无法配对不猜测型号。不保存动态键、图片、动作链接和令牌。
6. HTTP 抓取保存官网字段、当前冲突与脱敏爬取摘要，同事务按来源下单时间加 30 分钟同步付款任务截止缓存，不使用官网截止覆盖。浏览器辅助入口仅按上述最小字段契约合并，不改写付款任务。官网收款不改写员工的 pending/processing/completed/exception。现有任务显示官网确认付款及人工处理差异。
7. 订单入库保留一次首次官网刷新（initial），首次资格沿用已有链接、身份、状态和付款窗口校验；首次成功或失败后均不再安排周期刷新。待付款和支付未知订单后续全部手动刷新；历史 auto/page_open 任务执行前跳过。页面打开不请求官网，手动单项、批量及其进度轮询保持可用。

每次尝试记录脱敏页面诊断：HTTP 状态、响应字节数、Apple 最终主机、路径类别、标题类别及 init_data／guestOrderSpinner／浏览器校验脚本／orderDetail／订单头是否存在。失败摘要使用 PAGE_LOADING／PARSE／IDENTITY 等错误码，最终诊断保存在爬虫日志 context；不保存原始 HTML、动态跳转路径或查询参数、令牌、Cookie、邮箱、代理凭据及另一订单身份。历史身份标记不批量清除，仅在随后成功校验并同步该订单时按现有合并流程重新计算。

### 来源表达差异与真实冲突

- 付款方式比较将 `微信`／`微信支付`／`WECHAT` 映射为同一值，`支付宝`／`ALIPAY` 映射为同一值；统一大小写、空白及全半角。花呗与支付宝不合并，其他未知值仅在规范化文本相同时视为一致。
- 商品名称匹配和字段校验共用同一规则。首先比较规范化文本；对完整识别的 iPhone 数字代际、版本、中文颜色、容量组合，允许颜色与容量互换顺序、`G`／`GB` 和 `T`／`TB` 同义。不跨 `GB`／`TB` 换算，不删除未知词语，不以模糊相似度接受差异。其他商品或未完整识别的名称仍严格比较。
- 型号、代际、版本（如 Pro／Pro Max）、颜色、容量、数量真正不同仍产生冲突；两侧非空 SKU 不同不能通过名称匹配绕过型号差异。多条候选不按列表顺序猜测。
- 规范化仅用于比较，保留邮件来源快照与官网原文。历史重校验仅移除可证明等价的付款方式和名称冲突，保留身份、阶段、字段解析及其他真实异常；不请求官网、不修改官网观测时间或订单生命周期、不创建自动刷新任务。

历史表达冲突可使用 `npm run orders:revalidate-conflicts -- W1234567890` 预览，明确指定订单号（最多 100 个）后加 `--execute` 才执行。执行使用同一事务及订单行锁，只更新 `validationIssues`、`validationStatus`、`anomalyDetectedAt`；不更新 `updatedAt` 或最后官网更新时间。指定订单有缺失时整批拒绝，重复执行无变化。工具只处理已有问题中保存了双方非空文本、可以证明等价的付款方式／名称冲突，不清除“无法唯一匹配”等需要额外证据的问题。生产运行前按既有发布流程备份并核对预览范围。实现入口为 [revalidateOrderConflicts.js](../../scripts/revalidateOrderConflicts.js)。

### 生命周期与阶段字段

| Apple 原始状态               | 订单状态            | 支付状态                          | 取货状态         |
| ---------------------------- | ------------------- | --------------------------------- | ---------------- |
| PAYMENT_DUE_STORED_ORDER     | payment_due         | unpaid                            | not_ready        |
| PAYMENT_RECEIVED             | payment_received    | paid                              | not_ready        |
| PROCESSING                   | processing          | paid                              | not_ready        |
| READY_FOR_PICKUP             | ready_for_pickup    | paid                              | ready_for_pickup |
| PICKED_UP                    | picked_up           | paid                              | picked_up        |
| PAYMENT_EXPIRED_STORED_ORDER | payment_expired     | unpaid                            | not_applicable   |
| CANCELLED                    | cancelled           | 保留已确认支付证据                | not_applicable   |
| PICKUP_CANCELLED             | pickup_cancelled    | 保留已确认支付证据                | pickup_cancelled |
| SHIPPED / DELIVERED          | shipped / delivered | 不凭未验证配送枚举推断付款        | not_applicable   |
| 未知新枚举／混合阶段         | unknown             | 不猜测；各项均明确已付可确认 paid | unknown          |

未知原始枚举必须保存并产生待核对提示，不能由轨迹或正文中的旧阶段覆盖。仅缺少原始状态的旧页面允许正文回退。pending 是入库等待首次官网抓取的自定义状态，显示“待处理”；unknown 原样显示。completed 已从订单枚举移除，不能再作为付款或取货证据；人工任务四态不受影响。picked_up、delivered、payment_expired、cancelled、pickup_cancelled 为已确认终态。不新增官网状态历史表，只保存最新观测；观测时间不等于付款／取货发生时间。

官网金额第一来源为 `orderHeader.payNow.d.totalAmount`，付款截止来自 `orderItemDetails.d.paymentTimeToExpiryEpoch`（秒），付款方式来自 `billingInfo.d.paymentMethodPaymentTypeName`。同单不同截止取最早有效值。创建时间只有包含时分时才写入；截止优先 Epoch，回退准确创建时间加 30 分钟。

字段诊断区分 missing、null、invalid、value。金额、币种、截止和基础商品字段在缺失、null、解析失败时保留最近有效值；有效纠正值才替换。状态描述明确空值可以清空，缺失保留。支付证据不能因取消或字段消失被清空。履约 `deliveryDate` 原文保存为 `fulfillmentMessage`／`officialFulfillmentMessage`，不直接写入实际取货日期；API 展示层可用官网观测时间的北京时间日期把“今天／明天”派生为稳定的绝对预约日期和时段，原文保持不变。

原始响应、Pay Now URL、访客令牌、联系人明文不写爬取日志或普通 API；错误摘要区分 HTTP、响应流中断、JSON 解析及身份异常。真实证据来源见[生命周期方案](../planning/真实订单生命周期与官网数据映射优化方案.md)；本次新订单最终取货尚待独立验证，历史已取货样本不冒充本次终态。

## 代理与重试

- Worker 冷启动先将代理运行状态置为未就绪。上次切换失败且内存代理为空时，恢复并验证持久化的最后有效 Provider，再继续处理队列；保留原候选失败诊断，不自动重试失败的候选。恢复失败时暂停领取并公开阻塞码，恢复尝试最多每 60 秒一次，新切换请求可打破冷却。运行就绪与心跳分开判断，禁止把进程存活作为代理已恢复的证明。
- 付款倒计时优先官网业务阶段：付款已过期、已付款、已取消／终止明确展示，不再因缺少截止统一显示“等待官网时间”；只有仍需付款且缺少来源下单时间时显示“时间未知”。

- 队列触发类型与爬取日志来源分开：initial 在首次资格判断中保留原标识，成功／失败／金额警告日志映射为 auto；manual_single／manual_all 映射为日志 manual，历史 auto 映射为 scheduled，page_open 保留执行跳过。非标准上游状态码（如 631）保存在日志 context.upstreamHttpStatus，httpStatus 仅接受 100–599，避免日志校验掩盖实际抓取结果。

- 实际抓取要求 `PROXY_ENABLED=true`；关闭时不会自动回退为直连。
- [proxyManager](../../src/utils/proxyManager.js)是代理兼容门面，由 `PROXY_PROVIDER` 选择快代理隧道 Pro `kdl_tunnel`、快代理私密代理 `kdl_private`、网帆隧道 `fanproxy_tunnel` 或亦优 HTTP 短效直连 `yiyou_http` Provider。两种隧道模式使用固定主备 Host、端口和账密鉴权，不维护出口 IP 内存池。
- `PROXY_PROVIDER` 只定义 Worker 启动默认值，未显式配置时使用当前首选 `fanproxy_tunnel`。管理页也将网帆置于首位并标记为首选。管理员可通过系统页面请求切换 Provider；请求写入 PostgreSQL，Worker 在停止补位并等待在途任务完成后初始化候选 Provider，并使用全局限流时隙访问 Apple 中国首页做连通性检查。检查成功才原子切换新任务，失败保留旧 Provider；“首选”不表示请求失败后自动跨供应商降级，未知 Provider 必须失败关闭。
- 切换状态只保存 `requested/active/status/error/timestamp` 等非敏感元数据。隧道鉴权、短效代理提取 API URL/签名和代理密码仍只来自环境变量；四个 Provider 都配置完成时才具备四方一键切换条件。凭据变更需要按授权更新环境并重建 Worker，已经配置完成的 Provider 之间运行时切换不重启进程。
- 初次请求和所有重试统一经过 PostgreSQL 全局时隙限流器。`CRAWLER_REQUESTS_PER_SECOND` 默认 5、最高 10，附加小幅随机抖动；不再逐订单固定等待 5–10 秒。
- `CRAWLER_MAX_RETRY` 默认 3，规范上最多 3 次；请求超时由 `CRAWLER_TIMEOUT` 控制。
- HTTP 541/429 归类为 Apple 风控，快代理 441 归类为代理频率超限，407 归类为代理鉴权故障，快代理 517 归类为代理建链失败；407 会持久化暂停领取新任务。私密代理在 541 时废弃当前 IP；快代理隧道每次重试生成新 `sid`，网帆粘性模式切换到下一会话槽。网帆未公开数字错误码保留 HTTP_数字 并脱敏记录，不猜测返回方，不套用快代理专属 441/517 语义。
- 单次尝试的 541 只切换出口并进入下一次受限重试，后续尝试成功会清零连续风控计数；只有连续订单都在三次尝试中全部收到 541，达到 `CRAWLER_WIND_CONTROL_PAUSE_THRESHOLD` 后才暂停新任务。这样不会因某一个低质量出口误停整个 Worker，同时保留持续风控时的断路保护。
- Apple 订单入口会从 `www.apple.com.cn/xc/...` 跳转到 `secure10.www.apple.com.cn/shop/order/guest/...`。隧道轮转可能让同一次订单抓取的首跳和重定向使用不同出口，因此两种隧道 Provider 都通过 `sid` 保持单次尝试的出口一致。快代理每次尝试生成随机 `sid`，通过 `period-0.5` 将出口固定 30 秒；网帆使用 `acc-{账号}-cty-CN-sid-{会话ID}`，并按 `FANPROXY_TUNNEL_SESSION_POOL_SIZE` 建立有界会话槽轮询复用，重试切换到下一槽。槽数不得超过套餐允许的粘性会话通道数，禁止每次请求无限创建新 `sid`。
- 隧道默认使用兼容性优先的企业池 `type-std` 和质量优先 `pool-q10`；可通过 `KDL_TUNNEL_STICKY_PERIOD`、`KDL_TUNNEL_POOL_TYPE`、`KDL_TUNNEL_POOL_PRIORITY` 覆盖。`KDL_TUNNEL_USERNAME` 必须填写不带转发参数的基础用户名。
- 快代理隧道模式发送 `Connection: close` 和 `Accept-Encoding: gzip`，继续使用已验证的 Axios 原生代理配置；对照实验中自定义 `HttpsProxyAgent` 没有提高真实订单成功率，因此不引入第二套传输实现。响应流中断时丢弃不完整 HTML，下一次受限重试使用新代理重新建连并完整抓取；动态订单页不支持安全拼接两次响应，不实施 HTTP Range 式断点续传。用户名和密码仅允许通过环境变量注入，不写入日志或仓库。
- 网帆隧道同样使用 Axios 原生代理配置、`Connection: close` 和 gzip；账号、密码、Host、端口、`sticky_pool/basic` 会话模式与槽数仅从 `FANPROXY_TUNNEL_*` 环境变量读取。Apple 订单抓取默认使用 `sticky_pool`；`basic` 不附加 `sid`，只用于供应商连通性诊断，因为真实订单样本中跨跳出口变化大量触发 541。Provider 只拼接官方支持的 `acc/cty/reg/sid` 参数，不能复用快代理的 `period/type/pool` 用户名语法。网帆国内隧道不支持白名单认证，必须使用账密鉴权。
- 私密代理按需调用提取 API，保留仍在冷却期内的坏 IP 隔离记录，不因刷新代理列表立即清空；过期冷却自动清理。代理池耗尽时重新提取，Provider 初始化至少取得一个格式合法且可用的候选代理。
- 亦优 HTTP 支持短效提取与已购静态节点。短效模式使用官方 HTTPS 提取域名，只接受 `IP:端口 用户名 密码` 换行文本；提取 URL 仅存于 `YIYOU_HTTP_PROXY_API_URL`，5 分钟节点默认在 240 秒时整池过期并重新提取。2026-09-19 用户授权接入 10 个已购长效节点：`YIYOU_HTTP_STATIC_PROXIES_JSON` 保存上述行格式的 JSON 数组，`YIYOU_HTTP_STATIC_EXPIRES_AT` 保存控制台明确到期时间；静态配置优先且不访问短效提取 API，格式错误或到期立即拒绝加载，不回退旧 API。刷新静态列表不清除失败隔离；每条代理使用独立账密、禁用连接复用，541 立即隔离当前 IP，其他传输错误达到失败阈值后隔离。配置只保存在受保护的环境文件；响应日志只记录总数和无效数，不记录原始行或鉴权。

### 2026-09-07 同订单集 A/B

用户授权的 83 条真实订单链接按偏移 `0–82` 分为 9 个不重叠批次执行；每条订单同时进入隧道和私密 Provider，奇偶订单交替决定限流时隙的先后顺序。所有请求共用隔离 PostgreSQL 全局限流状态，统一 1 RPS，每订单每 Provider 最多 3 次，不写业务数据库，不保存 HTML、订单链接或代理凭据。

- 隧道 Pro 成功 `75/83`（90.36%），首次/第二次/第三次成功 `39/27/9`；144 次尝试中的失败分类为响应流中断 43、HTTP 541 9、`ECONNRESET` 12、超时 5。8 个最终失败为响应流中断 6、HTTP 541 1、超时 1。
- 私密代理成功 `55/83`（66.27%），首次/第二次/第三次成功 `28/9/18`；184 次尝试中的失败分类为响应流中断 110、HTTP 541 9、HTTP 515 4、`BAD_REQUEST` 2、`ECONNRESET` 2、超时 2。28 个最终失败为响应流中断 23、HTTP 541 2、HTTP 515 1、`ECONNRESET` 1、超时 1。
- 配对结果为双方成功 48、仅隧道成功 27、仅私密成功 7、双方失败 1；所有成功响应的订单身份匹配，零商品订单为 0。隧道样本解析 `completed/paid` 58 条、`cancelled/unpaid` 17 条；隧道 75 条和私密 55 条成功响应都未提供订单总金额，保持 `NULL`。

结论仅适用于本次试用规格和测试时段。私密代理能够提取、认证和轮换，但主要失败是 HTTP 200 后响应流中断而非 541，增加短效 IP 数量不能替代链路稳定性；当前不应将私密代理作为默认线路。隧道 Pro 也未达到 100%，生产启用前仍需继续评估出口质量、传输稳定性和业务可接受阈值。

### 网帆 20 并发套餐配置

供应商套餐升级不会自动更新应用配置。选中并确认 **20 并发、1 分钟粘性** 的套餐后，必须核对对应账密，再显式设置 `FANPROXY_TUNNEL_SESSION_POOL_SIZE=20`、`CRAWLER_WORKER_CONCURRENCY=20`、`CRAWLER_REQUESTS_PER_SECOND=5`、`CRAWLER_MAX_RETRY=3`，保留 `sticky_pool`。粘性时长由套餐控制，不向用户名添加其他供应商的时长参数。

20 个槽轮询复用，20 个任务可以同时等待响应，实际请求启动仍经过 PostgreSQL 全局限流器。通用代码默认值保持兼容旧套餐，不自动假定所有环境已购买 20 并发。

扩容后按已完成的刷新任务统计成功率，HTTP 403/541 按请求尝试另行统计并与变更前同口径比较；跳过、取消的任务不算成功样本。至少完成 100 个有效任务、成功率达到 95% 且 403/541 比例未上升时，才可将 RPS 从 5 提到 8；8 RPS 重新收集至少 100 个有效任务通过同样条件后最多提到 10。样本不足、失败率升高或代理未就绪时不提速。不得为凑样本恢复已付款或终态历史订单的自动刷新。

### 2026-09-08 网帆同订单集验证

用户授权从网帆控制台读取有效的国内隧道 1 天测试套餐并写入本地忽略的 `.env`；套餐为账密认证、HTTP(S)、1 分钟粘性、5 条会话并发。测试使用与上一日相同的 83 条真实订单链接、同一解析与身份校验逻辑、统一 1 RPS、每单最多 3 次，不写业务数据库、HTML、订单链接或代理凭据。由于快代理隧道 Pro 套餐当日已不可用，本结果与 2026-09-07 基线作跨时段对照，不是同时段并行 A/B。

- 官方基础账号模式访问 Apple 中国首页 `3/3`，但真实订单仅 `1/10`，27 次失败全部为 HTTP 541；该模式不能保证 Apple 首跳和重定向之间的出口一致性，不用于订单抓取。

用户名参数、频率、资源池和 gzip 规则以[快代理隧道代理 Pro 开发手册](https://www.kuaidaili.com/doc/dev/tps_pro/)为准；407、441、517 的含义以[隧道代理 Pro 错误码](https://www.kuaidaili.com/doc/dev/tps_prohttpresponse/)为准。网帆账密参数、会话与国内隧道鉴权边界以[网帆国内隧道账密认证说明](https://www.fanproxy.com/helps/detail/auth-package)为准。供应商文档不定义 541，因此本系统按 Apple 目标站风控响应处理，而不是误报为代理鉴权或频率错误。

## 自动调度和暂停

`AUTO_ORDER_REFRESH_ENABLED` 默认 false，作为现有刷新 Worker 的兼容启动开关保留，不能用关闭该开关实现手动模式。启用后 Worker 继续处理 initial 和人工任务，不再生成周期 auto 任务；旧到期调度逐批清空，旧 auto/page_open 任务执行前跳过，手动请求可以提升 pending 自动任务为人工任务。首次与手动刷新完成后 nextAutoRefreshAt 均为空。

任务、批次、逐订单新鲜度、Worker 心跳、全局请求时隙和暂停原因都持久化在 PostgreSQL。Worker 使用事务、订单行锁和 `FOR UPDATE SKIP LOCKED` 租约领取；租约过期后可由其他 Worker 恢复。管理员在排障后可通过恢复接口清除持久化暂停状态。

Worker 每 5 秒按“并发上限减去本进程在途任务数”领取新任务，领取循环不等待整批订单完成。在途任务占用名额直到结果持久化结束；慢任务不会阻塞其他空闲名额，新单仍可能等待下一个调度周期及全局限流。每轮为本 Worker 仍持有的在途任务续租，随后才恢复过期租约；结果写入失败会释放内存名额，遗留任务按租约恢复。

暂停后不再补位；收到代理切换请求后停止补位，等待在途任务全部完成再校验和切换代理，防止持续入队导致切换饿死或执行中更换 Provider。已失败的候选不会阻止最后有效代理继续领取。关闭 Worker 时先停止新一轮领取，再等待正在领取和执行的任务结束后关闭数据库；进程被强制终止时仍依靠租约恢复。

### 官网逐台节点与商品行（2026-09-09）

官网可能将数量为 2 的同一商品拆为 `orderItem-1of2-11`、`orderItem-2of2-11`，每个节点仍携带总数量 2。只有同一节点后缀、完整且唯一的 1..N 序号、`eyeBrowNumber`/`eyeBrowQuantity` 与节点一致、商品数量等于 N、全部公开商品与状态信息一致时，才能合并为一行并保留总数量。不同后缀、缺失节点、不同状态或不完整元数据均保留，不能仅凭商品名称去重。生命周期始终检查所有原始节点。

### 下单时间精度与时区（2026-09-09 修复）

`orderDate` / `order_date` 保留邮件或人工录入的来源下单时间，官网只有日期时禁止覆盖，官网精确时间独立保存在 `officialOrderCreatedAt`。日期冲突提示核对，不用官网日期补造时分秒。页面和导出统一北京时间（Asia/Shanghai）；日期筛选包含北京时间的完整起止日。仅有日期时仅展示日期，未知时间不使用入库时间或付款截止倒推。人工录入必须包含时分；无时区输入按北京时间解释。系统付款截止统一使用来源下单时间加 30 分钟，官网时间单独留存。历史修复只恢复可核验来源快照，不将来源时间宣称为官网精确时间。

### 商品筛选与官网不可用（2026-09-20）

商品筛选仅依赖本地索引，不触发爬虫。官网失败或未返回商品时保留原有索引；有效商品更新通过 Order 模型同事务更新筛选项，完整 SKU、容量、颜色等身份变化不得继承不匹配商品键。普通空白、容量单位和容量词序变化保留选择，来源快照只参与唯一无冲突匹配，不按剩余单项强行补筛选型号。该索引不改变现有官网合并、付款资格、真实状态和调度规则。部署新索引时，API 及写入商品的 Worker 必须配套升级，避免旧进程更新商品而不更新索引。

## 金额与官网刷新解耦（2026-09-21）

订单金额展示及聚合改用独立 orderAmount，按 [已确认价格映射](AOS文件采集与入库.md#订单金额价格映射2026-09-21-已批准) 在入库／商品变化时计算。官网金额解析仍可保留原 officialOrderAmount 观测记录，但不覆盖映射字段，不作为金额可用性的前置条件；缺失或错误官网金额不会使映射金额消失。官网确认商品或数量发生变化时，在同一次订单保存中重算映射金额。未知商品不回退官网金额。

### 来源支付方式保留（2026-09-21，本地适配）

普通官网合并将付款方式写入 officialPaymentMethod，paymentMethod 保留已有来源快照中的完整名称，无快照时保留来源订单值；来源缺失时才用官网值兜底。差异仍记录 source_conflict，resolution 为 source，提示“保留来源值，请核对”。不将微信分付与微信、支付宝银行分期与支付宝视为等价。浏览器刷新仍不更新付款方式。

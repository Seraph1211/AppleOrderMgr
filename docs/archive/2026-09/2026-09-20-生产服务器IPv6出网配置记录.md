## 授权与原始问题

用户确认分配 1 个 IPv6 地址、开通按流量计费的 10 Mbps 公网带宽、设置仅主动出规则和配置服务器；在实际购买确认页单独确认同意产品服务协议与服务等级协议。

原先只有交换机 IPv6 网段和 IPv6 网关，ECS 主网卡未分配地址，宿主机及应用容器强制 IPv6 请求均为 `ENETUNREACH`。本次未修改应用的强制代理规则，也未触发订单刷新。

CentOS 7.9 的 `/etc/sysconfig/network-scripts/ifcfg-eth0` 增加 `IPV6INIT=yes`、`DHCPV6C=yes`。新增 `/etc/cloud/cloud.cfg.d/99-preserve-network-config.cfg`，设置 `network.config: disabled`，防止 cloud-init 重写已有网卡文件；这意味着后续云端网络配置变化需同步维护操作系统配置。

单独运行 `ifup-ipv6 ifcfg-eth0` 和 DHCPv6 客户端，获取 `/128` 地址及 RA 默认路由 `fe80::ecff:ffff:feff:ffff`；没有重启 ECS、network、Docker 或任何应用容器。原 DHCPv4 客户端继续运行，IPv4 路由前后完全一致。持久配置已写入，未用生产重启验证恢复。

## 实测结果与 DNS 边界

北京时间 04:19:37，使用域名 TLS 校验并将目标解析固定到本轮验证过的 AAAA 地址：

```bash
curl --noproxy '*' -6 --connect-timeout 8 --max-time 15 \
  --resolve 'www.apple.com.cn:443:240e:971:7000:100:3::5a' \
  -o /dev/null -w '%{http_code} %{remote_ip} %{local_ip}\n' \
  https://www.apple.com.cn/
```

- GET 返回 HTTP 200，147999 字节，耗时 0.174 秒。
- 本机出口为分配的全局 IPv6，远端为 `240e:971:7000:100:3::5a`，不是 IPv4 映射地址或第三方 HTTP 代理。
- 同时 API `/api/health/ready` 返回 `healthy`、`db=ok`；全部已有容器保持运行，未重启。
- 当时阿里内网 DNS `100.100.2.136/138` 和 `223.5.5.5` 对该域名没有返回 AAAA，普通 `curl -6` 因此报解析失败；`119.29.29.29` 返回 `240e:971:7000:100:3::5a`、`::5b`，与初次实测一致。没有修改全局 DNS、hosts 或固化 Apple 的 CDN 地址。

因此结论是宿主机 IPv6 出网及指定 Apple IPv6 HTTPS 已通过；不能声称默认 DNS 下该域名始终能使用 IPv6，更不能视作真实订单链路验收。

## 应用边界与下一步

现有 `apple-order-mgr-prod-app` 网络仍为 IPv4，API 与 Worker 的现有 `yiyou_http` 代理链路保持原样。容器 IPv6 网络和应用出口策略属于下一阶段，需同时处理容器配置持久化、IPv6 转发/回程、DNS 选择与现有强制代理规则，不能直接关闭代理或重启共享 Docker。此次没有进行这些应用接入变更。

# 订单快照与基础资料匹配

> 状态：当前有效
>
> 最近核对：2026-10-12
>
> 基线：`f91515c`；生产 `20261012-recipient-matching`
>
> 验证范围：本地及隔离 PostgreSQL 回归、生产 250 笔授权补关联、独立数据库及公网接口回读

## 设计目的

基础 Apple ID 或取机人资料尚未导入时，仍能保存订单。订单保存必要快照，外键允许为空；关联用于追踪和补充，不应使订单展示依赖基础资料永远存在。

## 当前匹配规则

| 对象     | 条件                                                                                     | 无法唯一匹配                           |
| -------- | ---------------------------------------------------------------------------------------- | -------------------------------------- |
| Apple ID | 去首尾空白、忽略大小写匹配订单自身账号                                                   | 保留来源快照，外键为空                 |
| 取机人   | 全名＋身份证后四位唯一匹配；完整身份证仅用于提取后四位，手机号和邮箱不参与匹配或拦截 | 多候选、缺少有效尾号或证件证据冲突时保持空关联 |

实现见[公共订单接入](../../src/services/orderIngestionCore.js)和[身份匹配](../../src/services/profileOrderMatching.js)。全名由姓＋名比较，不按首字拆分，支持复姓。尾号新增保存于 orders.recipient_id_last4；没有独立尾号但有完整证件时，从完整证件提取后四位；两者均有而不一致时保持空关联。旧订单若未保留完整证件／尾号，不按手机号或邮箱回退匹配，需后续提供可靠来源。

取机人与账号档案完全独立；旧绑定仅作为已结束历史保留，不参与匹配。订单外键各自独立。张三从 A 换为 B 后，张三统计其 A+B 订单，A/B 各统计自己的订单；A 下其他取机人的订单不计入张三。解除基础档案绑定不迁移历史订单。

历史空关联提供预览／选中执行，见[API 契约](../design/API设计.md)。先只读拉取候选，由用户确认后执行；事务中重新验证订单与档案，不覆盖已有关联、快照、TAG 或付款任务。

## 数据一致性

订单保存和邮件日志处于同一事务；订单号存在时返回已有订单。官网同步首次合并前保存非敏感导入来源快照；身份一致后采用官网有效商品、数量（含 0）、付款方式、金额等值，并展示来源冲突，缺失不覆盖。订单号不一致时拒绝跨单更新，详见[爬虫说明](../design/订单爬虫.md)。

快照不是实时 JOIN 的别名；不能假定修改基础资料会自动重写历史订单。渠道改名更新档案 TAG 和用户授权，保留订单来源 TAG，见[渠道管理](../design/渠道管理说明.md)。

2026-09-17 用户授权清理生产测试基础资料时，仅删除 Apple ID／取机人档案并将订单对应外键置空；订单敏感快照、商品、TAG、付款任务和历史记录保留。一次性脚本 `scripts/clearTestProfiles.js` 默认只读预览，执行需匹配资料指纹，在事务内检查外键及订单／付款任务完整性；必须先备份、隔离恢复演练，不作为日常批量删除接口。

## 安全与字段

密码及身份证快照由模型 setter 加密，getter 解密仅供受控服务处理。API 另行脱敏，隐藏前端列不能替代服务端权限控制。字段、类型、索引以[数据库架构](数据库架构.md)为准，本页不复制 SQL 建表与明文插入示例。

上述订单快照权限不变；基础资料页面经用户批准，具有 `apple_ids.read` 的用户可直接读取 Apple ID 密码，具有 `recipients.read` 的用户可直接读取取机人身份证与手机号。订单快照权限仍独立；当前密保、详细地址及完整导出另按本轮批准的专用权限契约开放，详见 API 契约。

## 待验证

多匹配、事后关联、补齐范围和真实数据库并发行为需独立验收；历史“自动匹配不会丢单”不作为可靠性承诺。

## AOS 来源匹配（2026-10-12 已批准调整）

AOS 使用显式姓＋名与来源身份证后四位查询候选，只有一个匹配档案才关联。手机号、邮箱差异不拦截；15 列旧来源缺少尾号时保持待关联。缺失或歧义不阻止订单保存。联系邮箱与下单 Apple ID 分别保存，账号密码仅进入加密订单快照，不更新基础账号。完整来源 TAG 独立保留并可见；订单已存在时只关联来源，不补空或覆盖。

## 订单取机人 TAG 统一契约（2026-10-14）

本轮已实现、验收并生产发布，证据见[统一方案](../planning/订单取机人TAG统一方案.md)。所有来源及历史订单的业务 TAG 唯一读取 `orders.recipient_ref` 关联的 `recipients.tag`，档案修改实时生效。NULL、空串、全空白为缺失；非空值保留原字符串并区分大小写精确匹配。未关联或缺失不回退来源。`orders.tag`、`source_recipient_tag` 及 AOS 快照仅保留原始记录，不覆盖。

订单响应 `recipient_tag`、`tag` 为当前值或 null，新增 `recipient_tag_state`（unlinked／missing／present）；付款对应 `recipientTag` 和 `recipientTagState`。列表、详情、导出、筛选候选、仪表板、渠道聚合和用户 TAG 范围采用相同规则；缺失值不构成真实渠道或授权 TAG。本人付款任务所有权须与当前 TAG 范围相交，不要求额外的 orders.read。

自动分配对所有来源按当前 TAG 匹配规则，候选人也必须具有当前 TAG 范围；缺失只允许全部范围账号接单。无匹配规则沿用普通账号集合，已分配历史任务不自动转派。新企微通知采用当前值，旧投递记录保留。渠道改名仅更新档案 TAG 和授权配置，不改来源快照。修改既有档案 TAG、删除、导入覆盖 TAG、补关联等影响订单范围的操作要求全部范围及原功能权限。

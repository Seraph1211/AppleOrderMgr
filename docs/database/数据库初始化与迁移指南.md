## 配置来源

- [CLI 迁移配置](../../config/config.js)与[模型连接配置](../../src/config/database.js)均支持 `DATABASE_URL` 或 `DB_*`。不要同时维护两套互相冲突的值；生产当前统一使用 `DB_*`。本地 Compose 在容器内覆盖 `DB_HOST=postgres`、`DB_PORT=5432` 和 `DB_SSL=false`。
- 默认数据库名为 `apple_order_mgr`；test 环境的 CLI 使用 `DB_NAME_TEST`，但当前模型连接仍读取 `DB_NAME`。隔离测试必须显式对齐两者，不能只设置 NODE_ENV=test 就认为数据库已隔离。
- PostgreSQL 14+；TLS 使用 `DB_SSL`、`DB_SSL_REJECT_UNAUTHORIZED`。本页不保存实际凭据。

## 新建本地开发库

本地 PostgreSQL 由 [docker-compose.dev.yml](../../docker-compose.dev.yml)创建，并使用命名卷持久化。首次启动会自动运行 `migrate`：

```bash
docker compose -f docker-compose.dev.yml up --build -d
```

新增 Migration 或需要手动重试时执行：

```bash
docker compose -f docker-compose.dev.yml run --rm migrate
```

首次管理员用户名为 admin，密码通过 `ADMIN_INITIAL_PASSWORD` 注入。管理员种子不会跟随应用自动运行，需要显式执行：

```bash
docker compose -f docker-compose.dev.yml --profile tools run --rm seed-admin
```

首次登录不再强制改密；登录后进入首个有权页面，所有账号可在个人设置中自行改密。不要把全部种子文件作为首次生产初始化的默认步骤。

`npm run db:init` 当前只测试连接并提示执行迁移，不会同步模型或自动创建表。本地需要运行该命令时，应通过 `docker compose -f docker-compose.dev.yml exec api npm run db:init` 在容器内执行。表定义见[数据库架构](数据库架构.md)。

## 存量敏感数据

```bash
# 默认只读盘点
npm run security:migrate
```

加 `-- --execute` 才会写入数据；执行前需要备份、密钥确认、回滚方案和对应数据写入授权。结构迁移成功不能证明存量明文已转换，状态见[敏感资产处置记录](../security/敏感资产处置记录.md)。

## 迁移验证与回滚

仅在可丢弃的隔离库验证 `up → 校验 → down → up`。本地 CLI 命令通过 Compose 的 api 或一次性容器执行；`npm run db:migrate:undo` 回滚最近迁移，`npm run db:reset` 会回滚全部迁移再重建，不属于日常生产修复命令。

删除本地 Compose volume 会丢失整个本地开发数据库。`docker compose -f docker-compose.dev.yml down --volumes` 只能用于明确可丢弃的数据，不能用于生产。

需要检查字段、类型、唯一约束、外键、索引和数据兼容性；模型静态检查不能替代真实 Migration 验证。`20260907000002-enhance-email-processing.js` 已在精确命名的临时数据库完成 `up → 结构/索引校验 → down → 字段与表消失校验 → up`，并执行邮件并发与事务集成测试；该证据不代表当前开发库或生产库已经迁移。

## 备份与恢复要求

生产数据库位于服务器宿主机 PostgreSQL 15，不属于应用 Compose。2026-10-05 起按用户确认的发布边界，使用自定义格式备份完整业务数据，排除 AOS 监控日志明细 `public.monitor_log_entries`；不备份或恢复相关原始日志文件。保留结构、索引定义、监控配置和运行游标，其余业务数据仍做隔离恢复及迁移演练。此备份不包含 AOS 日志数据，不称为整库数据备份；不改变生产日志和保留期。

示例：

```bash
install -d -m 700 /var/backups/apple-order-mgr/<timestamp>
PGPASSWORD='<从受控环境读取>' pg_dump \
  -h 127.0.0.1 -U apple_user -d apple_order_mgr -Fc \
  --exclude-table-data=public.monitor_log_entries \
  -f /var/backups/apple-order-mgr/<timestamp>/database.dump
sha256sum /var/backups/apple-order-mgr/<timestamp>/database.dump \
  > /var/backups/apple-order-mgr/<timestamp>/database.dump.sha256
```

命令中的密码不能写入 Shell 历史或文档；实际发布应从权限为 `600` 的环境文件加载。备份必须先恢复到隔离 PostgreSQL 实例，并在隔离实例执行：

```bash
docker compose --env-file release.env -f docker-compose.prod.yml --profile tools run --rm migrate
docker compose --env-file release.env -f docker-compose.prod.yml --profile tools run --rm security-migrate
```

生产字段加密转换只执行一次。转换前做只读盘点，转换后核对各表行数、待迁移明文计数、`id_card_hash` 和 Migration 清单。加密密钥和数据库备份必须配套保管；只有备份而没有当时的密钥，无法恢复密文业务字段。

恢复生产数据库会覆盖发布后的写入，只能在回滚窗口中执行。不要把 `db:migrate:undo` 当作生产数据回滚方案。

生产操作见[部署指南](../deployment/生产环境部署指南.md)，不从旧文档复制服务器地址或数据库口令。

## 账号昵称、单会话与操作日志迁移

`20260909000003-add-account-sessions-and-audit.js` 新增 users 的 nickname、active_session_id、active_session_expires_at 和 operation_logs 表。发布时先迁移再更新 API／前端；原账号、登录名、密码和授权不变，旧版本 Token 需重新登录。旧 force_password_change 字段保留兼容，新代码不再用它限制登录和接单。

回退会删除新增会话及操作记录表，因此必须先备份操作日志；旧 API 没有单设备限制，不能把降级视为功能等价。上线、生产迁移和回退均遵循当前会话的单独授权。

### 三台设备会话扩容（2026-09-09）

`20260909000004-allow-three-account-sessions.js` 新增 `users.active_sessions`，未过期旧会话转入数组。先迁移后更新 API；现有登录可保留。down 将最新有效会话写回旧列，再移除数组与约束；退回单会话代码会使其余设备退出。正式发布前仍需备份与恢复演练。

### 取消设备登录数量限制（2026-09-24）

`20260924000001-remove-account-session-limit.js` 仅移除 `users_active_sessions_limit` 检查约束，不改写已有会话、账号、密码或权限。应用仍逐会话校验和撤销；改密、管理员重置与锁定仍清空全部会话。down 会恢复最多 3 条会话的约束；只要任一账号已有 4 条及以上会话就会原子失败，禁止为回退静默删除用户会话。生产回滚优先保留无上限数据库结构并恢复旧应用前评估兼容性。

### 账号软删除迁移

`20260909000005-add-user-soft-delete.js` 为 `users` 新增可空 `deleted_at`，既有账号初值为空，密码及关联不变。新代码使用 Sequelize paranoid 过滤已删除账号；删除时同时锁定账号和撤销会话。上线前备份并在隔离恢复库演练；回退应用优先保留新增列，旧代码没有隐藏已删除账号的能力，不能仅回退应用就声称软删除行为一致。Migration down 会移除删除标记，仅用于隔离测试或有备份的明确恢复步骤。

## AOS 文件采集与来源切换迁移

`20260910000001-add-aos-ingestion.js` 创建来源设置、设备、AOS 记录、操作任务、订单来源和门店字典六表，并增加订单来源快照、邮件范围资格及暂停字段。默认来源是邮件，已有成功邮件关联的订单可回填 email，其余历史订单保持 unknown。

`20260910000002-preserve-ingestion-history.js` 回填启用新规则之前已经尝试处理的邮件资格，以及成功／重复邮件的可追溯来源。不会给新接收的历史邮件普遍放行。up/down 均使用事务；生产执行前按既有迁移流程备份并验证实际数据，不能从本地已迁移推断线上状态。

`20260911000001-add-verified-pickup-stores.js` 在门店代码尚不存在时加入 Apple 中国大陆官网当前列出的全部 49 家直营店。代码、名称和城市来自各门店官方页面的结构化 `branchCode`、`name` 和地址信息，每条来源指向对应 Apple 官方页面；已有同代码人工字典不覆盖。down 只删除由本迁移写入且来源与核对时间均一致的记录，避免删除后续人工维护值。

`20260911000002-add-aos-device-credential-ciphertext.js` 为设备增加可空的 AES-256-GCM 凭证密文。现有 SHA-256 摘要不能反解，历史设备迁移后仍不可查看，需在管理页面轮换一次；轮换后旧凭证立即失效，新凭证同时保存摘要和密文。down 只删除密文列，采集器认证仍可继续使用摘要，但页面不再能查看凭证。

首次迁移的 down 会删除六张新表及新增字段，只用于可丢弃测试库或明确准备好备份的回退。Windows 本地队列不受服务器 Migration 自动清理；恢复后的服务端必须保留设备身份、许可和事件幂等记录，否则不能直接清空队列重新上传。应用回退优先保留新表与回执，停止 AOS 入口后按发布流程处理。

## 自有库存与销售迁移（2026-10-04）

本节描述隔离工作树的当前实现。正式 Migration 已在专用合成 PostgreSQL 库验证，不代表生产数据库已迁移或已完成真实库存交接。业务操作见[自有库存与销售管理](../design/自有库存与销售管理.md)，表结构权威入口见[数据库架构](数据库架构.md)和[自有库存与销售数据契约](自有库存与销售数据契约.md)。

### 正式迁移与初始状态

[`20261004000001-create-stock-management.js`](../../migrations/20261004000001-create-stock-management.js) 在单个迁移事务内创建 21 张 `stock_` 表及销售单号序列，包含基础资料、实物、销售、转运、费用、客户付款、公司到账、附件、审计及导入预览。不能用模型 `sync/alter` 或启动时补表代替正式 Migration。

迁移同时增加 `pickup_devices.stock_unit_id UUID NULL UNIQUE` 和 SN 组合外键。原取货绑定按已有 SN 建立 `registered` 实物身份并回填桥接，保留原设备 UUID、订单关联、SN 和时间。兼容回填不确认规格、位置、成本或取货事实，不产生现货、销量和货款。原取货绑定表及既有字段继续保留。

`stock_settings.enabled` 初始为 `false`。迁移只创建系统使用的“历史出货地点待核实”，不会编造重庆仓库、代卖方或官网价格。管理员在新应用内核实基础资料、切换时点及权限后再启用。关闭模块会阻止新的普通业务写入，但保留数据和受权限控制的读取；配置维护、受控旧桥接及原成功请求的授权重放按其既定规则继续工作。

执行顺序为：备份并验证恢复能力 → 在迁移窗口暂停旧取货写入 → 执行正式 Migration → 核对迁移记录、表结构及 SN 桥接 → 更新应用 → 完成配置及期初核对 → 明确启用。迁移 `up` 本身使用事务，未取得库存模块 advisory lock；旧版本代码也没有该锁，因此不能靠新锁替代停止旧写入的维护窗口。

### 统一事务锁与回退保护

新模块写入、已接入桥接的取货写入、显式桥接修复及 Migration `down`，均先取得 PostgreSQL 事务级 advisory lock `(641004, 1)`，再访问需锁定的业务记录。此锁顺序避免两条入口同时改变同一 SN、数量占用或资金分配。新增维护脚本也必须遵循同一顺序，不能先锁取货／实物行再等待模块锁。

应用回退优先保留这 21 张表、桥接列、审计与资金数据，停止新模块入口后恢复经核对兼容的应用。不要把 `npm run db:migrate:undo` 当成库存业务回滚手段。

`down` 在同一事务和模块锁内检查：实物是否仍全部为未入账的 `legacy_binding/registered` 桥接身份，以及是否存在销售、转运、库存事件、附件或已提交导入。出现上述业务／审计数据即拒绝删除并提示保留 schema 回滚应用；失败不会部分删表。仅在可证明可丢弃的隔离库、没有上述数据的情况下演练 `up → down → up`。允许的 `down` 只删除新增结构，保留原取货绑定与订单；它不是历史业务的撤销流程。

迁移验收应覆盖空库往返、旧取货 SN 的身份回填、旧 UUID／时间／订单不变及有业务数据拒绝 `down`。验证要求与证据见[自有库存与销售管理验收清单](../testing/自有库存与销售管理验收清单.md)，不把成功执行 DDL 视为真实库存已录入。

### 旧应用兼容与显式桥接修复

桥接列保持 nullable，允许旧代码新增取货记录时省略 `stock_unit_id`。这一结构兼容不代表旧应用理解实物在途、已售状态、库存权限或统一锁，也不授予混跑旧写入与新库存业务的安全保证。回退窗口应停止实物及资金操作并控制旧取货写入；新数据不能用旧版界面进行库存纠错。

若旧应用运行期间产生空桥接，恢复新版后先使用 [`repairPickupStockBridge.js`](../../scripts/repairPickupStockBridge.js) 盘点。命令必须在已核对连接目标的应用容器／受控环境运行；库存模块可保持关闭。

```bash
# 默认只读：仅报告 stock_unit_id 为空的取货绑定数量
npm run stock:repair-bridges

# 明确写入：将数字替换为已核实的有效内部管理员 ID
npm run stock:repair-bridges -- --apply --actor-id='<管理员ID>'
```

`--apply` 必须同时指定有效、未锁定的管理员作为审计操作者。脚本通过统一命令服务先取得模块事务锁，复用已有 SN 的实物身份或新建 `registered` 身份，再补空桥接；重复执行只处理仍为空的绑定。它不改变原设备 UUID、来源订单、时间、现货位置或成本，也不补猜销售、资金与实物事实。

补齐后重新运行默认只读盘点并核对 SN、来源关系及真实库存，再决定是否恢复模块业务。零空桥接只证明身份关联已补齐，不证明回退期间所有实际流转已登记。应用启动不会隐式运行修复，也不会自动打开库存开关。

导入预览的显式维护另见[Excel 导入规范](../design/Excel导入规范.md#过期预览维护)：`stock:cleanup-previews` 默认只读，显式清理仅作用于过期未提交载荷，保留已提交结果与业务记录。该维护不能用作库存回退或删除历史账目。

# 文档管理规范

> 状态：当前有效
>
> 最近核对：2026-09-06
>
> 基线：main@0fd7f80 与当前未提交工作树
>
> 验证范围：本地工作树静态核对；未验证真实数据库、邮箱、官网和生产环境

## 分类和入口

文档总入口为[docs/README.md](../README.md)。有效规范和操作说明放 design、database、development、deployment、security；尚未实施的方案放 planning；可复用用例放 testing；按日期冻结的历史事实放 archive。

根 README 仅维护项目简介、最短启动路径和关键链接。文档导航只做检索，不复制业务枚举、表结构和完整操作流程。

## 新增文档放置规则

新增前先查文档导航：同一主题已有文档时优先更新现有内容，只有独立主题或需要单独追溯的记录才新建。不得默认把新文档放在 docs 根目录或 development 目录。

| 内容类型                                     | 存放目录                | 选择依据与示例                                                                   |
| -------------------------------------------- | ----------------------- | -------------------------------------------------------------------------------- |
| 当前功能说明、接口、架构、技术决策           | `docs/design/`          | 如渠道管理、Excel 导入；内容描述现行规则和实现边界                               |
| 数据结构、匹配关系、迁移使用方式             | `docs/database/`        | 字段与约束统一更新数据库架构；迁移操作更新数据库初始化与迁移指南                 |
| 开发规范、工具说明、当前进度                 | `docs/development/`     | 如编码规范、前端规范、本地开发指南；不存放每次开发的长篇总结                     |
| 部署、日常运维、可复用排障方法               | `docs/deployment/`      | 发布步骤进入部署指南，常见问题的检查与恢复方法进入故障排查                       |
| 安全规则及仍在处理的安全事项                 | `docs/security/`        | 未闭环的敏感资产处置记录保持当前维护，不因日期较早就归档                         |
| 待确认需求、待实施方案、优化计划             | `docs/planning/`        | 如付款人与内部结算；明确待确认项，不作为现行接口或表结构                         |
| 可复用测试方法、验收清单                     | `docs/testing/`         | 保存用例、前置条件和预期结果，不把一次执行结果长期当作用例状态                   |
| 有日期的修复报告、事故复盘、测试结果、旧方案 | `docs/archive/YYYY-MM/` | 文件名使用 `YYYY-MM-DD-主题.md`，如 `2026-09-06-导入失败修复报告.md`（命名示例） |

新增有效文档同步[文档导航](../README.md)的对应分类；新增历史记录同步[历史索引](../archive/README.md)，新月份可在需要时创建。根 README 只在关键入口或启动方式变化时更新，不逐份罗列新文档。

规划落地后，把确认后的规则更新到对应当前文档；原规划标记实施状态并链接现行说明，有历史价值时归档。未完成的任务继续保留，不能仅通过移动文件把方案标成完成。

## 状态与职责

新文档应声明：状态、最近核对日期、适用范围、基线与验证范围。状态使用当前有效、待确认、待实施、历史归档或已废弃；安全记录允许使用“执行中”。阅读旧日期报告不等于重新验证。

| 文档          | 唯一负责内容                                    |
| ------------- | ----------------------------------------------- |
| 数据库架构    | 字段结构、约束和模型/迁移契约；冲突必须明确记录 |
| API 设计      | 当前端点、认证、请求响应契约与过渡例外          |
| 编码/前端规范 | 强制开发规则                                    |
| 开发进度      | 当前阶段、最近完成、验证、阻塞和下一步          |
| 优化计划      | 任务编号、优先级、依赖和验收标准                |
| 历史报告      | 指定时间和版本的事实、证据与决策背景            |

## 更新和合并

- 中文文件名和正文优先；README.md 等约定名称、代码标识符和第三方术语保留原文。
- 新能力未实现时写入规划，不在当前流程图和示例中冒充已实现。
- 新规则直接修改受影响正文；旧示例有追溯价值时归档，不用“顶部说明优先”覆盖全文。
- 新建、移动、合并、删除文档时同步索引和全部有效引用，包括 AGENTS、提示词、脚本与 CI。
- 删除前确认独有规则已有承接、历史证据可追溯、有效链接已修复。完全重复的表达不需要每份各留一个空壳文件。
- archive 保留原命令和旧文件名作为历史文本；不得从历史文本生成当前操作入口。

## 级联要求

表结构变更先更新数据库规范，再模型、迁移、接口和测试；API 变更先更新 API 文档，再实现与调用方；业务逻辑变更同步专题说明。完成每阶段更新开发进度，并链接测试证据。沿用[AGENTS.md](../../AGENTS.md)的授权与质量要求。

## Bug 修复文档规则

普通 Bug 不要求每个都新建报告。先判断是实现错误、规则变化还是重大故障，再按以下规则处理。

| 修复情形                                 | 必须记录或更新                                                                         | 不需要的操作                                                   |
| ---------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 实现偏离既有正确规范，修复恢复原预期     | 开发进度记录现象、根因、修复结果和验证；核心逻辑补回归测试，其他改动做与风险相称的验证 | 不改写正确规范来迎合原错误，不单独生成一份普通修复报告         |
| 修复改变业务规则、接口、数据或操作方式   | 先按授权确认语义变更，再按功能对照表更新相关规范、契约或操作文档；同步用例和开发进度   | 不只写“已修复”而让使用说明继续保持旧行为                       |
| 重大事故、反复发生、跨模块或需要审计追溯 | 新建有日期的修复/复盘报告到 archive，开发进度链接报告；可复用排障方法更新到故障排查    | 不把当时测试通过结论写成永久能力保证，不在多个位置复制整份报告 |
| 已定位但未修复，或仍有后续治理           | 在开发进度和对应优化任务记录状态、影响及下一步；安全未闭环事项继续维护安全记录         | 不因完成调查或归档就把问题标为已关闭                           |

开发进度中的普通修复记录至少包含：问题或任务标识、触发条件与影响、根因、修复内容、验证方式与结果、未验证项。需要完整报告时，另补日期、代码基线、环境、复现步骤、关键证据、预防措施和后续任务。真实数据、凭据、原始订单信息应脱敏。

可复用验收用例保留在 testing，某次执行结果写入有日期的报告；已冻结的旧报告不改成新版本结论，新增报告注明关联和复测结果。索引只在新建、迁移、删除或入口变化时调整，不要求每次修复都改 README。

## 完成前检查

1. 新内容已经放入对应目录，或合并进已有主题文档。
2. 按功能和 Bug 规则检查所有受影响文档，当前正文与确认后的行为一致。
3. 开发进度已记录完成、验证和未闭环事项；涉及计划任务时同步状态。
4. 新增或移动文档可从对应索引找到，引用及历史来源可追溯。
5. 运行下方文档检查；代码变更另按测试指南验证，文档检查不能替代功能回归。

## 验证

`npm run docs:check` 检查文档链接、锚点、导航可达性、过期路径及命令，另检查模型字段是否出现在数据库文档。它不验证数据库实际类型、索引、线上拓扑或接口运行结果。

日常只格式化本次修改文件，不为整理文档运行全仓写入格式化。发现代码与文档矛盾时先记录证据和未验证边界，不擅自修改业务语义。

# 常见故障排查

> 状态：当前有效
>
> 最近核对：2026-09-06
>
> 基线：main@0fd7f80 与当前未提交工作树
>
> 验证范围：本地工作树静态核对；未验证真实数据库、邮箱、官网和生产环境

## 前端白屏

1. 确认前端开发端口为 5173，API 端口为 3000；生产端口另看 Nginx。
2. 浏览器 Console 查模块导入、运行时异常；Network 查 JS 资源和 /api 请求。
3. API 客户端统一封装 baseURL；页面不要重复拼接 /api，见[client.js](../../frontend/src/api/client.js)。
4. 区分加载、401/403、500、空列表与渲染错误；空数据不使用 Mock 掩盖。
5. 查看 CSS/DOM 和当前路由是否挂载。清缓存或重新构建只在证据指向旧资源时进行。

## 认证与导出失败

新账号不再强制改密，账号可在多个设备同时登录且新登录不会替换旧设备。单台退出只撤销本机会话；改密、管理员重置或锁定会撤销全部会话，旧格式 Token 需重新登录。导出和模板应走带 Token 的客户端并处理 Blob；直接打开硬编码 URL 可能没有认证头。系统日志和用户管理需要 admin。

## 数据库与导入

ready 返回 503 时核对连接变量与实际迁移状态。CLI test 库与模型 DB_NAME 可能不同，先核实目标，不能直接重建数据库。导入消费令牌后失败需重新预览；返回 imported/skipped/errors 应逐项检查。

## 邮件与官网

当前仅扫描 UNSEEN；已被其他客户端读过的邮件不会自动回溯。关闭 IMAP_MARK_SEEN 可能导致同一未读邮件反复处理。官网同步需要代理和自动刷新开关；连续 541、代理失效、校验异常及终态订单都可能停止刷新。

## 提交问题记录

记录版本、时间、环境、复现步骤、期望/实际、请求 ID、脱敏日志、影响范围和已尝试操作。历史仪表板导入错误及代理事故可从[历史索引](../archive/README.md)查阅，不能直接照搬旧重启命令。

## 手动官网更新很快失败并显示“请稍后重试”

当前手动队列与旧自动爬虫独立。先看 `official_order_refresh_jobs` 的领取／完成时间、错误码，再对照独立研究库运行记录和受限输入文件大小。约 2–3 秒失败、`COLLECTOR_FAILED`、没有对应官网运行且输入临时文件为零字节时，应优先核对输入提取，不通过反复登录或换代理排查。

2026-10-03 制品的输入脚本强制 JOIN `apple_ids`；订单本身有账号／加密密码快照而账号主表未匹配时，提取返回零行并退出。宿主队列只解析 stdout，具体 stderr 错误丢失。只读核对存在性、匹配数、引用一致性和解密是否成功，禁止输出密码或完整链接；不要擅自批量补账号或改订单关联。此次影响、复现及待修复项见[故障定位记录](../archive/2026-10/2026-10-03-官网手动更新账号关联依赖故障定位.md)。

## 采集器升级与API内存

更新任务TRAY_STILL_RUNNING时，先核对实际运行版本和旧托盘所在登录会话。旧SYSTEM更新组件不能向其他会话桌面枚举窗口；1.2.1首次由对应桌面管理员运行已验签修复包，保留设备身份和队列，之后使用新版受限本机命名管道退出。不要强杀正在保存配置的GUI或把任务下发当作升级完成。

并发下载导致API OOM时查看内核cgroup日志和RestartCount。1.2.1服务端已改为流式制品摘要，真实20并发峰值约68MiB；临时2GB措施已随正式发布恢复768MB。复盘及验证范围见[修复记录](../archive/2026-09/2026-09-15-采集器更新故障与修复记录.md)。

## 库存全部查询异常、查看记录空白或菜单缺失

- 先区分商品／门店“配置已启用”和采集实际运行状态；看最后成功时间、最近尝试、当前失败原因和固定轮次覆盖，不把上次有货作为当前新鲜结果。
- 全部 NO_HEALTHY_PROXY 时只读核对库存健康页和 `inventory_validation_attempts` 最近完成记录。CONNECT 502/503/504 属临时代理网关故障；以 responseSource/tunnelStatus 区分代理响应与 Apple 响应，不能把所有 CONNECT 非 200 当成 Apple 风控。凭据、完整代理 URL 和原始敏感正文不得写入报告。
- 如确认是旧分类留下的错误暂停，应先发布分类修复、备份状态，再锁定并校验具体供应商和对应失败证据，仅纠正该条暂停；保留其他暂停、冷却、风险、租约和预算。禁止用清空整个状态表恢复，也不要重写历史失败轮次。观察下一轮真实成功和覆盖后才确认恢复。
- “查看记录”白屏应复现精确 SKU／门店下钻并检查筛选摘要，不只测试直接进入历史页；详情展开的手机入口也需要覆盖。
- 普通用户缺少库存菜单时，在用户管理检查是否显式授予 `inventory.read`；该权限只显示“库存监控”的三个查询页签。管理员另有“监控管理”的两个配置页签，普通用户不应调用设置、健康详情或采集操作接口。

本次生产证据见[库存故障与权限分组发布记录](../archive/2026-10/2026-10-03-库存故障与权限分组发布记录.md)。

## 库存运行提醒短时间反复异常与恢复

先区分 `health` 运行提醒和 `arrival/first/recovery` 库存事件；投递记录条数不等于群消息数，库存事件会按城市／门店合并。检查 `inventory_runtime.body.lastError`、保护闸门、近轮次覆盖率及脱敏请求结果，不能把一次 `TRANSPORT_UNKNOWN` 判为全部门店无货。

运行提醒采用持续异常／稳定恢复各 2 分钟、同类故障 30 分钟合并；严重保护状态立即排队，仍受静默和群限速约束。`healthAlerts` 保存观察与发送关联；`HEALTH_SUPERSEDED` 表示过时健康通知被取消，属于正常降噪。未知回执或 Worker 中断不盲目重发，明确失败按既有次数限制处理。排查时只读状态和脱敏结果，不通过反复发真实测试消息检查降噪。

## 大库备份期间 API 超时与分区建表等待

检查 `pg_stat_activity` 的等待类型与 `pg_blocking_pids`，用表锁关系追踪根阻塞源；避免输出包含个人信息的原始 SQL。完整 pg_dump 持有的表锁可能阻塞动态分区 DDL，若该事务还持有设备行锁，会继续阻塞心跳与全局 advisory lock 请求，耗尽 API 连接池。确认由当前任务的备份引起时，优先取消该备份会话并核验 readiness、锁等待和入库恢复，不直接终止所有业务事务。未完成 dump 必须标记不可恢复或删除；定向表备份不能宣称完整备份。后续完整备份与迁移需另行评估 DDL 并发和窗口，参见[2026-10-08 复盘](../archive/2026-10/2026-10-08-普通用户订单密码查看发布与备份锁等待复盘.md)。

# 下单时间精度修复记录

## 现象与根因

付款任务三条订单显示同日 08:00:00。只读核对发现官网 `orderPlacedDate` 只有日期，`parseOrderData` 生成 `YYYY-MM-DD`，`mergeOfficialOrder` 覆盖原邮件/人工录入的 `orderDate`，PostgreSQL 保存 UTC 午夜，前端转换为北京时间 08:00。全库同一条件命中 9 条，有完整来源快照；未证明其余全部订单的真实下单时间准确。

## 修复范围

- `orderDate` 保留来源时间；官网精确时间独立保存在 `officialOrderCreatedAt`，日期冲突保留来源并提示核对。缺失官网节点时保留已有冲突信息。
- 订单列表、详情、渠道订单、付款调度、付款任务、Apple ID 最近下单日期及导出统一北京时间。仅日期不补造时分秒，空值显示未知。
- 人工补单按北京时间展示并保留秒，必须输入时分；官网完整无时区时间按北京时间解析。
- 订单/统计日期范围覆盖北京时间完整起止日，趋势分组不依赖数据库会话时区，环比使用完整前一周期。
- 不改变付款截止、任务状态、分配资格。来源时间不等于已验证的官网精确时间。

## 历史恢复与回滚

`npm run orders:restore-times -- W订单号 ...` 默认预览，增加 `--execute` 才执行。明确指定 1–100 个订单，在事务中锁行，只修改符合“UTC 午夜、同日、存在不同的精确来源快照”条件的 `orderDate`；不改更新时间、来源快照、付款字段及任务。

生产先完整备份并恢复到临时库验证，再更新 API、前端与爬虫 Worker，阻止旧爬虫继续污染后定向恢复 9 条。迁移表不变。代码回滚时必须保持旧爬虫停止，避免重现覆盖；数据回滚仅针对恢复清单及已保存的原值，禁止用旧全库备份覆盖运行中新数据。

## 验证与发布

本地全量单测 421 项通过（57 项显式门控跳过），独立 PostgreSQL 生命周期集成 19 项通过。后端和前端 Lint 无错误（保留存量警告），前端构建、文档链接与 20 个模型字段覆盖检查通过。付款页面浏览器在 UTC 时区验证分页、单行/批量刷新、草稿、权限及下单时间通过，日期值不补造时间。

生产完整备份位于 `/var/backups/apple-order-mgr/order-time-20260909T110000Z/`，已恢复临时库校验 109 条订单、9 个付款任务、23 条 Migration 记录；临时库已删除。代码已发布并完成定向恢复，未进行真实支付验收。

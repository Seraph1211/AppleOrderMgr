## 官网刷新退役

官网爬虫、浏览器批量刷新、代理切换和系统爬虫日志已退役。旧接口返回 HTTP 410；历史数据只允许通过 `archive` schema 受控查询和恢复。

## 日常只读检查

```bash
cd /var/www/apple-order-mgr/current
docker compose --env-file release.env -f docker-compose.prod.yml ps
docker compose --env-file release.env -f docker-compose.prod.yml logs --tail=100 api
docker compose --env-file release.env -f docker-compose.prod.yml logs --tail=100 email-worker
docker compose --env-file release.env -f docker-compose.prod.yml -f images.override.yml --profile wecom logs --tail=100 wecom-worker
curl -i http://127.0.0.1:3001/api/health/live
curl -i http://127.0.0.1:3001/api/health/ready
curl -I https://apple.godp.me/
```

`live` 只说明 API 进程存活，`ready` 只额外验证数据库连通。两者都不能证明邮件处理或企微推送正常。

## 服务操作

更新 Compose 服务时使用：

```bash
docker compose --env-file release.env -f docker-compose.prod.yml -f images.override.yml --profile order-mail --profile wecom up -d api email-worker order-mail-worker wecom-worker
```

不要运行不带项目范围的 Docker 清理、停止或重启命令。PostgreSQL 和 Nginx 是宿主机共享服务，不能随应用 Compose 操作。

## 常见症状

| 症状          | 优先检查                                                                                                                           |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 前端打不开    | `current` 链接、静态文件、Nginx 站点配置和证书                                                                                     |
| API 502       | `api` 容器、`127.0.0.1:3001`、Nginx upstream                                                                                       |
| readiness 503 | PostgreSQL 连接、环境变量、Migration 状态                                                                                          |
| 邮件未入库    | `email-worker` 日志、IMAP 网络、授权码、精确地址／域名白名单、`SUBJECT_NOT_ALLOWED`／`SENDER_NOT_ALLOWED`、主题/正文格式、未读状态 |
| 邮件状态未更新 | `order-mail-worker` 日志、生命周期开关、订单号精确匹配和待复核原因                                                                 |
| 登录失败      | 用户状态、JWT 配置、当前设备会话是否失效                                                                                               |

## 日志与磁盘

应用日志写入 Docker stdout/stderr，并由 `json-file` 限制为每个容器最多 5 个 10 MB 文件。查看磁盘前先限定项目：

```bash
docker compose --env-file release.env -f docker-compose.prod.yml ps -q
docker system df
find /var/www/apple-order-mgr/releases -maxdepth 2 -type f -printf '%s %p\n' | sort -n | tail
```

发布目录和数据库备份的删除必须先列出版本、确认当前 `current` 指向和回滚保留策略，再单独执行。

## Nginx 与数据库

站点配置变更后：

```bash
nginx -t
systemctl reload nginx
```

数据库备份、恢复和迁移遵循[数据库初始化与迁移指南](../database/数据库初始化与迁移指南.md)。不要通过删除表、Migration 记录或数据库目录来处理迁移故障。

## 统一发布工具速查

先按[生产发布分级执行规范](生产发布分级执行规范.md)生成`release-classification.json`。A级纯静态
前端和B级严格无写入发布仅在24小时内完整恢复证明仍有效时复用；C级业务写入和D级Migration／
数据转换必须执行下列本次数据库备份与完整恢复。无法证明等级或恢复证明失效时按C级执行。

生产发布工具位于 root 专属目录并纳入制品 SHA-256。数据库凭据仅由受保护环境注入。备份、
隔离恢复和严格比较依次执行：

```bash
python3 productionReleaseBackup.py database-backup \
  --database apple_order_mgr --output <备份目录>/business.dump \
  --validation-sql productionReleaseDatabaseValidation.sql \
  --evidence <备份目录>/database-backup-evidence.json
python3 productionReleaseBackup.py isolation-proof \
  --container <隔离PG15容器> --target-database <apple_order_mgr_restore_本次ID> \
  --source-database apple_order_mgr --output <备份目录>/isolation-proof.json \
  --proof-key-file <0600认证密钥>
python3 productionReleaseBackup.py database-restore \
  --dump <备份目录>/business.dump --sha256 <备份证据中的SHA256> \
  --target-database <apple_order_mgr_restore_本次ID> \
  --isolation-proof <备份目录>/isolation-proof.json \
  --container-dump-path /restore-input/business.dump \
  --validation-sql productionReleaseDatabaseValidation.sql \
  --evidence <备份目录>/database-restore-evidence.json \
  --proof-key-file <0600认证密钥>
python3 productionReleaseBackup.py compare-validations \
  --source-evidence <备份目录>/database-backup-evidence.json \
  --restore-evidence <备份目录>/database-restore-evidence.json \
  --output <备份目录>/database-comparison.json
```

若仅 `schemaDigest` 因 PostgreSQL 原生重放发生差异，保留上述失败文件，禁止正则删 cast 或括号。
在发布锁和无 DDL 窗口另行运行 `schema-source-archive`，要求 before/after raw 摘要均等于原备份
源摘要且 archive list 零数据项；再用独立 reference、business schema-only、full restore 三个
无网 PG15 容器运行 `schema-native-proof`。最终 `compare-validations` 只接受 HMAC 认证的
`--native-schema-evidence`，三方 schemas/columns/types/sequences/constraints/indexes/partitions/
functions/triggers/relations/comments inventory 必须逐对象相同；还须使用同一精确 PG15 镜像和
受控 `--restrict-key` 生成三份完整 schema-only plain SQL，并要求原始字节摘要完全相同。不得
删除版本 header 或正文后比较；原失败和无效 attempt 不覆盖。

隔离容器由本次操作唯一创建，`--network none`、无端口，dump 精确只读挂载到
`/restore-input/business.dump`，并带 `isolated-restore=true`、
`side-effects-disabled=true`、`postgres-major=15`、`restore-database=<目标库>` 标签。
工具还会在容器内实查 PostgreSQL 15 和空库；任一步失败都不能切换。

序列不是 MVCC 快照的一部分，不把源库现场序列值与恢复值做相等比较。恢复摘要单独验证 dump
恢复出的 `last_value/is_called` 及拥有列最大值，确保下一次 `nextval` 不碰撞；schema、业务行
摘要和 Migration 仍按同一导出快照严格比较。

文件快照先生成 `consistency-proof` 再 `snapshot`。从 `/` 采集时每个生产路径都用独立
`--include-path` 指定，不把 `/`、`var` 或整个 `shared` 作为粗粒度 include。官网队列暂停、
在途归零和无活跃写入只用于取得一致边界，不得触发真实官网请求。恢复到新空目录逐文件验证
后，再与数据库恢复证据合成 `recovery-bundle`。

生产存在绝对符号链接时，链接本身和每一级 target 都分别使用 `--include-path`；例如运行时
Python 链接需同时纳入 `usr/bin/python3` 与 `usr/bin/python3.6`。清单保存原 target，隔离恢复
只在 target 已入清单时重映射到恢复根，不能跟随链接扩大为全机扫描。恢复后核对链接总数、
绝对／相对分类和逐链接最终目标，数量不符即失败。

manifest 每项必须含 `uid/gid`。Linux 原路径恢复默认保留 owner，并以 root 对链接执行不跟随目标
的 `lchown`；Mac 隔离演练先用 `ownership-map` 生成绑定 manifest 摘要的认证映射，再把该文件
传给 `restore --ownership-map`。不要用未认证的全局 uid 替换表，任一 owner 或 mode 复核失败
都不能登记 `recovery-bundle`。

并行准备计划配置 `resourceGuard`，探针使用 `productionReleaseResourceProbe.py` 读取备份盘余量、
本地 `/api/health/ready` 延迟及只读数据库锁等待。磁盘不足或探针异常立即停止；延迟／锁等待超
阈值时只把剩余可暂停只读步骤降为串行，维护窗口和发布锁内步骤不得并行。

`productionRelease.py validate --plan <计划>` 只验证结构，`run` 才执行。`resume` 只处理未回退
且无 unknown mutation 的同一 attempt；`rolled_back` 必须新建 attempt。清理先运行
`cleanup-plan`，候选为 0 是安全结果；复核计划摘要后才由获授权人员运行 `cleanup-apply`，不
配置自动清理。

## HTTPS 证书自动续期

`apple.godp.me` 使用宿主机 Certbot 的 Nginx 验证和安装插件。专属任务 `/etc/cron.d/apple-order-mgr-certbot` 设置 `CRON_TZ=Asia/Shanghai`，每日北京时间 04:37、16:37 检查；仅到续期窗口才签发新证书，成功后执行 `nginx -t` 和平滑 reload。`crond` 应运行且开机启用；不要把其他域名专属任务误当成本站自动续期。

```bash
cat /etc/cron.d/apple-order-mgr-certbot
systemctl is-active crond
systemctl is-enabled crond
openssl x509 -in /etc/letsencrypt/live/apple.godp.me/fullchain.pem -noout -dates
certbot renew --cert-name apple.godp.me --non-interactive --no-random-sleep-on-renew --dry-run
curl -I https://apple.godp.me/orders
```

日志位于 `/var/log/letsencrypt/letsencrypt.log`。手动续签前备份本站证书、续期参数和 Nginx 配置，再使用 `certbot renew --cert-name apple.godp.me --non-interactive --no-random-sleep-on-renew --deploy-hook '/usr/sbin/nginx -t && /usr/bin/systemctl reload nginx'`。验证证书有效期、严格 TLS 校验和 HTTP 到 HTTPS 跳转；不要使用 `curl -k` 作为恢复验收。当前旧版 Certbot 的 dry-run 跳过 deploy-hook，不能将模拟成功当作部署钩子已执行；真实续签后单独回读线上证书。

## 订单列表邮件通道

此通道与自动建单邮件、监控通知独立。先应用正式 Migration 20260920000003-add-order-mail.js，再为API和独立Worker配置相同 ORDER_MAIL_*；模板见仓库 .env.example。ORDER_MAIL_ENABLED 默认false，启用需明确配置账号及凭据。IMAP固定TLS 993、SMTP固定TLS 465，校验证书，不支持降级明文。生产环境文件是受保护配置，禁止将真实密码提交仓库；若用 ORDER_MAIL_PASSWORD_FILE，应给API和Worker分别挂载同一只读凭据文件，示例路径为 /run/secrets/order-mail-password。生产Compose未默认挂载此文件，须在部署override中声明volume；也可由受保护环境文件注入 ORDER_MAIL_PASSWORD。

启动本地专用通道命令：docker compose -f docker-compose.dev.yml --profile order-mail up -d order-mail-worker。生产按正式发布步骤发布迁移/API/前端后，使用 docker-compose.prod.yml 的 order-mail profile显式启动独立Worker；普通email-worker不会连接新总收件箱。原邮箱凭据、监控SMTP、全局订单来源开关不变。回滚前先停止order-mail-worker并关闭开关，禁止直接回滚含真实发送历史的数据库表。

首次同步默认最近30天，按服务端邮件日期搜索并持久化起点；之后修改回查天数不自动重置已存在游标。只读打开邮箱，不修改已读标记。每封上限10MB；默认接受apple.com、apple.com.cn及子域，真实来源须用邮件头核实后按ORDER_MAIL_SENDER_DOMAINS精确配置，不凭显示名称放行。暂不解析PDF等附件中的订单号，多订单号或无完整W订单号不自动关联。

管理员在用户权限管理授予“订单邮件 / 查看完整订单邮件、附件并转发”，依赖订单读取且继续受订单TAG范围限制。普通用户默认无此权限。

转发邮件同时提供 HTML 正文与纯文本备用，继续附加原附件及原始 EML；系统预览保持纯文本。外部图片是否加载取决于收件客户端。正文格式与真实 QQ 验收见[排版修复记录](../archive/2026-09/2026-09-20-邮件转发正文排版修复.md)。

queued=待发；sending=发送中；retry_wait=明确临时失败待重试；accepted=SMTP接受，非最终送达；unknown=网络或进程中断，需核对目标收件箱及邮件服务器日志，禁止盲目重新发送；failed=失败；cancelled=授权撤销或内容过期。发送前临时数据库失败使用PREPARE_TEMPORARY重试。原始内容180天清理；查看正文、下载附件和转发均有操作审计，发送队列保留加密目标和备注。

## 企微订单通知运维

功能入口与状态解释见[企微订单通知](../design/企微订单通知.md)。上线顺序为：备份 → 正式 Migration `20260920000004-add-wecom-notifications.js` → 包含新依赖的 API／收单 Worker 制品 → 显式启动 `wecom` profile → 后台保存测试群配置（自动通知关闭）→ 获授权后发送固定测试消息 → 核对群内实际收到 → 正式启用。

新增企微 Worker 不随默认 profile 启动；生产镜像同时供 API／收单 Worker／企微 Worker 使用。配置表默认关闭，Webhook 用现有字段密钥加密，不写 `.env.example` 或发布说明。需要恢复发送时先看页面暂停原因、积压、心跳；不要直接把 unknown 记录改回 pending，避免重复发消息。停用不会撤回已发出的网络请求。

回滚优先停用通知并停止企微 Worker、回退应用制品，保留通知表和历史供核对。Migration down 会删除配置与历史，只能在备份及明确数据库回滚授权后执行。切勿影响同机其他系统。

## 一、结论

1. 生产归档有 1,494 封邮件，涉及 488 个订单号；全部归档 MIME 可解析。与系统 485 笔订单比较，484 笔有归档邮件，4 个邮件订单号未在系统中找到，1 笔系统订单暂无归档邮件。这是两类关联缺口，不能据此认定邮箱漏收或 AOS 的具体故障原因。
2. 当前增量扫描范围内，符合现有完整订单号关联规则的邮件均已归档，没有发现本次漏收。扫描器状态在两次观测中正常，但不等于已验证所有断线和故障恢复场景。
3. 可取货通知有 217 封，全部明确包含“已可取货”和门店；215 封有确定的取货日期、时间段，2 封要求营业时间内到店，没有固定预约时段。
4. 付款状态可按当前预付到店业务的跨模板流程设计：订单确认邮件说明付款确认后才开始处理，处理邮件确认进入处理中。将匹配的处理中／可取货通知解释为付款已确认，是业务流程映射，不是正文出现逐字的付款回执；上线前须固化为有范围限制的规则。
5. 用户明确已取货不能从这些邮件判断，因此该状态不纳入本期邮件自动更新。电子收据与个人设置辅导邮件不参与本期状态判定。

## 二、方法与只读边界

通过既有 `PP_CloudServer` SSH 别名访问实际运行容器。数据库查询显式执行 `SET TRANSACTION READ ONLY`，归档主快照使用 REPEATABLE READ，并回读 `transaction_read_only=on`。没有运行 Migration、保存订单、修改任务、推进扫描游标、调整配置、重启应用或发送邮件。

从生产归档读取并解析全部 1,494 封 MIME，敏感正文仅保存在本地忽略目录，目录权限 700、文件权限 600；项目文档只记录数量、受控语句和用户明确指定的示例订单。代码检查确认 API 与实际订单邮件 Worker 的四个关键文件摘要相同，且与本地当前实现一致：`emailScanner.js`、`orderMailSync.js`、`orderMailService.js`、`orderMailContent.js`。

IMAP 使用 TLS 校验、只读 EXAMINE 和 `markSeen:false` 的 BODY.PEEK 读取。为每个文件夹冻结 `UIDNEXT-1` 上界，枚举所有现存 UID；对 From 域名符合当前 Apple 白名单的邮件，以邮箱身份＋UIDVALIDITY＋UID逐封核对归档。已归档正文以数据库内原件为分析来源，另抽取六类主题各一封邮箱原文校验 MIME SHA-256，6/6 一致；三个未归档候选重新读取全文分类。没有宣称全部邮箱 MIME 都重新下载并逐字节比较。

首次全量正文读取在完成部分读取后主动停止了本次临时诊断进程，改用上述 UID 逐封对账＋缺口原文＋模板抽样校验，减少重复下载；未停止生产 Worker。部分读取不作为完整性结论，最终结论只来自完成的对账快照。

当前代码的机制是新邮件事件触发＋每 30 秒主动扫描、连接就绪立即扫描、异常后 30 秒尝试重连；不依赖网页打开或刷新，不按未读状态决定是否接收。扫描成功只证明本轮接收遍历完成，不证明所有疑似邮件均已识别，更不证明业务状态已应用。

增量延迟按 IMAP INTERNALDATE 到归档 `createdAt` 计算，不按发件日期。排除首次历史回查，取北京时间2026-09-20 03:15之后收到且已归档的976封：中位数8.613秒、P95为29.409秒、最长58.599秒，超过60秒为0封，无负值。这是该正常运行窗口的实测，不包含尚未实现的状态解析／应用延迟，不构成未来故障下的时效保证。

仍需改造的边界：疑似订单邮件解析／关联失败只计数、单文件夹配置、缺少独立周期对账、缺少业务应用队列和独立积压告警。现有 `ignoredCount=102` 是处理计数，不可直接与本次邮箱总数相减来判断缺口；时间窗口和过滤路径不同。

没有执行故障注入，没有改已读标记、清理邮箱或调整原游标；不能将本次正常观测写成“永远不会漏收”。

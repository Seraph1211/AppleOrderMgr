# 库存监控 IPRoyal 优化实施方案

> 状态：开发与主审通过，等待生产切换及真实出口验收。
> 日期：2026-10-16。
> 授权：用户要求子 Agent 使用 GPT6.1 Sol／高推理编码与测试，主 Agent 验收通过后提交并部署。

## 已确认范围

对应上一轮用户可见问题编号：1 切换 IPRoyal 作为唯一 IP 来源；2 区分自动等待、人工处理、Worker 离线及库存失效；3 修复调度等待并区分未发送与请求失败；4 取消单次全局风控对已成功组合的硬中断；5 停止逐门店恢复有货消息，保留事件并合并健康摘要。用户回复第 8 条按其文字“以当前生产环境最新代码进行优化”执行，包含归集运行补丁和保护最新线上其他功能。

用户明确第 6、7 条无需处理：不改变三次请求恢复门槛、五分钟风险窗口、三并发、约 1 RPS、300 秒轮次、预算及既有健康通知观察／去重周期，不增加长期故障重复提醒。原策略确认稿 R1、R2、R6 不纳入本次。统计口径重构也不扩大到本次。

## 接入与业务设计

代理设计以[IPRoyal 库存代理接入](../design/IPRoyal库存代理接入.md)为准，使用已登录 Chrome 中既有住宅代理凭据、中国出口、十分钟粘性、高端池及 killswitch；暂不新增采购或开启自动充值。控制台核查仅余约 0.28 GB，实际可用性和用量以部署验证及供应商账单为准。

业务规则见[库存监控](../design/库存监控.md)和[API 契约](../design/API设计.md)。主健康信息与单组合结果分离；有效期不被冷却延长。只在连续新鲜无货转有货时提醒到货；中断后的有货保留 recovery 事件但不逐店推送；旧待发恢复消息跳过，投递历史保留。健康恢复摘要用“查询通道恢复”，按发送时真实覆盖／有货数量描述，不宣称完整或长期稳定。

## 基线与分工

隔离工作树从 3256c74 建立。读取生产 API 与库存 Worker 的实际源码保存于忽略目录；归集六个漂移模块（driver、guard、client、gate 及新增 tunnel／tunnelPolicy），再进行优化。发布候选以切换时最新生产镜像为基础，白名单覆盖库存文件；其他已发布功能不能因仓库差异被覆盖。

- proxy_dev：IPRoyal 驱动、隧道状态、保护与对应单测。
- behavior_dev：状态、调度、事件／通知、API、PC/H5 和业务自测。
- independent_test：独立负面测试、真实隔离 PostgreSQL 事务和权限／UI 验收。
- 主 Agent：方案边界、代码审查、真实制品校验、备份恢复、Git 提交及生产部署验收。

以上三个子 Agent 均指定 gpt-6.1-sol、high。不得将单元测试、HTTP 200 或 Worker 存活等同真实全国覆盖。

## 验收和发布

必须验证：唯一来源及配置严格验证、敏感信息脱敏、旧来源停用不污染新来源、真实出口摘要拒绝重用、410 会话失效有限轮换、541 原保护不变、迟到结果、预算重置等待、普通容量等待不报故障、未发送与实际失败、同轮成功保护、恢复事件保留与旧队列兼容、恢复摘要真实覆盖、PC/H5 与权限。

发布前按[生产部署指南](../deployment/生产环境部署指南.md#发布前备份和演练)执行排除 AOS 日志数据的业务备份和 PG15 隔离恢复比对。只更新库存相关 API／Worker 和前端；保留其他容器、共享配置与数据库历史。生产切换后独立回读运行源码摘要、有效配置白名单、健康和自然轮次。新代理真实失败时保留保护和原因，不清预算或伪造恢复。长期 48 小时稳定性另行验收，短期验收不替代。

## 能力与边界

执行器使用独立 Chrome 进程，默认同时处理 10 笔订单，可配置 1–10。每笔任务建立全新上下文并独占一个 SOCKS5 节点；不读取日常 Chrome 的 Cookie、登录信息，也不修改系统代理或个人 Chrome 的 PAC。50 个节点可以作为备用池循环租用，不表示只能处理 50 笔订单。不同入口节点是否真正对应不同公网出口，需要供应商及实测确认。

每笔最多三次尝试，遇到 HTTP 541／429、文档传输失败或未到达详情页的超时，释放上下文并换节点。只有包含身份、阶段和商品的结构化订单结果才进入解析和事务；无需金额、日期、门店或付款字段；仅页面文字、验证码、加载页及结构异常保留原值并转为待核对。此前人工读取 DOM 的部分字段同步，不等于这条自动链路已经通过真实官网验收。

所有实际页面请求和重定向仍向系统申请 PostgreSQL 全局许可，默认 5 RPS、上限 10 RPS。十并发指同时等待和处理的订单数，不保证十倍吞吐量。图片、媒体、字体请求直接取消；WebSocket 禁止建立，独立子目标和弹窗使该次任务停止。系统暂停、权限失效或 API 不可达会停止批次，不自动恢复系统开关。

## 运行前准备

1. 本机安装 Node.js 20+、Chrome，项目依赖中已包含 `playwright-core`；首次在本机运行前，在仓库根目录执行 `npm ci` 安装锁定依赖。日常 Docker 开发容器没有桌面 Chrome，实际采集 CLI 在本机运行；不要把执行器接到个人 Chrome 调试端口。
2. 目标 API 必须部署支持 `mode=isolated_batch` 的浏览器刷新接口，并已在授权范围内启用 `BROWSER_ORDER_REFRESH_ENABLED=true`，全局刷新未暂停。旧版接口缺少批次预算时执行器拒绝继续。实现本身不自动部署或修改生产开关。
3. 使用有 `orders.refresh` 权限的管理员正常登录系统 API，取得当前会话 JWT，保存为私密文本文件。不要从日常浏览器提取 Cookie／令牌，不把密码、JWT 或代理提取密钥写进命令行或 Git；正常登录仍受系统会话规则约束。
4. 准备至少与并发数相同数量的有效 SOCKS5 节点（神龙白名单免认证方式）；建议额外备用节点。此执行器不购买套餐、不自动提取付费节点。节点失效时，可在停止批次后更换配置中的代理列表，再用原检查点续跑待处理单。
5. 明确系统订单 ID 清单，最多 1000 笔且不能重复。准备独立的私密目录保存配置、令牌及检查点，目录权限 `700`，配置和令牌文件权限 `600`。

## 配置与启动

以下是结构示例。`192.0.2.0/24` 为文档示例地址，必须替换为实际已授权节点；订单 ID、API、绝对路径也须替换。配置和令牌是两个独立文件。

```json
{
  "apiBaseUrl": "https://apple.godp.me/api",
  "tokenFile": "/Users/你的用户名/订单刷新私有目录/login-token.txt",
  "checkpointFile": "/Users/你的用户名/订单刷新私有目录/批次状态.json",
  "orderIds": [195, 196, 197, 198, 199, 200, 201, 202, 203, 204],
  "concurrency": 10,
  "headless": false,
  "proxies": [
    "socks5://192.0.2.1:60006",
    "socks5://192.0.2.2:60006",
    "socks5://192.0.2.3:60006",
    "socks5://192.0.2.4:60006",
    "socks5://192.0.2.5:60006",
    "socks5://192.0.2.6:60006",
    "socks5://192.0.2.7:60006",
    "socks5://192.0.2.8:60006",
    "socks5://192.0.2.9:60006",
    "socks5://192.0.2.10:60006"
  ]
}
```

支持 `IP:端口` 简写。代理不接受 HTTP 协议、账号密码或重复节点；可选 `executablePath` 指定 Chrome 可执行文件绝对路径，默认查找系统 Chrome。默认显示专用浏览器，`headless=true` 可无头运行，但必须分别验证真实网站适配性。

在仓库根目录运行：

```bash
npm run orders:refresh:browser -- /绝对路径/批次配置.json
```

日志只包含系统 ID、状态、尝试次数、错误代码和汇总。退出码 `0` 表示清单全部成功，`2` 表示有失败、待核对、未完成或取消，`1` 表示配置／启动失败。每次采集预算 300 秒，票据有效期 330 秒；API 单次调用另有 35 秒超时。获取新票据只发生在任务取得空闲代理之后。

## 中断、续跑与核对

按 `Ctrl+C` 停止，执行器取消在途采集并关闭专用浏览器。再次运行同一配置即可续跑；允许调整并发及代理，订单清单及顺序、目标 API 必须与原批次一致。

| 状态           | 含义与续跑行为                                           |
| -------------- | -------------------------------------------------------- |
| `pending`      | 尚未完成，可在总共三次预算内续跑                         |
| `collecting`   | 上次在采集阶段中断，重启恢复为待跑；三次用尽则失败       |
| `submitting`   | 已持久化提交意图；中断后转 `needs_review`，不自动重放    |
| `succeeded`    | 系统返回成功，重启跳过                                   |
| `failed`       | 尝试耗尽或明确失败，重启跳过                             |
| `needs_review` | 无有效详情、身份异常、版本变化或提交回执不确定，重启跳过 |

检查点采用原子替换、文件及目录同步，并持有独占 `.lock` 文件。它不保存 JWT、任务票据、完整详情、访客 URL 或代理地址，仅保存代理摘要以避免续跑复用上次失败节点。不要删除或重置检查点来强行重试不确定提交。

若被强制结束后提示 `CHECKPOINT_LOCKED`，先读取 `.lock` 中 PID 并确认对应进程确实已退出，再删除该批次的锁文件。不能在旧进程仍运行时解除锁。待核对单先查询订单当前版本、成功时间及 CrawlLog／操作审计，确认是否已写入及失败原因，再决定是否建立新的明确范围批次。API 不可达导致提交没有回执时，也必须这样处理。

不修改业务数据的撤回方式是停止 CLI、保留检查点、关闭专用浏览器。已经成功提交的订单属于实际业务更新，不能通过删除检查点撤销；需另按备份和业务核对处理。

## 验收顺序

本地验证已覆盖：单元／接口测试；真实 Chrome 处理 20 笔合成订单，峰值十上下文、十个本地 SOCKS5 端口、Cookie 隔离、40 次请求／重定向许可、全部清理；隔离 PostgreSQL 并发回写测试的结果见[开发进度](../development/开发进度.md)。本地 SOCKS5 只转发到合成 HTTPS 服务，不访问 Apple 或消耗供应商额度。

真实环境使用明确授权的小批次，先 2、再 5、最后 10 并发，记录有效详情率、成功提交数、总耗时、超时／541／429、节点失效及浏览器资源占用。每级核对数据库字段、成功审计和系统实际页面；若只有加载页／DOM，没有有效结构化详情，则停止扩大范围，保留旧值。未通过这些验证前，不能宣称已经支持生产十并发稳定刷新。

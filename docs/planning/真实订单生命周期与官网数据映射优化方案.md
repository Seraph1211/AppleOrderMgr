## 一、结论摘要

1. 本次真实店内取货订单已确认依次出现 `PAYMENT_DUE_STORED_ORDER → PAYMENT_RECEIVED → PROCESSING → READY_FOR_PICKUP`；历史真实样本另已确认 `PICKED_UP`。`PAYMENT_RECEIVED` 是独立阶段，不能合并为“页面文案变化”。
2. 订单业务数据的第一权威来源是响应 HTML 中的 `<script id="init_data" type="application/json">`。移除 `script/style/template/noscript` 后，静态正文没有本次订单的状态、金额和轨迹数据；普通可见文本只能作为兼容回退。
3. 当前映射缺少 `PAYMENT_DUE_STORED_ORDER` 和 `PAYMENT_RECEIVED`，导致等待付款和官网已收款都被解析为 `status=unknown`、`paymentStatus=NULL`。进入 `PROCESSING` 后，系统仍不能确认已付款。
4. 官网付款前提供准确付款截止 Epoch、总金额和付款动作；付款后这些节点整体消失。系统必须采用“字段出现时保存、后续缺失不清空”的合并规则。
5. 当前付款截止依赖 `officialOrderCreatedAt + 30 分钟`，但本次官网只提供日期级下单时间，同时已经提供准确的付款截止 Epoch。现行设计因此无法给付款任务生成真实截止时间。
6. 当前系统一旦识别 `READY_FOR_PICKUP`，会因订单状态或 `paymentStatus=paid` 停止自动刷新，因此无法自动捕获后续 `PICKED_UP`，这是最初方案的同步目标；用户最新决定付款后只手动刷新，因此不再视为待修缺陷。
7. Apple 会在同一订单不同阶段更换 `orderItem-*` 动态键。本次从 `orderItem-11` 变为 `orderItem-0000101`；该键只能用于读取当前响应，不能作为跨阶段商品主键。

## 三、官网 HTML 与数据源结构

### 3.1 权威标签

真实订单入口会重定向到动态 `secureN.www.apple.com.cn` 访客订单页。业务数据位于：

```html
<script id="init_data" type="application/json">
  ...
</script>
```

当前页面的静态 `body` 主要是站点导航与通用内容。订单主内容由页面脚本根据 `init_data` 渲染，因此：

- `script#init_data` 内嵌 JSON 应作为第一解析源。
- Apple `currentStatus` 和 `statusDescription` 应优先于中文展示文案。
- 清理后的可见正文只用于旧页面或结构异常时的兼容回退，不能承担主要支付状态判断。
- 动态 `secureN` 主机、页面动作 URL、访客令牌和响应令牌不是业务状态字段，不能进入语义指纹或普通日志。

### 3.2 订单项定位

订单项容器为 `orderDetail.orderItems`：

- 优先按 `orderDetail.orderItems.c` 给出的顺序遍历。
- 每次响应中的 `orderItem-*` 键只作为节点定位符。
- 跨快照比较前必须把动态键标准化；持久化匹配应使用商品字段组合或后续确认的稳定 Apple 标识。
- 订单级状态不能永久固定为“首个商品状态”；多商品规则需要真实样本后单独确认。

### 4.2 本样本明确拿不到或不稳定的数据

- 精确下单时分：`orderPlacedDate` 只有日期。
- 精确支付发生时间：`PAYMENT_RECEIVED` 证明已经收款，但没有支付时间字段；首次抓取时间不能冒充支付时间。
- 稳定商品型号：本样本没有 `partNumber`、`sku`、`productId` 或 `modelNumber`。
- 付款后的订单总额和付款截止时间：付款后 `orderHeader.payNow` 与截止字段整体消失。
- 非空取货码：可取货阶段虽出现 `pin` 字段，但值为 `null`。
- 实际取货时间：尚未进入本次订单终态。
- 结构化收件人邮箱、电话和完整地址：本样本的订单 JSON 未提供这些实际值，只提供门店名称、布局定义和编辑能力标记。
- 稳定订单项键：同一商品的节点键会跨阶段变化。

## 五、与当前系统设计的矛盾

| 编号    | 优先级 | 矛盾                      | 当前行为                                                              | 真实证据与影响                                                                                                |
| ------- | ------ | ------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| LIFE-01 | P0     | 等待付款状态缺失          | `PAYMENT_DUE_STORED_ORDER` 映射为 `unknown`，`paymentStatus=NULL`     | 系统无法明确展示待付款，也无法用官网状态驱动付款任务                                                          |
| LIFE-02 | P0     | 已收款状态缺失            | `PAYMENT_RECEIVED` 仍为 `unknown/NULL`；`PROCESSING` 也不能派生已付款 | 本次付款后约 7 分钟才在可取货阶段被识别为已付；其他已具备截止条件的订单可能继续进入付款候选，存在重复操作风险 |
| LIFE-03 | P0     | 付款任务截止来源错误      | 只接受 `officialOrderCreatedAt + 30 分钟`；日期级下单时间不写入       | 官网已返回准确 `paymentTimeToExpiryEpoch`，系统却显示“时限未知”并不能安全自动分配                             |
| LIFE-04 | P0     | 阶段字段被无条件清空      | 成功刷新会无条件写入金额、币种、支付和取货字段，包括 `NULL`           | 付款后官网主动移除金额与截止节点，后续刷新可能擦除付款前已经取得的真实数据                                    |
| LIFE-05 | P0     | 自动刷新过早停止          | `READY_FOR_PICKUP` 或 `paymentStatus=paid` 会关闭自动刷新             | 系统不能自动观察 `PICKED_UP`；“付款监控停止”和“订单生命周期停止”被混为一件事                                  |
| LIFE-06 | P1     | 金额解析源错误            | 只从清理后的正文匹配“总计/金额”                                       | 金额真实存在于 `orderHeader.payNow.d.totalAmount`，当前输出 `NULL` 且没有解析错误                             |
| LIFE-07 | P1     | 支付状态依赖中文正文      | 主要靠“已付款/待付款”等可见文字推断                                   | 本次静态正文没有业务文案；原始状态明确但系统未利用                                                            |
| LIFE-08 | P1     | 订单状态语义过粗          | `pending` 展示为“待处理”，`PICKED_UP` 映射为泛化的 `completed`        | “等待付款”“官网已收款”“人工任务已完成”“已取货”容易混淆，无法还原真实阶段                                      |
| LIFE-09 | P1     | 取货状态粒度不足          | 处理中为 `NULL`，可取货为 `not_picked_up`                             | `not_picked_up` 同时可能表达尚未准备和已经可取，不能直接驱动取货运营                                          |
| LIFE-10 | P1     | `deliveryDate` 被当作日期 | 当前原样放入商品的 `deliveryDate`                                     | 该字段先后表达等待付款、明日取货、处理中提示、最晚取货日，不是稳定日期类型                                    |
| LIFE-11 | P1     | 原始状态证据未持久化      | 订单表只存归一化状态；商品中偶然保留原始状态                          | 不能解释映射来源、复盘状态变化或安全处理新枚举                                                                |
| LIFE-12 | P1     | 首商品代表整单            | 订单级状态取首个订单项                                                | 单商品样本可用，但多商品异步履约可能被错误汇总；需真实样本确认规则                                            |
| LIFE-13 | P1     | 动态节点键可能被当作身份  | 当前读取兼容多种键，但没有明确跨阶段身份规则                          | 本次键从 `orderItem-11` 变为 `orderItem-0000101`，直接按键比对会制造删除和新增                                |
| LIFE-14 | P2     | 付款方式来源没有区分      | `paymentMethod` 来自邮件，爬虫未读取官网值                            | 官网与邮件不一致时无法判断来源，也可能把展示名称误当成内部付款方式                                            |
| LIFE-15 | P2     | 传输失败分类仍不够精确    | 观测中出现代理 HTTP 424；流中断曾被摘要成 `HTTP_200` 失败             | 状态没有变化不等于请求成功；需要把响应状态、传输异常和解析异常分别记录                                        |

## 六、已确认的目标状态模型

建议把“Apple 官方生命周期”“官网支付状态”“履约/取货状态”和“内部付款任务处理状态”作为四个独立维度，禁止互相复用同一个 `completed` 或 `processing`。

### 6.1 推荐的 Apple 生命周期映射

| Apple `currentStatus`          | 建议订单生命周期   | 建议支付状态            | 建议取货状态       | 是否终态         |
| ------------------------------ | ------------------ | ----------------------- | ------------------ | ---------------- |
| `PAYMENT_DUE_STORED_ORDER`     | `payment_due`      | `unpaid`                | `not_ready`        | 否               |
| `PAYMENT_RECEIVED`             | `payment_received` | `paid`                  | `not_ready`        | 否               |
| `PROCESSING`                   | `processing`       | `paid`                  | `not_ready`        | 否               |
| `READY_FOR_PICKUP`             | `ready_for_pickup` | `paid`                  | `ready_for_pickup` | 否               |
| `PICKED_UP`                    | `picked_up`        | `paid`                  | `picked_up`        | 是               |
| `PAYMENT_EXPIRED_STORED_ORDER` | `payment_expired`  | `unpaid`                | `not_applicable`   | 是               |
| `CANCELLED`                    | `cancelled`        | 依据已确认支付/退款证据 | `not_applicable`   | 是               |
| `PICKUP_CANCELLED`             | `pickup_cancelled` | 依据已确认支付/退款证据 | `pickup_cancelled` | 是               |
| `SHIPPED`                      | `shipped`          | 待真实配送样本确认      | `not_applicable`   | 否               |
| `DELIVERED`                    | `delivered`        | 待真实配送样本确认      | `not_applicable`   | 是               |
| 未知新枚举                     | `unknown`          | `unknown`               | `unknown`          | 否，进入人工观察 |

推荐增加或明确保存以下原始字段：

- `officialRawStatus`：Apple `currentStatus` 原值。
- `officialStatusDescription`：Apple `statusDescription` 原值。
- `officialStatusObservedAt`：系统首次或最近观测到该状态的时间，仅表示观测时间。
- `officialFulfillmentMessage`：原始 `deliveryDate` 文案，不冒充日期。
- `officialPaymentExpiresAt`：由 `paymentTimeToExpiryEpoch` 转换的准确截止时间。

兼容方案是继续保留现有 `status` 值并只新增原始字段，但会持续把“等待付款/已收到付款”压缩到 `pending/processing`，不利于运营展示和审计。用户已批准上表的显式生命周期，数据库与 API 契约已据此同步。

### 6.2 付款任务与订单生命周期分离

- Apple 进入 `PAYMENT_RECEIVED` 时，立即把官网支付状态设为 `paid`，停止新增付款分配并标记现有任务“官网已确认付款”。
- 内部付款任务的 `pending/processing/completed/exception` 继续由员工维护，不因官网状态自动伪造人工处理结果。
- 官网已付款但人工任务未完成时保留差异提醒，不能继续作为待付款候选。
- 付款任务倒计时优先使用 `officialPaymentExpiresAt`；仅当官网明确提供带时分的创建时间且业务规则确认时，才用 `officialOrderCreatedAt + 30 分钟` 回退。
- 不允许用“首次抓到付款状态的时间”冒充实际支付时间。

## 七、字段保存与合并规则

### 7.1 按字段性质处理

| 字段性质           | 示例                                       | 建议规则                                                               |
| ------------------ | ------------------------------------------ | ---------------------------------------------------------------------- |
| 当前快照字段       | 原始状态、状态描述、履约文案、页面能力标记 | 当前响应明确存在时更新；新枚举不能静默映射为旧值                       |
| 一次出现、后续消失 | 总金额、币种、付款截止 Epoch               | 首次取得后保留；后续节点缺失不清空，只有官网明确返回纠正值才更新       |
| 身份与商品基础字段 | 订单号、商品名、数量、门店                 | 身份异常拒绝业务覆盖；其他官网有效值优先，缺失不覆盖并保存冲突         |
| 短时动作或令牌     | Pay Now URL、动作令牌、访客令牌            | 不进入普通订单表、接口、日志和 Fixture；只保存“动作是否存在”等低敏状态 |
| 未知语义字段       | `checkInWindowExpired` 等                  | 原始证据可留在受控日志，未确认前不驱动订单状态                         |

必须区分三种情况：字段未出现在响应中、字段明确为 `null`、字段解析失败。三者不能统一写成数据库 `NULL`。

### 7.2 最新快照与来源冲突

用户决定不新增官网状态历史表。保存最新官网原始状态、场景码、观测时间、商品级阶段及来源快照；来源快照用于比较导入值与官网值，不是官网历史表。冲突在订单列表每行最前面使用叹号图标展示，悬停或聚焦可查看字段、来源和差异；仅返回非敏感白名单。

## 八、已确认刷新策略

未付款／支付尚待确认、非终态订单每 60 秒自动刷新。官网确认已付款或已退款后停止自动刷新，后续只允许手动单笔、批量或全量刷新；打开列表和详情不触发官网访问。此前可取货每 5 分钟／1 小时的建议均已被用户最新决定取代。

身份异常暂停自动更新并阻止新付款分配；普通字段冲突按官网有效值合并后继续未付款轮询。多商品阶段不一致时逐项保存、整单显示状态待核对并禁止新付款分配；已付款停止规则优先，只有未付款／支付待确认且未全部终态时继续刷新。

## 九、建议实施任务与验收标准

### 9.1 实施顺序

用户确认本方案后，工程师按以下顺序执行，不能直接从解析器开始改：

1. 确认状态枚举、付款任务联动、字段保留规则和刷新频率。
2. 先更新[订单爬虫](../design/订单爬虫.md)、[数据库架构](../database/数据库架构.md)和[API 契约](../design/API设计.md)。
3. 新增正式 Migration、模型字段和来源快照，包含 `up/down`；不新增官网状态历史表。
4. 修改 `script#init_data` 解析、状态映射、金额与付款截止解析。
5. 修改持久化合并逻辑，禁止后续缺失清空阶段性数据。
6. 修改付款任务排除、截止时间与差异提醒。
7. 修改刷新策略，官网收款后只允许手动刷新，移除页面自动触发。
8. 修改前端状态文案、筛选和详情展示。
9. 补齐 Fixture、单元、数据库集成、API、前端和真实订单只读验收。
10. 更新开发进度与原爬虫重构计划，分开报告本地技术验收、真实官网验收和生产验收。

### 9.2 必须覆盖的回归用例

- 四个本次真实阶段的脱敏 Fixture：等待付款、已收到付款、处理中、可取货。
- 历史真实 `PICKED_UP` 和 `PAYMENT_EXPIRED_STORED_ORDER` Fixture。
- `PAYMENT_RECEIVED` 必须立即映射 `paymentStatus=paid`，并禁止进入新付款分配。
- `paymentTimeToExpiryEpoch` 必须生成准确截止时间；日期级 `orderPlacedDate` 不得伪造时分。
- 付款前取得金额，付款后字段缺失时金额、币种和截止时间不得被清空。
- `orderItem-11 → orderItem-0000101` 不能产生商品删除/新增或重复商品。
- `deliveryDate` 的状态文案不能作为通用日期直接解析。
- `PAYMENT_RECEIVED`、`PROCESSING`、`READY_FOR_PICKUP` 已确认付款后均停止自动刷新；手动刷新可更新到 `PICKED_UP`。
- 未知 Apple 枚举必须保存原值、标记未知并告警，不能自动当作成功终态。
- HTTP 状态、代理错误、响应流中断、JSON 缺失和业务身份不匹配必须分开记录。

### 9.3 仍需真实样本验收

- 本次订单最终 `PICKED_UP` 前后字段差异，特别是 `pin`、取货说明和实际时间。
- 多商品订单不同商品状态的订单级汇总规则。
- 配送订单 `SHIPPED/DELIVERED` 的物流字段与频率。
- 主动取消、取货取消、退款、退货和换货分支。
- 不同付款方式是否都使用相同 `payNow`、金额和截止字段。

## 十、用户已确认的决策

1. 使用显式 payment_due/payment_received/picked_up/payment_expired 生命周期，并扩展取货状态；旧值兼容，不无证据批量回填历史。
2. 仅未付款／支付待确认订单自动刷新；付款后手动刷新。已取消、过期、已取货等终态也停止自动刷新。
3. 不新增官网状态历史表，不开放商品图片和取货说明。
4. 官网订单数据最权威，缺失保留已有值；冲突显示行首叹号和详情。身份不匹配禁止跨单覆盖／自动改号及新付款分配。
5. 多商品无法明确汇总时显示状态待核对，逐项保存状态并暂停新付款分配；是否继续刷新服从第 2 项最新规则。
6. 本次订单终态证据后补，不阻塞已有范围开发；暂用已有历史已取货样本实现，完整真实生命周期验收仍待验证。

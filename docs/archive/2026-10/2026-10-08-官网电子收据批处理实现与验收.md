# 官网电子收据批处理实现与验收

> 日期：2026-10-08
>
> 状态：实现、隔离验收及有界生产验证完成；8 笔不同订单中 2 笔成功新增 4 条设备 SN、4 笔转人工、2 笔保留待重试。本轮调度器已退出，长期稳定成功率未验收。
>
> 需求：批量登录 AppleID 获取电子收据，订单号／SN 校验后自动回写订单设备，冲突转人工。沿用新 Worktree `apple-electronic-receipt-research/AppleOrderMgr`、分支 `codex/electronic-receipt-research`，基线 `cc3c120`。

## 实现结果

- 独立服务器 CLI 包含计划、运行、状态、停止、恢复、私密结果导出。冻结订单与账号身份，默认两个并发、同账号串行；共享 PostgreSQL 账号锁、全局限流、历史次数和登录冷却。
- 每次尝试保留独立目录；批次锁、原子替换及文件／目录 fsync 保护状态。未知提交先取得相同事务锁只读对账，原幂等键复用，成功单不重新采集。
- 按 IPRoyal 官方粘性会话格式分配新出口，前后探测必须一致；最多三次完整尝试。旧保护历史未重置。
- 一张订单的所有收据 SN 在现有库存命令事务中绑定；SN、订单或设备快照冲突整单拒绝，不自动改订单日期、入库或销售。
- 独立验证器解密原文，核对订单身份、各商品 quantity 之和、明确 SN、正文摘要、同 run 许可、非缓存响应及出口。派生 JSON 中的 SN 不能替代原文校验。

## 点击问题及修复

早期原生弹窗虽然取得真实收据，首请求漏过 CDP 限流；该结果只保留为研究证据，不能自动写入。后续直接新页导航被 Apple 重定向；仅修改链接 `target` 又被官网 JavaScript 的 `window.open` 覆盖。

最终在已受控详情页点击原链接，仅把对应精确收据 URL 的显示目标固定在受控页，保留官方认证、原生请求与原 URL。上下文守卫拒绝其他新窗口。对于异步启动的导航等待真实收据完成事件，不能使用旧详情页的 load 状态判断。页面数量校验由“商品行数”改成“各行 quantity 总和”。

已安装制品摘要 `f345a553e2a4ea32606834887daa32e4d7b8e089511200f6b276d8348f0221e7`；26 个发布文件逐项 SHA-256 与 Worktree 当前运行代码一致。该 R7 相比生产采集验证的 R4（`90a45cab6bc27`）只修改宿主调度脚本：认证需人工不会被后续出口／探测失败改成自动重试；`HTTP_TIMEOUT/HTTP_CONNECTION_FAILED` 纳入有上限的换出口重试；CLI 输出统一为 UTF-8。新增回归通过；收据采集、独立验证和绑定文件完全一致。R4 的真实超时失败及人工状态保持，不反向改写历史，也不计为 R7 成功。生产入口：


## 未证明的能力

- 本批不能证明长时间／大规模成功率。Apple 认证前置条件、代理质量和实际出口变化仍影响成功率。
- 不自动提交验证码、双重认证、协议确认，不承诺这些账号能无人值守完成。
- 当前交付为服务器 CLI 和现有设备数据回写；没有新增管理台批次页面或 HTTP 端点。
- 本 Worktree 的业务基线早于线上库存模块；绑定依赖已迁移的生产库存运行时，不可对旧应用直接启用。
- 上述验收当时尚未提交；后续源码同步与本地 main 提交状态以[开发进度](../../development/开发进度.md)为准，生产运行制品不因 Git 同步自动改变。

## 一、结论和推荐顺序

主要问题是**大量短日志采用逐片段关系型存储，重复元数据和逐片段索引放大了空间**。首次补采使成本集中暴露，现有可靠上传、完整查询能力本身仍有保留价值。没有证据表明本次主要由删除垃圾造成，也不能把全部索引视为可删除空间。

建议分三步：先建立容量与查询基线，验证两个分页索引的保守精简并补齐清理监控；再进行“压缩日志块＋精简回执／定位记录”的隔离原型；达到空间、性能、完整性和恢复门槛后才灰度迁移。第二步优先复用 PostgreSQL 保存压缩块，避免立即引入新的文件服务或搜索集群。

默认保留最近 **30 个北京时间自然日**的完整查询、真实重复行、文件版本、账号／实例上下文及现有权限。缩短查询范围、丢弃普通日志、延长归档期限均不是本方案默认动作。

## 三、根因与风险区分

### 3.1 首次补采集中导入存量，放大了既有设计成本

9 月 29 日升级后补采现存 30 天文件，历史样本与本次抽样均支持主要数据来自集中回填。真实重复文本按原要求保留，只有同事件或同文件版本／位置的重传才去重。不能把相同正文视为垃圾，更不能按正文哈希批量合并。

30 天保留是滚动窗口，不是固定容量上限；取决于实际每日字节、片段数量、文件重写次数和清理能力。截至本次读取，最早日期仍在窗口内；按既有规则，9 月 10 日数据从 **10 月 10 日北京时间零点**开始过期，当前保留不是清理故障。

### 3.2 元数据随每个短片段重复

每条保存 4 个 UUID、文件名、64 字符摘要、账号、多个时间、行号、分段、偏移和状态，再叠加数据库记录／页开销。样本正文仅约占记录字节的 25%。同一文件名和实例标识逐片段重复保存，设备、实例与文件 UUID 还在多个索引中重复保存。

上传 gzip 只减少网络载荷；接收后仍拆成各条 `message` 存入表。PostgreSQL TOAST 面向较大的单行值，不会自动把大量 89 字节短行作为一个块共同压缩，因而不能期待修改一个压缩参数消除本次放大。[PostgreSQL TOAST 说明](https://www.postgresql.org/docs/15/storage-toast.html)

### 3.3 两个分页索引为两种有效访问路径付出较高成本

实例分页按 `(device_id, local_id, business_date, sort_at, file_id, byte_offset, id)`；账号分页在日期之后加入 `account_number`。两者共占 **10.055 GiB**，是最大单项优化入口。

实例全量查询没有固定账号，账号索引不能直接提供跨账号的既有时间排序；账号查询依赖账号前缀，删掉账号索引又可能扫描大量无关账号。上下文前后检索也使用这两条路径。因此不能直接二选一，更不能将 UUID 主键或位置唯一索引作为普通冗余索引删除。[PostgreSQL 多列索引说明](https://www.postgresql.org/docs/15/indexes-multicolumn.html)

### 3.4 已识别的潜在风险，不冒充已发生故障

| 风险                   | 代码依据及影响                                                         | 当前结论                                            |
| ---------------------- | ---------------------------------------------------------------------- | --------------------------------------------------- |
| 过期清理吞吐不足       | 每轮 20 × 5,000，最多 10 万片段；常规每小时一次，理论约 240 万片段／天 | 高峰日超过清理能力会积压，未证明当前已有过期积压    |
| 多 API 清理重复竞争    | 完整日志清理在原 advisory lock 事务之外；内存互斥仅保护本进程          | 扩容时需独立数据库锁；不声称当前单 API 已发生此故障 |
| 稀有关键词或无匹配查询 | `message LIKE '%字面词%'`；普通 B-tree 不直接索引正文包含关系          | 范围内可能大量检查正文，尚未测得本轮生产 P95        |
| 账号候选重复扫描       | 每次从片段表 `DISTINCT account_number`                                 | 热点日需评估扫描量，可改小型日汇总                  |
| 业务与日志争用         | 共享数据库；接收事务对设备行加锁，同设备日志请求串行                   | 优化前需测锁等待，不直接移除保护锁                  |
| 容量验收不足           | 现有十万条合成性能与 2,752 万片段真实规模不同；上线已提示容量风险      | 增补真实分布、峰值、保留周期和恢复演练门槛          |

普通 `DELETE` 与 `VACUUM` 主要让空间可复用，并不保证操作系统可用空间同步上升；`VACUUM FULL` 需要强锁和额外副本空间。清理行数、数据库可复用空间、实际磁盘释放量必须分别记录。[PostgreSQL 空间回收说明](https://www.postgresql.org/docs/15/routine-vacuuming.html)

## 四、第一阶段 索引精简与容量治理

### 4.1 保守精简分页排序键

优先验证从两个分页索引及查询排序元组中移除末尾 `id`，保留 `sort_at, file_id, byte_offset` 的完整顺序。

安全依据：所有日志列表／上下文限定设备，唯一约束 `(device_id, file_id, byte_offset)` 保证同设备中不会出现相同文件位置，因此前三个排序字段已经能区分记录。原来末尾 `id` 不会实际打破平局。**主键 `id`、回执语义、位置唯一约束均保留**。

查询、前后上下文的比较元组与索引必须同步。现有游标存放 `id＋scope`，仍可按 ID 取得锚点；核对空游标、旧游标和筛选摘要兼容后可维持 API 格式。未经代码调整，不能假设只删索引列就一定得到等价执行计划。

按 2,752 万片段、两个索引、每项少 16 字节估算，减少的纯 UUID 键数据约 **0.82 GiB**。这不是实际磁盘释放承诺：新旧页密度、对齐、内部页和构建方式都会影响结果。单靠这一项不足以解决 23.49 GiB 的总体成本，不将 10.055 GiB 全部计为可节省空间。

进一步只保留时间的短索引、BRIN 替换、调整 fillfactor 等作为对照实验，不能默认发布；它们可能引入同毫秒大量记录排序、额外范围扫描或随机写入页分裂。日期索引只有 0.178 GiB，优先级低于两个分页索引。

### 4.2 实施和回退约束

先在隔离 PostgreSQL 15.18 中比较现有索引、移除 `id` 后索引、必要时精简前缀方案。覆盖账号／实例首页、深游标、前后上下文、无账号、同毫秒、稀有词和无匹配查询，记录 `EXPLAIN (ANALYZE, BUFFERS)`、索引大小、写入／重传耗时及 WAL。只选择收益明确且无关键路径退化的候选。

批准上线后使用新的正式 Migration，逐个 `CREATE INDEX CONCURRENTLY`，确认有效并验证查询后再逐个淘汰旧索引。该操作不能放进普通事务块，会增加 I/O 并可能等待事务；失败后的无效索引要检查和处置，不能仅凭 Migration 退出码宣布成功。[PostgreSQL 并发建索引说明](https://www.postgresql.org/docs/15/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY)

回退分两种：旧索引仍在时恢复原查询；旧索引已删除时重建需要时间、空间和 I/O，不承诺秒级回退。发布前测算候选索引、排序临时文件、WAL、正常增长和保留备份的峰值余量，不同时重建两个大索引。

### 4.3 清理和监控

- 为完整日志清理增加独立数据库互斥，按小批次提交，并以耗时、WAL、锁等待和业务负载设预算；有积压时分次续跑，不简单扩大为无界大事务。
- 增加最早未清理日期、过期片段估计、上次成功、累计删除、删除速率、失败原因、死行和磁盘告警。目标是在高峰过期输入下，清理平均吞吐持续高于到期速率；具体限额由隔离演练确定。
- 分别统计当天实时上传、历史补传、新文件版本、位置重传和冲突；采集状态不能只显示发现字节而缺少实际持久化对账。
- 记录每日正文、表、索引、WAL、临时空间、备份量及查询 P50／P95／P99。告警依据“剩余空间能覆盖多少天增长”和迁移峰值预算，而非只观察数据库总大小。
- 评估表级自动分析／自动清理参数，按真实变更量与运行开销调整，不全局禁用 autovacuum，也不为取得新统计在本轮生产执行 `ANALYZE`。

## 五、第二阶段 压缩存储原型与查询优化

### 5.1 推荐原型

正文和片段属性按有限大小的块压缩保存；数据库保留共享元数据、块目录和必要的可靠回执。首个原型仍把压缩数据放在 PostgreSQL `BYTEA` 中，回执、块和目录可在同一事务持久化，完整备份也能保持一致。外部文件／对象存储放到后续按测量决定，不作为首期依赖。

以下为候选职责，**不是已批准或已存在的表结构**：

| 组成               | 保存内容                                                                                                  | 目的                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 实例、文件版本目录 | 设备／实例、原 fileId、文件名等共享信息；内部紧凑主键                                                     | 减少每条正文重复的元数据，原 UUID 与来源信息保持可追溯     |
| 压缩日志块         | 原文、异常 rawBase64、事件 ID、行号／分段、业务日、loggedAt／sortAt、账号等无损片段序列；格式版本、块摘要 | 让重复文本跨片段压缩；禁止截断、合并真实重复行             |
| 块目录与查询目录   | 实例、业务日、精确排序边界、账号成员关系、片段数、压缩／解压字节、版本与状态                              | 先定位候选块，再小范围解压；不能仅按文件名或创建时间查找   |
| 精简回执／定位记录 | 原事件 UUID、文件位置、载荷摘要、块定位和片段序号                                                         | 保持事件与位置双重幂等、载荷冲突检测、旧 ID 详情与游标定位 |
| 每实例每日账号目录 | 原始账号文本及可见范围                                                                                    | 账号候选从小目录读取，不反复对数百万片段 DISTINCT          |

第一版保留逐片段的精简回执，明确承担它的表与唯一索引成本；不能用“正文压缩后很小”忽略这部分。后续若想改为批次回执、连续区间摘要，须先设计新的采集协议和旧客户端兼容，不能牺牲当前全局事件冲突检查。

块大小先比较 256 KiB 与 1 MiB 的未压缩载荷，并设置最长约 5—10 秒封块候选值。两项均是实验参数；端到端时效还包含现有 30 秒扫描和上传等待。跨请求缓冲必须可靠落盘，只有数据和对应回执事务提交后才确认上传；不能提前回执后留在内存等压缩。小流量不得为了凑块长期不可见，大流量限制并发压缩、内存及解压上限。

用真实分布比较现有 gzip 与候选 Zstandard 的体积、CPU、解压延迟和备份恢复时间，再选实现。没有测量前不承诺压缩率、节省 GiB 或直接指定新增依赖。

### 5.2 查询语义必须保持

1. 原排序仍按 `sort_at/file_id/byte_offset`，保留逻辑事件 ID；不把新 BIGINT 的生成顺序当作原文件 UUID 顺序。块内维护排序与源位置映射，块间按真实边界归并，不能假设文件偏移对应单调时间。
2. `logged_at` 时间筛选与 `sort_at` 排序仍分开。无时间行、可信 XML 续行、同毫秒、乱序日志、前导零账号、未知账号和跨午夜需分别验证。
3. 账号目录与日期／实例严格隔离；块的时间边界、账号成员关系可以多选候选，但不得漏选。保留账号和实例两种前后各 20 片段上下文。
4. 关键词继续对单片段做字面包含匹配，包含 `%`、`_`、反斜杠等时遵循现行规则；压缩字节不可直接搜索，必须解压核对。词组跨片段仍按现行边界处理。
5. 稀有词／无匹配可能遍历大量候选块。首先测限定实例／日期下的成本；必要时增加无漏检的块级检索辅助信息。若要引入可续查后台搜索，应单列 API／交互变更并确认，不能超时后把部分结果当作完整结果。
6. 迁移期间游标应绑定存储代次或由稳定 ID 路由；清理、过期和历史补传状态明确展示。既有契约并不保证历史补传期间固定快照，不夸大连续翻页的完整性。

### 5.3 按日生命周期

日志块按片段的北京时间 `business_date` 分组和分区；一个源文件可以含不同业务日，不能只依据文件名日期删除。当天及迟到数据以新增块写入，已提交块保持不可变。

PostgreSQL 15 分区表的唯一／主键约束必须包含分区键，不能直接把现有 `id` 或文件位置唯一约束改成“带日期的唯一”而放过跨日期冲突。建议首版精简回执仍使用非分区全局唯一表，日志块及目录按业务日分区；清理先按依赖有界清除过期回执，再移除对应块分区，并记录可恢复步骤。若未来分区回执，必须单独解决全局幂等。[PostgreSQL 分区限制与维护](https://www.postgresql.org/docs/15/ddl-partitioning.html)

精简回执仍需要常规清理／空间复用治理，不能把分区描述为全部成本消失。分区移除也需评估锁和依赖；不在本方案分析阶段执行。30 天外按原业务规则过期，不默认无限期留档。

### 5.4 未优先采用的路线

| 方案                                        | 判断                                                                           |
| ------------------------------------------- | ------------------------------------------------------------------------------ |
| 直接减少到 7／14 天或只留错误日志           | 改变已确认完整性与查询范围，非默认方案                                         |
| 按正文去重                                  | 会丢失真实重试次数、发生顺序和上下文，排除                                     |
| 两个分页索引直接删一个                      | 两种查询路径不同，排除未经验证的直接删除                                       |
| 仅设置 TOAST 压缩或上传 gzip                | 不能消除短行元数据和逐片段宽索引的主要成本                                     |
| 只做行表归一化                              | 风险较低，可作压缩原型未达标的回退方向；仍保留逐片段分页索引，收益有限且须测量 |
| 立即建设 Elasticsearch／ClickHouse／Loki 等 | 本轮缺少规模与收益证据支持新增服务，先验证现有基础设施方案                     |

| 压缩文件直接放服务器目录                    | 需新增原子落盘、权限、对象与数据库一致性、备份和恢复链路，后续确有收益再引入   |

## 六、迁移与回滚

1. **隔离验证**：基于获准的受限真实样本或隔离恢复数据，保留分布而不将原始日志提交 Git。先确定格式、索引、全局幂等和查询算法，再更新数据库架构、API、服务器监控说明及 Migration；不直接改已发布旧 Migration。
2. **影子存储**：旧表保持读取权威，通过旧表的持久数据构建新块。已可靠存入旧表才发原回执，新存储失败不能使数据丢失。迁移进度必须覆盖迟到回填，不能只按 `created_at > 上次时间` 跳过晚提交事务。
3. **一致性对账**：按设备／实例／业务日／文件版本比较事件集合、位置集合、片段数和确定性摘要；将排序输出、关键词、上下文结果作差分。记录迁移水位与失败可重试范围。
4. **灰度切读**：按实例启用新查询，维护存储代次和旧 ID 定位；新增写入在最终切换前短期使用可原子提交的双写，或保留可完整重放的持久入站记录。未追平时不切主。
5. **逐批回收**：按已验证的日期／文件范围释放旧副本，正常过期窗口继续生效。不能一次双份复制整个 23.49 GiB 再发现磁盘不足，也不能把旧表 `DELETE` 当作已归还磁盘。
6. **完成切换**：仅在全量覆盖、恢复演练、容量／性能通过，且回滚窗口满足后删除旧表／索引。释放前核对旧副本范围与受限备份，保留审计清单。

回滚必须说明新写入如何补回旧路径。旧表仍完整时可切回；已释放的范围需要从压缩块或验证过的备份恢复，耗时取决于规模，不能声称切配置即可秒级回退。禁止整库覆盖恢复其他业务。

本次根盘实际可用约 **29.41 GiB**，会随并行工作和正常运行变化，不使用历史清理记录的 32.47 GiB 作为上线保证。发布前重新计算：

`所需峰值余量 = 当前批次新数据和新索引 + 构建临时文件 + WAL 高水位 + 保留期内业务增长 + 必要回滚／备份增量 + 安全余量`

压缩块仍在 PostgreSQL 内时，隔离合成库完整恢复必须包含块、目录与回执；2026-10-07核对到生产既有常规业务备份排除AOS日志，新组件沿用排除，不改变用户备份边界；如后续外置，必须联合快照清单和对象校验。区分归档可解压、核心表抽样恢复、包含日志的完整恢复，不能互相替代。延续已确认的备份保留策略，另一个存储优化方案不自动授权扩大或删除备份。

### 7.2 必须保持的正确性

## 九、2026-10-07 实施说明（验收进行中）

用户授权在 `codex/aos-log-storage-optimization` 独立工作树实现 P1/P2 和可灰度 P3。正式 Migration 为并行空表，初始模式 `rows`。采用现有 Node.js zlib gzip，无新增依赖；按有限载荷成不可变日块，每上传请求提交即可查，长期内存聚合不作为可靠回执前提。256 KiB/1 MiB 参数在隔离实验比较。

全局回执主键与文件位置唯一保持非分区；文件目录共享设备/文件 UUID，块共享实例/文件名。块账号目录包括未识别成员与精确边界；1/2/3 字元 Bloom 只筛候选，原文再做字面包含。按重叠块真实边界归并，`loggedAt` 与排序时间分别处理。

迁移工具必须覆盖 `shadow/backfill/verify/read-switch/abort/revert/retire/status`：持久keyset遍历及最终补漏捕获迟到提交；全量验证在锁外逐块认证，最终设备锁只做有界尾部确认，避免阻塞实时上传数分钟。旧表清理只在验证覆盖后显式分日范围执行，不将DELETE当作磁盘归还；本次不使用VACUUM FULL。完整性/容量/查询性能和恢复通过前保持旧读权威。

## 目标与边界

本次使用一个新创建的真实订单，按官网实际状态变化持续采集页面证据，建立以下映射：

1. Apple 官网可见 HTML 标签、选择器和状态文案。
2. 页面内嵌订单 JSON 的原始字段路径、枚举和值是否存在。
3. 各阶段可获取、不可获取、新增、变化和消失的数据。
4. 当前系统 `status`、`paymentStatus`、`pickupStatus` 的解析结果。
5. 基于真实证据建议修正的状态、字段、解析和展示规则。

本轮只允许新增并运行 `scripts/observeAppleOrderLifecycle.js`，以及维护本文件。不得修改现有业务代码、数据库、Migration、前端、配置文件、测试或已有文档；不得写入业务数据库或生产环境。最终只输出建议修正清单，后续代码变更需另行授权。

## 安全规则

- 只使用网帆国内隧道代理，不允许失败后直连或切换其他 Provider。
- 网帆端点、账号和密码只从进程运行时环境或标准输入读取，不写入脚本、仓库、日志和本文件。
- 订单链接不放入命令行参数，避免出现在进程列表和 Shell 历史中。
- 原始 HTML 和订单 JSON 仅保存在 Git 已忽略的 `test-artifacts/order-lifecycle/`，目录权限为 `0700`、文件权限为 `0600`。
- 原始证据可能包含订单号、Apple ID、姓名、联系方式、地址或取货信息，不提交 Git、不复制到本文件。
- 文档、控制台输出和后续对比结论只使用订单指纹和脱敏值。
- 所有请求均为 HTTP GET；不登录 Apple 账号，不提交付款、取消、退款、取货或配置变更。

## 观测脚本

脚本提供三种模式：

- `--self-test`：无网络自检 URL 校验、脱敏和 JSON 字段展开逻辑。
- `--check-proxy --stdin`：从标准输入读取网帆配置，只读访问 Apple 中国首页验证代理链路。
- `--stdin` 或 `--stdin --watch`：读取网帆配置和订单链接，单次或每 60 秒持续观测。

每次页面语义发生变化时，脚本保存：

- `原始页面.html`：精确页面证据，仅限本地私有目录。
- `原始订单数据.json`：内嵌订单 JSON，仅限本地私有目录。
- `脱敏DOM清单.json`：可见文本、标签、近似 CSS 路径和业务相关属性。
- `脱敏JSON字段清单.json`：全部 JSON 叶子字段路径、类型和脱敏值。
- `脱敏摘要.json`：HTTP、当前系统解析结果、字段数量和相邻阶段可用性差异。
- `polls.ndjson`：每次轮询的时间、响应状态、重试次数和三个系统状态，不含订单及代理明文。

持续观测最低间隔固定为 60 秒；单轮最多尝试三次，每次使用新的网帆 `sid`。全国混播使用控制台实际生成的 `acc-{账号}-sid-{会话}` 格式，只有指定地区时才追加 `cty/reg`；HTTP 407 后不继续重试。持续模式遇到单轮网络失败会写入脱敏失败记录并继续下一轮，避免一次瞬时故障中断全生命周期。脚本不调用现有的数据库刷新队列，也不写 `orders`、`crawl_logs` 或任何业务表。

## 付款前阶段初步结论

- 订单入口经 Apple 重定向到动态 `secureN.www.apple.com.cn` 访客订单页；安全域名编号和动作令牌会随请求变化，不能作为业务状态变化依据。
- 首两轮代理请求返回 HTTP 424，第三轮首次尝试返回 HTTP 200；后续轮询存在偶发 424，持续监控必须保留失败重试和不中断机制。
- 订单业务数据位于 `<script id="init_data" type="application/json">`。剔除 `script/style/template/noscript` 后的静态 `body` 文本不包含待付款状态、订单金额或后续状态轨迹；不能只依赖普通可见正文选择器。
- 付款前权威路径为 `orderDetail.orderItems.orderItem-*.orderItemStatusTracker.d.currentStatus`，真实值为 `PAYMENT_DUE_STORED_ORDER`。当前映射表没有该枚举，因此输出 `unknown`。
- 同一状态跟踪对象已提供 `possibleStatuses`：`PAYMENT_RECEIVED`、`PROCESSING`、`READY_FOR_PICKUP`、`PICKED_UP`。这些是该订单返回的可能轨迹，不等于各阶段已经实际发生。
- `orderItemDetails.d.deliveryDate` 在付款前是状态文案而不是日期；当前值表达“正在等待付款”。字段名不能直接决定字段语义。
- `orderItemDetails.d.paymentTimeToExpiryEpoch` 提供精确付款截止时间，而 `paymentTimeExpiry` 为空字符串。该样本截止时间为 2026-09-08 20:41:00（GMT+8）。
- `orderHeader.d.orderPlacedDate` 只提供日期，不含时分；现有 `officialOrderCreatedAt` 因此保持 `NULL`。如果仍仅用该字段计算付款期限，会漏掉官网已经提供的精确 Epoch。
- `orderHeader.payNow.d.totalAmount` 在 JSON 中提供订单总额和币种，但静态正文没有金额。现有解析只扫描正文，因此错误输出金额缺失且无解析错误。
- JSON 还提供付款方式展示、Pay Now 动作、商品名称与数量、店内取货类型、门店信息、联系人和通知能力等；动作 URL、访客令牌、联系人及地址属于敏感数据，只保存在私有原始证据中。
- 付款前稳定语义快照包含 313 个 JSON 叶子字段、311 个非空字段和 110 条脱敏 DOM 记录。去除动态安全域名、动作 URL 和响应令牌后，连续轮询语义指纹保持稳定。

## 付款后阶段初步结论

- 2026-09-08 20:23:19（GMT+8）首次确认付款后页面，权威 `currentStatus` 从 `PAYMENT_DUE_STORED_ORDER` 变为 `PAYMENT_RECEIVED`。
- `statusDescription` 从空字符串变为 `DEFERRED_PAYMENT_RECEIVED`。这两个原始字段都应保留证据，不能仅从中文文案猜测支付状态。
- `orderItemDetails.d.deliveryDate` 从“正在等待付款”变为“明天到 Apple Store 零售店取货。”；同一个字段随阶段从状态文案切换为履约提示，仍不是稳定的结构化日期。
- 付款后 `orderHeader.payNow` 整个节点消失，同时删除 Pay Now 动作、总金额、付款倒计时、付款截止 Epoch 和付款前取消相关字段。付款前后对比为新增 1 个叶子路径、删除 37 个叶子路径、变更 3 个叶子值。
- `billingInfo` 仍保留付款方式展示及若干账单能力标记，但付款后页面不能再取得付款前 JSON 中的订单总金额。金额必须在付款前阶段保存，不能假设后续页面始终可补抓。
- 后续可能轨迹仍为 `PAYMENT_RECEIVED`、`PROCESSING`、`READY_FOR_PICKUP`、`PICKED_UP`，说明 `PAYMENT_RECEIVED` 是独立的真实阶段，并非页面直接跳到 `PROCESSING`。
- 当前系统映射表没有 `PAYMENT_RECEIVED`，且静态正文中没有“已收到付款”文本，因此仍错误输出 `orderStatus=unknown`、`paymentStatus=NULL`、`pickupStatus=NULL`。
- 付款后快照包含 277 个 JSON 叶子字段，较付款前减少 36 个净字段；原始 HTML 的订单业务信息仍位于 `script#init_data`，普通静态正文选择器仍无法取得。

## 履约处理中阶段初步结论

- 2026-09-08 20:25:13（GMT+8）首次确认进入 `PROCESSING`；上一阶段 `PAYMENT_RECEIVED` 已被独立捕获，没有被轮询跳过。
- `statusDescription` 从 `DEFERRED_PAYMENT_RECEIVED` 变为 `PROCESSING_IMM_PICKUP`，`deliveryDate` 变为“你的商品很快将准备完毕，可供提取”。
- 当前系统能把 `PROCESSING` 映射为 `status=processing`，但 `paymentStatus` 仍为 `NULL`；进入处理阶段后已经付款是明确事实，不能继续依赖静态正文中的付款关键词。
- Apple 把同一商品的动态键从 `orderItem-11` 改为 `orderItem-0000101`，商品内容和后续轨迹保持一致。`orderItem-*` 键不能作为跨阶段稳定业务 ID，字段差异比较应先标准化该键。
- 处理中快照为 279 个 JSON 叶子字段，比已收款阶段净增 2 个字段；主要增加账单联系人编辑动作包装，不代表新增订单业务资料。

- 排查时发现三个历史观测进程并行轮询；已按明确 PID 终止两个旧进程并验证只保留一个最新进程，没有删除快照或影响现有 crawler Worker。

## 结论与适用边界

Apple 官网电子收据具有所需的结构化订单号、序列号、商品名和料号。**本轮四笔订单中，208 在新会话完整取得一张收据，并验证两条 SN；其余三笔没有取得有效收据。** 208 是历史已知成功对照，样本并非随机选取，不由 1/4 推导常规成功率或稳定性。

新收据采集时间为北京时间 **2026-10-08 17:56:45**，HTTP 200、`text/html`，订单身份、商品数量、SN 格式与唯一性、来源摘要均通过；两条 SN 与旧收据及现有设备一致，所以是新鲜读取两条已知 SN，不是新增发现两台设备。另已离线复核 2026-10-07 的历史原文，该历史证据不计入本轮新鲜成功数。

审计发现成功收据的新窗口首个请求漏过现有 CDP 拦截，收据 run 的许可计数为 0；因此**收据数据验证通过，运行保护验收未通过**。已停止后续外部请求，保留问题和原始计数，不将事后补记伪装为事前许可。实验脚本不能直接上线或扩大批量。

最重要的新证据是：**访客详情没有 `invoiceUrl`，不能判定订单没有收据**。本轮访客响应含有 `orderDetail.d.signInURL`；从这一订单专属入口完成 AppleID 认证和商城交接后，1356 的登录详情才出现收据 URL 与可见“查看电子收据”链接。但收据 GET 返回 303 并转向商城错误页，详情成功不能计为收据成功。

研究使用“HTTP 访客会话＋官方浏览器 AppleID 认证＋HTTP 承接商城登录与详情＋浏览器点击收据”。成功收据最后一跳由原生浏览器发出，没有经过 HTTP 桥接。浏览器仍执行官网认证脚本，因此不能称为已经实现纯 HTTP AppleID 登录。实验同时变化了账号、代理、浏览器模式和最后一跳传输，不证明某一个改动单独解决了风控。

本轮只读生产订单与设备数据；账号和请求门禁的尝试记录、冷却及加密研究证据会正常写入独立研究库／目录。没有生产订单、日期、设备、库存回写，没有管理台发布或既有服务重启，没有恢复旧批次。

## 登录与收据链路

1. 使用原始订单链接取得完整访客详情，校验订单身份。
2. 从本次响应读取 `orderDetail.d.signInURL`。实际入口是商城订单详情的 `fetchOrder`／`guestOrderSpinner` action，随后进入 `/shop/signIn/orders`。保留官网返回的上下文，不拼接猜测 token。
3. 同一代理内由浏览器完成 AppleID 认证。`signin/init`、`signin/complete` 200 仅表示认证阶段进展。
4. 单独观察 `/shop/signIn/idms/authx` 和登录后的目标订单详情。二者通过后才进入商城会话就绪阶段。
5. 从该详情的 `orderHeader.d.invoiceUrl` 获取同主机、只读 `/shop/order/print/invoice/[INVOICE]/[TOKEN]` 路径。路径中的实值具有访问能力，不写入公开文档或普通日志。
6. 获取收据原文后解析 `orderInvoices`，对每张收据的订单号、商品行和显式 SN 字段做一致性检查，最后才记为 `RECEIPT_VERIFIED`。

既有收据采集函数的顶层 `outcome=SUCCEEDED` 可以只表示详情成功；必须同时读取 `receipt.outcome`。正式封装应统一返回明确的收据结果，不能由顶层成功自动触发设备回写。

## 历史真实收据字段复核

来源是旧受控研究目录中订单 208 的收据 run 490，原采集时间 `2026-10-07T13:30:42.371Z`，即北京时间 21:30:42。离线容器禁用网络，旧目录只读挂载，使用原密钥解密并检查原文 SHA-256：

`7cf5776a242ca1dc981b81855ccbc64f832b7db3876155dead3e6007fa622447`

严格解析得到 1 张收据、2 个 SN，每个商品含 `serialNumber`、`partNumber`、`productName`。本轮导出 JSON 明确标注 `evidenceType=historical-not-fresh`，保留来源时间和摘要，不含 AppleID、密码、Cookie、代理认证或收据访问 URL。

| 需要的信息 | 原文模型位置 | 校验 |
| --- | --- | --- |
| 订单号 | `orderInvoices.orderInvoice-*.invoiceOrderSummary.d.orderNumber` | 每张收据必须等于输入订单与详情订单 |
| 序列号 | `invoiceLineItems.invoiceLineItem-*.d.lineItemSerialInfo[]` | `hasLineItemSerialInfo=true`；明确字符串、格式合规、无重复 |
| 商品名／料号 | 同一商品行的 `productName`／`partNumber` | 非空，逐 SN 保持商品关联 |
| 数量 | `quantityOrdered`／`quantityShipped` 与 SN 数量 | 与订单详情预期总数交叉核对，不把部分行计为全单成功 |

收据路由虽然含 `invoice`，本研究操作的是“查看电子收据”的只读入口；没有执行发票申请、抬头修改或其他订单操作。当前严格解析器整体拒绝含无 SN 商品行或部分发货的收据，未来支持配件／分次履约时需另定逐行结果契约。

## IPRoyal 与实验隔离

通过用户已有登录的 IPRoyal 平台提取 6 条中国区、24 小时粘性配置，无购买、充值或新 API 密钥创建。没有将配置条数等同于独立 IP 数量。代理原文仅保存在私密配置中，报告只记录配置索引及出口校验结果。

官方支持 `POST /v1/access/generate-proxy-list`；本轮 UI 提取已经满足验证需求，未实际调用该 API。后续接口化建议见[研究方案](../../planning/官网电子收据采集研究方案.md#iproyal-提取方式)。

本地试验源码、输入摘要、版本和诊断脚本位于新 Worktree 的忽略目录 `.tmp/receiptResearch/`；主工作区已有的 42 个源码文件复制为研究快照，没有修改原文件或将其全部纳入本分支。`sourceManifest.json` 记录输入基线，`experimentManifest.json` 记录最终实验版本。

服务器新目录 `/var/tmp/apple-electronic-receipt-research-20261008` 内保存私密配置、结果及加密证据；旧运行目录仅用于只读依赖与历史原文复核。实验容器使用固定镜像、独立临时文件系统和受限资源，复用既有研究 PostgreSQL Gate，保持每单本轮最多三次实际运行、账号冷却及 541 历史。已有拦截路径按共享预算申请请求许可；上述新窗口盲区需要先修复，不能宣称出站覆盖完整。原响应与 Cookie 不进入 Git。

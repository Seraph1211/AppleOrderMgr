## 管理台手动更新

订单管理中的“更新官网状态”提交单笔；勾选后“更新选中官网状态”支持多笔。全选本页和全选筛选结果含义分开显示，后者提交时固定当前权限与筛选匹配的订单 ID，最多 10000 单。进度区可查看逐单结果、切换近期批次、取消尚未开始的任务；关闭网页后服务器继续处理。打开页面及重新加载只读取系统数据。

仅回写 `orders.official_raw_status` 和 `official_status_observed_at`；同单多种状态去重后以 `|` 分隔。商品、金额、邮件、付款、取货、业务 `status` 及 `updated_at` 均不变。复用原官网字段，保留已有历史值与观测时间，不从归档回填；没有观测的订单显示“尚未更新”，需要手动查询。

持久安装目录为 `/var/www/apple-order-mgr/shared/official-orders`，其中 `release` 是交付代码、`deps` 是固定 Node 依赖；沿用专用数据库和加密会话。人工队列运行于 `apple-official-order-queue.service`，通过固定 Docker 命令调用 API 容器内的私有命令，API 不暴露完成接口也不挂载 Docker socket。每个任务最多一个在途浏览器；中断租约五分钟后失败，不自动重复登录。

首次生产批量窗口将累计请求上限由 1470 提升到 201470，保留旧计数和三次/订单/24小时、生产单次 300 请求（`maxRunRequests=300`，硬上限 400）、5 RPS 限制；独立工具默认仍为 200，增加的额度用于服务器冷登录和访客详情在一次操作内完成。达到上限显示失败，运维调整有限上限后由用户重新提交；不定期刷新、不自动补历史。

发布前备份业务库和研究目录并在隔离库演练 Migration；上线只替换 API/前端，保留邮件、企微、库存 Worker。停止服务使用 `systemctl stop apple-official-order-queue`（等待当前查询结束）；回滚恢复旧 API/前端，保留新字段、队列及私密证据。不要执行有数据的 down。

## 直接验收

在 `PP_CloudServer` 执行：

```bash
bash /var/www/apple-order-mgr/shared/official-orders/release/scripts/runOfficialOrderServer.sh 1196
```

`1196` 是系统订单 ID，可替换为已有订单 ID。当前三单样本为 `1196`、`1209`、`1273`，账号会话已经在服务器建立。运行从生产 API 容器只读取得这笔订单的原始链接、Apple ID 和密码，然后在隔离容器取数；用户电脑没有浏览器、代理或 Cookie 中继职责。

标准输出是脱敏摘要。只有 `outcome=SUCCEEDED` 且进程退出码为 `0` 才算成功。完整字段写到摘要中的 `resultFile`：容器内 `/research/private/results/` 对应宿主机 `/var/www/apple-order-mgr/shared/official-orders/private/results/`。文件权限 `0600`，包括 `orderNumber`、`products[].name`、`quantity`、`rawStatus`、`source.observedAt`、HTTP 来源及响应摘要。`source.path` 的联系人、订单号、访客令牌均脱敏，查询参数不落普通日志。

三单交付快照为服务器 `private/results/官网订单数据验收.json`；它是带观测时间的验收结果，后续实时状态必须重新执行命令。逐次结果另存，不覆盖上一份正确观测。

## 工作路径

1. 无可复用会话时，从 `https://www.apple.com.cn/shop/goto/account` 进入账户中心；等待官方页面后台 Cookie 生成，在真实 IDMS 表单登录。仅 Cookie 存在或登录 HTTP 200 都不算订单成功。
2. 从官网提供的账户页进入订单列表，精确寻找目标订单，再跟随对应详情入口。列表只有商品短名时，不能当作完整规格交付。
3. 列表没有目标订单时，打开系统原有官方查单链接。访客订单可以不出现在账号列表中；工具不会执行“关联订单”或修改账号。
4. 已有服务器会话时，优先通过原始查单链接读取详情。会话到期或官网要求重新登录时，按账号冷却规则处理登录。持久会话按账号加密绑定，最长六小时，不延长原会话创建时间冒充更新。
5. 只接受官网 `orderDetail` 中完全匹配的订单号、完整商品集合、数量及逐项原始状态。`/shop/orderx/guestx/…?_a=fetchOrder` 的 JSON 与 HTML 内 JSON 模型均支持；加载页、空列表、其他订单和缓存响应均不能成功。

账号登录和联系人邮箱是不同字段。入口校验同时支持现有 `/xc/cn/vieworder/订单号/联系邮箱` 与 `/shop/order/list/订单号/联系邮箱`，不会把 Apple ID 自动当成联系邮箱。

凭据读取以订单账号为准：关联账号或同名账号唯一匹配时读取账号主表，并校验已有订单密码快照；订单未关联且账号主表没有匹配时读取订单已有的加密密码快照。引用冲突、重复账号、异常账号、解密失败或主表与快照密码不一致均停止，不通过回退掩盖冲突。此路径不新增账号、不更改关联或密码。

## 资源、预算与失败处理

- 单次一个浏览器，宿主机文件锁与 PostgreSQL 账号锁阻止重入；无后台定时查询。现有国内网帆套餐作为出口，不依赖本机 VPN，不新增采购。
- 独立工具默认每次最多 200 个请求，生产手动窗口为 300；均限 180 秒，外层守护 190 秒；所有官网 HTTP 请求、重定向、iframe 及 Worker 子请求统一取得 PostgreSQL 许可，210–229ms 间隔，对应不超过初始 5 RPS。取消和失败不退预算。
- 同一订单在交付工具内 24 小时最多三次运行；一次运行最多提交一次密码，同账号提交后至少冷却 30 分钟。研究阶段的其他尝试独立保留，不能将工具台账当作研究首次成功率。
- 429 至少冷却 30 分钟，并遵守更长的 `Retry-After`；541、代理鉴权或连接失败暂停当前出口。工具不连续自动重放失败请求。更换已授权国内出口仍沿用数据库原计数；没有有效备用时保留失败。
- 密码拒绝、双重认证或其他人工验证暂停账号 24 小时；不猜密码、不解锁、不替用户回答安全问题。
- 可用内存低于 1.5 GiB、宿主机 CPU 连续一分钟超过 85%、现有 API 连续三次不健康或超时时，守护程序停止该采集容器。浏览器上限 1 CPU／1 GiB，专用数据库上限 0.25 CPU／256 MiB。

历史研究与独立交付阶段累计硬上限为 `1470`，该阶段结束已用 `1223`。本轮上线沿用旧计数，生产有限累计上限为 `201470`。计数不会因重启、换出口、失败或迁移而归零。后续操作者需要新的有限请求窗口时，可在服务器 `private/collectorConfig.json`（`0600`）显式配置更高的**累计上限**，保持数据库旧计数；可选 `proxyFile` 仅接受 `private/` 内的文件名。未配置时使用 `maxTotalRequests=1470` 和 `fan-1.json`。更换文件不等于代理可用，须保留验证记录。

常见退出：`REQUEST_BUDGET` 为预算耗尽，`ORDER_ATTEMPT_LIMIT` 为单日次数已满，`ACCOUNT_BUSY`／`COLLECTOR_BUSY` 为正在执行，`*_COOLDOWN` 为持久化暂停，`AUTH_REJECTED`／`HUMAN_VERIFICATION_REQUIRED` 为账号问题，`NO_VALID_ORDER_DATA` 为未得到完整详情。冷登录加访客详情可能在 200 请求内无法完成；如果该次已经保存有效服务器会话，下一次有预算的手动命令可复用，不需要电脑登录。不得把这类中间状态称为成功。

输入阶段失败直接展示具体原因：`ORDER_CREDENTIALS_MISSING` 为订单或账号缺少密码，`ACCOUNT_REFERENCE_CONFLICT` 为关联冲突，`CREDENTIAL_SNAPSHOT_MISMATCH` 为两处密码不一致，`ORDER_INPUT_READ_FAILED` 为读取异常。固定错误码从标准错误透传，不展示原始日志；失败立即删除未完成的临时输入，不启动浏览器。历史任务保留原有错误码，新版本不重写旧审计记录。

## 部署构成与数据边界

当前持久目录 `/var/www/apple-order-mgr/shared/official-orders` 包含 `release/` 代码、`deps/` 依赖、`private/` 输入／密钥／加密会话／结果、`evidence/` 加密原文和脱敏台账、`pgdata/` 专用 PostgreSQL。专用库停机复制后在同名容器恢复，旧研究目录 `/var/tmp/apple-account-research-20261003` 及停止的 `apple-account-research-db-backup-20261003` 作为迁移前备份保留。队列设为 systemd 开机启动，数据库设为 unless-stopped；已验证进程重建和持久化迁移，整机重启、凭据更新及长期保留期另行验收。

运行依赖已在服务器就绪：Docker、Python 3.6 队列及 Python 2/3 兼容资源守护、`flock`、Playwright 镜像 `mcr.microsoft.com/playwright@sha256:eff16c30e6f3f4af0a03fa4b706120d5e9b0891c344a27d64559aff5900a4a27`，内含 Node.js 24、Chromium 153 和 Xvfb。Node.js 原生 WebSocket 要求 22+。JS 依赖已从既有研究环境复制到持久目录 `deps/` 并只读挂载；不向生产 API 安装浏览器。宿主队列显式使用 UTF-8 解析子进程及结果，兼容服务器 ASCII 默认 locale。

专用数据库仅允许 `apple-account-research-db/apple_account_research`。显式迁移入口为 `npm run official:migrate -- /research`，SQL 在 `scripts/officialOrder/migrations/001-initialize.sql`；相应 down 文件保留旧 `runs`、`budget` 审计表，不能用于重置预算。运行器本身不建表或 `sync/alter`。

生产数据提取使用 `BEGIN READ ONLY`、八秒 SQL 超时和精确系统 ID，按上述规则读取主表或订单凭据快照；只输出到服务器私密文件。独立工具本身不写业务数据；手动产品队列另有正式 Migration、API 和列表接入，仅同步官网状态。邮件状态、付款任务、取货记录和通知链路保持原有语义，旧爬虫仍退役。输入脚本依赖同版 API 中的 `officialOrderInput.js`，发布须先等待手动队列空闲并停止，再一起替换 API 与宿主 `release` 代码；不能只更新其中一端。

核心实现：`officialOrderCollector.js` 负责浏览器状态机，`officialOrderCdp.js` 负责多目标协议，`officialOrderGate.js` 负责持久化限制，`officialOrderParser.js` 负责完整性解析，`officialOrderSupport.js` 负责身份／来源／密文校验。CLI 在 `scripts/collectOfficialOrder.js`，服务器入口在 `scripts/runOfficialOrderServer.sh`。
